被问“决策引擎 TPS 和全链路耗时怎么测算”，应该怎么拆？	先区分口径：1. TPS 是入口请求数、节点执行数还是外数调用数；2. 全链路耗时 = 网关/鉴权 + 参数校验 + 流程节点调度 + 规则/模型执行 + 外部 IO + 落库 + 回调。<br>测算方法：压测给出 P50/P95/P99、错误率、CPU/内存/连接池/线程池；线上用 traceId 串联每个节点耗时，识别同步 IO 和异步补偿的边界。	面试 真实面试 项目 性能监控 TPS	高德架构-TPS耗时测算	Hard
流程中断，比如外数失败，怎么设计处理链路？	按失败类型分层：1. 可重试：超时、网络抖动，用有限次数重试 + 指数退避；2. 不可重试：参数非法、授权失败，直接失败并记录原因；3. 供应商异常：进入处理中/待补偿状态，异步重试或人工介入；4. 所有节点保存输入、输出、错误码和 traceId，支持重放、对账和审计。<br>核心：流程状态不能因为一次外部 IO 失败而丢失，要能恢复。	面试 真实面试 项目 流程中断 外数	高德架构-流程中断处理	Hard
多租户场景下，线程共享用户信息导致串用，怎么把 ThreadLocal 问题说成工程事故？	表达模板：背景是多租户请求会把租户/用户上下文放入 ThreadLocal；问题出在线程池复用，任务结束后上下文未清理或子线程继承了旧上下文，导致后续请求读到错误租户信息。<br>解决：1. 统一封装 Executor，提交任务时 capture/replay/restore；2. finally 中 remove；3. 对直接 new Thread 或未接入封装的线程创建方式做扫描/治理；4. 增加租户隔离压测和日志审计。	面试 真实面试 项目 ThreadLocal 多租户	高德架构-ThreadLocal用户串用	Hard
普通 ThreadLocal、InheritableThreadLocal、TransmittableThreadLocal 在项目里怎么说？	ThreadLocal：线程内隔离，线程池复用时必须 remove。<br>InheritableThreadLocal：创建子线程时复制父线程值，但线程池里的工作线程早已创建，所以对线程池场景不可靠。<br>TransmittableThreadLocal：在任务提交时捕获父线程上下文，执行前恢复到工作线程，执行后还原/清理，适合 traceId、租户、用户上下文。<br>项目落点：TTL 不是免死金牌，必须统一 Executor 接入并治理绕过入口。	面试 真实面试 项目 ThreadLocal TTL	高德架构-ThreadLocal用户串用	Medium
ASM 扫描线程创建方式，在这个项目里应该怎么解释？	不要说成“ASM 解决一切”。更准确：ASM 是字节码读写工具，可在构建期或启动期扫描/增强类，识别直接 `new Thread`、裸 `ExecutorService`、未包装任务提交等风险点，插入统一包装或给出治理报告。<br>面试边界：优先用规范和统一线程池封装解决；ASM 属于兜底治理，成本是复杂度、兼容性和排查难度。	面试 真实面试 项目 ASM ThreadLocal	高德架构-ASM原理	Hard
Feign 调用失败和重试如何回答，才能避免“重试雪崩”的追问？	回答分三层：1. 超时：连接超时、读超时必须显式配置，不能无限等待；2. 重试：只对幂等接口和明确瞬时错误做有限重试，带退避和抖动；3. 保护：熔断、限流、隔离线程池/连接池、快速失败、降级返回。<br>关键句：重试会放大流量，必须和幂等、超时、熔断一起设计。	面试 真实面试 项目 Feign 重试 雪崩	高德架构-服务调用失败处理	Hard
MySQL 和 TiDB 的使用场景怎么选？	TiDB 适合海量数据、水平扩展、HTAP/复杂查询和 MySQL 协议兼容诉求；MySQL 适合单机或主从能承载的 OLTP、强依赖生态和低运维复杂度场景。<br>面试表达：不是“大数据量就上 TiDB”，要看数据规模、写入热点、事务模型、延迟要求、SQL 复杂度、团队运维能力和成本。	面试 真实面试 项目 MySQL TiDB	高德架构-TiDB选型	Medium
TiDB 如何支撑大量数据并保证性能？	核心机制：1. 数据按 Region 切分，分布在多个 TiKV 节点；2. Region 通过 Raft 复制保证高可用；3. PD 负责调度、负载均衡和元信息；4. TiDB Server 无状态，负责 SQL 解析优化和执行；5. 热点通过 Region split、调度和索引设计缓解。<br>边界：跨 Region 事务和复杂查询仍有成本，不能把 TiDB 当无限扩容的 MySQL。	面试 真实面试 项目 TiDB 分布式数据库	高德架构-TiDB性能	Hard
外部进件 SDK 为什么要提供？优势是什么？	回答：SDK 把接入协议、签名验签、幂等号、错误码、重试、超时、序列化、日志 trace 等通用能力沉到客户端侧，降低外部接入方犯错概率。<br>优势：1. 接入成本低；2. 口径统一；3. 兼容性可控；4. 方便灰度升级；5. 平台可以沉淀最佳实践，而不是让每个客户重复实现。	面试 真实面试 项目 SDK 进件	京东-SDK优势	Medium

DDD 在智能分控项目里如何拆域，别只背概念？	可以按业务能力拆：1. 进件域：接收、校验、幂等、渠道；2. 流程域：节点编排、状态流转、补偿；3. 决策域：规则、模型、策略版本；4. 外数域：供应商接入、超时重试、结果标准化；5. 审批域：人工任务、权限、流转；6. 通知/回调域：结果推送和对账。<br>每个域有自己的聚合、状态和不变量，跨域用事件或应用服务编排。	面试 真实面试 项目 DDD 智能分控	京东-DDD拆域	Hard
