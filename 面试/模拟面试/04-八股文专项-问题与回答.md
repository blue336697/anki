## 主要问题

### 1. “联合索引字段顺序”说得不够严谨

你说：

> 逻辑删除字段 + 租户 code + 机构 code + 时间 + 状态

这个思路有业务味道，但面试官会追问：**为什么这个顺序？**

联合索引不是把查询字段都塞进去就完事了，要考虑：

- 等值条件放前面
- 范围条件一般放后面
- 高区分度字段优先
- 排序字段能否复用索引
- 最左前缀原则

比如常见查询是：

```sql
where deleted = 0
  and tenant_code = ?
  and org_code = ?
  and status = ?
  and create_time between ? and ?
order by create_time desc
limit ?, ?
```

那索引可以考虑：

```sql
idx_task_list(deleted, tenant_code, org_code, status, create_time)
```

但如果 `status` 区分度很低，或者时间范围筛选更关键，也可能调整成：

```sql
idx_task_list(deleted, tenant_code, org_code, create_time, status)
```

所以你不能绝对说固定就是某个顺序，要讲“根据查询频率、选择性、排序方式和执行计划决定”。

### 2. “逻辑删除字段”放索引最前面不一定总是好

`deleted` 通常只有 0 和 1，区分度很低，单独放最前面不一定收益高。

但如果系统所有查询都强制带：

```sql
deleted = 0
```

它可以作为联合索引的一部分。

更稳妥的说法是：

> 如果逻辑删除字段是所有业务查询的固定过滤条件，可以纳入联合索引，但是否放最前，需要结合租户、机构、状态、时间字段的选择性和执行计划确认。

这样更像高级开发。

---

### 3. 深分页解决方案还可以再完整一点

你说用“某个唯一键且有序自增作为锚点”，这个方向是对的，本质是 **游标分页 / keyset pagination**。

但最好明确讲：

传统分页：

```sql
select *
from task
where tenant_code = ?
order by id desc
limit 100000, 20;
```

问题是数据库需要先扫描 / 跳过前 100000 条，再取 20 条。

优化后：

```sql
select *
from task
where tenant_code = ?
  and id < last_id
order by id desc
limit 20;
```

这样可以利用索引直接从 `last_id` 之后继续扫，避免大量 offset。

但也要补一句边界：

> 这种方式适合“上一页 / 下一页”场景，不适合直接跳到第 10000 页。如果业务强依赖跳页，需要结合搜索引擎、缓存、异步导出或者限制最大页数。

这个边界非常加分。

---

### 4. “覆盖索引”表述要准确

你最后说“大联合字段，回表的时候不需要回到”，这里应该叫 **覆盖索引**。

准确说法是：

> 如果列表页只展示少量字段，可以把这些字段放进联合索引中，使查询直接从二级索引拿到结果，避免回表，这叫覆盖索引。

例如：

```sql
idx_task_page(
  tenant_code,
  org_code,
  status,
  create_time,
  id,
  task_name,
  task_code
)
```

不过也要注意：

> 覆盖索引不能无限加字段，否则索引会过大，反而影响写入和缓存命中率。

```sql
limit 0, 20
```

```sql
limit 100000, 20
```

```sql
where tenant_code = ?

order by id desc
limit 20
```

所以总结一下，我不会简单地“所有字段都建索引”，而是根据核心 SQL、字段选择性、排序分页方式、写入频率和执行计划来设计索引。对于高频查询路径重点优化，对于低频复杂查询可以考虑异步导出、搜索引擎或者限制查询范围。

# 1. 这条 SQL 到底能用到联合索引的哪部分？

索引是：

```sql
idx_task_query(tenant_code, org_code, status, create_time)
```

SQL 是：

```sql
where tenant_code = 'T001'
  and status in (1, 2, 3)
  and create_time >= '2026-01-01'
  and task_name like '%风控%'
order by create_time desc
limit 20;
```

注意：**SQL 里没有 `org_code` 条件。**

联合索引遵循最左前缀原则：

```sql
tenant_code -> org_code -> status -> create_time
```

你只给了 `tenant_code`，跳过了第二列 `org_code`，后面的 `status` 和 `create_time` 通常就不能继续作为高效的索引定位条件使用。

所以更准确的说法是：

> 这条 SQL 最多主要利用到 `tenant_code` 这一段索引。由于跳过了联合索引中的 `org_code`，后面的 `status` 和 `create_time` 很难继续用于精确缩小扫描范围。`status`、`create_time`、`task_name like '%风控%'` 更多可能变成索引扫描后的过滤条件。

你刚才说“能利用租户号、状态和时间”，这个不严谨。

# 2. `task_name like '%风控%'` 为什么不能靠普通联合索引解决？

B+Tree 索引适合：

```sql
task_name = 'xxx'
task_name like '风控%'
```

但不适合：

```sql
task_name like '%风控%'
```

因为前面有 `%`，数据库无法从索引有序结构中确定起点，只能扫描。

所以你说“把任务名称加入联合索引”只能解决一部分问题：

```sql
idx_xxx(tenant_code, status, create_time, task_name)
```

它最多让查询在扫描索引时可以顺便拿到 `task_name`，减少回表，也就是**覆盖索引**收益。

但它不能让：

```sql
like '%风控%'
```

本身变成高效索引查找。

也就是说：

> 加 `task_name` 到联合索引，可能减少回表，但不能解决前置通配符导致的索引不可用问题。

这个区分面试里很重要。

## 第一层：先调整联合索引

如果这个 SQL 确实高频，而且 `org_code` 不是必传条件，那原索引：

```sql
idx_task_query(tenant_code, org_code, status, create_time)
```

对这个查询不合适。

可以新建更贴合这个查询的索引：

```sql
idx_task_list(tenant_code, status, create_time)
```

如果还有逻辑删除条件，应该 SQL 里补上：

```sql
where deleted = 0
  and tenant_code = 'T001'
  and status in (1, 2, 3)
  and create_time >= '2026-01-01'
```

索引可以是：

```sql
idx_task_list(deleted, tenant_code, status, create_time)
```

或者：

```sql
idx_task_list(tenant_code, status, create_time)
```

具体顺序看数据分布和执行计划。

---

## 第二层：处理 `task_name` 模糊搜索

如果只是偶发模糊查询，可以接受：

```sql
先用 tenant_code/status/create_time 缩小范围
再过滤 task_name like '%风控%'
```

但如果“按任务名包含搜索”是高频能力，不能只靠 MySQL B+Tree。

常见方案：

### 方案 A：改成交互约束

如果业务允许，把包含搜索改为前缀搜索：

```sql
task_name like '风控%'
```

然后可以考虑：

```sql
idx_task_name(task_name)
```

或者联合索引：

```sql
idx_task_name_query(tenant_code, task_name)
```

### 方案 B：全文索引

如果是 MySQL，可以考虑全文索引：

```sql
FULLTEXT(task_name)
```

但中文分词、相关性排序、维护成本都要评估。

### 方案 C：搜索引擎

如果任务名搜索是核心高频功能，且数据量大，可以同步到：

- Elasticsearch
- OpenSearch
- Solr

用搜索引擎解决包含搜索、分词、相关性排序、复杂筛选。

### 方案 D：冗余搜索字段 / 倒排表

如果系统不想引入 ES，也可以做轻量方案：

- 任务名称分词后写入搜索表；
- 维护关键词到任务 ID 的倒排关系；
- 先查 ID，再回查任务表。

- QPS 多少？

- 批量 insert 吞吐；
- TPS/QPS；
- CPU；
- IO wait；
- redo log 写入量；
- binlog 体积；
- Buffer Pool 脏页比例；
- 主从复制延迟。

# 更标准的回答

## 1. 同步方案怎么选？

我会优先考虑 **Binlog CDC** 或 **Outbox + MQ**，不优先选择业务代码双写。

### 不优先双写

业务代码里同时写：

```text
MySQL 成功
ES 成功
```

看起来简单，但实际有很多问题：

- MySQL 成功，ES 失败怎么办？
- ES 成功，MySQL 回滚怎么办？
- 重试导致重复写怎么办？
- 业务链路被 ES 可用性拖慢怎么办？

所以双写一般不作为首选。

---

## 方案 A：Binlog CDC

流程：

```text
业务写 MySQL
   ↓
MySQL binlog
   ↓
Canal / Debezium / Flink CDC
   ↓
MQ / 同步服务
   ↓
ES / OpenSearch
```

优点：

- MySQL 仍然是唯一事实源；
- 业务代码不感知 ES；
- 不侵入核心写链路；
- 可以重放 binlog；
- 适合构建搜索读模型。

缺点：

- 有同步延迟；
- CDC 组件复杂度高；
- 要处理乱序、重复、DDL 变更、全量初始化。

---

## 方案 B：Outbox + MQ

业务事务里同时写业务表和 outbox 表：

```text
begin
  insert/update task
  insert outbox_event
commit
```

然后异步任务扫描 outbox 表，投递 MQ，消费者写 ES。

优点：

- 业务数据和事件在一个 MySQL 事务里提交；
- 不会出现“业务写成功但事件丢失”；
- MQ 或 ES 失败后可以重试。

缺点：

- 要维护 outbox 表；
- 有额外开发成本；
- 仍然是最终一致性。

---

## 2. MySQL 写成功，ES 写失败怎么办？

核心原则：**MySQL 是准的，ES 可以重建。**

如果是 MQ 方案：

- 消费 ES 失败，不 ack；
- 消息自动重试；
- 重试多次失败后进入死信队列；
- 死信队列由补偿任务处理；
- 失败原因要告警；
- 消费要幂等。

幂等方式可以用：

```text
task_code 作为 ES document id
```

这样重复写同一条任务，不会生成多条脏数据。

如果是 CDC 方案：

- 同步服务失败可以从 offset 位点继续消费；
- ES 写失败可以重试；
- 严重失败时可以根据 MySQL 全量重建 ES 索引。

---

## 3. ES 延迟，前端查到旧数据怎么办？

这里要分业务场景。

### 如果列表搜索允许最终一致

比如任务列表、历史记录搜索，一般可以接受秒级延迟。  
前端可以提示：

```text
数据同步可能存在短暂延迟
```

- 支付服务重试

关键 SQL 是：

支付确认：

```sql
UPDATE stock_freeze_record
SET status = 'CONFIRMED',
    confirmed_at = NOW()
WHERE order_id = #{orderId}
  AND sku_id = #{skuId}
  AND status = 'FROZEN';
```

超时释放：

```sql
UPDATE stock_freeze_record
SET status = 'EXPIRED',
    released_at = NOW()
WHERE order_id = #{orderId}
```

```text
CONFIRMED -> EXPIRED
EXPIRED -> CONFIRMED
RELEASED -> CONFIRMED
```

通过 SQL CAS 条件：


## 逐点评价

### 1. `for update` 锁什么？

你说：

> 锁的是 where 条件命中的记录

只说对了一半。

更准确：

> InnoDB 的锁是加在**索引记录**上的。`select ... for update` 会对扫描到的索引记录加排他锁。  
> 如果是唯一索引等值命中一条已存在记录，通常是记录锁。  
> 如果是范围查询、非唯一索引、未命中记录，或者 RR 隔离级别下为了防止幻读，可能产生 next-key lock，也就是记录锁 + 间隙锁。

关键不是“where 命中哪些记录”，而是：  
**执行计划扫描了哪些索引范围，就可能锁哪些索引范围。**

---

### 2. “更新条目大于 1 就变成间隙锁”是错的

你说：

> 当要更新的条目大于 1，就会从行锁变为间隙锁

这个不对。

是否产生间隙锁，不是看更新几行，而是看：

- 隔离级别
- 查询条件
- 是否使用唯一索引
- 是否等值查询
- 是否范围扫描
- 是否命中记录
- 是否需要防止幻读

举例：

```sql
SELECT * FROM sku_stock WHERE sku_id = 100 FOR UPDATE;
```

如果 `sku_id` 是唯一索引且记录存在，在 RR 下通常锁这条索引记录，不锁 gap。

但：

```sql
SELECT * FROM sku_stock WHERE sku_id > 100 FOR UPDATE;
```

这是范围查询，RR 下可能加 next-key lock，锁范围和间隙。

再比如：

```sql
SELECT * FROM sku_stock WHERE sku_id = 100 FOR UPDATE;
```

如果 `sku_id` 没有索引，可能扫全表，锁大量记录，甚至效果接近表级锁。

### 3. 推荐条件更新，不只是因为“加锁影响吞吐”

你说用原子 SQL 更新，方向是对的，但原因没说到位。

推荐：


核心原因是：

1. **少一次网络往返**：不需要先查再改。
2. **缩短锁持有时间**：直接 update，InnoDB 获取锁后立即判断和修改。
3. **避免应用层读旧值再写回**。
4. **天然防并发超扣**：`available_stock >= qty` 是数据库层的原子条件。
5. **通过 affected_rows 判断成功失败**，不需要业务层自己判断库存是否足够。

你可以说“吞吐更好”，但要补这几个点。

### 4. 唯一索引下 UPDATE 的并发行为

如果 `sku_id` 是唯一索引：

```sql
UPDATE sku_stock
SET available_stock = available_stock - 1
WHERE sku_id = 100
  AND available_stock >= 1;
```

并发行为是：

- 多个事务同时更新同一 `sku_id`
- InnoDB 会对这条索引记录加排他锁
- 只有一个事务先拿到锁并更新
- 其他事务等待锁释放
- 后续事务拿到锁后，会基于**最新已提交版本**重新判断 `available_stock >= 1`
- 如果仍满足，继续扣
- 如果不满足，影响行数为 0

所以不会扣成负数。

这句话很关键：

> `UPDATE` 是当前读，不是快照读，会读取最新可见的已提交版本，并加锁更新。

### 5. RR 和 RC 你说乱了

你最后说：

> 可重复读每个 session 看到的数据应该都是最新的

这是错的。

准确说：

## 快照读

普通 `SELECT`：

```sql
SELECT available_stock FROM sku_stock WHERE sku_id = 100;
```

- **RR**：同一个事务内多次普通 SELECT 看到的是事务开始后第一次一致性读建立的 ReadView，结果保持一致，不一定是最新。
- **RC**：每条普通 SELECT 都会生成新的 ReadView，所以能看到其他事务已经提交的新数据。

## 当前读

这些是当前读：

```sql
SELECT ... FOR UPDATE
UPDATE
DELETE
INSERT
```

它们读取的是最新已提交数据，并加锁。

所以扣库存的 `UPDATE` 在 RR 和 RC 下都会按当前读来处理，而不是按普通快照读。

你可以这样答：

>
> 高并发扣库存时，我更推荐直接条件更新：
>
> ```sql
> UPDATE sku_stock
> SET available_stock = available_stock - #{qty}
> WHERE sku_id = #{skuId}
>   AND available_stock >= #{qty};
> ```
>

> 在隔离级别上，普通 SELECT 在 RR 下是事务级 ReadView，同一事务内结果可重复；在 RC 下是语句级 ReadView，每次 SELECT 都可能看到新提交数据。

## 二、处理流程

服务收到发券事件后：

### 1. 先插入幂等表

先根据幂等键插入一条记录，状态为：

```text
INIT / PROCESSING
```

如果插入成功，说明这是第一次处理，可以继续执行。

如果唯一键冲突，说明之前处理过，这时候要查当前状态：

- `SUCCESS`：直接返回成功
- `PROCESSING`：说明正在处理中，可以返回处理中，或者忽略本次消息
- `FAILED / RETRYABLE_FAILED`：判断是否允许重试
- `FINAL_FAILED`：返回失败或进入人工处理

这里不能只说“幂等过滤”，要说清楚**不同状态下怎么处理重复请求**。

---

## 三、发券和幂等表更新的事务问题

这里有两个关键异常场景。

### 场景 1：幂等表插入成功，但发券失败

这时幂等表状态可以更新为：

```text
RETRYABLE_FAILED
```

并记录失败原因和下次重试时间。

之后由定时任务扫描：

```text
state in (INIT, PROCESSING, RETRYABLE_FAILED)
and updated_at < now - timeout
```

进行补偿重试。

如果失败是库存不足、券模板失效、用户不满足条件这类业务不可重试错误，则状态改成：

```text
FINAL_FAILED
```

不再无限重试。

如果是网络超时、下游服务异常、数据库瞬断，则进入可重试状态。

---

### 场景 2：发券成功，但幂等表状态更新失败

这个场景非常关键。

我的判断是：**发券成功是业务事实，幂等表只是过程状态，所以最终应该以发券记录表为准。**

补偿任务定期扫描幂等表中长时间处于：

```text
PROCESSING / INIT / RETRYABLE_FAILED
```

的记录，然后反查发券记录表：

- 如果发券记录已经存在且状态为 `ISSUED`，则把幂等表修正为 `SUCCESS`
- 如果发券记录不存在，则重新执行发券
- 如果发券记录存在但状态异常，则根据发券记录状态做修复或人工介入

这样可以保证最终一致性。

---

## 四、重复发券如何防住

这里不能只依赖幂等表，因为幂等表状态可能更新失败。

所以发券动作本身也必须幂等。

也就是说发券记录表必须有唯一约束：

```sql
unique(biz_type, biz_id, user_id, coupon_template_id)
```

发券时先插入发券记录，或者在发券服务内部做唯一键保护。

如果第二次同样请求过来：

- 如果发券记录已存在且成功，直接返回成功
- 如果发券记录存在但处理中，返回处理中或等待
- 如果发券记录失败，则根据失败原因决定是否重试

这样即使消息重复投递、接口超时重试、定时任务重复补偿，也不会重复给用户发券。

我会把失败分成几类。

### 1. 可重试失败

比如：

- MQ 抖动
- 下游服务暂时不可用
- 数据库连接异常

这类进入延迟重试，使用指数退避，例如：

```text

```

并限制最大重试次数。

### 2. 不可重试业务失败

比如：

- 券模板不存在

- 库存不足
- 订单状态不合法

这类不应该无限重试，直接进入：

```text
FINAL_FAILED
```

同时记录原因，必要时通知业务方。

### 3. 未知异常 / 边界问题

如果超过最大重试次数仍然失败，就进入：

```text
DEAD_LETTER / MANUAL_CHECK
```

同时报警，保留现场：

- 幂等键
- 原始消息
- 请求参数
- 错误堆栈
- 当前状态
- 重试次数
- 下游返回结果

研发介入排查。

## 这题推荐答案

### 一、整体方案

我会把优惠券库存设计成三层：

1. **Redis 库存**：高并发下的快速库存拦截，负责原子预扣减。
2. **DB 库存表**：最终库存事实，负责持久化扣减和对账基准。
3. **发券记录表**：用户权益事实，负责防重复发券。

核心原则是：

> Redis 负责抗并发，DB 负责最终一致，发券记录负责用户权益和幂等。

---

## 二、防超发怎么做

### 1. Redis 原子扣减

活动开始前把券模板库存加载到 Redis：

```text
coupon:stock:{coupon_template_id} = 100000
```

用户支付成功消息到来后，发券服务先执行 Redis Lua 脚本：

```lua
if stock <= 0 then
    return -1
else
    decr stock
    return 1
end
```

必须用 Lua 或 Redis 原子命令，不能先查再扣。

如果 Redis 预扣失败，直接返回库存不足，不进入后续发券流程。

---

### 2. DB 库存条件扣减

Redis 扣减成功后，再异步/同步落 DB：

```sql
update coupon_stock
set available_stock = available_stock - 1,
    used_stock = used_stock + 1
where coupon_template_id = ?
  and available_stock > 0;
```

这个 SQL 本身可以防 DB 层超发。

如果更新行数是 1，说明 DB 扣减成功。  
如果更新行数是 0，说明 DB 库存不足或状态异常，要回滚 Redis 预扣库存，并进入异常补偿。

---

### 3. 发券记录唯一约束

发券记录表必须有唯一索引：

```text
unique(biz_type, biz_id, user_id, coupon_template_id)
```

例如：

```text
ORDER_PAY + order_id + user_id + coupon_template_id
```

这样即使 MQ 重复投递、接口超时、定时任务重复补偿，也不会重复发券。

---

## 三、库存扣减和发券记录写入怎么保证一致性？

如果在同一个服务同一个数据库里，最稳的是：

```text
DB 扣库存 + 插入发券记录
```

放在一个本地事务里：

```text
begin;

update coupon_stock
set available_stock = available_stock - 1,
    used_stock = used_stock + 1
where coupon_template_id = ?
  and available_stock > 0;

insert into user_coupon_record(...);

commit;
```

这样可以保证：

- 库存扣成功，发券记录一定写成功
- 发券记录写成功，库存也一定扣成功
- 事务失败整体回滚

Redis 只是前置限流/预扣，不作为最终事实。

---

如果库存服务和发券服务拆成两个服务，就不能依赖本地事务，需要最终一致：

```text
Redis 预扣
DB 扣库存成功
发送发券消息
发券服务插入发券记录
```

同时要配合：

- 本地消息表 / 事务消息
- MQ 重试
- 幂等消费
- 定时补偿
- 对账任务

## 四、异常场景

### 场景 1：Redis 扣减成功，DB 扣减失败

可能原因：

- Redis 和 DB 库存不一致
- DB 库存已经为 0
- DB 更新异常

处理方式：

```text
Redis 库存 +1 回补
记录异常日志
触发库存对账
本次发券失败
```

注意：这时候不能继续发券。

---

### 场景 2：DB 扣库存成功，但发券记录写入失败

如果二者在同一个数据库事务里，直接整体回滚，不会出现这种不一致。

如果跨服务，库存已扣但发券失败，则要走补偿：

- 记录库存扣减流水
- MQ 重试发券
- 定时任务扫描“库存已扣但未发券”的记录
- 重新触发发券

这里一般**不能简单把库存加回去**，因为用户已经命中了活动资格，支付成功后业务预期是发券。除非业务定义允许“发券失败退库存”。

---

### 场景 3：发券记录写入成功，但 DB 库存扣减失败

正常流程应该先扣库存再发券，所以这属于异常数据。

处理方式不能只说“不存在”，要有兜底：

1. 查询是否存在对应库存扣减流水
2. 如果发券记录存在，但库存流水不存在：
   - 优先尝试补扣库存
   - 如果库存足够，补扣成功后修复状态
   - 如果库存不足，进入人工处理/运营兜底
3. 不建议直接删除用户券，因为用户可能已经看到甚至使用了券

这里原则是：

> 用户权益一旦对用户可见，回滚成本很高，通常优先补库存账，而不是回滚用户权益。

## 五、Redis 库存和 DB 库存如何协同？

比较稳的表达是：

```text
Redis：抗高并发，快速失败
DB：最终库存事实
库存流水：记录每一次库存变化
发券记录：记录用户权益事实
```

## 主要问题

### 1. “乱序谁先消费就以谁为准”不对

乱序不能以先到为准，要以**业务状态机 + 事件版本/时间 + 当前状态**为准。

比如：

```text
支付成功 -> 发券
订单取消 -> 撤销发券
```

如果“订单取消”先到，“支付成功”后到，不能简单谁先到谁赢。  
应该看当前订单最终状态、事件版本、业务规则，决定是否允许状态流转。

正确原则是：

> 消息可以乱序到达，但状态不能乱序流转。

---

### 2. “消费端超时没 ack 就认为消息丢失”不准确

消费端没 ACK，MQ 一般会重投，这叫**消费失败/消费超时**，不等于消息丢失。

真正消息丢失更多发生在：

- 订单本地事务提交了，但 MQ 没发出去
- MQ 发出去了但 Broker 未持久化
- 生产者以为发成功，实际失败
- 消息被错误消费并 ACK，但业务没落库
- 人为误删 / 配置问题

所以“消息丢失”要靠**发送端本地消息表 + 消费端业务对账**发现，而不是只靠 ACK 超时。

---

### 3. “本地事务回滚后再发补偿 MQ”是危险答案

如果订单服务本地事务已经回滚，理论上不应该发支付成功 MQ。  
如果已经发出去了，说明你把 MQ 发送放在了事务提交之前，设计有问题。

正确做法是：

- 不要在本地事务提交前发送最终业务消息
- 用本地消息表/事务消息保证：只有事务提交成功，消息才对外可见
- 如果误发，消费端要反查订单状态，不符合就丢弃或转异常

不是“再发一个回滚 MQ 让状态流回去”。这种设计会把下游搞复杂，而且可能出现补偿消息也丢失/乱序。

---

### 4. RocketMQ 事务消息理解不完整

RocketMQ 事务消息不是“不引入表”。  
它解决的是：

```text
本地事务 和 MQ 消息发送 的原子性问题
```

流程是：

1. 发送 half message
2. 执行本地事务
3. 提交/回滚消息
4. Broker 不确定时回查本地事务状态

但它依然要求你有一个地方能查询本地事务状态，比如订单表、支付流水表、本地消息表。

所以不是“完全靠 RocketMQ 控制状态流转”。

## 一、发送端：保证本地事务提交成功后消息一定能发出去

订单服务支付成功时，不能简单：

```text
更新订单状态 -> 发送 MQ
```

因为可能出现：

```text
订单提交成功，但 MQ 发送失败
```

也不能：

```text
发送 MQ -> 更新订单状态
```

因为可能出现：

```text
MQ 发成功，但订单事务回滚
```

所以我会用两种方案之一。

---

### 方案一：本地消息表

订单服务在同一个本地事务里做两件事：

```text
1. 更新订单状态为 PAID
2. 插入本地消息表，状态为 INIT
```

事务提交后，由异步任务扫描本地消息表发送 MQ。

发送成功后，把消息状态改成：

```text
SENT
```

如果发送失败，则重试。超过次数报警。

这样可以保证：

> 只要订单支付事务提交成功，消息一定能通过本地消息表被补偿发出去。

---

### 方案二：RocketMQ 事务消息

也可以用 RocketMQ 事务消息：

1. 先发送 half message
2. 执行订单本地事务
3. 本地事务成功则 commit message
4. 本地事务失败则 rollback message
5. 如果生产者挂了，Broker 回查本地事务状态

回查时根据订单表/支付流水判断：

```text
订单是否已支付
```

如果已支付，提交消息；否则回滚消息。

## 二、MQ 层：保证消息至少投递一次

MQ 层一般不承诺 exactly once，而是：

```text
at least once
```

所以系统设计上必须接受：

- 消息重复
- 消息延迟
- 消息乱序
- 短时间不可用

我不会依赖 MQ 保证业务幂等，而是在消费端做幂等。

如果对顺序要求强，可以按业务 key 分区，例如：

```text
order_id / user_id
```

让同一个订单的消息进入同一个队列，降低乱序概率。

但即使用顺序消息，也不能完全依赖 MQ 顺序，消费端仍然要做状态机校验。

## 三、消费端：幂等 + 状态机 + 反查

发券服务消费支付成功消息时，先做三件事。

### 1. 幂等控制

根据：

```text
biz_type + biz_id + user_id + coupon_template_id
```

建立幂等键，插入幂等表或发券记录表唯一索引。

如果已经成功发券，直接 ACK 并返回成功。

---

### 2. 状态机防乱序

消费端维护状态机，不允许状态回退。

例如发券状态：

```text
INIT -> PROCESSING -> SUCCESS
INIT -> PROCESSING -> FAILED
FAILED -> PROCESSING -> SUCCESS
```

但不允许：

```text
SUCCESS -> PROCESSING
SUCCESS -> FAILED
```

更新时使用条件更新：

```sql
update coupon_issue_record
set status = ?
where id = ?
  and status in (?, ?);
```

如果当前状态不允许流转，说明消息重复、乱序或非法，直接忽略或记录异常。

---

### 3. 反查订单状态

发券前最好反查订单状态，尤其是关键业务：

```text
订单是否真实支付成功？
订单是否已取消/退款？
活动是否有效？
用户是否满足条件？
```

如果订单不是已支付，即使收到了支付成功消息，也不能发券。

这个可以防止：

```text
MQ 发出去了，但订单本地事务回滚
```

或者异常误发消息。

## 四、补偿对账：发现消息丢失和状态不一致

消息丢失不能只靠 MQ ACK 判断，要靠业务对账。

### 1. 发送端补偿

订单服务扫描本地消息表：

```text

and retry_count < max
```

继续发送 MQ。

### 2. 消费端补偿

发券服务扫描幂等表/发券任务表：




## 1. 如何处理 MQ 重复消息？

- 幂等表唯一键
- 发券记录唯一键
- 状态机条件更新

重复消费到达时：

- 如果已经成功，直接 ACK
- 如果处理中，忽略或稍后重试
- 如果失败，判断是否允许重试

## 2. 如何处理消息乱序？

不能谁先到谁赢。

处理方式：

1. 通过 `order_id/user_id` 做消息分区，尽量保证同一业务 key 顺序
2. 消费端做状态机校验
3. 事件带版本号或状态版本，例如 `event_version`
4. 消费时判断当前状态是否允许流转
5. 必要时反查订单最终状态

原则：

> 只接受能从当前状态合法流转的事件，不合法的乱序事件丢弃、延迟重试或进入异常表。

---

## 3. 如何判断消息丢失？

通过业务对账判断：

```text
订单已支付，但没有对应发券成功记录
```

或者：

```text
本地消息表长时间未发送成功
```

而不是简单靠消费端 ACK 超时。

---

## 4. MQ 发送成功但订单服务本地事务回滚怎么办？

正确设计下不应该让消息对消费者可见。

解决方式：

- 本地消息表：事务回滚，消息表也回滚，不会发送
- RocketMQ 事务消息：本地事务失败，rollback half message

如果因为异常导致消费者收到了，消费端要反查订单状态。  
如果订单不是已支付，则不发券，并记录异常。

---

## 5. 订单本地事务提交成功但 MQ 发送失败怎么办？

用本地消息表或事务消息补偿。

本地消息表方案：

```text
订单状态 PAID 和消息记录一起提交
后台任务扫描未发送消息并重试
```

超过次数报警。

## 6. 本地消息表、事务消息怎么选？

>
> 如果希望方案更通用、可观测性更强、便于人工补偿和跨 MQ 迁移，我更倾向本地消息表。  
>
> 在强业务场景下，我甚至会采用“本地消息表 + MQ 重试 + 消费端幂等 + 对账补偿”的组合，因为本地消息表能保留明确的业务事实和消息发送状态，排障和补偿都更可控。

首先，发券请求本身应该具备幂等性。我们在调用前会生成一个全局唯一的业务请求号，比如 `requestId` 或者 `orderNo + activityId + userId`，这个编号在整个发券链路里唯一。下游发券方需要基于这个请求号做幂等控制，保证同一笔请求无论被调用多少次，最终只会发一张券或者返回同一个发券结果。

其次，在我方数据库层面也要做防重和状态控制。比如发券记录表里对业务唯一键加唯一索引，同时状态流转要用条件更新控制，例如：

```sql
update coupon_issue_record
set status = 'ISSUING'
where id = ?
  and status = 'INIT'
```

这样可以避免并发任务、重复 MQ 消费、接口重试导致同一笔发券记录被重复推进。对于数量类资源，比如活动库存、券库存，也要用带条件的扣减：

```sql
update activity_stock
set remain_count = remain_count - 1
where activity_id = ?
  and remain_count > 0
```

第三，针对超时场景，我不会直接认为失败。因为 HTTP 超时只代表我方没有拿到响应，不代表下游没有处理成功。所以我会把这类状态标记成 `UNKNOWN` 或者 `ISSUING`，然后进入异步补偿任务。补偿任务的处理策略是：先查状态，查不到再有限重试发券。重试需要有次数限制和退避机制，比如 3 次即时重试，失败后进入延迟队列，按 1 分钟、5 分钟、30 分钟逐步拉开，避免把下游服务打爆。

第四，如果对方提供查询接口，我方会定时查询下游发券状态，把本地状态同步成成功、失败或未知。如果对方不提供查询接口，那我会在对接前就要求明确一种对账机制：要么对方提供状态查询接口，要么对方定时调用我方提供的查询/对账接口，或者双方基于对账文件做离线核对。核心原则是：不能让超时请求长期停留在不可知状态。

第五，针对用户侧一定要有容灾和补偿方案。技术上不能只考虑接口成功失败，还要结合业务损失评估：比如券是否有有效期、券金额多大、用户是否已经到店或准备使用、用户感知是否强。如果最终确认发券失败，可以根据场景做重新发券、补发等额券、延长有效期、发放补偿券，或者走人工客服兜底。这个补偿策略需要产品、运营和技术一起提前定义，而不是事故发生后临时拍脑袋。

以后你回答八股题，强制用这个结构：

```text
1. 先给结论
2. 解释原理
3. 结合业务场景
4. 讲风险和边界
5. 讲工程落地方案
```

比如：

> **结论**：接口超时后可以重试，但要区分异常类型。  
> **原理**：超时不代表失败，可能是请求成功但响应丢失。  
> **业务场景**：发券、支付、扣库存这类接口必须幂等。  
> **风险**：盲目重试可能导致重复发券、重复扣减、库存不一致。  
> **落地**：业务唯一键、唯一索引、状态机、条件 update、查询补偿、对账、告警、人工兜底。

## 七、下一阶段建议

八股专项可以先结束，但不要完全停。下一阶段建议切到：

### **项目深挖 + 八股嵌入式追问**

> Redis 为什么快？  
> MySQL 索引怎么设计？

- 你的发券任务为什么要用 MQ？消息重复消费怎么处理？
