## 卡片列表

### Card 1

Front：

为什么幂等不能解决优惠券库存超发问题？

Back：

幂等解决的是同一业务请求被重复处理的问题，不能解决多个不同用户/订单并发竞争同一库存的问题。<br>防超发依赖：1. Redis 原子扣减/Lua 作为流量闸门；2. DB 条件更新作为最终事实，如 update stock set remain=remain-1 where id=? and remain>0；3. 库存流水/发券记录唯一约束；4. 对账修复 Redis、DB、发券记录不一致。<br>一句话：幂等防重复，原子扣减和事务约束防超卖。

### Card 2

Front：

优惠券库存系统中，Redis 库存、DB 库存、发券记录三者分别是什么角色？

Back：

角色划分：1. Redis 库存：高并发流量闸门，快速判断和原子预扣，降低 DB 压力；2. DB 库存：最终库存事实，依赖事务、条件更新、库存流水保证一致；3. 发券记录：用户权益事实，决定用户是否真正拿到券。<br>协同原则：Redis 可作为前置缓存，但最终必须能通过 DB 库存流水和发券记录对账修复。

### Card 3

Front：

Redis 扣库存成功但 DB 扣库存失败怎么办？

Back：

处理：1. DB 扣减失败说明最终事实未成功，不能发券成功；2. 需要回补 Redis 库存或记录待修复差异；3. 写入库存异常流水/补偿事件，异步修正 Redis；4. 如果已创建发券流程，需要阻断发券或进入失败补偿；5. 定期对账 Redis 剩余库存、DB 剩余库存、库存流水、发券记录。<br>关键：Redis 是闸门，不是最终事实。

### Card 4

Front：

DB 库存扣减如何用 SQL 防止并发超卖？

Back：

核心是原子条件更新：update coupon_stock set remain = remain - 1, used = used + 1 where template_id = ? and remain > 0。<br>判断 affected rows：1 表示扣减成功，0 表示库存不足或状态不允许。<br>还需要：1. template_id 或活动维度索引；2. 库存流水唯一键防重复扣；3. 乐观锁 version 可选；4. 事务内写发券记录或事件表；5. 高并发下避免先 select 再 update 的竞态。
