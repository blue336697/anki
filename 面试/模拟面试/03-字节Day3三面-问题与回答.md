### 面试版回答

当时我们做的是银行流水解析后的标签能力。流水解析完成后，需要通过规则引擎给每条流水打上业务标签，后续风控指标会基于这些标签做统计分析。

最初产品设计的是**单标签模型**，也就是一条流水在三级标签体系下，每一级只归属一个标签。比如一级是收入/支出，二级是消费/转账，三级是具体类型。

但我在开发和联调过程中发现一个问题：真实流水并不一定天然满足单标签语义。比如一条微信红包流水，它既可能属于“红包”，也可能命中“敏感金额消费”或者“异常交易行为”。如果强制单标签，会丢失一部分风险特征。

我当时把这个问题反馈给产品，并提出过两种方案：

1. **继续单标签，但需要明确标签优先级**
   - 好处是统计简单，不会重复计数；
   - 缺点是标签表达能力弱，部分风控特征会被覆盖。

2. **改成多标签模型**
   - 好处是能更完整表达一条流水的多个业务属性；
   - 缺点是后续指标分析容易出现重复统计，需要额外定义统计口径。

由于当时排期比较紧，产品判断多标签场景占比不高，所以第一版还是按单标签上线。但上线后通过真实数据回流，我们发现多标签场景比例明显高于预期，尤其是红包、转账、敏感金额、疑似经营流水这些场景经常重叠。

后来我们做了一版模型调整，把流水和标签关系从单值字段改成了一对多关系。技术上主要调整了三块：

第一，**数据模型调整**。  
原来流水表里只有一个标签字段，后来改成了流水主表加标签关系表，支持一条流水挂多个标签。

第二，**规则引擎输出调整**。  
原来规则命中后会按照优先级返回一个标签，后来改成返回标签集合，同时保留命中规则、命中原因和标签层级，方便后续追踪。

第三，**指标统计口径调整**。  
这是多标签后最容易出问题的地方。我们后来区分了两类指标：

- 如果是按“标签命中次数”统计，可以允许一条流水贡献到多个标签；
- 如果是按“流水金额/流水笔数”统计，就必须以流水 ID 去重，避免重复累加金额。

比如一条 100 元流水同时命中了“红包”和“敏感金额”，在标签分布统计里可以两个标签都计一次，但在总支出金额统计里只能算一次 100 元，不能算成 200 元。

这个事情给我的反思比较深。第一，业务建模不能只看产品原型，要结合真实数据分布去验证。第二，研发在发现模型边界问题时，不能只是口头反馈，最好用样本数据、影响范围和风险案例推动决策。第三，对于标签、指标、规则这类系统，一开始就要把“标签表达”和“统计口径”分开设计，否则后期很容易因为口径不清导致数据争议。

如果现在让我重新做，我会在第一版就至少预留多标签扩展能力，即使产品侧暂时只展示一个主标签，也可以在底层保留标签集合和主标签字段。这样既不影响一期交付，也能降低后续模型演进成本。

## 规则生成的约束与治理机制

在规则生成环节，系统不会只让模型直接生成最终规则，而是会要求它同时输出几类内容：

### 1. 规则表达式 / DSL 生成

首先，模型需要生成对应的规则表达式，也就是系统可以直接执行的规则 DSL。

这部分关注的是：

- 规则条件是否完整；
- 字段引用是否正确；
- 逻辑运算符是否符合系统语法；
- 不同条件之间的优先级是否明确；
- 是否存在歧义、冲突或者无法执行的表达。

比如一条规则不只是简单生成：

> 如果 A 且 B，则命中风险标签。

而是要转成系统能够识别和执行的结构化规则表达式。

---

### 2. 自然语言解释

除了规则本身，系统还会要求模型生成一段非常“大白话”的自然语言解释。

这段解释的作用是让业务、测试、研发都能看懂：

- 这条规则到底在判断什么；
- 哪些字段参与了判断；
- 每个条件的含义是什么；
- 命中规则代表什么风险；
- 如果多个条件组合在一起，它们之间是“且”“或”还是优先级嵌套关系；
- 为什么这条规则应该这样设计。

比如它不能只说：

> 当近 6 个月收入波动异常且负债较高时命中。

而是要解释成：

> 这条规则主要用来识别收入不稳定但负债压力较大的客户。如果客户最近 6 个月的收入波动幅度超过阈值，同时当前负债水平又比较高，系统会认为这类客户后续还款能力存在不确定性，因此命中该风险规则。

这样方便人工审核，也方便后续定位问题。

---

### 3. 逻辑谓词和优先级说明

对于复杂规则，系统还会要求模型明确说明逻辑谓词之间的优先级。

例如：

- `A AND B OR C` 到底是 `(A AND B) OR C`，还是 `A AND (B OR C)`；
- 多个风险条件同时存在时，哪个优先级更高；
- 是否存在短路逻辑；
- 是否存在互斥条件；
- 是否会覆盖已有规则。

这部分主要是为了避免模型生成“看起来对，但实际执行结果有歧义”的规则。

---

## 测试数据来源

规则生成后，需要进入测试验证阶段。测试数据主要有三类来源。

### 1. 线上真实数据

优先级最高的是线上真实进件数据。

因为线上数据最能反映真实业务分布，包括：

- 正常样本；
- 已知风险样本；
- 历史命中样本；
- 未命中但后续表现异常的样本；
- 不同产品、不同客群、不同渠道的数据差异。

线上数据可以验证这条规则在真实环境下的覆盖率、命中率和误伤情况。

---

### 2. 人工构造测试数据

第二类是人工构造的测试数据。

这类数据主要用来覆盖一些线上样本不一定经常出现，但规则必须正确处理的情况，比如：

- 字段为空；
- 字段缺失；
- 极大值；
- 极小值；
- 边界阈值；
- 多条件同时命中；
- 条件刚好不命中；
- 异常格式；
- 跨字段逻辑冲突。

人工测试数据的价值在于可以主动验证规则边界，而不是只依赖线上数据被动覆盖。

---

### 3. 系统维护的关键边界 Case 集

除了线上数据和人工测试数据，系统还会长期维护一份关键边界 case 集。

这部分 case 来源于持续测试和历史版本迭代，比如：

- 曾经线上出过问题的样本；
- 规则误杀过的样本；
- 规则漏判过的样本；
- 某次版本上线后暴露出的异常样本；
- 特别容易验证规则对错的典型样本；
- 不同规则之间容易冲突的样本。

这些 case 会沉淀成一套回归测试资产。

每次规则变更、模型版本更新、标签逻辑调整时，都会优先跑这批 case，确保新规则没有破坏已有逻辑。

---

## 新旧链路对比机制

当系统触发新的规则改动，或者命中了新的风险标签时，同一笔进件会同时走新旧两条链路。

也就是说：

- 旧链路继续按照原有规则执行；
- 新链路按照新生成或新调整后的规则执行；
- 两边都会产出规则命中结果；
- 系统会生成对比报告。

对比报告主要统计：

### 1. 命中数量变化

例如：

- 新规则比旧规则多命中了多少笔；
- 少命中了多少笔；
- 哪些样本从不命中变成命中；
- 哪些样本从命中变成不命中。

这可以判断新规则是放宽了，还是收紧了。

---

### 2. 指标类别下的统计变化

系统还会按指标类别进行聚合统计，比如：

- 收入类指标；
- 负债类指标；
- 稳定性指标；
- 异常交易指标；
- 经营风险指标；
- 欺诈风险指标。

每个类别下都会统计：

- 命中数量；
- 命中占比；
- 相比旧链路的增减幅度；
- 影响最大的规则或标签；
- 是否集中影响某类客群或产品。

---

### 3. 标签命中变化

如果新链路命中了新的标签，系统也会重点分析：

- 新标签命中的样本数量；
- 新标签与旧标签是否重叠；
- 是否出现大量新增命中；
- 是否有明显误伤；
- 是否命中了历史风险样本；
- 是否对审批结果产生明显影响。

# 3. 高危问题

## 高危 1：容易把项目讲成“我参与过”，而不是“我主导过”

你有时候会说：

- 组长推动；
- 产品要求；
- 测试配合；
- 我是校招生；
- 团队后来改了。

这些表达会削弱你。

高级开发面试里，你要主动改成：

> 我当时识别到第一版全链路大模型方案在时延、成本和准确性上不可控，所以推动把链路拆成 Java 指标计算、Python 结构化解析、AI 只生成模板配置。我的核心动作是抽象出 4 类模板规则，推动解析链路从模型直出改成配置驱动，并补了配置校验、样本回放和灰度验证机制。

你要减少“背景解释”，增加“我推动的变化”。

---

## 高危 2：指标口径不稳

你多次出现类似问题：

- 命中率到底是全量命中率、召回率，还是原规则命中样本保留率？
- 100 条流水是什么样本？
- 80% 是线上数据占比，还是正负样本比例？
- 模板成功率是没报错，还是人工验收正确？
- 新链路多命中 20%，是好事还是误伤？

真实三面会非常在意这个。

你后续所有指标都必须固定成三层口径：

1. **分母是什么**
2. **分子是什么**
3. **统计周期 / 样本来源 / 是否人工标注**

例如：

> 新增命中准确率 = 新规则新增命中的样本中，经人工标注确认应该命中的样本数 / 新规则新增命中的样本总数。

不能再只说“命中率提高”。

---

## 高危 3：质量体系经常从“人工兜底”开始

你在多个问题中会自然说：

- 人工介入；
- 运营看；
- 用户确认；
- 客服处理；
- 测试环境再测。

这不是不能说，但不能作为第一答案。

高级开发应该先讲系统机制：

- 静态校验；
- 语法校验；
- schema 校验；
- 字段级校验；
- 业务一致性校验；
- 样本回放；
- golden case；
- shadow mode；
- 新旧链路 diff；
- 误伤抽检；

`ThreadPoolExecutor` 的执行顺序是：

### 2. MySQL 和 Redis 的定位要说清

你说“四种状态都放 MySQL 可以接受”，这个方向没错，但要补一句核心原则：

> MySQL 是任务状态的最终事实源，Redis 只是缓存、加速查询、前端实时展示或分布式锁/短期状态使用。

也就是：

- **MySQL：权威状态、可追溯、可恢复、可审计**
- **Redis：临时状态、进度缓存、WebSocket 推送辅助、锁、幂等控制、热点查询**

不能让 Redis 成为最终状态源，尤其金融/风控系统不行。

---

### 3. Redis 和 MySQL 不需要强行“一个原子操作”

你说要设置一个原子性操作，让 Redis 和 MySQL 一起完成。

这里要小心。MySQL 和 Redis 跨存储强一致很难，不能随口说“原子”。

更常见方案：

### 方案 A：先写 MySQL，再删 / 更新 Redis

状态变更以 MySQL 为准：

1. 开事务更新 MySQL 状态；
2. 提交成功；
3. 更新 Redis 缓存或删除缓存；
4. 推 WebSocket；
5. 如果 Redis / WebSocket 失败，后续靠重试或前端轮询补偿。

### 方案 B：Outbox 事件表

如果要保证消息推送可靠：

1. MySQL 事务内更新任务状态；
2. 同事务写一条 outbox 事件；
3. 后台任务投递 WebSocket / MQ；
4. 投递成功后标记事件完成；
5. 投递失败可重试。

这个比你说的“Redis -> WebSocket -> MySQL”稳得多。

---

### 4. WebSocket 不应该参与状态一致性的主链路

WebSocket 是通知通道，不是状态源。

正确思路：

> 状态先落库，WebSocket 只是把最新状态推给前端。即使 WebSocket 推送失败，前端也能通过任务 ID 查询 MySQL 或 Redis 中的最终状态。

不要把 WebSocket 放进状态更新事务里。

---

### 5. running 卡死不能只靠 catch 异常

你说异常 catch 后状态变失败。这个只能处理代码显式抛异常。

但 running 卡死可能是：

- 服务宕机；
- 线程池任务丢失；
- Python 服务无响应；
- 网络超时；
- 进程被 kill；
- Redis 状态丢失；
- 数据库连接中断；
- 下游 OCR 长时间不返回；
- WebSocket 推送失败；
- 消费者拿到任务后还没更新状态就挂了。

这些不会都走 catch。

所以必须有：

- `heartbeat_time`；
- `update_time`；
- `lease_timeout`；
- 定时扫描；
- 幂等重试；
- 最大重试次数；
- 死信 / 人工处理。
