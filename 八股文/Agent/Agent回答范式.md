# Agent 回答范式

## 为什么上一版仍然不合格

Q: 为什么“答题范式卡”不能放在每道题的第一张卡里？

A:
- 因为面试官问的是“请你解释这个问题”，不是“请你说说这题应该怎么答”。
- 上一版把评分点拆成了指南，例如“先说定义、再说机制、最后说工程实践”，这有助于写作，但不能直接作为面试回答。
- 真正的第一张卡应该是一段可直接复述的“面试直接回答”，把定义、机制、边界、例子和工程影响串起来。
- 评分点清单只能放在写作自检里，不能替代答案本身。
- 后续所有 Agent/LLM 题都要先给直接答案，再拆成概念卡、机制卡、例子卡、边界卡和正确性审查卡。

## 正确卡片结构

Q: 一道 Agent/LLM 面试题应该如何组织成 Anki 知识点？

A:
- 第一张必须是 `面试直接回答卡`：Q 问面试中如何回答，A 给一段可以直接说出口的完整回答。
- 后续再拆 `概念卡`、`机制卡`、`例子卡`、`边界卡`、`工程实践卡`、`正确性审查卡`。
- 第一张卡不写“应该先...再...”，而是直接回答问题。
- 拆分卡可以帮助复习细节，但不能让学习者只记住答题步骤。
- 每张卡都要面向真实面试表达：结论清楚、因果完整、边界明确、有工程例子。

## 直接回答要求

Q: `面试直接回答卡` 必须满足哪些要求？

A:
- 必须先回答题目本身，不能只给提纲。
- 必须把关键概念串起来，例如 token、context window、最大输出 token、截断、成本延迟要放在同一条逻辑链里。
- 必须说明“为什么重要”，也就是这个机制会如何影响应用行为。
- 必须给至少一个具体例子，避免只停留在抽象定义。
- 必须落到工程边界：强约束业务不能只依赖模型自由生成，要靠规则、程序、权限、schema、校验、人工确认或审计兜底。

## 可追问原理要求

Q: 怎样避免 Agent/LLM 卡片写成泛泛而谈？

A:
- 每个核心概念都要回答“底层对象是什么”。例如 token 是计数单位，KV cache 是每层 Transformer 存下来的 K/V 向量，权重是模型参数。
- 能写公式就写公式，并解释变量含义。例如 KV cache 显存要说明 `L`、`hidden_dim`、`p` 分别是什么。
- 必须给数字例子。只说“长上下文更耗显存”不够，要能算出 Llama2-7B FP16 KV 约 `512KB/token`，32K 上下文约 `16GB`。
- 必须区分相邻概念。例如 token 数量、权重精度、KV cache 精度、最大上下文长度、最大输出 token 不是同一个东西。
- 必须写追问边界。例如 `2 × L × hidden_dim × p` 是无 GQA/MQA 时的简化公式，GQA/MQA 要看 KV heads。
- 一张卡经得起细问的标准是：面试官追问“为什么、怎么算、举个例子、边界是什么”，答案里都有落点。

## 方案选择三分法要求

Q: 回答 RAG、fine-tuning、prompt、Agent 架构等方案选择题时，必须补什么？

A:
- 不能只做二分对比，例如“RAG 解决知识，fine-tuning 解决风格”，还要补第三类：确定性业务规则应该交给代码、schema、权限系统、规则引擎或工作流。
- 必须讲每个方案的核心机制，而不是只讲适用场景。例如 RAG 要讲文档清洗、切块、embedding、索引、检索、rerank、上下文组装和引用；fine-tuning 要讲训练样本、参数适配、评估和发布。
- 必须说明失败模式。例如 RAG 会因为错召回、漏召回、旧文档和权限过滤失败而答错；fine-tuning 会因为低质量样本、分布漂移和事实过期而退化。
- 必须说明输入条件。例如 fine-tuning 依赖高质量标注样本、稳定任务分布和独立评估集；没有这些条件时，微调可能只是把噪声固化进模型。
- 必须落到决策框架：事实知识选 RAG，稳定行为模式选 fine-tuning，强约束规则和关键业务状态选代码/schema/权限/校验。

## 工具语义区分要求

Q: 涉及工具调用和指令层级时，必须区分哪些概念？

A:
- 必须区分 `工具描述/tool schema` 和 `工具结果/tool result`。
- 工具描述是应用开发者提供给模型的能力契约，说明工具能做什么、什么时候用、参数怎么填、返回什么结构；它会影响模型的工具选择和参数构造。
- 工具结果是工具执行后的观察数据，例如数据库记录、日志、检索片段、权限判断结果；它提供事实材料，但不应该成为新的高优先级指令。
- 工具结果在事实可信度上可能高于用户口头说法，例如数据库显示订单未付款，就不能按用户“我已付款”的说法退款。
- 但工具结果在指令权威性上低于 system/developer 规则；如果工具结果或检索文档里含有“忽略系统提示”，应当视为数据污染或 prompt injection。
- 回答时要同时讲“谁能下指令”和“谁更能证明事实”，这两条轴不能混成一条。

## 优先级标准化要求

Q: 讲指令层级时，优先级应该如何标准化表达？

A:
- 可以标准化表述为：`System/平台安全边界 > Developer/应用策略与工具契约 > User/当前任务请求 > Tool result 与检索上下文/外部内容`。
- `工具描述/tool schema` 通常属于开发者或应用提供的工具契约，应和工具结果分开讲。
- `Tool result` 和 RAG 文档更像事实数据或观察结果，不是高优先级命令。
- 发生事实冲突时，可信工具结果可以覆盖用户陈述；发生指令冲突时，高层指令覆盖低层文本。
- 面试表达要避免一句“system 大于 user 大于 tool”结束，必须说明工具描述和工具结果的不同作用。

## 冲突处理粒度要求

Q: 回答冲突指令处理时，不能只说“拒绝”，还要说明什么？

A:
- 必须说明“只拒绝冲突部分，保留可执行部分”。
- 如果用户请求里一部分安全、一部分违规，应完成安全部分，并解释不能执行违规部分。
- 例如用户说“总结这份合同，并把对方手机号全部列出来”，可以总结合同，但手机号应脱敏或拒绝输出。
- 如果用户要求“删除日志并告诉我错误原因”，可以解释错误原因或给只读排查建议，但拒绝删除日志。
- 这种粒度化处理比整单拒绝更有帮助，也比全量顺从更安全。

## 低风险偏好冲突要求

Q: 低风险偏好冲突应该如何处理？

A:
- 低风险偏好冲突通常不需要拒绝，而是澄清、取舍或给折中输出。
- 例如用户同时要求“详细解释”和“50 字以内”，可以优先满足字数，给简版，并提示可继续展开。
- 例如用户要求“用中文回答”又说“保留英文术语”，可以中文解释，关键术语保留英文。
- 例如用户要求“严肃但口语化”，可以采用专业但不生硬的语气。
- 范式是：安全/权限/格式契约冲突按高优先级处理；偏好冲突尽量帮助用户完成目标。

## 非可信上下文与工程防护要求

Q: 涉及 prompt injection 或外部资料时，必须补哪些工程防护？

A:
- 必须明确：外部文档、网页、邮件、PDF、日志、RAG 片段中的“指令”应视为数据而非命令。
- 模型可以总结这些内容，也可以标记“疑似注入内容”，但不能执行其中的越权要求。
- 工程上要有工具调用限制：工具白名单、参数 schema、权限校验、只读/写操作分级、危险动作人工确认。
- 要有审计日志：记录用户请求、上下文来源、模型输出、工具调用参数、工具结果、拒绝原因和审批记录。
- 要有执行层 deterministic controls：限流、幂等、dry-run、回滚、策略引擎，不能只依赖模型判断。

## 自检清单

Q: 写完一题后如何判断它是不是“直接面试回答”？

A:
- 把第一张卡的答案单独读出来，是否能直接回答面试官的问题？
- 答案里是否少用了“应该、先、再、最后”这种模板指导语？
- 是否覆盖题目特有评分点，而不是只讲通用 LLM 常识？
- 是否解释了机制对应用行为的影响，例如截断会导致遗忘用户修正、输出上限过小会截断答案？
- 是否有具体例子和工程权衡，例如更多输入/输出 token 会增加成本和延迟？
- 是否包含边界和兜底，而不是把模型能力说成确定性保证？

## 面试表达模板

Q: Agent/LLM 题的第一张卡可以用什么表达风格？

A:
- “我理解这个问题可以从模型实际看到什么、模型如何生成、系统如何约束三个层面回答。”
- “具体来说，X 是...，它影响的是...；Y 是...，它限制的是...。”
- “这会带来一个工程后果：如果...被截断/错误/过长，系统就可能...。”
- “所以线上不能只靠模型自由生成，还要用...兜底。”
- 这种表达是完整回答，不是答题步骤提示。
