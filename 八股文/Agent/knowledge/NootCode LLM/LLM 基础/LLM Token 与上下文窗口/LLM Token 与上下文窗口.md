# LLM Token 与上下文窗口

来源：https://www.nootcode.com/problems/llm-tokens-context-windows

## 面试直接回答卡
Q: 面试中如何直接回答“Token 与上下文窗口是什么，它们对 LLM 应用有什么影响？”

A:
- Token 是模型处理文本的基本单位，不一定等于一个汉字或一个英文单词，可能是字、词片段、标点、空格组合或多字符片段。LLM 的输入和输出最终都会被 tokenizer 转成 token 序列。
- 上下文窗口是一次模型调用中模型能直接看到和处理的 token 总容量。系统指令、用户问题、历史对话、RAG 检索片段、工具结果，以及给输出预留的空间都会消耗这个窗口。
- 这里要区分两个概念：总上下文窗口是模型一次调用的总容量；最大输出 token 数是生成阶段的单独上限。输入太长会挤压可生成空间，最大输出 token 设得太小则会导致答案没说完就被截断。
- 如果从本地推理原理看，token 本身只是“数量”，但每进来一个 token，模型通常要在每层 Transformer 中为它缓存一组 K 向量和 V 向量，也就是 KV cache。上下文越长，KV cache 越大，显存占用会随 token 数近似线性增长。
- 截断会直接改变应用行为。比如用户前面纠正过“不要退款，只查询物流”，但这条历史被裁掉后，模型可能仍按退款流程回答；再比如关键系统约束、业务规则或检索证据被截断，模型就可能忘记格式要求、引用错误材料或做出错误建议。
- 工程上不能简单追求“上下文越长越好”。更多输入 token 和输出 token 通常意味着更高成本、更长延迟；本地部署还会带来更大的 KV cache 显存压力，也可能引入更多噪声，降低答案质量。

## 概念卡
Q: Token 和上下文窗口的核心区别是什么？

A:
- Token 是计量单位，表示模型实际处理文本的基本粒度。
- 上下文窗口是容量限制，表示一次调用最多能放入多少 token。
- Token 既包括输入 token，也包括模型生成的输出 token。
- 上下文窗口通常约束“输入 + 输出”的整体容量；API 里还常有单独的最大输出 token 参数。
- 面试表达：token 解决“怎么计量”，context window 解决“本次模型能看多少”。

## 最大输出 Token 卡
Q: 最大输出 token 数和总上下文窗口是什么关系？

A:
- 总上下文窗口是模型一次调用可处理的总 token 上限，包含输入侧和输出侧的预算。
- 最大输出 token 数是生成阶段允许模型最多生成多少 token 的上限。
- 如果输入内容已经接近总上下文窗口，即使最大输出 token 设置很大，实际也可能没有足够空间生成长答案。
- 如果最大输出 token 设置过小，模型可能刚列出前两点就停止，导致回答不完整、JSON 没闭合、代码缺尾部。
- 工程上要同时控制输入裁剪和输出预算，而不是只调一个参数。

## 截断影响卡
Q: 截断会怎样改变 LLM 应用行为？

A:
- 历史修正被截断：用户前面说“以后都用中文回答”，被裁掉后模型可能又切回英文。
- 业务约束被截断：系统要求“不能承诺退款”，如果低优先级业务提示或检索规则被裁掉，模型可能生成违规承诺。
- 证据材料被截断：RAG 片段只剩结论没有来源，模型可能引用错误或补全不存在的细节。
- 工具结果被截断：日志、表格、JSON 只保留一部分，模型可能基于不完整数据做判断。
- 输出被截断：答案、代码、SQL、JSON 可能不完整，进入下游系统会解析失败或行为异常。

## 消耗来源卡
Q: 一次 LLM 调用中，哪些内容会消耗上下文窗口？

A:
- 系统指令、开发者指令、角色设定、安全规则和输出格式要求。
- 用户当前问题、多轮历史对话、用户上传文件抽取文本。
- RAG 检索片段、文档标题、来源、引用、元数据。
- 工具调用结果，例如数据库查询、日志、接口返回、代码运行结果。
- 输出预算，尤其是长报告、长代码、长 JSON 或多步骤解释。

## 工程权衡卡
Q: 为什么上下文窗口不是越大越好？

A:
- 成本：输入 token 和输出 token 通常都会计费，长上下文会显著增加调用成本。
- 延迟：模型处理更多输入和生成更多输出通常更慢，端到端体验变差。
- 显存：本地推理时，每个上下文 token 通常会产生 KV cache，长上下文会线性放大显存占用。
- 质量：无关上下文太多会引入噪声，模型可能引用错误片段或忽略真正关键的信息。
- 安全：塞入更多历史、日志和文档会扩大敏感信息暴露面。
- 维护：长 prompt 更难调试，失败时不容易判断是哪段上下文造成的问题。

## KV Cache 原理卡
Q: 为什么上下文 token 会占用显存？KV cache 到底是什么？

A:
- Transformer 生成时，每来一个 token，每一层都会为这个 token 计算 attention 需要的 Key 向量和 Value 向量。
- 为了生成下一个 token 时不用重新计算所有历史 token 的 K/V，推理框架会把历史 token 的 K/V 存起来，这就是 KV cache。
- 所以上下文 token 数不是只影响“计数”和“计费”，在本地推理里还会影响显存：上下文越长，缓存的 K/V 越多。
- Query 通常是当前生成步临时计算，历史上需要长期保存的是 K 和 V，所以公式里会有 `×2`。
- 这也是为什么长上下文模型不只是位置编码或训练能力问题，还涉及显存、带宽和推理吞吐。

## KV Cache 公式卡
Q: 单个 token 的 KV cache 显存大致怎么算？

A:
- 常见简化公式：`Bytes_per_token = 2 × L × hidden_dim × p`，默认 batch=1 且每层 KV 宽度等于 `hidden_dim`。
- `×2` 表示 K 一份、V 一份。
- `L` 是 Transformer 层数，例如 Llama2-7B 是 32 层。
- `hidden_dim` 是隐藏维度，例如 Llama2-7B 是 4096。
- `p` 是 KV cache 单个数值的字节数，例如 FP16 是 2B，INT8 是 1B，INT4 是 0.5B。
- 更通用的公式是：`Bytes_per_token = 2 × L × n_kv_heads × head_dim × p`。如果模型使用 GQA/MQA，`n_kv_heads × head_dim` 可能小于 `hidden_dim`，不能机械套简化公式。

## KV Cache 计算例子卡
Q: 用 Llama2-7B 举例，32K 上下文的 KV cache 大约占多少显存？

A:
- Llama2-7B 可用简化估算：`L=32`，`hidden_dim=4096`。
- KV 用 FP16 时，`p=2`，单 token KV 字节数是 `2 × 32 × 4096 × 2 = 524288B`，约 `512KB/token`。
- 如果上下文是 `32768` token，KV cache 约 `32768 × 512KB = 16GB`。
- KV 用 INT8 时，`p=1`，约 `256KB/token`，32K 上下文约 `8GB`。
- KV 用 INT4 时，`p=0.5`，约 `128KB/token`，32K 上下文约 `4GB`。
- 这个例子说明：上下文长度和 KV 精度会直接决定长上下文本地推理的显存压力。

## Token、权重精度、KV 精度区分卡
Q: token 数、权重精度、KV cache 精度、上下文大小分别控制什么？

A:
- Token 数是纯计数：用来统计输入输出长度、卡上下文上限、计费，但它本身不说明单个 token 在显存里占几 KB。
- 权重精度控制模型底座大小：FP16、INT8、INT4 权重量化会影响模型加载后的静态显存，不随当前 token 数增长。
- KV cache 精度控制每个上下文 token 的缓存体积：KV FP16、INT8、INT4 会让同样数量 token 的 KV 显存约按 `1 : 1/2 : 1/4` 缩放。
- 上下文大小控制最多能放多少 token：例如 128K 或 1M token 是容量上限，真正显存还要看模型层数、KV 宽度和 KV 精度。
- 关键区别：权重量化让“模型底座”变小，KV 量化让“每个上下文 token 的缓存”变小，两者默认是不同开关。

## 权重量化与 KV 量化追问卡
Q: 为什么 7B INT4 权重很小，长上下文仍然可能很吃显存？

A:
- 权重量化只减少模型参数本身的静态占用，例如 7B INT4 权重可能只需要几 GB 级显存。
- 但如果 KV cache 仍然用 FP16，长上下文的历史 token 仍会按 FP16 存 K/V。
- 以 Llama2-7B 的简化估算为例，32K 上下文的 FP16 KV cache 约 `16GB`。
- 这意味着即使权重只有约 `3-4GB`，总显存也可能接近 `权重 3-4GB + KV 16GB + 运行时开销`。
- 所以在长上下文本地部署里，KV cache 量化有时比权重量化更影响“能不能跑得动”。

## 工程实践卡
Q: 生产系统如何管理 token 与上下文窗口？

A:
- 对长对话做状态抽取，只保留目标、约束、已完成动作和待确认事项。
- 对知识问答使用 RAG，只召回授权、相关、较新的片段，并附来源。
- 对大工具结果先摘要或结构化提取，不把完整日志、表格、JSON 全塞进窗口。
- 对强格式输出预留足够最大输出 token，并在生成后做 JSON/schema/parser 校验。
- 对高风险场景，关键业务规则、权限和执行动作不能只靠上下文提示，要由后端规则、程序逻辑和人工确认兜底。

## 正确性审查卡
Q: 解释 token 与上下文窗口时要避免哪些不严谨说法？

A:
- 不要说 token 等于字或词，应该说 token 是 tokenizer 的切分单位。
- 不要说上下文窗口等于长期记忆，它只是本次调用可直接看到的内容。
- 不要忽略最大输出 token，上下文窗口和输出上限是相关但不同的限制。
- 不要把截断说成只影响“少看一点内容”，它会改变模型行为、格式完整性和下游系统稳定性。
- 不要把 token 计数和 KV cache 显存混为一谈：计费通常按 token 数，显存压力取决于模型结构、上下文长度、KV 宽度和 KV 精度。
- 不要把权重量化和 KV 量化混为一谈：INT4 权重不代表 KV cache 也是 INT4。
- 不要机械套 `2 × L × hidden_dim × p` 到所有模型；GQA/MQA 模型要看 `n_kv_heads × head_dim`。
- 不要说长上下文一定提升效果，更多 token 同时带来成本、延迟、显存、噪声和安全风险。
