# 为 AI Agent 设计工具调用体系

来源：https://www.nootcode.com/problems/ai-agent-tool-design

## 面试直接回答卡
Q: 面试中如何直接回答“如何为 AI Agent 设计工具调用体系？”

A:
- Agent 工具调用体系的核心，是把 LLM 的语言理解和规划能力，连接到受控的外部能力上，比如查数据库、搜文档、跑测试、创建工单、发起审批。模型负责理解任务和提出调用意图，但真正执行必须由受控服务端完成。
- 设计工具时不能只暴露一堆 API，要给每个工具定义清楚用途、参数 schema、返回结构、错误码、权限范围、超时、重试和幂等策略。
- 要特别区分读工具和写工具。查询订单、搜索文档这类读操作风险相对低；退款、删除、发布、转账、改权限这类有副作用的写操作必须有权限校验、人工确认、审计日志和回滚预案。
- 举个例子，Agent 可以调用“查询订单”拿到订单状态，但是否能退款、退多少钱、是否需要审批，应该由后端规则和风控系统判断，而不是模型根据用户描述自由决定。
- 所以工具调用不是让模型随便操作系统，而是把模型意图放进一个有权限、规则、幂等、审计和人工确认的执行框架里。

## 核心机制卡
Q: AI Agent 为什么需要工具调用体系？

A:
- LLM 擅长语言理解、计划和生成，但不能凭自身知道实时订单、数据库状态、线上配置或用户权限。
- 工具调用把外部能力封装成可控接口，例如查文档、查订单、跑测试、开工单、发起审批。
- Agent 通过“理解任务 -> 选择工具 -> 填参数 -> 执行 -> 观察结果 -> 决定下一步”的循环完成复杂任务。
- 好的工具体系不是 API 越多越好，而是每个工具都有清晰边界、参数约束、权限和失败语义。
- 面试一句话：工具让 Agent 能做事，工程边界决定它能不能安全做事。

## 机制拆解卡
Q: 一个可靠的工具调用链路包含哪些环节？

A:
1. 工具声明：描述工具用途、限制、参数含义和返回结构。
2. 参数 schema：限制类型、枚举、必填字段、范围和格式。
3. 调用决策：模型判断是否需要工具、调用哪个工具。
4. 执行网关：服务端做鉴权、限流、幂等、超时、重试和风控。
5. 结果反馈：返回结构化结果、错误码、可恢复建议和下一步状态。
6. 审计确认：对高风险动作记录日志，必要时要求人工确认。

## Tool Schema 例子卡
Q: 工具参数 schema 为什么比自然语言参数更可靠？

A:
- 例如退款工具不要设计成 `action: "帮用户退一下款"` 这种自由文本。
- 更可靠的 schema 是：`order_id: string`，`amount_cent: integer`，`reason_code: enum`，`idempotency_key: string`，`dry_run: boolean`。
- `order_id` 用来查订单，`amount_cent` 防止金额单位歧义，`reason_code` 防止随意编原因。
- `idempotency_key` 防止模型重试或循环时重复退款。
- `dry_run=true` 可以先让工具返回“是否满足退款条件”，真正退款再进入确认或审批。
- 这就是把模型的自然语言意图，变成后端可校验、可审计、可拒绝的结构化动作。

## 举例卡
Q: 设计“查询订单并申请退款”的 Agent 工具时要注意什么？

A:
- 查询订单是读工具，要校验用户是否有权查看该订单。
- 申请退款是写工具，必须有幂等键，防止模型循环或重试导致重复退款。
- 金额、订单状态、支付流水、退款原因要由后端业务规则校验，不能只相信模型填参。
- 大额退款、异常订单、跨账号请求应进入人工确认。
- 工具返回应结构化，例如 `NEED_HUMAN_CONFIRMATION`、`PERMISSION_DENIED`、`INVALID_ORDER_STATE`，方便模型和系统决定下一步。

## 边界与失败模式卡
Q: 工具调用体系有哪些常见失败模式？

A:
- 工具描述模糊：模型误把查询工具当修改工具，或把测试工具当发布工具。
- 参数过宽：大段自然语言参数难校验，容易注入、歧义或越权。
- 权限缺失：Agent 能访问用户无权访问的数据。
- 幂等缺失：重试或循环造成重复付款、重复退款、重复发消息。
- 错误不可恢复：工具只返回失败，模型不知道是权限、参数、超时还是业务规则问题。

## 工程实践卡
Q: 如何设计安全可维护的 Agent 工具？

A:
- 工具小而明确：一个工具只做一个动作，避免“万能执行器”。
- 读写分离：只读、低风险写、高风险写使用不同权限和确认策略。
- 参数结构化：优先 enum、number、object schema，减少不可控自由文本。
- 执行可控：限流、超时、重试上限、幂等键、回滚和审计日志。
- 人在环：删除、发布、转账、退款、改权限等动作默认需要确认或审批。

## 正确性审查卡
Q: 讲 Agent 工具调用时要避免哪些错误说法？

A:
- “模型决定调用就直接执行”：危险，执行必须经过服务端权限和规则校验。
- “工具越多 Agent 越强”：不一定，工具过多会增加选择错误和维护成本。
- “自然语言参数最灵活”：关键业务应优先结构化，灵活不等于安全。
- “失败让模型自己重试就行”：不够，要有重试上限、幂等和人工介入。
- “Agent 是责任主体”：工程责任仍在系统设计方，必须有审计、回滚和安全边界。
