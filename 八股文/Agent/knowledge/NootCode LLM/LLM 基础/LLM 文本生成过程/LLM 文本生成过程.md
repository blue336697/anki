# LLM 文本生成过程

来源：https://www.nootcode.com/problems/llm-generation-process

## 面试直接回答卡
Q: 面试中如何直接回答“LLM 文本生成过程”？

A:
- LLM 生成文本本质上是基于当前 context window 内的 token，自回归地预测下一个 token。模型不会一次性写完整段答案，而是每一步根据已有输入和已生成内容，计算词表里每个候选 token 的分数，再通过解码策略选出下一个 token。
- 输入会先被 tokenizer 切成 token，系统指令、用户问题、历史消息、工具结果、RAG 片段都会进入上下文窗口。超出窗口并被截断的内容，不能直接影响当前预测，所以长对话或长文档场景要特别注意上下文管理。
- 模型每一步会输出 logits，经过 softmax 变成概率分布。解码时如果用 greedy decoding，就每步选概率最高的 token，输出更稳定但多样性较低；如果用 sampling，temperature、top-p、top-k 会影响随机性和多样性。
- 同一个提示词多次运行可能不同，是因为 sampling 可能在某一步选到不同 token，而早期 token 的差异会改变后续上下文，使后面的概率分布也跟着变化。
- 工程上要把 LLM 输出当作概率性生成结果：开放式写作可以接受多样性，但客服政策、SQL、代码、金额、权限、审批等强约束任务，不能只靠模型自由生成，要用规则、schema、程序校验、工具结果和人工确认兜底。

## 核心机制卡
Q: LLM 生成文本的完整过程是什么？

A:
- LLM 首先把系统指令、用户输入、历史消息、工具结果等内容切成 token，并放入当前 context window。
- 模型只能基于这个窗口内的 token 继续预测；如果早期历史因为窗口限制被截断，它就不能直接影响当前生成。
- 在每一步生成时，模型根据已有上下文计算词表中每个候选 token 的 logits，再通过 softmax 转成概率分布。
- 解码策略从概率分布中选择下一个 token，把它追加到上下文后继续下一轮。
- 这个循环会持续到遇到停止符、达到输出长度上限、触发 stop sequence，或被系统中断。

## 机制拆解卡
Q: 从输入到输出，LLM 每一步具体做了什么？

A:
1. Tokenization：把文本切成 token id，token 可能是字、词片段、空格、标点或多字符组合。
2. Context window 装载：把可见输入放进上下文窗口，窗口外内容如果没有被摘要或检索回来，就不会直接参与预测。
3. Transformer 前向计算：模型读取上下文 token，得到当前位置的隐状态。
4. Logits 与 softmax：模型为词表中每个候选 token 输出分数，softmax 把分数转成概率分布。
5. Decoding：用 greedy 或 sampling 等策略选 token。
6. 自回归循环：新 token 会成为后续预测的上下文，因此早期 token 选择会影响后续生成方向。

## 解码策略卡
Q: greedy decoding 和 sampling 有什么区别？

A:
- Greedy decoding 是每一步都选择概率最高的 token，优点是输出更稳定、更可复现，缺点是可能保守、模板化，甚至卡进局部最优表达。
- Sampling 是按概率分布抽样，低概率 token 也可能被选中，因此输出更有多样性。
- Temperature 会改变分布尖锐程度：低 temperature 更接近稳定输出，高 temperature 增加发散和创造性。
- Top-p/top-k 会限制候选集合：top-k 取概率最高的 k 个，top-p 取累计概率达到阈值的候选集合。
- 面试表达：greedy 偏确定，sampling 偏多样；稳定性和创造性通常要按任务取舍。

## 输出差异卡
Q: 为什么同一个提示词多次运行可能得到不同结果？

A:
- 如果使用 sampling，模型每一步不是固定选最高概率 token，而是按概率抽样，所以第一次和第二次可能从某一步开始选到不同 token。
- 早期 token 的差异会改变后续上下文，后面每一步的概率分布也会随之变化，最终答案可能越来越不同。
- Temperature、top-p、top-k、随机种子、模型版本、系统提示词、工具结果、检索片段顺序都可能影响输出。
- 即使问题相同，如果对话历史、当前时间、权限状态或上下文裁剪不同，模型看到的实际输入也不同。
- 所以生产系统要记录 prompt 版本、模型版本、采样参数、检索结果和工具调用，方便复现和排查。

## 举例卡
Q: 用例子说明逐 token 生成为什么会影响答案质量。

A:
- 用户问“Redis 为什么单线程还快？”，模型第一步可能生成“因为”，后面继续生成“它主要基于内存和 IO 多路复用”。
- 如果早期生成走偏，比如写成“因为 Redis 给每个连接分配一个线程”，后续内容可能围绕这个错误前提继续解释。
- 这类错误不是语法问题，而是早期 token 选择把答案引到错误路径上。
- 如果上下文里还有错误资料，或者问题要求强行回答，模型更容易生成流畅但错误的解释。
- 工程上要用检索来源、低随机性参数、答案校验和必要的人工审核降低这种风险。

## 工程实践卡
Q: 理解 LLM 文本生成过程后，工程系统应该怎么设计？

A:
- 对开放式写作、总结、改写，可以允许一定 sampling，让输出更自然。
- 对客服政策、代码补丁、SQL、金额、权限、审批等强约束任务，应降低随机性，并使用 schema、规则和程序校验。
- 对事实性问题，应通过 RAG 或工具查询提供来源，不要让模型凭语言模式猜。
- 对长对话，应做摘要、检索、状态抽取和上下文裁剪，避免关键约束被窗口挤掉。
- 关键业务逻辑不应只依赖模型自由生成，最终决策要交给规则系统、程序逻辑、权限系统或人工确认兜底。

## 正确性审查卡
Q: 解释 LLM 文本生成过程时有哪些常见误区？

A:
- “模型查出答案”：不准确。多数生成场景是基于上下文预测 token，不是从固定答案库取句子。
- “上下文等于无限记忆”：错误。模型只能直接利用当前 context window 内的 token。
- “greedy 一定最好”：不一定，它稳定但可能缺少多样性，也可能生成保守或重复答案。
- “temperature 低就不会错”：错误。低随机性不能弥补错误上下文、缺失知识或业务规则缺失。
- “同一个 prompt 必然同一个输出”：不一定，sampling、服务端版本、检索结果和上下文状态都可能带来差异。
