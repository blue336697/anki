# LLM 模型选型与权衡

来源：https://www.nootcode.com/problems/llm-model-selection-trade-offs

## 面试直接回答卡
Q: 面试中如何直接回答“LLM 模型选型需要权衡什么？”

A:
- LLM 模型选型不是简单选择“最强”或“最贵”的模型，而是在质量、延迟、成本、上下文长度、工具调用能力、结构化输出能力、数据合规和业务风险之间做权衡。
- 大模型通常推理、复杂指令遵循和泛化能力更强，但延迟和成本更高；小模型更便宜、更快，适合分类、路由、简单抽取、改写等边界清晰的任务。
- 长上下文模型能放入更多材料，但输入 token 变多会增加成本和延迟，也可能引入噪声；本地部署还要看 KV cache 显存是否扛得住。支持工具调用和 schema 输出的模型更适合 Agent 和生产工作流。
- 实际选型不能只看公开榜单，要用自己的真实评测集测试准确率、幻觉率、引用正确率、格式稳定性、工具调用成功率、延迟和成本。
- 线上通常会采用多模型路由、缓存、降级、灰度和回滚；高风险业务里模型只能做理解、生成和辅助判断，最终仍要靠规则、权限、程序校验和人工确认兜底。

## 核心权衡卡
Q: LLM 模型选型主要权衡什么？

A:
- 大模型通常推理能力、复杂指令遵循和泛化能力更强，但延迟和成本更高。
- 小模型通常更便宜、更快，适合分类、路由、简单抽取、改写等边界清晰的任务。
- 长上下文模型能看更多材料，但不保证全部信息都被正确利用，也会增加成本和延迟。
- 支持工具调用、结构化输出、多模态、函数调用的模型更适合 Agent 和生产工作流。
- 企业选型要结合任务风险：高风险场景不能只看模型输出，还要看校验、审计和人工确认链路。

## 评估维度卡
Q: 评估一个模型是否适合业务，要看哪些维度？

A:
- 质量：准确率、幻觉率、指令遵循、推理能力、引用正确率、格式稳定性。
- 性能：首 token 延迟、总延迟、吞吐、并发、超时和稳定性。
- 成本：输入输出 token 费用、重试、缓存、人工审核、评测和失败损失。
- 能力：context window、工具调用、JSON/schema、多语言、代码、多模态。
- 部署资源：权重显存、KV cache 显存、KV 量化支持、批量推理吞吐。
- 治理：数据是否出域、日志保留、权限隔离、合规审计、版本可控。

## 长上下文选型卡
Q: 为什么选长上下文模型时不能只看“支持多少 token”？

A:
- 标称上下文长度只说明最多能放多少 token，不说明每个 token 的 KV cache 有多大。
- 模型层数、KV heads、head dim、KV 精度都会影响单 token KV 显存。
- 例如无 GQA 简化估算下，Llama2-7B FP16 KV 约 `512KB/token`，32K 上下文约 `16GB`。
- 如果模型支持 GQA/MQA，KV cache 可能比 `hidden_dim` 简化公式更小；如果没有 KV 量化，长上下文仍可能很吃显存。
- 所以选型要同时看上下文长度、实际业务有效上下文、推理框架 KV 量化能力、显存预算和吞吐目标。

## 举例卡
Q: 为什么一个系统里经常组合使用多个模型？

A:
- 企业知识助手可以先用小模型判断问题类型：闲聊、文档问答、工单创建、代码排查。
- 简单 FAQ 走小模型加检索，降低平均成本和延迟。
- 跨文档推理、故障分析、复杂方案设计再调用强模型。
- 对最终 JSON、SQL、工具参数可以用规则或另一个模型做校验。
- 这种分层比所有请求都打到最大模型更经济，也更容易做风险治理。

## 边界与误区卡
Q: 模型选型有哪些常见误区？

A:
- “榜单第一就适合业务”：不一定，榜单任务和真实业务输入差异很大。
- “越大越好”：不一定，简单任务用大模型可能只是增加成本和延迟。
- “小模型不可靠”：不绝对，边界清晰任务上小模型可能足够好。
- “模型升级只有收益”：不一定，格式、风格、工具调用行为可能退化。
- “只看 token 单价”：不够，还要算重试、超时、人工介入和事故成本。

## 工程实践卡
Q: 模型选型如何落地？

A:
- 建真实评测集，覆盖高频、长尾、恶意输入、边界输入和业务关键场景。
- 定义可量化指标：准确率、引用正确率、格式合规率、工具调用成功率、延迟、成本。
- 做灰度和 A/B，不一次性全量切换。
- 保留回滚路径：模型版本、prompt 版本、工具版本和检索配置都要可回退。
- 对强约束业务，模型只做理解、生成和辅助，最终判断由规则、程序和人工机制兜底。

## 正确性审查卡
Q: 回答模型选型时如何体现 senior 感？

A:
- 不只说“选某某大模型”，而是说按任务、风险和指标分层选型。
- 不只看离线 demo，而是关注线上分布、失败样本、监控和回滚。
- 不只比较质量，还要比较端到端延迟、成本和治理要求。
- 不把模型当唯一决策者，高风险场景要有权限、规则、校验和审计。
- 能明确回答“什么时候不用大模型”，通常比只会推荐大模型更成熟。
