# LLM 不适合处理的任务类型

来源：https://www.nootcode.com/problems/poor-fits-for-llms

## 面试直接回答卡
Q: 面试中如何直接回答“哪些任务不适合直接交给 LLM？”

A:
- LLM 不适合直接承担强确定性、强实时性和高风险执行的最终责任。它可以生成解释、草稿和候选方案，但不应该直接决定账务、权限、库存、退款、转账、删除、发布这类关键动作。
- 原因是 LLM 输出是概率性的，不天然保证可复现、可验证，也不天然知道最新订单状态、余额、库存、线上配置或用户权限。
- 例如“是否给用户退款”不能只让模型根据用户描述判断，因为退款资格涉及订单状态、支付流水、售后规则、风控、金额计算和用户身份。模型可以负责收集信息、解释规则、生成客服话术，但最终判断要由业务系统和人工审批完成。
- 对医疗、法律、金融、生产安全等高风险场景也是一样，LLM 可以辅助检索和总结，但不能无约束地产生最终结论或执行动作。
- 所以更准确的说法不是“这些场景完全不能用 LLM”，而是不能让 LLM 单独负责事实、计算、权限和执行；这些必须交给确定性系统、规则引擎、程序校验和人工确认。

## 任务类型卡
Q: 哪些任务不适合直接交给 LLM？

A:
- 强确定性任务：账务计算、库存扣减、权限判断、幂等状态变更。
- 实时事实任务：当前余额、订单状态、线上配置、库存数量，除非接入可靠工具。
- 高风险决策：医疗诊断、法律结论、金融交易、生产安全动作。
- 大规模精确计算：排序、聚合、统计、复杂数学计算，应由程序或数据库完成。
- 安全敏感操作：删除数据、发邮件、转账、改权限、发布线上变更。

## 原因拆解卡
Q: 为什么这些任务不适合只依赖 LLM？

A:
- LLM 输出具有概率性，不天然保证确定性、可复现和可验证。
- 模型可能没有最新或私有数据，只能根据上下文猜测。
- 自然语言输出难以作为交易、权限、账务等系统的唯一依据。
- 模型可能受 prompt injection、上下文噪声或用户诱导影响。
- 高风险任务的失败成本很高，必须有确定性控制和责任链。

## 举例卡
Q: “让 LLM 判断是否给用户退款”为什么危险？

A:
- 退款涉及订单状态、支付流水、售后规则、用户身份、风控和金额计算。
- 如果模型只根据用户描述判断，可能被诱导，或者缺少订单真实状态。
- 正确做法是后端服务判断退款资格，模型负责解释规则、收集信息或生成客服话术。
- 大额、异常或跨账号退款应进入人工审批。
- 这个例子说明：LLM 可以参与交互层和辅助决策，但不能直接替代业务规则引擎。

## 改造策略卡
Q: 不适合直接处理的任务，如何改造成适合 LLM 参与？

A:
- 把确定性计算交给工具：计算器、数据库、业务服务、规则引擎。
- 把权限判断交给后端：模型只能看到授权后的数据和动作。
- 把高风险动作改为草稿、建议或待确认请求。
- 把复杂任务拆成信息收集、事实查询、候选生成、校验、执行。
- 把输出结构化，并通过 schema、程序校验和人工确认后再进入下游。

## 确定性边界例子卡
Q: LLM 可以参与库存扣减吗？边界在哪里？

A:
- LLM 可以理解用户意图，例如“用户想买 2 件 A 商品”，也可以生成客服解释。
- 但库存是否足够、如何扣减、如何防止超卖，必须由库存服务和数据库事务处理。
- 真正扣减要依赖锁、乐观版本号、事务、幂等请求号等确定性机制。
- 如果让模型直接判断“应该扣库存”，它不知道实时库存，也不能保证并发一致性。
- 所以 LLM 适合做人机交互层，不适合做强一致业务状态机。

## 边界与误区卡
Q: 讨论“不适合 LLM”时有哪些误区？

A:
- “LLM 不能用于金融/医疗/法律”：过于绝对。它可以辅助解释、检索和草拟，但不应无约束做最终决策。
- “LLM 不会算数”：它能做简单计算，但不适合作为可靠计算引擎。
- “接了工具就安全”：工具还需要权限、幂等、审计和确认。
- “人工确认会降低智能化”：高风险场景中，人在环是安全设计的一部分。
- “模型回答得自信就能执行”：自信语气不等于事实和权限都成立。

## 正确性审查卡
Q: 回答这题时，如何体现工程边界？

A:
- 要区分“LLM 能参与”和“LLM 能最终负责”。
- 要把事实、计算、权限、执行从自由生成中剥离出来。
- 要说明强约束业务应由规则系统、程序逻辑、状态机和人工确认兜底。
- 要考虑审计、回滚、幂等、风控和合规。
- 要避免把 LLM 描述成万能自动化执行器。
