# LLM 指令遵循的局限性

来源：https://www.nootcode.com/problems/llm-instruction-following-limits

## 面试直接回答卡
Q: 面试中如何直接回答“LLM 指令遵循有什么局限？”

A:
- LLM 能理解和遵循自然语言指令，但这种遵循是概率性的，不像程序 `if/else` 那样有强保证。指令越长、约束越多、上下文越复杂，模型漏掉或误解某条规则的概率就越高。
- 常见问题包括指令冲突、上下文窗口过长导致关键规则被弱化或截断、外部文档里的 prompt injection、输出格式太复杂、任务本身缺少必要信息。
- 还要注意指令层级：系统指令、开发者指令、用户指令、工具结果和检索文档的可信度不同，不能把所有文本都当成同等优先级的指令。
- 因此生产系统不能只靠“请严格遵守”来保证安全。权限判断、金额计算、退款、删除、发布、发邮件、转账、改权限这些动作必须由后端规则、状态机、schema 校验、权限系统和人工确认控制。
- 简单说，prompt 是软约束，工程系统里的规则、程序逻辑和审计才是硬边界。

## 核心局限卡
Q: 为什么不能把 LLM 当作绝对服从指令的程序？

A:
- LLM 根据上下文和训练分布生成响应，遵循指令的能力是统计性的。
- 自然语言指令可能模糊、冲突、过长或包含隐含前提。
- 模型可能被检索文档、用户输入或历史消息中的噪声干扰。
- 对复杂格式或多约束任务，模型可能满足一部分要求但漏掉另一部分。
- 所以 prompt 可以引导模型，但不能替代确定性权限控制、业务规则和校验逻辑。

## 机制拆解卡
Q: 哪些因素会导致模型不遵循指令？

A:
1. 指令冲突：系统要求简洁，用户要求详细，工具结果要求补充异常说明。
2. 上下文过长：关键约束被挤到窗口边缘，甚至被截断。
3. 格式复杂：嵌套 JSON、多字段枚举、严格类型约束容易漂移。
4. 上下文污染：外部文档含有“忽略之前指令”等恶意文本。
5. 任务不可解：缺少必要事实时，模型可能猜而不是拒答。

## 举例卡
Q: 为什么“只输出 JSON，不要解释”仍然可能失败？

A:
- 模型可能在 JSON 前后加“下面是结果”这类自然语言。
- 字段类型可能错，例如把数字写成字符串，或漏掉必填字段。
- 用户输入中有换行、引号、特殊字符时，模型可能生成非法 JSON。
- 如果上下文里有多个示例 schema，模型可能混用字段。
- 工程上应使用函数调用、schema、JSON parser、失败重试和降级策略。

## Schema 校验例子卡
Q: 如何把“只输出 JSON”从软约束变成硬约束？

A:
- 软约束是 prompt 写“请只输出 JSON”，但模型仍可能输出解释文字或漏字段。
- 硬约束是服务端定义 JSON schema，例如必须有 `user_id:string`、`risk_level:enum(low,medium,high)`、`reasons:string[]`。
- 模型输出后先用 parser 解析，解析失败直接重试或返回修复任务。
- 解析成功后再做 schema 校验，字段缺失、类型错误、枚举越界都不能进入下游。
- 如果这个 JSON 会触发风控、退款、发送消息等动作，还要继续做权限和业务规则校验。

## 边界与误区卡
Q: 哪些事情不能只靠 LLM 遵守指令？

A:
- 权限判断：用户能不能查订单、删文件、看日志，必须由后端权限系统决定。
- 金额计算：账务、报价、税费要由确定性程序计算。
- 状态变更：退款、发布、删除、发邮件、转账要有确认和审计。
- 合规拒答：敏感内容控制要有策略层、检测层和日志。
- 工具执行：模型只能提出调用意图，真正执行要由受控服务端完成。

## 工程实践卡
Q: 如何提升指令遵循的可靠性？

A:
- 指令分层：系统约束、任务目标、输出格式、示例和禁止项分开写。
- 减少冲突：不要在不同段落给互相矛盾的规则。
- 结构化输出：优先使用 schema、枚举、函数调用和字段说明。
- 校验闭环：解析失败、字段缺失、权限不足要可恢复。
- 高风险动作：加入人工确认、幂等键、限流和审计。

## 正确性审查卡
Q: 解释指令遵循局限性时，怎样避免过度承诺？

A:
- 不要说“prompt 写严就一定遵守”，prompt 只是软约束。
- 不要说“系统提示词绝对不会被影响”，模型表现仍可能受复杂上下文干扰。
- 不要说“模型自检可以替代校验”，自检仍是模型输出。
- 不要把用户输入、检索文档和工具结果都当可信指令来源。
- 正确表达是：关键约束要下沉到 schema、权限、状态机、程序逻辑和人工确认。
