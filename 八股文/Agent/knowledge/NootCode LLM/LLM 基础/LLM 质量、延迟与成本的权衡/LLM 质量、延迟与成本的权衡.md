# LLM 质量、延迟与成本的权衡

来源：https://www.nootcode.com/problems/llm-quality-latency-cost-tradeoffs

## 面试直接回答卡
Q: 面试中如何直接回答“LLM 应用为什么要权衡质量、延迟和成本？”

A:
- LLM 应用里质量、延迟和成本天然互相牵制。通常更强的模型、更长的上下文、更多检索和工具调用、更多后置校验可以提升答案质量，但会增加 token 消耗、模型计算时间、外部 IO 和总成本。
- 输入 token 越多，模型预填充阶段越重；输出 token 越多，生成步骤越多。本地部署时，长上下文还会线性放大 KV cache 显存。再加上 RAG、数据库查询、代码执行、重试和校验，端到端延迟会明显上升。
- 如果为了省钱和降延迟，改用小模型、减少上下文、减少校验，简单问题可能没问题，但复杂问题、事实问答、强格式输出和高风险决策的错误率可能上升。
- 工程上通常按任务分层：简单 FAQ 走缓存或小模型，复杂分析走强模型和更多上下文；低风险任务可以快，高风险任务要保留引用、校验、审批和审计。
- 所以优化目标不是单纯让模型更快或更便宜，而是在业务风险、用户体验和预算之间找到可接受的平衡。

## 核心权衡卡
Q: 为什么 LLM 应用总要权衡质量、延迟和成本？

A:
- 质量提升通常依赖更强模型、更充分上下文、多步检索、工具调用和后置校验。
- 这些手段会增加输入输出 token、模型计算、外部 IO 和端到端等待时间。
- 降低成本和延迟通常会减少上下文、换小模型、减少调用次数或减少校验，可能牺牲复杂问题质量。
- 不同场景目标不同：客服更看重稳定和响应速度，报告生成可接受慢一些但要求更完整。
- 面试一句话：LLM 应用优化是系统级 trade-off，不是只调 temperature 或换模型。

## 机制拆解卡
Q: 哪些因素决定一次 LLM 请求的成本和延迟？

A:
- 输入 token：系统提示词、历史、RAG 片段、工具结果越多，预填充计算和费用越高。
- 输出 token：生成越长，解码步骤越多，成本和总耗时越高。
- 模型能力：大模型通常更贵更慢，但复杂任务质量更好。
- KV cache：本地推理里上下文越长，历史 token 的 K/V 缓存越大，显存和带宽压力越高。
- 工具链路：搜索、数据库、代码执行、权限查询都会拉长端到端路径。
- 重试和校验：提高可靠性，但会增加额外调用和等待。

## 本地部署成本卡
Q: 长上下文为什么会显著影响本地部署成本？

A:
- API 计费通常按 token 数，但本地部署还要关心显存，尤其是 KV cache。
- 每个上下文 token 都会在每层 Transformer 中缓存 K/V，显存占用随上下文长度近似线性增长。
- 例如 Llama2-7B 在 FP16 KV 下约 `512KB/token`，32K 上下文的 KV cache 约 `16GB`。
- 如果 KV 量化到 INT8 或 INT4，同样 32K 上下文可能约降到 `8GB` 或 `4GB`。
- 所以长上下文场景里，成本不只是 token 费用，还包括 GPU 显存、吞吐下降和部署复杂度。

## 举例卡
Q: 企业知识助手如何平衡三者？

A:
- 简单 FAQ 先查缓存或固定知识库命中，避免每次调用强模型。
- 普通文档问答只召回少量高相关片段，而不是塞整篇文档。
- 复杂故障分析再启用强模型、多步检索和更长输出。
- 对低风险闲聊减少工具调用；对高风险政策和操作建议要求引用、校验和人工确认。
- 通过日志监控每类请求的 token、延迟、失败率、用户反馈和人工介入率，再决定优化方向。

## 策略对比卡
Q: 常见优化策略分别解决什么问题？

A:
- 模型路由：用小模型处理简单任务，大模型处理复杂任务，降低平均成本。
- 缓存：减少重复问题、重复检索和重复工具调用。
- 上下文裁剪：减少 token 和噪声，但要防止关键约束被裁掉。
- 流式输出：降低用户感知等待，不一定减少模型总成本。
- 异步化：适合报告、批处理、离线分析，不适合必须实时反馈的交互。

## 边界与误区卡
Q: 优化三者时有哪些坑？

A:
- 过度裁剪上下文会导致模型看不到关键事实，质量下降。
- 小模型看似便宜，但如果错误率和重试率高，整体成本可能更高。
- 缓存如果不考虑权限、版本和过期时间，可能返回越权或过期答案。
- 减少校验能降低延迟，但可能让错误进入下游系统。
- 只看模型调用耗时不够，端到端还包括检索、工具、网络、队列和后处理。

## 正确性审查卡
Q: 回答这题如何体现工程成熟度？

A:
- 要按业务风险分级，而不是所有请求都用同一套模型和参数。
- 要把成本看成总成本，包括重试、人工审核、事故损失和评测维护。
- 要说明流式输出改善的是感知延迟，不等同于降低 token 成本。
- 要强调强约束决策必须保留规则、程序校验、权限和审计。
- 要用数据闭环优化：监控指标、失败样本、灰度实验和回滚策略缺一不可。
