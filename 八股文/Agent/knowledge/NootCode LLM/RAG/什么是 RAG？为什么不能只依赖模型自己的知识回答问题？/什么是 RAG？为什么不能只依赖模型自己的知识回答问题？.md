# 什么是 RAG？为什么不能只依赖模型自己的知识回答问题？

来源：https://www.nootcode.com/problems/what-is-rag

## 面试直接回答卡
Q: 面试中如何直接回答“什么是 RAG？为什么不能只依赖模型自己的知识回答问题？”

A:
- RAG 是 Retrieval-Augmented Generation，也就是先从外部知识库检索和问题相关的资料，再把这些资料作为上下文交给 LLM 生成答案。
- 它解决的不是“让模型变聪明一点”这么笼统的问题，而是把回答绑定到可更新、可追溯、可权限控制的外部知识上。
- 不能只依赖模型自己的参数知识，是因为模型参数里的知识可能过时、不完整、没有来源、无法访问企业私有数据，而且模型会倾向于生成听起来合理但未必真实的答案。
- 例如用户问“公司 2026 年报销餐补标准是多少”，模型预训练知识不可能知道企业内部最新制度；RAG 应该检索最新制度文档，把相关条款放进上下文，再要求模型基于条款回答并给出处。
- 但 RAG 不是万能兜底。如果检索召回错了、文档过期、权限过滤没做、chunk 切分破坏语义，模型仍然可能给出错误答案。
- 所以线上 RAG 的核心是“检索、权限、引用、答案约束、更新机制”共同工作，而不是简单把搜索结果拼进 prompt。

## 概念卡
Q: RAG 的核心链路是什么？

A:
- 用户问题进入系统后，先做 query rewrite、意图识别或权限过滤。
- 检索层从文档库、向量库、搜索引擎或数据库中找到候选片段。
- 排序层用向量相似度、关键词匹配、reranker 或业务规则筛出最相关证据。
- 生成层把问题、证据、引用信息和回答约束放进上下文，让模型生成答案。
- 后处理层做引用校验、格式校验、敏感信息过滤和失败兜底。

## 为什么需要外部知识卡
Q: 为什么模型参数知识不能替代 RAG？

A:
- 参数知识是训练时压缩进权重里的统计模式，不等于可查询数据库。
- 它通常有训练时间边界，不能天然知道最新政策、订单状态、内部文档。
- 参数知识缺少可验证来源，用户很难判断答案来自哪一页、哪一条规则。
- 企业数据存在权限边界，同一个问题对不同用户可见资料不同，模型权重本身无法表达当前用户权限。
- 事实型业务问题需要“可追溯证据 + 当前状态”，这更适合检索和工具，而不是让模型凭记忆回答。

## 例子卡
Q: 举一个 RAG 比模型裸答更可靠的例子。

A:
- 问题：“A 产品的退款窗口是多久？”
- 模型裸答可能根据通用电商经验回答“7 天”或“30 天”，但这只是概率猜测。
- RAG 会检索产品政策文档，找到“标准版 7 天、企业版按合同附件约定”。
- 生成时应回答：“标准版为 7 天；企业版需要查看合同附件”，并给出文档标题、章节和更新时间。
- 如果没有检索到证据，正确回答应是“当前知识库未找到依据”，而不是编一个看似合理的天数。

## 边界卡
Q: RAG 有哪些常见边界和失败原因？

A:
- 检索失败：相关文档没被召回，模型只能基于错误证据回答。
- 证据污染：召回了过期文档、低质量网页或恶意 prompt injection 文本。
- 上下文窗口限制：召回内容太多会挤掉关键片段，或让模型抓不住重点。
- 权限错误：把别的租户或高权限文档检索给低权限用户。
- 生成漂移：模型没有严格基于证据，自己补充了证据中不存在的结论。

## 工程实践卡
Q: 一个可靠 RAG 系统应该如何约束模型回答？

A:
- Prompt 中明确要求“只基于给定证据回答”，证据不足时输出无法确定。
- 每个 chunk 带文档 ID、标题、页码、更新时间、权限标签和版本号。
- 检索前后都做 ACL 过滤，避免越权内容进入模型上下文。
- 对高风险答案做引用覆盖检查，确保关键结论能追溯到具体证据。
- 对召回为空、证据冲突、文档过期等情况设计失败状态，而不是强行生成。

## 正确性审查卡
Q: 解释 RAG 时有哪些误区？

A:
- 不要把 RAG 说成“消除幻觉”，它只能降低无依据生成的概率。
- 不要说“向量库就是 RAG”，向量库只是检索组件之一。
- 不要忽略权限，RAG 检索到不该看的文档比模型答错更严重。
- 不要把外部文档里的指令当命令，RAG 片段是数据，不是高优先级指令。
- 不要只讲生成效果，还要讲引用、更新、删除、评估和审计。
