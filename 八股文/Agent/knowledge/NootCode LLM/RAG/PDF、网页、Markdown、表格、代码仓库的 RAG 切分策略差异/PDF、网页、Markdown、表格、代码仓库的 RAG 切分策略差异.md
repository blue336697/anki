# PDF、网页、Markdown、表格、代码仓库的 RAG 切分策略差异

来源：https://www.nootcode.com/problems/rag-chunking-by-content-type

## 面试直接回答卡
Q: 面试中如何直接回答“PDF、网页、Markdown、表格、代码仓库的 RAG 切分策略有什么差异？”

A:
- RAG 切分不能只按固定 token 数硬切，因为不同内容类型的语义边界不同。好的 chunk 应该既能被检索命中，又能在单独放进上下文时保留足够语义。
- PDF 要重点处理页码、标题层级、页眉页脚、脚注和表格跨页问题；网页要清洗导航、广告和重复组件，保留正文结构和 URL；Markdown 可以利用标题层级和代码块边界；表格要保留表头、单位和行列关系；代码仓库要按文件、函数、类、调用关系和 README 结构切。
- 例如表格里一行“标准版 7 天”如果脱离表头，就不知道是“退款窗口”还是“试用期”；代码里只切出函数体但没有文件路径和类名，也很难判断适用上下文。
- 切分还要配合 metadata，例如文档 ID、页码、章节路径、表头、代码路径、版本、权限标签，便于引用和过滤。
- 工程上通常不是一种 chunker 处理所有内容，而是按内容类型走不同 parser，再统一进入索引。
- 评价切分好坏要看检索命中率、引用可验证性、答案 groundedness 和失败样本，而不是只看 chunk 平均长度。

## PDF 切分卡
Q: PDF 做 RAG 切分要注意什么？

A:
- PDF 的文本顺序可能和视觉顺序不同，两栏排版、页眉页脚、脚注容易污染正文。
- 需要保留页码、标题、章节路径，引用时用户才能回到原文验证。
- 表格和图片可能需要单独解析或 OCR，不能只抽纯文本。
- 跨页段落和跨页表格要合并，否则 chunk 会缺上下文。
- 对合同、制度类 PDF，要特别保留条款编号和版本日期。

## 网页切分卡
Q: 网页内容做 RAG 切分要注意什么？

A:
- 先清洗导航栏、推荐列表、广告、评论区和 cookie 提示等噪声。
- 保留 URL、标题、发布时间、作者、站点来源和正文结构。
- 对文档站点，可以按 H1/H2/H3 标题层级切分。
- 对动态页面，要确认抓取的是最终正文，不是空壳或重复模板。
- 网页可信度差异大，来源可信度和更新时间要进入 metadata。

## Markdown 切分卡
Q: Markdown 为什么适合按结构切分？

A:
- Markdown 天然有标题层级、列表、代码块、表格和引用块。
- 可以按标题树切分，并把上级标题拼进 chunk metadata 或 chunk 前缀。
- 代码块不能被普通段落切断，否则示例失去意义。
- 列表项如果互相依赖，应保持在同一个 chunk 或保留前置说明。
- Markdown 文档常用于技术文档，版本、仓库路径和 commit 信息也很重要。

## 表格切分卡
Q: 表格 RAG 切分为什么不能只按行转文本？

A:
- 表格语义依赖表头、单位、行列关系和合并单元格。
- 单行“7 天、免费、企业版”脱离表头时不可解释。
- 可行做法是每个 chunk 带表名、表头、单位、行主键和相关列。
- 对宽表可以按列组切分，对长表可以按行组切分。
- 对需要计算的问题，RAG 只给文本片段可能不够，应转成结构化查询或工具计算。

## 代码仓库切分卡
Q: 代码仓库做 RAG 切分应该按什么边界？

A:
- 优先保留文件路径、语言、类名、函数名、注释和导出符号。
- 函数、类、接口、配置段是比固定 token 更自然的切分边界。
- README、API 文档、测试用例和代码实现应作为不同来源但可关联。
- 检索时关键词和符号索引通常比纯向量更重要，例如函数名、错误码、配置键。
- 复杂问题可能需要代码图谱或调用链工具，不能只靠 chunk 检索。

## 正确性审查卡
Q: 解释 RAG 切分策略时有哪些误区？

A:
- 不要说“每 500 token 切一段”就是通用答案，固定长度只是兜底策略。
- 不要让 chunk 失去标题、表头、页码、路径这些定位信息。
- 不要把 PDF、网页、表格、代码都当普通纯文本处理。
- 不要忽略 overlap 的副作用，过大 overlap 会增加噪声、成本和重复召回。
- 不要只看 chunk 数量，关键是单个 chunk 能否独立支持一个可验证答案。
