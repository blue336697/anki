# 多租户 RAG 系统如何隔离数据？

来源：https://www.nootcode.com/problems/multi-tenant-rag-data-isolation

## 面试直接回答卡
Q: 面试中如何直接回答“多租户 RAG 系统如何隔离数据？”

A:
- 多租户 RAG 的隔离目标是：A 租户的问题不能检索、看到、引用、缓存或通过日志间接泄露 B 租户的数据。这个隔离不能只靠 prompt，必须在存储、索引、检索、缓存、日志和工具权限层一起实现。
- 最基本做法是每个文档、chunk、embedding、引用预览都带 `tenant_id`、workspace、ACL、版本等 metadata，检索时服务端强制加过滤条件，模型不能自己决定能不能看。
- 隔离强度可以分层：低风险场景用共享索引加 tenant filter；中高风险场景用租户级 namespace 或独立索引；强合规场景甚至用独立存储、独立密钥和独立部署。
- 还要注意非显性泄露，比如答案引用里露出别的租户文档标题、检索缓存跨租户复用、日志保存了原文片段、评估样本混入租户私有数据。
- 例如用户属于 tenant=A，query 进入检索时必须携带 `tenant_id=A`，向量库过滤、关键词索引过滤、rerank 输入、LLM 上下文和引用展示都只能包含 A 可见数据。
- 面试里要强调：多租户隔离是后端权限和数据架构问题，不是告诉模型“不要泄露其他租户”就能解决。

## 隔离层次卡
Q: 多租户 RAG 可以在哪些层做隔离？

A:
- 存储层：不同租户独立 bucket、数据库 schema、表分区或加密密钥。
- 索引层：共享索引加过滤、租户 namespace、租户独立索引。
- 检索层：服务端强制 `tenant_id` 和 ACL filter。
- 生成层：只有已授权 chunk 能进入 LLM 上下文。
- 缓存层：检索缓存、答案缓存、引用缓存按租户和权限维度隔离。
- 日志层：日志脱敏，并限制运维和评估人员访问。

## 共享索引卡
Q: 共享索引加 tenant filter 有什么优缺点？

A:
- 优点是成本低、运维简单、跨租户规模化容易。
- 适合数据敏感度较低、租户数量多、单租户数据量小的场景。
- 风险是任何过滤条件遗漏、缓存 key 设计错误或向量库过滤 bug 都可能越权。
- 需要把 `tenant_id` 作为强制条件，由服务端注入，不能来自用户输入。
- 对高敏感租户，应考虑 namespace、独立索引或物理隔离。

## 权限过滤卡
Q: 为什么多租户 RAG 不能只在生成后过滤答案？

A:
- 一旦越权 chunk 进入模型上下文，模型可能已经在答案中吸收或改写了敏感信息。
- 即使最终文本过滤掉明显字段，模型也可能泄露摘要、统计或推断信息。
- 引用标题、文件路径、部门名称也可能构成泄露。
- 正确做法是在检索前、检索后、rerank 前后、生成前多层过滤。
- 生成后过滤只能作为最后兜底，不能作为主要权限控制。

## 缓存与日志卡
Q: 多租户 RAG 容易忽略哪些间接泄露点？

A:
- 检索结果缓存没有把租户和权限版本放进 cache key。
- 答案缓存被不同租户复用，导致 B 租户看到 A 租户答案。
- Rerank 或 LLM 请求日志保存了原始 chunk，运维后台越权可见。
- 引用预览展示了无权限文档标题或路径。
- 评估集和标注平台混入租户私有数据，没有脱敏和访问控制。

## 工程实践卡
Q: 多租户 RAG 的安全基线是什么？

A:
- 所有文档、chunk、embedding、引用都带租户和 ACL metadata。
- 服务端根据认证身份注入权限过滤，不接受模型或用户传来的权限声明。
- 检索、rerank、生成、引用展示使用同一套授权结果。
- 缓存 key 包含 tenant、user/role、ACL version、index version。
- 定期做越权检索测试，例如用 A 用户查询 B 租户特有关键词。
- 记录审计日志：谁在什么时间检索了哪些文档和引用。

## 正确性审查卡
Q: 解释多租户 RAG 隔离时有哪些误区？

A:
- 不要把“prompt 要求保密”当隔离方案。
- 不要只过滤最终答案，越权内容不能进入模型上下文。
- 不要忽略引用、缓存、日志、评估平台这些旁路。
- 不要让用户传 `tenant_id` 决定检索范围，必须来自认证和授权系统。
- 不要认为共享向量库天然安全，过滤和隔离策略要经过测试和审计。
