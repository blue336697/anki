# RAG 中如何处理短问题、模糊问题与多子问题

来源：https://www.nootcode.com/problems/rag-short-ambiguous-multi-question

## 面试直接回答卡
Q: 面试中如何直接回答“RAG 中如何处理短问题、模糊问题与多子问题？”

A:
- 短问题、模糊问题和多子问题的共同难点是 query 不再等于用户真实信息需求。RAG 不能直接把原句丢给向量库，而要先做 query understanding。
- 短问题通常缺上下文，例如用户只问“怎么处理？”需要结合会话历史、当前页面、上传文档或业务对象补全；模糊问题有多个可能意图，需要澄清或多路检索；多子问题则要拆解成子 query 分别检索和回答。
- 例如用户在退款文档页问“这个多久到账”，系统应补全成“退款到账时间”，而不是检索所有“到账”；用户问“部署和回滚怎么做”，应拆成“部署流程”和“回滚流程”两条检索。
- 对模糊但低风险的问题，可以先检索多个候选意图并在答案里说明假设；对高风险或会影响执行的问题，应先问澄清问题。
- 对多子问题，最终答案要按子问题组织，每个子答案附对应引用，避免一个证据回答所有问题。
- 工程上可以用 query rewrite、conversation state、intent classification、sub-question decomposition 和 multi-hop retrieval，但要记录改写后的 query，方便调试和评估。

## 短问题卡
Q: RAG 如何处理短问题？

A:
- 利用会话历史补全省略对象，例如“这个”指代当前文档或上一轮实体。
- 利用 UI 上下文补全，例如当前页面是“退款接口”，短问“超时呢”应转成“退款接口超时处理”。
- 利用用户权限和业务状态过滤候选范围。
- 如果补全不确定，应向用户澄清，而不是强行检索。
- 改写后的 query 要可观测，便于排查错误召回。

## 模糊问题卡
Q: RAG 如何处理模糊问题？

A:
- 先识别歧义来源：对象不清、时间不清、版本不清、产品线不清、用户意图不清。
- 低风险问答可以给出假设，例如“如果你指的是企业版退款...”。
- 高风险操作或合规场景应先澄清，例如“你问的是标准版还是企业版？”
- 可以做多路检索，分别检索不同解释，再比较证据是否收敛。
- 如果证据冲突，应展示分歧并说明需要更多条件。

## 多子问题卡
Q: RAG 如何处理一个问题里包含多个子问题？

A:
- 先拆解子问题，而不是用一个宽泛 query 检索所有内容。
- 每个子问题单独检索、rerank 和保留证据。
- 生成答案时按子问题分段，每段附对应引用。
- 检查是否每个子问题都有证据覆盖，缺失的部分要标注不确定。
- 对互相依赖的子问题，可以先回答前置事实，再回答后续推理。

## 例子卡
Q: 举例说明多子问题拆解如何提升 RAG 质量。

A:
- 用户问：“企业版怎么退款，失败了怎么重试，谁审批？”
- 如果直接检索整句，可能只召回“退款流程总览”。
- 拆成三个 query：企业版退款条件、退款失败重试策略、企业版退款审批人。
- 每个 query 召回不同文档或章节，最终答案按三段组织。
- 如果审批文档没找到，应只标注审批人未知，不能影响退款条件和重试策略的回答。

## 工程实践卡
Q: query rewrite 和问题拆解要注意什么？

A:
- 改写不能改变用户意图，只能补全省略和明确检索表达。
- 应保留原始 query、改写 query、拆解结果和使用的上下文来源。
- 对权限敏感对象，改写后仍要做 ACL 过滤。
- 对多路检索结果要去重和合并，避免上下文爆炸。
- 评估时同时看改写是否正确、每个子问题是否召回到证据、最终答案是否完整。

## 正确性审查卡
Q: 解释短问题、模糊问题和多子问题时有哪些误区？

A:
- 不要直接把所有原始 query 丢给向量库，短问题往往信息不足。
- 不要过度改写，把用户没说的条件当事实。
- 不要所有模糊问题都追问，低风险场景可以说明假设后回答。
- 不要用单一引用覆盖多个子结论，每个子问题要有自己的证据。
- 不要忽略会话历史被截断的问题，缺少历史时应承认上下文不足。
