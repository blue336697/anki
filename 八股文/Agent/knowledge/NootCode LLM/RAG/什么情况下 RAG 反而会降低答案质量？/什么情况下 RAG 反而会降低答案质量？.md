# 什么情况下 RAG 反而会降低答案质量？

来源：https://www.nootcode.com/problems/when-rag-reduces-answer-quality

## 面试直接回答卡
Q: 面试中如何直接回答“什么情况下 RAG 反而会降低答案质量？”

A:
- RAG 会降低质量，通常不是因为“检索增强”这个思路错了，而是检索到的上下文比模型原本的知识更噪、更旧、更冲突，或者把模型注意力从问题本身带偏。
- 常见情况包括：chunk 切分破坏语义、top-k 太大引入噪声、向量检索召回相似但不相关内容、旧版本文档覆盖新版本、权限过滤后证据不完整、用户问题太短导致检索词不明确。
- 例如用户问“怎么配置退款重试”，检索系统召回了“支付重试”“退款失败码”“旧版退款流程”三类文档，模型可能把支付重试和退款重试混在一起，生成一个看似完整但实际错误的流程。
- RAG 还可能把 prompt injection 文本带进上下文，例如网页片段写“忽略之前所有规则”，如果系统没有把外部内容标成非可信数据，答案质量和安全性都会下降。
- 所以 RAG 质量取决于检索质量、证据排序、上下文压缩、权限和版本控制，以及模型是否被约束只基于证据回答。
- 工程上不能只看“有没有召回内容”，还要评估召回是否正确、证据是否足够、答案是否被证据支持。

## 失败类型卡
Q: RAG 降低答案质量的主要类型有哪些？

A:
- 错召回：召回了语义相似但业务对象不同的文档。
- 漏召回：关键证据没进上下文，模型根据残缺资料推断。
- 噪声过多：top-k 太大，模型被低相关片段干扰。
- 版本冲突：旧文档、新文档同时出现，模型没有版本优先级。
- 切分错误：chunk 缺少标题、表头、前置条件，单看片段会误解。
- 安全污染：外部文本里的注入指令或敏感信息被带入生成。

## 例子卡
Q: 举例说明“相似但不相关”的检索如何误导 RAG。

A:
- 用户问：“退款接口的幂等键应该怎么传？”
- 向量检索可能召回“支付接口幂等键”“订单创建幂等键”“退款接口错误码”。
- 这些片段都包含“接口、幂等、订单”等词，但只有退款接口文档真正回答问题。
- 如果 rerank 没有区分接口名和操作类型，模型可能把支付接口字段 `payment_idempotency_key` 误用到退款接口。
- 正确做法是保留接口路径、方法名、版本、字段表头等结构信息，并让 reranker 优先匹配具体 API。

## 机制卡
Q: 为什么 top-k 过大会让 RAG 变差？

A:
- LLM 在上下文里看到的是一堆 token，不会自动知道哪些片段最可信。
- 低相关片段越多，越容易引入相互冲突的前提、旧版本规则或相邻概念。
- 上下文窗口有限，噪声片段还会挤掉关键证据。
- 对长答案任务，模型可能为了综合所有片段而把不该合并的信息混在一起。
- 所以 top-k 不是越大越好，应结合 query 类型、chunk 长度、rerank 分数和证据覆盖来调。

## 工程实践卡
Q: 如何降低 RAG 反向拉低质量的风险？

A:
- 对文档做版本、权限、来源可信度和更新时间元数据管理。
- 使用 hybrid search 和 rerank，避免只靠向量相似度。
- 对 chunk 保留标题、章节路径、表头、代码路径等上下文。
- 检索结果按业务规则去重、去旧版、去低可信来源。
- 生成前做上下文压缩，只保留能回答问题的证据。
- 生成后做引用覆盖检查，答案里的关键结论必须能回指到证据。

## 评估卡
Q: 如何判断 RAG 是增强了还是降低了质量？

A:
- 做对照实验：同一批问题比较 no-RAG、RAG、RAG+rerank 的答案。
- 分开看 retrieval quality 和 answer quality，不要只看最终主观满意度。
- 对 retrieval 看 recall@k、precision@k、MRR、nDCG 和证据覆盖。
- 对 answer 看 groundedness、faithfulness、correctness、citation accuracy。
- 重点抽查失败样本，标注是错召回、漏召回、旧文档、生成漂移还是权限问题。

## 正确性审查卡
Q: 解释“RAG 可能降低质量”时有哪些误区？

A:
- 不要把问题都归因于模型，很多错误来自索引、切分、排序和权限。
- 不要认为召回越多越可靠，噪声和冲突会降低答案稳定性。
- 不要忽略短问题和模糊问题，query 不清晰时检索更容易跑偏。
- 不要让模型自己判断文档版本，版本优先级应在检索和排序层处理。
- 不要把外部文档内容当高优先级指令，RAG 片段只能作为证据数据。
