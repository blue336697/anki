# RAG 和 fine-tuning 分别解决什么问题？

来源：https://www.nootcode.com/problems/rag-vs-fine-tuning

## 面试直接回答卡
Q: 面试中如何直接回答“RAG 和 fine-tuning 分别解决什么问题？”

A:
- RAG 和 fine-tuning 解决的是两类不同问题。RAG 主要解决“答案应该基于哪些外部事实”，fine-tuning 主要解决“模型应该以什么能力、风格或格式完成任务”。
- RAG 不改模型权重，它的机制是先把文档清洗、切块、向量化并建立索引，请求时检索相关 chunk，经过 rerank 和权限过滤后放进上下文，让模型基于证据回答。
- Fine-tuning 会改变模型参数或适配参数，让模型更稳定地学会某类输出风格、任务格式、领域表达或操作习惯，适合有高质量标注样本、任务分布稳定的分类、抽取、格式遵循、语气统一场景。
- 如果问题是“2026 年报销规则是什么”，应该优先 RAG，因为规则会变且需要出处；如果问题是“把客服回复稳定写成公司要求的语气和 JSON 字段”，可以考虑 fine-tuning。
- 如果问题是“退款金额不能超过实付金额”“输出必须满足 JSON Schema”“用户没有权限不能查文档”，这些确定性规则不应该靠 RAG 或 fine-tuning 学出来，而应该由代码、schema、权限系统和校验流程强制执行。
- 两者也可以组合：RAG 提供事实证据，fine-tuning 提升模型使用证据、输出格式和领域表达的一致性。
- 面试里要强调：fine-tuning 不适合当作可更新知识库，RAG 也不能替代模型对任务模式和输出规范的学习。

## 对比卡
Q: RAG 和 fine-tuning 的关键区别是什么？

A:
- 知识位置不同：RAG 的知识在外部索引和文档库里，fine-tuning 的模式被写进模型参数或适配层。
- 更新时间不同：RAG 更新文档和索引即可，fine-tuning 需要重新训练、评估、发布。
- 可追溯性不同：RAG 可以给文档引用，fine-tuning 输出通常不能说明来自哪条训练样本。
- 权限控制不同：RAG 可以按用户权限过滤文档，fine-tuning 很难按请求动态隔离参数中的知识。
- 成本结构不同：RAG 有检索和长上下文成本，fine-tuning 有训练、评估和模型维护成本。

## RAG 机制卡
Q: RAG 的核心机制应该如何完整描述？

A:
- 离线阶段：接入文档，清洗噪声，解析 PDF/网页/表格/代码等格式。
- 切分阶段：按章节、段落、表格、代码符号等边界切成 chunk，并保留文档 ID、页码、标题、版本、权限标签。
- 索引阶段：为 chunk 生成 embedding，同时可以建立 BM25/关键词索引和 metadata 索引。
- 在线阶段：用户问题经过 query rewrite、权限过滤、向量/关键词/hybrid 检索、rerank，筛出证据。
- 生成阶段：把证据、引用 ID 和回答约束放进上下文，让模型基于证据回答。
- 风险是：错召回、漏召回、旧文档、权限过滤失败或 chunk 缺上下文，都会导致最终答案变差。

## 适用场景卡
Q: 哪些场景应该优先用 RAG？

A:
- 企业内部知识库问答，例如制度、流程、项目文档、工单记录。
- 高频更新事实，例如产品价格、政策版本、库存状态、API 文档。
- 需要引用来源的答案，例如法律、合规、金融、医疗辅助说明。
- 不同用户可见不同资料的多租户或权限敏感系统。
- 文档体量大、长尾问题多，不适合把所有事实塞进训练集。

## 适用场景卡
Q: 哪些场景更适合 fine-tuning？

A:
- 输出格式高度固定，例如稳定抽取字段、分类、打标签。
- 企业语气、客服话术、领域术语表达需要一致。
- 任务样本很多且分布稳定，例如把自然语言转成某种内部 DSL。
- 小模型需要学习大模型示范的处理模式，用微调降低推理成本。
- Prompt 很长且主要是行为规范而非事实知识时，可以把部分模式固化进模型。
- 前提是有高质量标注样本：输入、期望输出、边界样本、负例和评估集都要清楚，否则 fine-tuning 可能只是把错误模式固化进模型。

## 方案选择框架卡
Q: 面试中如何系统选择 RAG、fine-tuning 或确定性代码/schema？

A:
- 问题是“事实从哪里来”：优先 RAG，尤其是频繁更新、私有、需要引用和权限控制的知识。
- 问题是“模型如何稳定表达或执行某类语言任务”：考虑 fine-tuning，前提是样本高质量、任务分布稳定、收益超过训练维护成本。
- 问题是“业务规则必须百分百满足”：用代码、schema、权限系统、规则引擎或工作流，不要让模型自由判断。
- 例如“订单是否可退款”应由订单状态机和退款规则判断；模型可以解释原因，但不能自己决定放行。
- 例如“输出 JSON 字段必须合法”应由 JSON Schema 校验；fine-tuning 可以提高合规率，但最终仍要 deterministic validation。

## 组合使用卡
Q: RAG 和 fine-tuning 如何组合？

A:
- RAG 负责拿到当前证据，fine-tuned 模型负责更稳定地使用证据。
- 例如法律检索助手先检索法条、案例和合同条款，再由微调过的模型按“结论、依据、风险、建议”格式输出。
- 微调样本里可以训练模型“不知道就说不知道”“引用证据编号”“不要使用证据外事实”。
- 但训练样本不能替代实时检索，因为法规、合同、政策会更新。
- 组合方案也要评估两部分：retrieval 是否找对证据，generation 是否正确使用证据。

## 评估权衡卡
Q: RAG 和 fine-tuning 的评估重点有什么不同？

A:
- RAG 要分开评估 retrieval quality 和 answer quality。
- Retrieval quality 看 recall@k、precision@k、MRR、nDCG、证据覆盖、权限过滤是否正确。
- Answer quality 看 correctness、faithfulness、groundedness、citation accuracy、拒答是否合适。
- Fine-tuning 要看 held-out eval set 上的任务准确率、格式合规率、边界样本表现、分布外退化和人工偏好评分。
- 确定性规则要看单元测试、schema 校验、权限测试、审计日志和回归测试，不能用“模型大概会遵守”当验收标准。

## 边界卡
Q: 把事实塞进 fine-tuning 会有什么问题？

A:
- 更新慢：事实变更后需要重新训练和发布模型。
- 难删除：用户要求删除某条数据时，参数中是否仍记住很难验证。
- 难隔离：不同租户的私有知识混进同一个模型会有泄露风险。
- 难引用：模型无法可靠指出答案来自哪份文档哪一页。
- 容易过拟合：模型可能学到过期或错误样本，并在新问题上自信复述。

## 正确性审查卡
Q: 解释 RAG vs fine-tuning 时有哪些误区？

A:
- 不要说 RAG 比 fine-tuning 永远更好，它们解决的问题不同。
- 不要说 fine-tuning 可以可靠记忆所有业务事实，尤其是频繁更新和权限敏感事实。
- 不要说 RAG 不需要训练，embedding 模型、reranker 和生成模型仍可能需要领域适配。
- 不要漏掉 RAG 的基本流程，文档清洗、切块、向量化、索引、检索和 rerank 都会影响质量。
- 不要忽略 fine-tuning 对高质量标注样本和稳定任务分布的依赖。
- 不要把确定性业务规则交给模型学习，关键规则要用代码、schema、权限和校验兜底。
- 不要忽略评估，组合方案要分别评估检索质量和答案质量。
- 不要把 prompt engineering、RAG、fine-tuning 看成互斥，它们常常是分层配合。
