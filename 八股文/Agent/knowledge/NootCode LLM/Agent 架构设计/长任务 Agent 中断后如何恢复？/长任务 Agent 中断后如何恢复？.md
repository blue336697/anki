# 长任务 Agent 中断后如何恢复？

来源：https://www.nootcode.com/problems/long-task-agent-interruption-recovery

## 面试直接回答卡
Q: 面试中如何直接回答“长任务 Agent 中断后如何恢复？”

A:
- 长任务 Agent 的恢复本质是分布式任务恢复问题，不能只靠把聊天历史重新喂给模型。系统要持久化任务状态、计划、步骤进度、工具调用结果、外部副作用、产物和预算。
- 恢复时不能简单从头重跑，因为很多工具调用可能有副作用，例如发邮件、创建工单、扣款、提交配置。必须通过幂等键、步骤状态和外部系统查询判断哪些步骤已完成。
- 通常做法是把任务拆成可检查点的 step，每个 step 有状态：pending、running、succeeded、failed、needs_human、skipped。中断后从最后一个安全检查点恢复。
- 恢复前要重新验证外部世界状态，因为中断期间订单、权限、文档、文件和用户需求可能已经变化。
- 例如 Agent 中断前已创建退款工单但没返回最终答案，恢复时应先查工单是否存在，而不是再创建一次。
- 工程上要有状态机、持久化存储、幂等、锁、超时、重试、人工确认和审计日志，模型只负责解释状态和决定下一步，不负责单独保证一致性。

## 状态模型卡
Q: 长任务 Agent 需要持久化哪些状态？

A:
- 用户目标和约束，例如语言、输出格式、截止时间。
- 当前计划、步骤列表、依赖关系和验收标准。
- 每步状态：pending、running、succeeded、failed、blocked、needs_human。
- 工具调用记录：工具名、参数、幂等键、结果、错误和时间戳。
- 产物：文件、报告、工单、代码 diff、引用证据。
- 预算：token、时间、费用、重试次数、最大步骤数。

## 恢复流程卡
Q: Agent 中断后恢复通常怎么做？

A:
- 加载任务状态和最近检查点。
- 检查是否有 running 状态的步骤，并查询外部系统确认结果。
- 对有副作用的动作根据幂等键判断是否已执行。
- 重新校验权限、输入文件、索引版本和用户目标是否仍有效。
- 从 pending 或 failed-but-retryable 的步骤继续。
- 如果状态不一致或风险高，转人工确认，而不是自动继续。

## 幂等卡
Q: 为什么幂等对长任务 Agent 很关键？

A:
- Agent 可能因为网络、进程重启、工具超时而不知道某个动作是否成功。
- 如果没有幂等键，重试可能导致重复发邮件、重复创建工单、重复扣款。
- 幂等键把“同一个意图的同一次动作”绑定到唯一请求。
- 恢复时先查外部系统是否已有该幂等键对应结果。
- 对写操作，幂等和审计比模型判断更可靠。

## 例子卡
Q: 举例说明 Agent 中断恢复的正确处理。

A:
- 任务：生成采购审批材料并提交审批。
- 已完成：收集报价、生成 PDF、创建审批草稿。
- 中断点：提交审批时工具超时。
- 恢复时先查审批系统：如果审批单已存在，则记录 succeeded 并继续通知用户。
- 如果不存在且幂等键未使用，再重试提交。
- 如果状态不明确，应请求人工确认，避免重复提交。

## 边界卡
Q: 哪些中断场景不能自动恢复？

A:
- 外部系统状态无法确认，重复执行会造成损失。
- 用户权限已变化，原来允许的动作现在不允许。
- 输入文件或文档版本已更新，继续旧计划会产生错误。
- 用户目标在中断期间被修改，旧计划不再适用。
- 预算耗尽或连续失败超过阈值，需要人工决策。

## 正确性审查卡
Q: 解释长任务恢复时有哪些误区？

A:
- 不要只保存聊天记录，聊天记录不能表示步骤状态和外部副作用。
- 不要从头重跑长任务，有副作用步骤可能重复执行。
- 不要让模型记忆承担一致性，状态机和存储才是来源。
- 不要忽略外部状态复核，中断期间世界可能变了。
- 不要自动恢复所有任务，高风险或状态不明时应人工确认。
