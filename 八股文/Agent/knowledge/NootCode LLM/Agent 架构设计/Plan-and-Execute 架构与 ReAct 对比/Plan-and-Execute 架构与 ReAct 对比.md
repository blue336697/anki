# Plan-and-Execute 架构与 ReAct 对比

来源：https://www.nootcode.com/problems/plan-and-execute-vs-react

## 面试直接回答卡
Q: 面试中如何直接回答“Plan-and-Execute 架构与 ReAct 有什么区别？”

A:
- ReAct 是边想边做，每一步根据当前观察决定下一步；Plan-and-Execute 是先生成一个相对完整的计划，再由执行器按步骤执行，必要时监控和重规划。
- ReAct 适合信息不完整、需要边查边判断的任务，例如排查一个线上问题；Plan-and-Execute 适合目标明确、可以拆解为多个子任务的长任务，例如生成调研报告、迁移项目、跑一组数据分析。
- Plan-and-Execute 的好处是全局结构更清楚，便于进度管理、并行子任务、检查遗漏；缺点是初始计划可能基于不完整信息，执行中容易过时。
- ReAct 的好处是灵活，能快速利用最新 observation；缺点是容易短视、重复调用工具、缺少全局路线。
- 实践里常组合使用：先 plan，再每个步骤内部用 ReAct 执行，遇到失败或新信息再 replan。
- 无论哪种架构，真正可靠性来自状态持久化、工具权限、预算、检查点、失败处理和人工确认，而不是模型把计划写得漂亮。

## ReAct 卡
Q: ReAct 更适合什么任务？

A:
- 需要边探索边决策的任务。
- 工具观察结果会显著改变下一步，例如排查、搜索、调查、调试。
- 问题一开始信息不足，需要通过工具逐步收集证据。
- 任务较短或步骤数不多，过度规划收益不大。
- 例如“为什么这个订单退款失败”“这个接口为什么超时”。

## Plan-and-Execute 卡
Q: Plan-and-Execute 更适合什么任务？

A:
- 目标较清晰，可以拆成多个阶段或子任务。
- 需要进度展示、检查清单、并行执行或多人协作。
- 任务时间较长，中间可能中断和恢复。
- 需要先评估风险、成本和依赖关系。
- 例如“为某系统设计迁移方案并产出清单”“整理一个领域调研报告”。

## 架构机制卡
Q: Plan-and-Execute 通常有哪些组件？

A:
- Planner：把目标拆成步骤、依赖、验收标准和风险点。
- Executor：执行单个步骤，可以是工具调用、ReAct 子循环或固定工作流。
- State Store：记录计划、步骤状态、工具结果、产物和错误。
- Monitor：判断进度、失败、超时、预算和是否需要重规划。
- Replanner：当环境变化、工具失败或证据冲突时更新计划。

## 例子卡
Q: 用一个例子说明两者差异。

A:
- 任务：“分析一个支付系统最近的失败率上升原因并给出报告。”
- ReAct 可能直接开始查监控、查日志、查发布记录，边看结果边决定下一步。
- Plan-and-Execute 会先列计划：指标确认、按渠道分组、查发布、查依赖、查风控、汇总报告。
- 如果中途发现失败集中在某支付渠道，执行器可以局部用 ReAct 深挖。
- 最终报告再按计划中的验收标准检查是否覆盖所有渠道和时间段。

## 边界卡
Q: Plan-and-Execute 有哪些风险？

A:
- 初始计划可能建立在错误假设上，后续执行越认真越偏。
- 计划过细会消耗 token 和时间，低价值任务不划算。
- 执行器可能机械执行过时步骤，不根据 observation 调整。
- 计划和实际状态不同步，恢复时可能重复执行或漏执行。
- 需要明确 replan 条件，否则系统会在错误计划上继续推进。

## 正确性审查卡
Q: 对比 Plan-and-Execute 和 ReAct 时有哪些误区？

A:
- 不要说 Plan-and-Execute 一定更高级，它只是更适合长任务和结构化任务。
- 不要说 ReAct 没有计划，ReAct 也可能有局部计划，只是计划和行动交错。
- 不要忽略混合架构，生产系统常用 planner + ReAct executor。
- 不要把计划当确定性保证，计划仍需要监控、重规划和验收。
- 不要让模型计划高风险动作后自动执行，危险步骤要人工确认。
