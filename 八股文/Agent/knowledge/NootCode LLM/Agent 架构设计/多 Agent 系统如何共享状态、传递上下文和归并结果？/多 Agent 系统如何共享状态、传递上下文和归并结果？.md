# 多 Agent 系统如何共享状态、传递上下文和归并结果？

来源：https://www.nootcode.com/problems/multi-agent-state-context-result-merging

## 面试直接回答卡
Q: 面试中如何直接回答“多 Agent 系统如何共享状态、传递上下文和归并结果？”

A:
- 多 Agent 系统不能简单把所有历史消息广播给所有 Agent。正确做法是区分全局任务状态、各 Agent 私有状态、可共享产物和最小必要上下文。
- 状态共享要有明确 owner。全局状态记录目标、计划、子任务、权限、产物、决策和审计；子 Agent 只拿自己完成任务所需的上下文，并返回结构化结果。
- 上下文传递要做裁剪、脱敏、版本标记和来源标注，避免泄露、污染和上下文爆炸。
- 结果归并要有规则：按证据质量、版本、权限、置信度、负责人优先级或人工确认处理冲突，不能简单让最后一个 Agent 覆盖前一个。
- 例如调研任务中，Research Agent 给证据，Analysis Agent 给结论，Review Agent 给风险，Orchestrator 最终合并时要保留引用和冲突说明。
- 工程上需要 task graph、shared store、message schema、artifact store、conflict policy、审计日志和评估集，模型只参与判断和总结，不应单独承担一致性。

## 状态分类卡
Q: 多 Agent 系统里状态可以分成哪些类型？

A:
- Global state：任务目标、计划、子任务状态、预算、权限和最终产物。
- Agent private state：某个 Agent 的局部推理、中间缓存、工具结果。
- Shared artifacts：报告、代码 diff、数据表、引用证据、文件。
- Message log：Agent 之间交换的请求、回复、状态更新。
- Decision log：关键取舍、人工确认、冲突处理和拒绝原因。

## 上下文传递卡
Q: 多 Agent 之间传递上下文要注意什么？

A:
- 只传递子任务所需的最小上下文，不广播全部历史。
- 传递时标注来源、时间、版本、权限和可信级别。
- 对隐私和跨租户数据做脱敏和 ACL 过滤。
- 对长上下文做摘要，但摘要要保留引用和不确定性。
- 避免把一个 Agent 的建议伪装成系统指令传给另一个 Agent。

## 结果归并卡
Q: 多 Agent 结果如何归并？

A:
- 先检查每个结果是否符合 schema 和任务验收标准。
- 对事实结论要求证据和来源，不接受无依据断言。
- 对冲突结果按来源可信度、时间版本、权限范围和专业角色处理。
- 对无法自动消解的冲突，展示差异并请求人工确认。
- 最终输出要有 owner，不能让多个 Agent 的口径并列失控。

## 冲突处理卡
Q: 多 Agent 输出冲突时应该怎么处理？

A:
- 事实冲突：看证据来源、时间、版本和可验证性。
- 规则冲突：以系统/开发者策略和业务规则为准。
- 权限冲突：以服务端 ACL 和工具结果为准。
- 方案冲突：让 reviewer 或用户基于成本、风险、收益取舍。
- 格式冲突：由 orchestrator 按下游 schema 统一。

## 例子卡
Q: 举例说明多 Agent 状态和结果归并。

A:
- 任务：生成上线风险评估。
- Code Agent 分析代码 diff，返回受影响模块和测试建议。
- Ops Agent 查监控和容量，返回资源风险。
- Security Agent 检查权限和敏感接口。
- Orchestrator 把三方结果按 schema 合并，标注证据、冲突和缺口。
- 如果 Security Agent 认为不能上线，最终输出必须突出阻断风险，而不是被其他乐观结论覆盖。

## 正确性审查卡
Q: 解释多 Agent 状态共享和归并时有哪些误区？

A:
- 不要把所有上下文广播给所有 Agent，安全和成本都会失控。
- 不要把摘要当事实来源，摘要必须能回溯到原始证据。
- 不要让最后返回的 Agent 覆盖其他结果，归并要有规则。
- 不要忽略权限和租户隔离，Agent 间通信也要做访问控制。
- 不要让模型单独保证一致性，状态存储、schema 和审计是必要基础设施。
