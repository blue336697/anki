# 多 Agent 协作适合什么场景？什么时候单 Agent 更好？

来源：https://www.nootcode.com/problems/multi-agent-collaboration-vs-single-agent

## 面试直接回答卡
Q: 面试中如何直接回答“多 Agent 协作适合什么场景？什么时候单 Agent 更好？”

A:
- 多 Agent 协作适合任务可以自然拆分、角色边界清楚、工具权限不同、可以并行推进或需要独立评审的场景。单 Agent 更适合目标简单、上下文强共享、低延迟、低成本和责任边界清晰的场景。
- 多 Agent 的价值不是“Agent 越多越聪明”，而是把复杂任务拆成多个有清晰职责的执行单元，例如 researcher 负责找资料，coder 负责改代码，reviewer 负责审查。
- 它适合跨领域任务、长任务、并行搜索、专家评审、生成-验证分离、权限隔离等场景。
- 但多 Agent 会带来协调成本、上下文丢失、重复工作、结果冲突、调试困难和成本上升。
- 如果一个 Agent 能在共享上下文内完成任务，就不要为了架构显得复杂而拆多个 Agent。
- 工程上选择单 Agent 还是多 Agent，要看任务拆分收益是否超过协调成本，并且要有状态共享、消息协议、结果归并、权限和审计设计。

## 适合多 Agent 卡
Q: 哪些场景适合多 Agent？

A:
- 任务天然分工明确，例如调研、实现、测试、审查。
- 需要并行处理多个子问题，例如多个数据源检索或多个候选方案评估。
- 需要不同权限边界，例如财务 Agent 不能暴露 HR 数据。
- 需要独立验证，例如一个 Agent 生成方案，另一个 Agent 做事实检查。
- 任务很长，需要阶段化产物和角色责任。

## 单 Agent 更好卡
Q: 什么时候单 Agent 更好？

A:
- 任务简单，一轮或少数几轮工具调用即可完成。
- 上下文必须高度一致，拆分会丢失细节。
- 成本和延迟敏感，多 Agent 通信开销不划算。
- 责任归属要清楚，不希望多个 Agent 相互推诿。
- 没有稳定的子任务边界，拆分后反而更混乱。

## 协作模式卡
Q: 多 Agent 常见协作模式有哪些？

A:
- Manager-worker：一个调度者分配任务，多个 worker 执行。
- Debate/critique：多个 Agent 给方案或审查意见，再归并。
- Pipeline：前一个 Agent 的产物作为后一个 Agent 的输入。
- Blackboard：多个 Agent 读写共享状态或任务板。
- Specialist routing：根据任务类型路由到专业 Agent。

## 例子卡
Q: 举例说明多 Agent 比单 Agent 更合适的情况。

A:
- 任务：“为一个支付系统设计压测和扩容方案。”
- Research Agent 收集历史流量、峰值、瓶颈和事故记录。
- Infra Agent 分析机器、数据库、缓存和限流策略。
- Cost Agent 估算资源成本。
- Reviewer Agent 检查方案是否遗漏风险和回滚。
- 最后由 Orchestrator 归并成一个一致方案，并标注冲突和假设。

## 风险卡
Q: 多 Agent 协作有哪些常见风险？

A:
- 协调开销大，通信成本超过任务收益。
- 子 Agent 目标不一致，产物格式和假设不同。
- 上下文传递不完整，后续 Agent 基于残缺信息决策。
- 多个结果互相冲突，没有明确归并规则。
- 权限边界不清，低权限 Agent 可能接触高权限上下文。

## 正确性审查卡
Q: 解释多 Agent 取舍时有哪些误区？

A:
- 不要说多 Agent 一定更强，很多任务单 Agent 更稳。
- 不要把角色拆分当可靠性保证，仍需评估和验收。
- 不要让多个 Agent 共享所有上下文，最小必要上下文更安全。
- 不要忽略归并责任，最终输出要有明确 owner。
- 不要忽略成本，多 Agent 会增加 token、工具调用和调试复杂度。
