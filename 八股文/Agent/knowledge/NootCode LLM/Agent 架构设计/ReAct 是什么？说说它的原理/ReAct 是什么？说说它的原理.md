# ReAct 是什么？说说它的原理

来源：https://www.nootcode.com/problems/react-reasoning-and-acting

## 面试直接回答卡
Q: 面试中如何直接回答“ReAct 是什么？说说它的原理？”

A:
- ReAct 是 Reasoning + Acting 的 Agent 思路，核心是让模型在推理和行动之间交替进行：先根据目标判断下一步，再调用工具，拿到观察结果后继续判断。
- 典型循环可以写成 Thought/Action/Observation：模型思考需要什么信息，选择一个 action 调工具，工具返回 observation，再进入下一轮。
- 例如问“某个 API 最近为什么变慢”，Agent 先判断要查监控，调用监控工具；发现只在某版本后变慢，再查发布记录；最后结合证据给出结论。
- ReAct 的价值是把模型的语言推理和外部世界的事实观察连接起来，减少纯靠模型记忆或猜测。
- 但现代工程里不一定暴露完整 chain-of-thought，通常会把内部推理隐藏，只记录结构化决策、工具调用和观察结果。
- 生产 ReAct 还必须加工具白名单、参数 schema、最大步数、重复调用检测、错误恢复和人工确认，否则很容易循环、误调用或越权。

## 机制卡
Q: ReAct 的执行循环是什么？

A:
- 输入目标和当前状态。
- 模型判断下一步需要知道什么或做什么。
- 选择工具并生成结构化参数。
- 工具执行并返回观察结果。
- Agent 把观察写入状态，判断是否完成、继续、重试、澄清或失败。
- 循环直到满足停止条件或触发预算/安全限制。

## 例子卡
Q: 用一个例子说明 ReAct 的 Thought/Action/Observation。

A:
- 目标：排查订单退款失败。
- Thought：需要先知道订单状态和退款错误码。
- Action：调用 `get_order(order_id)` 和 `get_refund_logs(order_id)`。
- Observation：订单已支付，退款日志返回 `RISK_REVIEW_REQUIRED`。
- Thought：失败原因可能是风控审核，需要查审核状态。
- Action：调用风控查询工具。
- 最终：基于工具结果回答“退款失败是因为风控审核未通过”，并给出可执行下一步。

## 工程实现卡
Q: ReAct 在工程里通常如何落地？

A:
- 不让模型输出自由文本工具名，而是使用 tool schema 或函数调用结构。
- 工具参数要做类型、枚举、权限、单位和必填校验。
- 每一步记录 action、参数、observation、耗时、错误和 token 成本。
- 对相同工具相同参数的重复调用做缓存或去重。
- 对写操作、外部发送、扣款、删除等动作加人工确认和幂等键。

## 边界卡
Q: ReAct 的局限性是什么？

A:
- 容易局部贪心，每一步都看起来合理，但整体计划不优。
- 工具多时选择空间变大，模型可能误选工具或构造错误参数。
- 如果 observation 噪声大或含 prompt injection，下一步决策会被污染。
- 长任务容易循环、重复查同一信息或忘记早期目标。
- 对强流程任务，固定工作流或 Plan-and-Execute 可能更稳定。

## 对比追问卡
Q: ReAct 和普通 function calling 有什么区别？

A:
- Function calling 是模型输出结构化工具调用的一种接口能力。
- ReAct 是一种组织多步推理和工具调用的 Agent 架构模式。
- 一次 function call 可以是 ReAct 循环中的一个 Action。
- ReAct 还包含状态更新、观察解释、继续/停止判断和多步控制。
- 所以不能把“能调函数”直接等同于“有 ReAct Agent”。

## 正确性审查卡
Q: 解释 ReAct 时有哪些误区？

A:
- 不要把 ReAct 说成必须展示完整思维链，生产系统通常隐藏内部推理。
- 不要把工具返回结果当成绝对可信指令，外部文本仍可能是低信任数据。
- 不要只讲 Thought/Action/Observation 格式，要讲停止条件和安全控制。
- 不要认为 ReAct 天然减少幻觉，错工具、错观察和错总结仍会导致错误。
- 不要让模型直接执行高风险动作，执行层要权限、审批和审计。
