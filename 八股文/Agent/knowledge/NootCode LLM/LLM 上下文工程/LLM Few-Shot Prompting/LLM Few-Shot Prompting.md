# LLM Few-Shot Prompting

来源：https://www.nootcode.com/problems/llm-few-shot-prompting

## 面试直接回答卡
Q: 面试中如何直接回答“Few-Shot Prompting 是什么，什么时候有用？”

A:
- Few-shot prompting 是在 prompt 中给模型几个输入输出示例，让模型从示例中学习当前任务的格式、判断标准、边界和风格。它不是训练模型参数，而是在上下文里临时给模型一个“参照分布”。
- 它特别适合标准难以用一句规则说清，但可以通过例子体现的任务，比如文本分类口径、客服话术风格、信息抽取格式、风险标签判定、SQL 生成样式。
- 好的 few-shot 示例要覆盖典型正例、反例、边界例和容易混淆的例子。只给一个理想正例，模型可能学到表面格式，却学不到判断边界。
- Few-shot 的代价是占用上下文窗口、增加 token 成本，也可能把示例里的偏见、错误字段或过时规则带入输出。
- 工程上要把示例当成可维护资产：有版本、有评测、有失败样本回流，而不是随手在 prompt 里贴几段样例。

## 概念卡
Q: Few-shot prompting 和 zero-shot prompting 有什么区别？

A:
- Zero-shot 只给任务说明，不给示例。
- Few-shot 给出若干输入输出样例，让模型模仿映射关系。
- Few-shot 不更新模型权重，只改变本次上下文。
- 示例能同时传递格式、风格、标签边界和隐含判断口径。
- 代价是占用上下文窗口，示例越多，留给真实输入和输出的空间越少。

## 示例选择卡
Q: Few-shot 示例应该如何选择？

A:
- 覆盖高频典型场景，让模型学会主路径。
- 覆盖边界场景，例如“看起来像投诉但其实是咨询”。
- 覆盖反例，告诉模型什么不应该归为某类。
- 示例格式要和期望输出完全一致，避免模型学到错误结构。
- 示例数量不一定越多越好，关键是代表性和区分度。

## 具体例子卡
Q: 用客服意图分类举例说明 few-shot 的价值。

A:
- 任务是把用户消息分类为 `refund`、`logistics`、`complaint`。
- 如果只写规则“退款相关归 refund”，用户说“别退款，我只是想查物流”，模型可能误判 refund。
- Few-shot 可以给反例：输入“不要退款，只查物流”，输出 `logistics`，理由是用户明确否定退款意图。
- 再给边界例：输入“物流太慢我要投诉”，输出 `complaint`，不是单纯 logistics。
- 这些例子能把标签边界具体化，比抽象规则更容易被模型模仿。

## 可追问原理卡
Q: Few-shot 为什么能改变模型输出？

A:
- 模型生成时会把示例和当前输入一起放进 context window。
- 示例形成一种局部模式：相似输入应该映射到相似输出结构。
- 模型不是记住规则执行，而是在当前上下文中进行模式补全。
- 示例越接近真实输入分布，模型越容易复用正确模式。
- 如果示例和真实任务分布差异很大，模型反而会模仿错误口径。

## 边界卡
Q: Few-shot prompting 有哪些坑？

A:
- 示例占 token，可能挤掉真实上下文或输出空间。
- 示例质量差会污染输出，模型会认真模仿坏例子。
- 示例过拟合某种格式，输入稍变就不稳定。
- 示例里有敏感数据会扩大泄露风险。
- 示例更新不及时，会让模型沿用过期规则。

## 工程实践卡
Q: Few-shot 示例如何工程化维护？

A:
- 把示例放进版本化 prompt 模板或配置中心，不要散落在代码里。
- 从真实失败样本中挑选边界例，定期更新。
- 用评测集比较 zero-shot、few-shot 和规则/模型组合的效果。
- 给示例加注释只供开发者维护，真正给模型的内容保持简洁一致。
- 对结构化输出仍要做 schema 校验，不能只靠示例保证格式。

## 正确性审查卡
Q: 解释 few-shot 时有哪些常见误区？

A:
- 不要说 few-shot 是微调，它不会更新模型权重。
- 不要说示例越多越好，示例太多会增加成本和噪声。
- 不要只给正例，缺少反例会导致边界模糊。
- 不要把示例当作安全边界，权限和执行仍要靠系统控制。
- 不要在示例中放真实隐私数据，应脱敏或合成。
