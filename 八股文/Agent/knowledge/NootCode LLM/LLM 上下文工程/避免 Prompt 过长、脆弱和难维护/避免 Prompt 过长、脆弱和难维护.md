# 避免 Prompt 过长、脆弱和难维护

来源：https://www.nootcode.com/problems/avoid-overlong-fragile-prompts

## 面试直接回答卡
Q: 面试中如何直接回答“如何避免 Prompt 过长、脆弱和难维护？”

A:
- Prompt 过长、脆弱和难维护的根因，通常是把太多业务规则、安全策略、格式约束、示例、工具说明和临时补丁都堆进一段自然语言里。短期能跑，长期会变成不可测试的“魔法文案”。
- 要避免这个问题，首先要拆分职责：系统安全边界放 system，产品行为放 developer，业务规则配置化，输出格式用 schema，工具能力用结构化声明，few-shot 示例单独版本化。
- 其次要减少自然语言承担强约束。比如“必须输出合法 JSON”不能只靠 prompt，要用 JSON schema 和 parser 校验；“不能越权查询”不能靠模型自觉，要靠后端权限系统。
- 还要建立 prompt 评测和回滚机制。每次改 prompt 都应该跑高频样本、边界样本、恶意样本和格式样本，观察质量、成本、延迟和工具调用变化。
- 面试总结：好的 prompt 不是越长越完整，而是边界清楚、结构化、可测试、可版本化，并且把硬约束下沉到系统。

## 脆弱原因卡
Q: Prompt 为什么会变得脆弱？

A:
- 规则互相冲突，例如“详细解释”和“只输出 JSON”同时存在。
- 新增补丁规则越来越多，没有统一结构。
- few-shot 示例过时或覆盖不足。
- 外部上下文太长，关键规则被稀释或截断。
- 强约束只靠自然语言，没有 schema 和程序校验。

## 重构方法卡
Q: 如何重构一个过长 prompt？

A:
- 拆层：安全、任务、工具、格式、示例分开维护。
- 删噪声：删除重复、口号式、无可验证效果的句子。
- 配置化：业务枚举、阈值、政策版本不要硬编码在 prompt 中。
- 结构化：输出格式用 JSON schema 或函数调用定义。
- 测试化：用评测集验证重构前后行为是否退化。

## 具体例子卡
Q: 一个脆弱 prompt 可能长什么样？

A:
- “你是专家，请严格输出 JSON，不要解释，但要详细说明原因，并且如果用户问退款就按政策回答，除非特殊情况...”
- 这段里“不要解释”和“详细说明原因”冲突。
- “特殊情况”没有定义，模型会自由解释。
- “按政策回答”没有提供政策版本和来源。
- 更好的做法是把原因放入 `reasons` 字段，把特殊情况定义为枚举，把政策从知识库检索并附来源。

## 可追问原理卡
Q: 为什么 prompt 越长不一定越可靠？

A:
- 长 prompt 会消耗上下文窗口，挤压用户输入、RAG 证据和输出空间。
- 重复或冲突规则会让模型难以判断优先级。
- 规则越多，越难靠人工 review 判断是否有回归。
- 模型对长上下文的利用不是完美的，关键规则可能被噪声稀释。
- 长 prompt 还会增加输入 token 成本和首 token 延迟。

## 工程实践卡
Q: 如何让 prompt 可维护？

A:
- Prompt 版本化，记录变更原因和影响范围。
- 建评测集，覆盖格式、工具、安全、业务边界。
- Prompt 模板模块化，不同模块单独维护。
- 使用 schema、权限、规则系统承接硬约束。
- 灰度发布，保留快速回滚能力。

## 正确性审查卡
Q: 避免长脆弱 prompt 时有哪些误区？

A:
- 不要把所有约束都塞进自然语言 prompt。
- 不要用“严格遵守”替代程序校验。
- 不要为了修一个失败样本随手加一句补丁，先分析是否影响其他样本。
- 不要忽略 prompt token 成本和延迟。
- 不要把外部文档里的规则当成高优先级指令。
