# LLM 提示词的维护

来源：https://www.nootcode.com/problems/llm-prompt-maintainability

## 面试直接回答卡
Q: 面试中如何直接回答“LLM 提示词为什么需要维护，怎么维护？”

A:
- 提示词在生产系统里不是一次性文案，而是会影响模型行为的业务逻辑资产。它会规定任务目标、输出格式、工具策略、安全边界、示例和失败处理方式。
- 如果提示词没有版本、评测和变更流程，后续改一句话就可能导致输出格式漂移、工具调用变化、成本上升或安全策略失效。
- 维护提示词要像维护代码一样：模块化拆分系统规则、业务规则、输出 schema、few-shot 示例；每次修改要有评测集、灰度、回滚和变更记录。
- 还要把容易变化的内容配置化，例如政策版本、字段枚举、工具说明；把强约束下沉到 schema、权限和程序校验，不要全塞进自然语言。
- 面试里可以总结：提示词维护的目标是让模型行为可理解、可测试、可回滚，而不是靠一段越来越长的 prompt 硬撑。

## 维护对象卡
Q: 一个生产 prompt 里通常有哪些需要维护的部分？

A:
- 角色和任务目标：模型应该扮演什么系统角色，解决什么问题。
- 安全和拒答策略：哪些内容不能做，冲突时如何处理。
- 输出格式：JSON schema、字段含义、枚举值、单位。
- 工具说明：什么时候调用工具、参数含义、错误处理。
- Few-shot 示例：典型例子、边界例、反例。
- 业务规则：政策口径、SOP、风控阈值、版本说明。

## 变更风险卡
Q: 修改 prompt 可能引入哪些回归？

A:
- 格式回归：原本稳定 JSON 变成自然语言解释。
- 行为回归：原本先检索再回答，变成直接凭记忆回答。
- 安全回归：拒答边界变松，开始回答敏感内容。
- 成本回归：prompt 变长或工具调用增多，token 和延迟上升。
- 质量回归：新规则改善一类问题，却破坏另一类边界样本。

## 可追问原理卡
Q: 为什么 prompt 维护不能只靠人工阅读？

A:
- LLM 行为是概率性的，同一句修改可能影响多个下游行为。
- Prompt 中的规则有相互作用，例如新增“详细解释”可能破坏“只输出 JSON”。
- Few-shot 示例会改变模型局部分布，新增一个坏例子可能污染整类输出。
- 长 prompt 中位置、措辞、重复规则都会影响模型注意和遵循。
- 所以维护必须配合自动评测、日志回放和灰度，而不是只靠 reviewer 觉得合理。

## 工程实践卡
Q: 如何工程化维护 prompt？

A:
- Prompt 模板版本化，记录变更原因、作者、影响范围。
- 建评测集，覆盖高频、边界、恶意输入、格式输出和工具调用。
- 把输出 schema 放到代码或配置里，模型输出后强校验。
- 灰度发布 prompt 版本，对比质量、成本、延迟、失败率。
- 保留回滚能力，线上异常时能快速切回上一版。

## 具体例子卡
Q: 一个提示词维护事故可能怎么发生？

A:
- 原 prompt 要求“只输出 JSON”，下游 parser 依赖这个格式。
- 业务方新增一句“请详细解释原因，让用户看得懂”。
- 模型开始在 JSON 前输出“下面是分析”，parser 解析失败。
- 更好的做法是把解释放进 schema 字段 `reasons`，并让 parser 校验。
- 这个例子说明：prompt 变更要考虑下游契约，不只是语言表达。

## 正确性审查卡
Q: 解释提示词维护时有哪些误区？

A:
- 不要把 prompt 当普通文案，它是影响系统行为的逻辑资产。
- 不要用越来越长的自然语言规则替代 schema 和程序校验。
- 不要没有评测就上线 prompt 修改。
- 不要把 few-shot 示例硬编码成无人维护的历史包袱。
- 不要忽略 prompt 成本，长提示会增加输入 token、延迟和维护复杂度。
