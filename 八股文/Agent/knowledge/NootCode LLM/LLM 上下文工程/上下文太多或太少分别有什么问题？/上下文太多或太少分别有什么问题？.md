# 上下文太多或太少分别有什么问题？

来源：https://www.nootcode.com/problems/too-much-or-too-little-context

## 面试直接回答卡
Q: 面试中如何直接回答“上下文太多或太少分别有什么问题？”

A:
- 上下文太少的问题是模型缺少事实依据和任务约束，只能靠训练分布猜答案，容易幻觉、答非所问、漏掉用户偏好或业务规则。比如没有给订单状态，却让模型判断能否退款，它很可能给出看似合理但不可执行的建议。
- 上下文太多的问题是成本、延迟、噪声和安全风险都会上升。模型看到更多 token，不代表会更好地使用它们；无关文档、重复历史、过期规则可能干扰模型，让它引用错材料或忽略真正关键的证据。
- 本地推理还要考虑 KV cache，长上下文会让每个历史 token 的 K/V 缓存占用显存，显存和带宽压力随上下文长度增长。
- 所以好的上下文工程不是“尽量多塞”，也不是“尽量省”，而是给模型刚好足够、可信、相关、结构清晰、权限正确的上下文。
- 工程上通常用 RAG 召回、状态摘要、上下文裁剪、去重、重排、权限过滤和引用机制来控制上下文质量。

## 上下文太少卡
Q: 上下文太少会导致哪些问题？

A:
- 缺事实：模型不知道真实订单、配置、日志、文档内容。
- 缺约束：模型不知道输出格式、业务规则、安全边界。
- 缺历史：模型忘记用户前面的修正和偏好。
- 缺证据：答案无法引用来源，难以验证。
- 缺状态：多步任务不知道哪些已经完成，容易重复或漏做。

## 上下文太多卡
Q: 上下文太多会导致哪些问题？

A:
- 成本更高：输入 token 增加，API 调用费用上升。
- 延迟更高：prefill 更重，首 token 更慢。
- 噪声更大：无关材料会干扰模型判断。
- 截断风险：关键内容可能被挤出窗口。
- 安全风险：更多历史和文档可能暴露敏感信息。
- 本地显存压力：KV cache 随上下文 token 增长。

## 具体例子卡
Q: 上下文太多为什么可能降低 RAG 问答质量？

A:
- 用户问“退款失败原因”，系统召回 20 段文档，其中只有 2 段和退款网关相关。
- 其余文档包含物流、会员、优惠券、客服话术。
- 模型可能引用客服话术里的“请等待 3 个工作日”，而忽略网关错误码。
- 如果上下文超过窗口，真正关键的错误码片段还可能被裁掉。
- 更好的做法是 rerank、去重，只保留最相关且有来源的少量片段。

## 可追问原理卡
Q: 为什么“更多上下文”不等于“更多理解”？

A:
- 模型看到的上下文是 token 序列，注意力资源和位置利用并非无限完美。
- 无关 token 会稀释任务信号，增加模型选择错误证据的机会。
- 长上下文会增加 prefill 计算和 KV cache。
- 多个相互矛盾的材料会让模型混合答案。
- 所以核心不是上下文数量，而是相关性、可信度、结构和优先级。

## 工程实践卡
Q: 如何控制上下文刚好够用？

A:
- 对知识问答用检索和 rerank 控制相关性。
- 对长对话用状态摘要保留目标、约束、已完成动作。
- 对文档片段去重，避免重复内容占窗口。
- 对敏感内容做权限过滤，再进入 prompt。
- 对答案要求引用证据，便于发现上下文不足或错误。

## 正确性审查卡
Q: 解释上下文多少时有哪些误区？

A:
- 不要说窗口越大效果越好，长上下文会带来噪声、成本和显存压力。
- 不要为了省 token 砍掉关键规则、来源和用户修正。
- 不要把历史全保留，长对话应抽取状态。
- 不要忽略权限过滤，上下文越多越容易越权暴露。
- 不要只看 token 数，还要看内容质量和任务相关性。
