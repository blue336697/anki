# 长对话超过 Context Window 时怎么办

来源：https://www.nootcode.com/problems/long-conversation-exceeds-context-window

## 面试直接回答卡
Q: 面试中如何直接回答“长对话超过 Context Window 时怎么办？”

A:
- 长对话超过 context window 时，不能简单把最早消息粗暴截掉，因为被截掉的可能是用户目标、关键约束、权限确认或之前的工具结果。正确做法是把对话管理成“短期上下文 + 长期状态 + 可检索记忆”。
- 短期上下文保留最近几轮交互和当前任务相关材料；长期状态保存稳定信息，比如用户目标、偏好、已完成步骤、待确认事项；可检索记忆保存历史事实和文档，按需 RAG 召回。
- 对多步任务，还要维护结构化 task state，例如 `goal`、`constraints`、`completed_steps`、`open_questions`、`tool_results`，而不是只保存自然语言摘要。
- 超窗处理还要考虑安全：过期权限确认不能永久有效，敏感信息不应长期记忆，用户修正和拒绝必须优先保留。
- 面试总结：长对话管理不是“压缩聊天记录”，而是把对话转成可更新、可检索、可验证的状态。

## 超窗风险卡
Q: 长对话超出窗口会带来哪些风险？

A:
- 忘记用户最初目标，开始偏题。
- 忘记用户修正，例如“不要退款，只查物流”。
- 忘记已完成步骤，重复调用工具。
- 忘记安全约束或权限确认状态。
- 输出不一致，前后口径变化。
- 历史工具结果被截断，基于不完整信息判断。

## 处理策略卡
Q: 长对话可以用哪些策略处理？

A:
- 滑动窗口：保留最近 N 轮，适合短任务。
- 摘要压缩：把早期对话压成摘要，适合普通聊天。
- 结构化状态：抽取目标、约束、进度、待办，适合 Agent 任务。
- RAG 记忆：把历史片段向量化，按需召回。
- 分层记忆：短期上下文、长期偏好、任务状态分开管理。

## 结构化状态卡
Q: 为什么长任务不能只靠自然语言摘要？

A:
- 摘要可能漏掉细节，例如金额、订单号、用户否定条件。
- 摘要无法直接表达任务状态机。
- 工具结果、审批状态、幂等键需要结构化保存。
- 后续执行要依赖明确字段，而不是让模型从摘要里猜。
- 结构化 state 可以被程序校验、更新和审计。

## 具体例子卡
Q: 处理“帮我排查线上慢查询”的长对话应该保留什么？

A:
- `goal`: 找出接口变慢原因。
- `constraints`: 只读查询，不能修改生产配置。
- `time_range`: 用户指定的故障时间段。
- `completed_steps`: 已查监控、已查慢 SQL、已查下游超时。
- `tool_results`: 关键日志 id、trace id、指标截图摘要。
- `open_questions`: 是否允许查询更长时间范围。

## 可追问原理卡
Q: 为什么长对话摘要也可能引入错误？

A:
- 摘要本身是模型生成，可能遗漏、改写或合并冲突信息。
- 早期错误摘要会成为后续上下文，持续影响后续回答。
- 如果摘要没有来源，后面很难追溯原始对话。
- 权限、时间、金额等精确信息不适合只保存在自由文本摘要中。
- 所以关键状态应结构化保存，并尽量保留可追溯引用。

## 工程实践卡
Q: 长对话系统如何设计上下文管理？

A:
- 每轮更新 task state，而不是只追加聊天记录。
- 摘要要带版本和来源，必要时可回看原文。
- RAG 召回历史时做权限过滤和时间过滤。
- 对用户修正、拒绝、约束变更设置更高保留优先级。
- 对高风险动作重新确认，不能依赖很久以前的确认。

## 正确性审查卡
Q: 解释长对话超窗时有哪些误区？

A:
- 不要简单删除最早消息，可能删掉关键目标或约束。
- 不要把摘要当绝对真实，它也可能幻觉或漏信息。
- 不要把长期记忆和当前授权混为一谈。
- 不要永久保存敏感信息，记忆系统也要有隐私治理。
- 不要让模型仅凭历史摘要执行高风险动作，执行前要重新校验和确认。
