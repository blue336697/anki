# 模型输出进入下游系统前应该做哪些 validation？

来源：https://www.nootcode.com/problems/llm-output-validation-before-downstream-systems

## 面试直接回答卡
Q: 面试中如何直接回答“模型输出进入下游系统前应该做哪些 validation？”

A:
- 模型输出进入下游系统前，必须按风险分层做校验。因为 LLM 输出是概率性文本，不保证格式合法、字段完整、事实正确、权限合规或业务安全。
- 第一层是格式校验，例如 JSON 是否能解析、字段是否存在、类型是否正确、枚举是否在允许范围内、字符串长度是否超限。
- 第二层是语义和业务校验，例如金额不能为负、开始时间不能晚于结束时间、订单状态必须允许退款、SQL 只能查询白名单表。
- 第三层是权限和安全校验，例如用户是否有权访问对应数据、是否包含隐私、是否试图执行删除/转账/发邮件等高风险动作。
- 第四层是事实校验和执行前确认，例如引用是否存在、工具结果是否支持结论、高风险动作是否需要人工审批。面试总结：LLM 输出不能直接进下游，必须经过 parser、schema、业务规则、权限和审计链路。

## 校验层次卡
Q: LLM 输出 validation 可以分成哪几层？

A:
- 语法层：JSON/XML/SQL 是否能解析。
- Schema 层：字段、类型、枚举、必填项、长度限制。
- 业务层：金额、状态、时间、库存、订单规则是否成立。
- 权限层：用户是否有权看数据或执行动作。
- 安全层：是否包含敏感信息、危险命令、越权动作。
- 事实层：结论是否有工具、文档、数据库或日志支持。

## 具体例子卡
Q: 如果模型输出一个退款请求 JSON，应该如何校验？

A:
- 先 parse JSON，不能解析就拒绝或重试修复。
- 校验 schema：`order_id` 是字符串，`amount_cent` 是整数，`reason_code` 在枚举内。
- 查订单：订单是否存在，是否属于当前用户，是否已支付。
- 校验业务：退款金额不能超过可退金额，订单状态允许退款。
- 风控和审批：大额或异常退款进入人工确认。
- 幂等：必须带 `idempotency_key`，防止重复执行。

## 可追问原理卡
Q: 为什么 validation 不能只让模型自检？

A:
- 模型自检仍然是模型生成，可能重复同样错误。
- 格式合法性可以由 parser 确定性判断，没必要交给模型猜。
- 权限和业务状态来自后端系统，模型上下文可能缺失或过期。
- 高风险动作需要可审计的确定性链路。
- 自检可以作为辅助，但不能替代程序化校验。

## SQL 校验卡
Q: 模型生成 SQL 进入执行前要做什么校验？

A:
- 只允许 SELECT，禁止 DELETE、UPDATE、DROP、ALTER 等写操作。
- 表和字段必须在白名单内。
- 自动加 LIMIT，避免全表大结果。
- 参数化执行，避免拼接注入。
- 在只读账号和隔离环境执行。
- 记录 SQL、用户、时间、结果行数和错误信息。

## 工程实践卡
Q: validation 失败后应该怎么处理？

A:
- 可恢复格式错误可以让模型基于错误信息重试一次。
- 权限失败不能重试绕过，要明确拒绝。
- 业务规则失败要返回可解释原因，例如“订单已超过退款期”。
- 高风险不确定状态进入人工确认。
- 重试要有次数上限，避免循环和成本失控。

## 正确性审查卡
Q: 讨论输出 validation 时有哪些误区？

A:
- 不要把模型输出当作可信结构化数据。
- 不要只校验 JSON 语法，字段语义和业务规则同样重要。
- 不要让模型决定自己是否有权限。
- 不要把 validation 失败都交给模型无限重试。
- 不要忽略审计，高风险输出要能追踪来源、版本和执行结果。
