# 缓存一致性与MESI

## 概念卡
Q: 多核 CPU 为什么需要缓存一致性？

A:
- 每个核心都有自己的 L1/L2 cache，同一内存地址可能被多个核心缓存
- 如果一个核心修改了数据，其他核心缓存里的旧副本必须失效或更新
- 缓存一致性协议保证多核心对同一地址的读写能看到合理顺序
- 常见协议是 MESI：Modified、Exclusive、Shared、Invalid
- Java 可见性问题最终会落到缓存、写缓冲、内存屏障等硬件机制

## 机制卡
Q: MESI 四个状态怎么理解？

A:
- Modified：当前核心独占且已修改，内存中是旧值，未来要写回
- Exclusive：当前核心独占但未修改，和内存一致
- Shared：多个核心可读共享，和内存一致
- Invalid：当前缓存行无效，不能直接使用
- 写共享数据时，其他核心对应缓存行通常会被置为 Invalid

## 边界卡
Q: MESI 能解决所有并发可见性问题吗？

A:
- MESI 解决的是同一缓存行在多核缓存中的一致性
- 程序层还会受到编译器重排、CPU 乱序、写缓冲、StoreLoad 等影响
- Java 需要 volatile、锁、final 语义、内存屏障来建立 happens-before
- 一致性不等于原子性，i++ 仍然需要锁或原子类
- 面试别把硬件缓存一致性和 Java 内存模型混成一个层次

## 对比追问卡
Q: 缓存一致性和伪共享有什么关系？

A:
- MESI 以 cache line 为粒度维护一致性
- 伪共享中多个线程写不同变量，但变量位于同一 cache line
- 每次写都会让其他核心的整行缓存失效，即使逻辑上没有共享变量
- 这会造成一致性流量放大，吞吐下降
- 解决要从数据布局入手，而不是只加 volatile

## 正确性审查卡
Q: 关于缓存一致性有哪些常见误区？

A:
- “有 MESI 就不需要 volatile”：错。MESI 不负责语言层重排和 happens-before
- “volatile 能保证复合操作原子”：错。volatile 主要保证可见性和有序性
- “伪共享是多个线程写同一个变量”：不准确。伪共享写的是同一缓存行上的不同变量
- “缓存一致性没有成本”：错。跨核失效和同步会带来明显性能损耗
