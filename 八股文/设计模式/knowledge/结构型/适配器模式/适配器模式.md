# 适配器模式

## 意图卡
Q: 适配器模式解决什么问题？
A:
- 适配器把一个已有接口转换成调用方期望的接口
- 它用于兼容旧系统、第三方 SDK、遗留接口或不一致的数据模型
- 调用方依赖目标接口，适配器内部调用被适配对象
- 核心价值是隔离接口不匹配，而不是修改已有类
- 面试表达：适配器解决“接口形状不一致但能力可复用”的问题

## 类型卡
Q: 类适配器和对象适配器有什么区别？
A:
- 类适配器通过继承被适配类实现转换，受语言单继承限制
- 对象适配器通过组合持有被适配对象，更灵活也更常用
- 对象适配器可以适配多个实现，并便于替换和测试
- Java 工程中通常优先使用对象适配器
- 组合优先于继承的原则在适配器模式中很典型

## 工程落点卡
Q: 适配器模式在后端工程中有哪些常见落点？
A:
- 封装第三方支付、短信、地图、OSS、风控 SDK
- 把外部 DTO 转换为内部领域模型或统一接口
- 老接口迁移新接口时提供兼容层
- Spring MVC 的 HandlerAdapter 也是典型适配思想
- 防腐层中常用适配器隔离外部系统模型污染内部领域

## 正确性审查卡
Q: 适配器模式有哪些常见误区？
A:
- “适配器就是工具类转换”：不完整。它强调稳定目标接口和隔离外部变化
- “适配器越通用越好”：错误。过度通用会吞掉语义，难以排查问题
- “适配器可以隐藏所有差异”：错误。能力缺失、语义不一致不能靠适配硬补
- “直接改旧接口更简单”：短期可能简单，但会影响已有调用方
- “适配器和代理一样”：不同。适配器改接口，代理控制访问
