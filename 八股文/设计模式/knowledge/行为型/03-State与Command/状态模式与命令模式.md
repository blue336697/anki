# 状态模式与命令模式
## 01-State
Q: State 模式如何替代复杂状态分支？
A:
- context 将状态相关行为委托给 State 对象，状态实现控制允许操作和下一状态。
- 适合状态多、每状态行为差异大且迁移频繁扩展；简单有限状态用 enum+显式表更直观。
- 迁移必须保持领域不变量并记录审计，不能任意 setState。
- 状态对象若无数据可共享，有状态则注意生命周期。
## 02-Command
Q: Command 将什么封装成对象？
A:
- 把请求意图、参数和执行入口封装，支持排队、日志、重试、撤销或权限检查。
- Command 是要做的事，Event 是已经发生的事实；命名时态和处理语义不同。
- 跨进程 command 必须版本化、幂等并验证授权。
- 不是每个方法调用都需要 Command 类。
## 03-代码
Q: 用枚举状态对象怎样保护订单迁移？
A:
```java
enum OrderState {
    DRAFT { OrderState confirm(){ return CONFIRMED; } },
    CONFIRMED;
    OrderState confirm(){ throw new IllegalStateException(); }
}
final class Order {
    private OrderState state = OrderState.DRAFT;
    void confirm(){ state = state.confirm(); }
}
```
- 非法状态没有分支遗漏，复杂副作用仍由聚合协调。
## 04-撤销
Q: Command 的 undo 为什么通常不是“调用反方法”？
A:
- 外部副作用可能不可逆，库存/支付需要补偿命令而非时光倒流。
- 内存编辑器可保存 memento 或 inverse operation；分布式流程需 Saga 与幂等。
- 命令执行结果和版本应记录，防重复撤销。
- 不应承诺所有业务操作可撤销。
## 05-对比
Q: State、Strategy、Command 如何快速区分？
A:
- State 表达对象生命周期行为，Strategy 表达可替换算法，Command 表达一次请求。
- State/Strategy 都常用委托，Command 还可被存储、调度和审计。
- 同一系统可用 Command 触发聚合 State 迁移，并由 Strategy 计算规则。
- 选择模式看意图，不看类图是否相似。
