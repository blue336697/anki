# 单例模式

## 意图卡
Q: 单例模式解决什么问题？适合哪些场景？
A:
- 单例保证一个类在进程内只有一个实例，并提供全局访问点
- 适合无状态服务、配置中心客户端、线程池、连接池管理器、注册表等共享资源
- 关键价值是控制实例数量和生命周期，而不只是“少 new 一个对象”
- 在 Spring 中默认单例 Bean 是容器级单例，不等同于 JVM 全局单例
- 面试表达：先讲约束实例数量，再讲线程安全、序列化、反射和容器边界

## 实现卡
Q: Java 中常见单例实现方式如何比较？
A:
- 饿汉式简单线程安全，但类加载时就创建，可能浪费资源
- 懒汉式延迟创建，但普通写法线程不安全
- 双重检查锁需要 `volatile` 防止指令重排导致半初始化对象被看到
- 静态内部类利用类加载机制实现懒加载和线程安全
- 枚举单例天然防反射和反序列化破坏，是 Effective Java 推荐写法

## 工程落点卡
Q: 单例模式和 Spring 单例 Bean 有什么区别？
A:
- 传统单例通常由类自己控制构造器和实例获取
- Spring 单例由容器控制生命周期和依赖注入，默认作用域是每个容器一个实例
- 多个 Spring 容器可能有多个同类型单例 Bean
- Spring 单例 Bean 不保证内部状态线程安全，有可变字段仍需并发控制
- 工程实践中更推荐把对象交给容器管理，而不是到处写 `getInstance()`

## 正确性审查卡
Q: 单例模式有哪些常见误区？
A:
- “单例一定线程安全”：错误。实例创建安全不代表内部状态并发安全
- “Spring 单例就是 JVM 单例”：错误。它是容器作用域单例
- “双重检查锁不用 volatile”：错误。没有 `volatile` 可能看到未完成初始化对象
- “所有工具类都应该单例”：不完整。纯函数工具类用静态方法即可
- “单例方便全局访问所以多用”：危险。滥用会隐藏依赖，降低可测试性
