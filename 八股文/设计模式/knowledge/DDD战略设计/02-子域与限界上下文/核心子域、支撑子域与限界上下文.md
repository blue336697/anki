# 核心子域、支撑子域与限界上下文
## 01-子域分类
Q: Core、Supporting、Generic Subdomain 如何影响投入？
A:
- 核心子域承载企业差异化能力，应投入最佳团队和定制模型；支撑子域必要但非竞争优势。
- 通用子域如认证、邮件常可采购或使用成熟方案，避免把有限精力平均分配。
- 分类是业务战略判断，不等于某个微服务大小，也会随公司阶段变化。
- “所有模块都很核心”通常意味着没有做取舍。
## 02-上下文边界
Q: Bounded Context 到底限制什么？
A:
- 它限定一套模型和通用语言的有效范围；同一“客户”在营销、订单、风控中可有不同属性与规则。
- 边界内术语必须一致，边界间通过明确契约翻译，不共享一个万能领域对象。
- 上下文是语义和团队边界，未必一对一进程/微服务；单体中也可有多个上下文。
- 拆分依据业务一致性与语言，不应按数据库表或技术层机械切。
## 03-识别方法
Q: 怎样识别限界上下文，而不是凭感觉画框？
A:
- 寻找语言含义变化、规则一起变化、强一致事务和不同团队决策权。
- 业务能力、事件风暴中的 policy/aggregate cluster 与组织沟通路径提供候选边界。
- 用关键场景穿越边界，检查是否需要频繁同步内部细节；过多跨界调用说明切分需调整。
- 边界是模型假设，可通过演进验证，不要求首次一次到位。
## 04-代码示例
Q: 如何避免订单上下文直接依赖 CRM 的 Customer 实体？
A:
- 订单只保存完成订单决策所需的 BuyerId/快照，通过端口获取必要信息。
```java
record BuyerId(String value) {}
interface BuyerPolicy {
    boolean canPlaceOrder(BuyerId buyerId);
}
final class Order {
    private final BuyerId buyerId;
    Order(BuyerId buyerId) { this.buyerId = buyerId; }
}
```
- CRM 模型变化不会传播进订单聚合，跨上下文契约保持小而稳定。
## 05-误区
Q: 限界上下文与微服务有哪些常见误区？
A:
- “一个上下文必须一个微服务”错误；部署边界还受吞吐、团队和运维能力影响。
- “一个微服务可随意混多个模型”会重新制造大泥球，至少应保持模块隔离。
- 共享数据库让上下文绕过契约写彼此表，实际破坏自治。
- 优先建立模型边界，再决定单体模块或服务化时机。
