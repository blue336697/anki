# 通用语言、模型与知识消化
## 01-核心含义
Q: DDD 的核心为什么不是“多写几个 Entity 类”？
A:
- DDD 用领域专家与开发者共同维护的模型解决复杂业务认知问题，代码只是模型的一种表达。
- 通用语言必须进入需求、事件、接口、测试和代码命名，避免“业务说冻结、代码写 disable”形成翻译层。
- 模型会随知识消化迭代，不追求第一版画出永恒对象图。
- 简单 CRUD 领域未必值得承担 DDD 的建模和组织成本。
## 02-知识消化
Q: 团队怎样从业务访谈得到可执行的领域模型？
A:
- 围绕业务事件、规则、例外和决策追问，而不是只收集页面字段；Event Storming 可暴露命令与事件。
- 把含糊名词改成有边界的概念，识别同词异义和异词同义，并记录规则示例。
- 用场景测试验证模型能否回答“何时允许、谁负责、失败后怎样”，再落到对象和服务。
- 模型评审应有领域专家参与，不能由技术团队闭门按表结构反推。
## 03-代码语言
Q: 如何让 Java 代码真正体现通用语言？
A:
- 类型和方法直接使用业务词，行为方法表达意图，不暴露 setStatus 让外部任意拼状态。
- 值对象承载 Money、Address 等规则，领域异常用业务含义命名。
- 包结构按领域能力而非 controller/service/dao 纯技术层切割。
- 注释不应长期翻译糟糕命名，无法命名往往说明模型尚未澄清。
## 04-代码示例
Q: “确认订单”怎样从贫血写法改成领域行为？
A:
- 聚合自己检查当前状态并产生合法状态迁移，调用者只表达 confirm 意图。
```java
final class Order {
    private OrderStatus status = OrderStatus.DRAFT;
    void confirm() {
        if (status != OrderStatus.DRAFT)
            throw new IllegalStateException("只有草稿订单可确认");
        status = OrderStatus.CONFIRMED;
    }
}
```
- 规则与状态在一起，任何入口调用都不会绕过；持久化映射不应迫使开放公共 setter。
## 05-边界审查
Q: 通用语言最常见的失败方式是什么？
A:
- 只制作词汇表却不进入代码和验收；同一词在不同上下文仍被强行统一。
- 让数据库表名成为模型，业务行为散落在 service 的 if/else，实体退化为 DTO。
- 过早追求完美名词而不通过真实场景验证，模型与业务演进脱节。
- 应定期从生产事件、客服术语和规则变更反向修正模型。
