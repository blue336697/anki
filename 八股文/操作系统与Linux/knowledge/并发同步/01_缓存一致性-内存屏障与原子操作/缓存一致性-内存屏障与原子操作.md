# 缓存一致性、内存屏障、原子操作与伪共享

> 基线：硬件缓存一致性保证单个 cache line 的一致视图，不自动提供程序期望的跨变量顺序。Linux 内核内存模型与语言内存模型也不能混用。

## 01-缓存层次
Q: 多核 CPU 缓存为什么会让共享内存并发变复杂？
A:
- 每个核有私有或分级缓存，同一物理地址的 cache line 可同时出现在多个核。
- 读写首先落到本地缓存、store buffer 和乱序执行流水线，内存系统再通过一致性协议协调所有权。
- 不同核观察两个独立地址的先后顺序可能不同，编译器也会在单线程语义允许范围内重排。
- 因此“源码先写 A 再写 B”不能自动推导另一 CPU 先看到 A 后看到 B。

## 02-coherence
Q: MESI 类缓存一致性协议大致保证什么？
A:
- cache line 处于 Modified、Exclusive、Shared、Invalid 等状态，写入者先获得独占所有权并使其他副本失效。
- 一致性保证对同一位置的写入形成可协调顺序，避免两个核长期保留冲突值。
- 协议具体状态可能是 MESIF/MOESI 等扩展，不能把 MESI 四态当成所有 CPU 固定实现。
- 它不保证对不同 cache line 的操作顺序，也不替代锁、原子和内存屏障。

## 03-consistency
Q: Cache coherence 和 memory consistency 有什么区别？
A:
- coherence 关注单一内存位置：各 CPU 最终如何观察对该位置的读写。
- consistency/memory model 规定跨多个位置的读写允许以什么顺序被其他线程观察。
- 一个系统可以保持每个变量一致，却允许 `data` 和 `ready` 被另一 CPU 以反直觉顺序看到。
- acquire/release、锁和 barrier 用来建立程序需要的 happens-before，而不是修改一致性协议名称。

## 04-store-buffer
Q: Store Buffer 为什么会产生“本核已写、他核还看不到”的窗口？
A:
- CPU 把待提交写入放入 store buffer，使执行流水线不必等待 cache line 所有权和一致性通信完成。
- 本核可能通过 store forwarding 立即读到自己的新值，而其他核仍只能看到旧缓存副本。
- 写缓冲会按架构规则排空，特定 barrier 或带内存序的原子操作约束可见顺序。
- 这种优化是高性能必要机制，正确并发不能依赖“过一会儿自然可见”。

## 05-编译器与CPU屏障
Q: 编译器屏障和 CPU 内存屏障分别防止什么？
A:
- 编译器屏障约束编译器不要把内存访问跨越某点重排，但不一定生成硬件 fence。
- CPU barrier 约束处理器和内存系统的加载/存储顺序；不同架构有 full、read、write 等强弱指令。
- Linux 的 `smp_mb/rmb/wmb` 等同时包含适当编译器约束，并按架构生成最小必要指令。
- `volatile` 主要约束编译器访问，既不保证复合操作原子，也通常不等价于跨核 full barrier。

## 06-acquire-release
Q: acquire/release 如何建立发布与消费关系？
A:
- 生产者先初始化数据，再用 release store 发布指针或 ready；release 禁止此前操作被移到发布之后。
- 消费者用 acquire load 观察到发布值后，acquire 禁止后续数据读取被移到观察之前。
- 若 acquire 读到了对应 release 写，前面的初始化对消费者可见，形成同步关系。
- 只在一侧使用 acquire 或 release 不够；发布变量必须用匹配原子/内核原语并正确处理循环检查。

## 07-原子操作
Q: 原子读改写操作提供哪些能力？
A:
- compare-and-swap、fetch-add 等保证对一个原子对象的读改写不可被其他 CPU 看到中间状态。
- 它们可带 relaxed、acquire、release 或更强内存序；“操作原子”与“周围访问有序”是两个维度。
- 锁通常由原子指令竞争一个状态，再配合睡眠/唤醒和内存屏障构成。
- 大于硬件支持宽度、未对齐或普通变量上的复合操作不能假设天然原子。

## 08-ABA
Q: 无锁 CAS 中的 ABA 问题是什么？
A:
- 线程读取指针值 A 后暂停，其他线程把它改为 B、释放/复用对象，再改回数值相同的 A。
- 原线程 CAS 只比较位模式会成功，却不知道对象生命周期和中间状态已经变化。
- 可用版本戳指针、引用计数、hazard pointer、epoch/RCU 或不复用策略管理生命周期。
- CAS 循环本身不等于无锁算法正确，内存回收往往比原子更新更难。

## 09-伪共享
Q: false sharing 为什么在没有逻辑共享变量时仍会变慢？
A:
- 两个线程更新不同变量，但变量位于同一 cache line，一方写入会使另一核的整条 line 失效。
- cache line 所有权在核间来回传递，产生一致性流量、store stall 和吞吐下降。
- 使用对齐/填充、per-CPU 分片、批量合并可降低抖动，但会增加内存和汇总成本。
- perf c2c、硬件计数器和对照布局压测可验证，不能看到多线程慢就一律归因伪共享。

## 10-正确性审查
Q: 关于缓存和原子性，哪些常见说法需要纠正？
A:
- “MESI 保证线程安全”错误；它不定义跨变量业务顺序和复合不变量。
- “volatile 能保证自增原子”错误；读、加、写仍是多个步骤。
- “CAS 不加锁所以没有竞争成本”错误；热点 cache line 上失败重试和一致性通信可能非常昂贵。
- “x86 较强内存序所以不需要并发原语”错误；编译器重排、数据竞争和可移植性仍要求正式同步。
