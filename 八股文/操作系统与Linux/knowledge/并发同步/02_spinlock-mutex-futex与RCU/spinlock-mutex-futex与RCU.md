# spinlock、mutex、futex、seqlock 与 RCU

> 基线：锁的选择首先由执行上下文决定：能否睡眠、临界区长度、读写比例、实时性和对象生命周期，而不是简单比较“谁更快”。

## 01-spinlock
Q: 内核 spinlock 适合什么场景？
A:
- 竞争失败者在 CPU 上循环等待，不发生睡眠，适合不可睡眠上下文和极短临界区。
- 持锁期间不能执行可能调度的操作，否则等待者浪费 CPU，当前任务还可能造成死锁。
- SMP 中锁通过原子操作和 cache line 所有权串行化；单核/抢占配置下实现细节可能退化为禁抢占。
- 中断也访问同一数据时需使用 irqsave/bh 变体匹配上下文，普通 spin_lock 不自动防本地中断重入。

## 02-mutex
Q: 内核 mutex 与 spinlock 的竞争路径有什么不同？
A:
- 无竞争时 mutex 可通过原子 fast path 获得；竞争时任务进入等待队列并睡眠，把 CPU 让给其他工作。
- 解锁选择并唤醒等待者，涉及调度、队列和 cache 转移，长临界区更划算。
- mutex 只能在可睡眠进程上下文使用，不能在硬中断、softirq 或持自旋锁时获取。
- 某些实现会短暂 optimistic spinning 等待正在运行的持锁者，但不改变其可睡眠锁语义。

## 03-semaphore与completion
Q: semaphore、mutex 和 completion 的语义差别是什么？
A:
- mutex 表达单一所有者互斥，持有者负责解锁，并提供所有权与调试语义。
- counting semaphore 表达多个许可，down 消耗、up 归还，不一定绑定持有线程。
- completion 表达一次或多次事件完成，等待者睡眠直到 `complete`，比用锁模拟“任务做完了”更准确。
- 选择原语应匹配不变量，不能因为 API 都可能睡眠就互换。

## 04-futex
Q: 用户态 pthread mutex 为什么需要 futex？
A:
- 无竞争时锁状态在用户内存用原子操作改变，不进入内核，这是 futex 的 fast path 思想。
- 竞争时线程调用 `futex(FUTEX_WAIT)`，内核按用户地址对应 key 把任务挂入哈希等待队列。
- 解锁者发现有等待者后调用 `FUTEX_WAKE` 唤醒一个或多个任务；内核不替用户维护完整锁策略。
- wait 会再次校验用户值以避免检查与入队间丢失唤醒，返回后用户仍需循环 CAS 竞争。

## 05-优先级反转
Q: 什么是 priority inversion，PI futex 如何缓解？
A:
- 高优先级任务等待低优先级持锁者，而中优先级任务持续抢占低优先级者，导致高优先级间接长期阻塞。
- priority inheritance 临时提升持锁者优先级，使其尽快运行并释放锁，再恢复原优先级。
- PI 需要内核跟踪等待关系和实时调度语义，成本高于普通 futex，且无法修复任意用户级依赖。
- 优先级天花板、缩短临界区和避免实时线程依赖普通线程同样重要。

## 06-rwsem
Q: 读写锁为什么不一定比互斥锁快？
A:
- 多个读者可并发、写者独占，适合读多且读临界区足够长的场景。
- 读者计数和所有权本身是共享 cache line，极短读路径可能因原子操作比 mutex 更贵。
- 持续读流量可能让写者饥饿，现代实现会用公平或写者优先策略，具体取决于原语。
- 若“读”内部仍修改共享 cache 或引用生命周期，读锁也不能自动保证正确。

## 07-seqlock
Q: seqlock 如何让读者无锁读取一致快照？
A:
- 写者持锁并把 sequence 变为奇数，完成多字段更新后再变为偶数。
- 读者先读 sequence，复制数据，再检查 sequence 是否变化或为奇数；不一致则重试。
- 读者不会阻塞写者，适合写少、读快且数据可安全重复读取的统计/时间信息。
- 被保护数据不能含读者可能解引用后被释放的指针，否则重试之前已可能 use-after-free。

## 08-RCU读取
Q: RCU 为什么能让读路径几乎不写共享锁变量？
A:
- 读者进入 RCU read-side critical section，读取通过 RCU 发布的指针，不与每次读写者争用同一锁。
- 更新者构造新版本并原子替换指针，旧对象在 grace period 结束前仍保留。
- grace period 保证所有在替换前可能看到旧对象的既有读者已经离开临界区，然后才可回收。
- RCU 保护的是访问与生命周期，复杂多字段更新仍可能需要锁、序列号或不可变结构。

## 09-RCU宽限期
Q: grace period 为什么不是“固定等待几毫秒”？
A:
- 内核需要观察所有相关 CPU/任务经历 quiescent state，证明旧读侧临界区已结束。
- CPU offline、长期内核执行、抢占模型和不同 RCU flavor 会影响检测方式和时长。
- `synchronize_rcu()` 等待宽限期可阻塞，`call_rcu()` 注册回调异步回收，不能在任意原子上下文等待。
- 新读者在指针替换后开始不妨碍回收旧对象，因为它们应看到新版本。

## 10-deadlock
Q: 内核和用户程序常见死锁条件如何落地排查？
A:
- 互斥占有、持有并等待、不可剥夺和循环等待构成经典必要条件；工程上重点是锁顺序图和等待链。
- 同一线程递归获取非递归锁、进程上下文与中断反向加锁、等待工作而工作又等当前锁都是常见模式。
- 内核 lockdep 动态记录锁类依赖并报告潜在环；用户态可用线程 dump、futex wait、eBPF/perf off-CPU 分析。
- 超时只能让系统逃离部分等待，不证明共享状态仍一致，真正修复要消除依赖环或缩小锁域。

## 11-正确性审查
Q: 关于 Linux 锁和 RCU，哪些说法需要纠正？
A:
- “spinlock 一定比 mutex 快”错误；竞争和临界区稍长时自旋会浪费 CPU。
- “futex 是一种完全由内核维护的锁”错误；它主要提供按用户地址等待/唤醒，锁状态机在用户态。
- “RCU 没有同步开销”错误；更新、宽限期、回调和内存屏障都有成本，只是读路径优化突出。
- “读写锁适合所有读多写少”错误；短读、NUMA 计数争用和写者延迟可能使它更差。
