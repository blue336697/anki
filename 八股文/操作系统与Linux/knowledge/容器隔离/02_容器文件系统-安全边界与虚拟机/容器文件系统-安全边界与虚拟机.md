# 容器文件系统、安全边界与虚拟机

> 基线：容器是 Linux 隔离机制、rootfs、运行时和镜像规范的组合；它共享宿主内核，因此安全边界弱于硬件虚拟机。

## 01-rootfs
Q: 容器 root filesystem 是什么？
A:
- rootfs 是进程 mount namespace 中作为 `/` 的文件系统树，包含用户态库、程序、配置和设备视图。
- 它不包含独立内核；容器执行系统调用仍进入宿主 Linux 内核。
- 镜像层通常以只读 lower layer 叠加，容器再有可写 upper layer，并挂载 proc、sysfs、tmpfs 等运行时文件系统。
- 删除容器可写层不等于删除外部 volume，持久数据生命周期必须单独管理。

## 02-OverlayFS
Q: OverlayFS 的 lower、upper、work、merged 分别是什么？
A:
- lowerdir 是一个或多个只读基础层，upperdir 保存容器可写变化，workdir 供 OverlayFS 原子操作和内部工作。
- merged 是用户看到的合并视图，同名 upper 对象遮蔽 lower；删除 lower 文件用 whiteout 表达。
- 首次修改 lower 文件可能触发 copy-up，把整个文件或必要元数据复制到 upper，造成写放大和延迟。
- 数据库等高写工作负载更适合 volume/专用文件系统，不应把镜像可写层当高性能持久盘。

## 03-capabilities
Q: Linux capabilities 为什么比单一 root/non-root 更细？
A:
- 内核把传统 root 权限拆成 NET_ADMIN、SYS_ADMIN、SYS_PTRACE 等能力集合，并区分 permitted/effective/bounding/ambient。
- 容器运行时可默认丢弃多数能力，只添加业务确实需要的最小集合。
- `CAP_SYS_ADMIN` 覆盖面极广，授予后接近扩大内核攻击面，不能当作解决权限错误的通用开关。
- capability 仍由当前 user namespace 解释，并受 no_new_privs、文件能力和 exec 规则影响。

## 04-seccomp
Q: seccomp 如何缩小容器系统调用攻击面？
A:
- seccomp-BPF 根据系统调用号和参数做过滤，可允许、拒绝、记录、trap 或通知用户态代理。
- 默认 allowlist/denylist 应与应用实际 syscall 集匹配，阻止不需要的内核入口。
- 它不理解高层文件路径和业务语义，也不能修复允许 syscall 中的内核漏洞。
- io_uring 等可间接执行多类操作，安全策略与内核版本需要共同评估，不能只套旧 syscall 列表。

## 05-LSM
Q: SELinux/AppArmor 等 LSM 与 namespace/capability 如何配合？
A:
- namespace 改变可见资源，capability 判断特权操作，LSM 进一步按安全标签或路径策略决定主体能否访问对象。
- 即使容器内 UID 0 且持有某些 capability，SELinux/AppArmor profile 仍可拒绝文件、网络和内核操作。
- seccomp 控制 syscall 入口，LSM 控制对象访问，二者不是替代关系。
- 生产隔离要组合最小权限、只读文件系统、LSM、seccomp 和及时内核补丁。

## 06-设备与proc-sys
Q: 为什么把宿主 `/dev`、`/proc`、`/sys` 全量可写挂进容器很危险？
A:
- 设备节点可直接操作块设备、内存、GPU 或内核驱动，绕过普通文件隔离。
- `/proc/sys`、sysfs 和 debugfs 暴露大量全局内核配置与对象，部分 namespace 并未虚拟化。
- privileged 容器常获得设备、能力和宽松安全策略，安全边界接近宿主进程。
- 只暴露必要设备和伪文件，使用只读/遮蔽挂载，并明确哪些设置是宿主全局。

## 07-container-vs-VM
Q: 容器与虚拟机在隔离层次上有什么本质差异？
A:
- 容器进程直接使用宿主内核，namespace/cgroup 隔离用户空间视图和资源，启动快、开销小。
- 虚拟机通过 hypervisor 提供虚拟硬件，guest 运行自己的内核，内核故障域和版本可与宿主分离。
- 容器逃逸常利用共享内核漏洞或过大权限；VM 仍有 hypervisor/设备模拟攻击面，但边界通常更强。
- Kata、gVisor 等方案在兼容、性能和隔离间增加中间层，不能简单归类为传统容器或完整 VM。

## 08-资源可见性
Q: 容器内 `free`、`top`、`/proc/cpuinfo` 为什么可能误导？
A:
- procfs 很多信息来自全局内核视图，是否按 cgroup/namespace 虚拟化依内核和运行时。
- 应用可见 CPU 数、quota 和 cpuset 不一定一致，运行时/语言旧版本可能按宿主 CPU 创建过多线程。
- 容器内存要看 cgroup memory.current/max/events，宿主 MemAvailable 只说明全局压力。
- 诊断必须同时标注宿主、namespace 和 cgroup 层，避免把一层指标解释成另一层资源。

## 09-rootless边界
Q: rootless 容器提供了什么，又不能提供什么？
A:
- 通过 user namespace 把容器 root 映射为宿主普通用户，降低运行时或容器逃逸后的宿主权限。
- 网络、低端口、设备和 cgroup 委派需要用户态网络、系统服务或额外配置，性能与功能可能受限。
- 宿主共享内核仍在攻击面内，内核漏洞和错误文件挂载仍可能造成影响。
- rootless 是纵深防御，不是“不需要 seccomp/LSM/更新”的证明。

## 10-正确性审查
Q: 关于容器隔离，哪些说法需要纠正？
A:
- “镜像里包含完整操作系统内核”错误；常规容器镜像主要是用户态 rootfs。
- “容器等于轻量虚拟机”会掩盖共享内核和安全边界差异。
- “非 root 用户就绝对安全”错误；capability、挂载、设备、内核漏洞和组权限仍可能越权。
- “资源 limit 设置后应用一定能自动感知”错误；运行时可能仍按宿主资源决定线程和缓存。
