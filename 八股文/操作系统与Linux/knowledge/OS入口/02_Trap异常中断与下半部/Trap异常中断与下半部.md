# Trap、异常、中断与 Linux 延后执行

> 基线：先按同步/异步与来源分类，再落到 Linux 硬中断、softirq、tasklet、workqueue 和 threaded IRQ。不同架构入口细节不同。

## 01-事件分类
Q: Trap、fault、abort、硬件中断应如何区分？
A:
- CPU 异常通常与当前指令同步：fault 可在修复后重试，如缺页；trap 常在指令完成后报告，如断点；abort 通常难以精确恢复。
- 硬件中断由设备或定时器异步产生，与当前执行指令没有直接因果关系。
- 系统调用也是软件主动进入内核的受控入口，但现代 x86-64 常使用专用 `syscall` 路径，不必等同于传统软件中断。
- “中断”在口语中常泛指所有内核入口，面试时应明确同步异常还是外部 IRQ。

## 02-IDT与入口
Q: x86 中断或异常到来后，CPU 和 Linux 入口代码分别做什么？
A:
- CPU 根据向量查询 IDT 门描述符，检查入口地址与权限，必要时切换特权级和内核栈，并压入硬件规定现场。
- Linux 入口汇编补充保存通用寄存器，建立统一 `pt_regs` 布局，处理 GS、栈和安全缓解。
- 通用分派代码识别异常或 IRQ，调用架构与设备处理函数；退出时检查软中断、抢占、信号和返回模式。
- IDT 只解决“向量到入口”，设备来源确认、中断控制器 ACK 和驱动处理由后续层完成。

## 03-进程上下文与中断上下文
Q: 进程上下文和硬中断上下文有什么关键差别？
A:
- 进程上下文代表当前 `task_struct` 主动执行系统调用或内核线程，可在允许位置睡眠并被调度。
- 硬中断上下文是异步打断当前 CPU 的紧急处理，不代表被中断任务的业务请求，通常不能睡眠。
- 中断处理应快速确认设备、保存最少状态并安排延后工作，避免长时间阻塞该 CPU 的其他中断和调度。
- 代码能否睡眠取决于执行上下文、锁和中断状态，不是“内核代码都不能睡眠”。

## 04-上半部与下半部
Q: 为什么中断处理要拆成上半部和下半部？
A:
- 上半部在硬中断上下文快速读取/确认设备状态、屏蔽或 ACK 中断，并把后续工作排队。
- 协议解析、批量包处理和可延后的工作放到 softirq、NAPI、workqueue 或线程化中断中完成。
- 这样缩短硬中断关闭或屏蔽窗口，降低系统尾延迟并允许批量处理提高吞吐。
- 拆分不是固定二选一 API；具体机制取决于能否睡眠、延迟要求、并发模型和子系统约定。

## 05-softirq
Q: Linux softirq 的执行与并发特点是什么？
A:
- softirq 是预定义的高性能延后执行机制，可在硬中断退出、显式触发或 `ksoftirqd` 内核线程中运行。
- 同一种 softirq 可在不同 CPU 并发执行，处理函数不能假设全局串行，通常依赖 per-CPU 数据和专用同步。
- softirq 上下文不能执行会睡眠的操作；处理过久会消耗调度延迟，因此内核会把剩余工作交给 `ksoftirqd`。
- 网络收发、定时器和 RCU 等子系统大量使用 softirq，但现代细节要以目标内核版本为准。

## 06-tasklet与workqueue
Q: tasklet 和 workqueue 的本质区别是什么？
A:
- tasklet 构建在 softirq 上，仍运行于不可睡眠的原子上下文，并提供同一 tasklet 实例不并发执行等约束。
- workqueue 由内核工作线程在进程上下文执行，处理函数可以睡眠、获取可睡眠锁或执行阻塞 IO。
- workqueue 有共享 worker pool、并发和救援等复杂策略，排队工作时要管理对象生命周期和取消竞态。
- 新代码并非看到“下半部”就默认选 tasklet；许多场景更适合 threaded IRQ、NAPI 或 workqueue。

## 07-线程化中断
Q: threaded IRQ 解决什么问题？
A:
- 驱动可保留极短 primary handler，只确认中断并唤醒专用 IRQ 线程，把大部分处理放到可调度进程上下文。
- 线程处理允许睡眠并可设置调度优先级，PREEMPT_RT 等低延迟系统尤其依赖中断线程化。
- 若设备需要在唤醒线程前立即屏蔽或读取易失状态，primary handler 仍不能省略。
- 线程化会增加调度和唤醒成本，不代表所有高速数据面都优于 NAPI 式轮询批处理。

## 08-关中断与禁止抢占
Q: local IRQ disable、spin_lock_irqsave 和 preempt_disable 分别限制什么？
A:
- local IRQ disable 只阻止当前 CPU 处理可屏蔽硬中断，其他 CPU 仍可并发访问共享数据。
- preempt_disable 阻止当前任务被内核抢占，但硬中断仍可发生，也不保护其他 CPU。
- `spin_lock_irqsave` 同时获取自旋锁并保存/关闭本地 IRQ，常用于同一数据既被进程上下文又被本地中断访问。
- 这些操作扩大延迟敏感区，应保持极短；它们不是跨 CPU 的万能串行化。

## 09-中断风暴
Q: 线上出现中断风暴时应怎样定位？
A:
- 观察 `/proc/interrupts` 各 CPU 计数增长、设备 IRQ affinity、`/proc/softirqs` 和 `ksoftirqd` CPU 使用。
- 网络场景结合网卡队列、NAPI budget、丢包、软中断 backlog、RPS/RFS 与 IRQ 分布判断热点。
- 设备持续报中断但没有有效工作可能是驱动 ACK、硬件或链路异常；单纯迁移 affinity 只会转移症状。
- 使用 perf、tracepoint 或 ftrace 确认耗时 handler，调整前保留计数和时间窗口作为证据。

## 10-正确性审查
Q: 关于中断和下半部，哪些说法需要纠正？
A:
- “异常都是错误、中断都来自硬件”过度简化；系统调用、断点和缺页具有不同同步语义。
- “下半部一定是 softirq”错误；还可能是 threaded IRQ、workqueue、NAPI 等机制。
- “中断上下文属于被打断进程，所以可以睡眠”错误；硬中断不能依赖该任务的调度上下文。
- “关本地中断就能保护多核共享数据”错误；其他 CPU 不受影响，仍需跨 CPU 同步。
