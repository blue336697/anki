# 用户态、内核态与 Linux 系统调用链路

> 基线：以 x86-64 Linux 的典型路径解释机制，具体寄存器和入口汇编具有架构差异。用户态/内核态是 CPU 特权状态，不是两个独立进程。

## 01-特权级
Q: 为什么操作系统要区分用户态和内核态？
A:
- CPU 用特权级限制页表、设备寄存器、中断控制和特权指令，用户程序不能直接破坏全局机器状态。
- 用户进程只能访问页表允许的用户地址；内核代码可以管理进程、内存、文件和设备，但也承担更高故障风险。
- Linux 通常主要使用 x86 Ring 3 运行用户代码、Ring 0 运行内核，不等于通用架构永远只有两个硬件级别。
- 权限隔离依靠 CPU 模式、页表权限和内核入口校验共同完成，不只是一个布尔变量。

## 02-系统调用目的
Q: 系统调用与普通函数调用的本质差异是什么？
A:
- 普通函数调用仍在同一特权级和地址空间内，只改变指令流与用户栈。
- 系统调用执行受控特权切换，CPU 从预设入口进入内核，内核根据系统调用号分派服务。
- 参数来自不可信用户空间，内核必须校验指针、长度、权限和对象状态，不能直接相信调用方。
- 返回时恢复用户寄存器和执行位置，并把结果或负 errno 通过 ABI 交给用户态封装。

## 03-x86-64入口
Q: x86-64 Linux 执行 `syscall` 指令时大致发生什么？
A:
1. 用户态按系统调用 ABI 把编号和参数放入约定寄存器，执行 `syscall`。
2. CPU 从 MSR 中取得内核入口地址并改变特权状态，保存返回 RIP/RFLAGS 的必要信息，但不会自动完成全部高级上下文管理。
3. 入口汇编切换到内核栈、保存 `pt_regs` 形式的寄存器现场，建立可供 C 代码处理的上下文。
4. 内核校验编号后调用对应 `__x64_sys_*` 路径，结束时处理调度、信号和审计，再通过安全返回路径回用户态。

## 04-系统调用ABI
Q: 为什么系统调用 ABI 与 C 函数 ABI 不能混为一谈？
A:
- 系统调用号、参数寄存器、返回值和被破坏寄存器由内核 ABI 约定；C 函数调用遵循编译器平台 ABI。
- x86-64 系统调用常用 `rax` 放编号，参数使用特定寄存器序列，并因 `syscall` 指令约束处理 `rcx/r11`。
- libc 的 `open()`、`read()` 等包装可能做参数转换、线程取消点或改用其他系统调用，不一定是一条指令直达同名内核函数。
- 跨架构、32/64 位兼容层和 seccomp 过滤都要求以目标 ABI 为准。

## 05-用户指针
Q: 内核为什么不能直接解引用用户传入的指针？
A:
- 用户地址可能未映射、无权限、跨页失效或被另一线程并发修改，直接访问可能在内核态触发异常。
- Linux 使用 `copy_from_user`、`copy_to_user`、`get_user` 等接口，在受控异常表和访问检查下复制数据。
- 即便第一次校验通过，用户仍可能在校验与使用之间修改内存，因此安全敏感结构通常要复制到内核缓冲后再验证。
- 零拷贝接口也不是跳过权限校验，而是通过固定页、共享映射或内核对象重新安排数据所有权。

## 06-阻塞系统调用
Q: 系统调用执行中发生阻塞时，用户线程处于什么状态？
A:
- 当前线程仍是发起系统调用的 `task_struct`，只是在内核路径中因等待 IO、锁或事件进入可睡眠状态。
- 调度器保存该任务上下文并运行其他可运行任务；事件到达后唤醒，线程继续从内核等待点执行。
- 系统调用返回用户态前，可能已经经历多次调度和 CPU 迁移，并非“进入内核后一直占着 CPU”。
- 中断信号、超时和可重启系统调用会影响等待结果，用户代码必须正确处理 `EINTR` 与部分完成。

## 07-vDSO
Q: `clock_gettime` 等调用为什么有时不需要真正陷入内核？
A:
- 内核把 vDSO 代码和只读时间数据映射到进程地址空间，libc 可在用户态读取经过同步的数据。
- 这样避免特权切换、入口汇编和调度检查，显著降低高频时间查询成本。
- 若硬件时钟源或调用类型不支持安全用户态计算，vDSO 会回退到真正系统调用。
- 因此“调用 libc API 就一定发生 syscall”不成立，应使用 `strace`、perf 或反汇编验证实际路径。

## 08-返回与errno
Q: 内核返回负错误码后，应用为什么看到 `-1` 和 `errno`？
A:
- Linux 内核系统调用约定通常用负数表示 `-Exxx`，成功则返回非负结果或特定值。
- libc 包装检测错误范围，把线程局部 `errno` 设置为正错误号，并向调用者返回 `-1`。
- `errno` 只在调用明确失败后有意义，后续成功调用不保证把它清零。
- 部分 IO 返回短读短写不是错误；应用要根据返回字节数继续处理，而不能只检查 errno。

## 09-性能成本
Q: 系统调用成本来自哪里，为什么不能简单说“切换一次上下文”？
A:
- 成本包括特权入口/返回、寄存器现场、边界校验、Spectre 等安全缓解、缓存和分支预测扰动，以及系统调用自身工作。
- 进入内核态不必然发生调度意义上的进程上下文切换；若调用立即完成，仍是同一任务继续运行。
- 阻塞、竞争或抢占才可能触发调度器切换到另一任务，成本远高于单纯 mode switch。
- 优化应减少无意义调用、批量处理或使用共享队列，而不是绕开内核安全边界。

## 10-正确性审查
Q: 关于用户态和系统调用，哪些常见说法需要纠正？
A:
- “用户态切到内核态就是进程切换”错误；特权级切换和任务调度是不同概念。
- “内核拥有一个独立进程替用户执行所有 syscall”错误；多数系统调用在当前任务的进程上下文中运行。
- “传入指针只需判断非空”错误；内核必须安全复制并处理缺页、权限和并发修改。
- “所有 libc 函数都对应同名系统调用”错误；包装、缓存、vDSO 和多系统调用组合都很常见。
