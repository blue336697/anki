# CFS、EEVDF、实时调度与睡眠唤醒

> 基线：经典教材常讲 CFS 的 vruntime 红黑树；Linux 从 6.6 开始逐步转向 EEVDF 选择公平类任务，现代回答必须说明版本演进。

## 01-调度类
Q: Linux 为什么使用多个调度类而不是一个统一优先级队列？
A:
- STOP、DEADLINE、实时、普通公平和 IDLE 等调度类具有不同策略与优先级层级。
- 调度器从高到低询问调度类是否有可运行实体，再由该类内部算法选择任务。
- 普通服务通常在公平调度类，实时策略可长期压制普通任务，配置错误会造成系统失去响应。
- cgroup CPU 控制、CPU affinity 和调度类共同决定实际可用 CPU，不能只看 nice。

## 02-CFS模型
Q: 经典 CFS 如何用 vruntime 模拟公平 CPU？
A:
- CFS 把理想多任务 CPU 上每个任务应获得的时间映射为虚拟运行时间 vruntime。
- 权重高的任务实际运行相同时 vruntime 增长更慢，因此更容易再次被选择；nice 值通过权重而非线性时间片生效。
- 经典实现把可运行实体按 vruntime 组织在红黑树，靠近最小 vruntime 的任务代表获得 CPU 较少。
- 这是理解历史与大量生产内核的基础，但不能声称所有新内核仍完全按“最左节点”规则工作。

## 03-EEVDF
Q: EEVDF 相对经典 CFS 的核心选择逻辑是什么？
A:
- Linux 6.6 起逐步引入 Earliest Eligible Virtual Deadline First，仍追求权重公平，但显式计算 lag 和虚拟 deadline。
- lag 为正表示任务相对公平份额欠 CPU；调度器先从 eligible 任务中选择虚拟 deadline 最早者。
- 短 slice 的延迟敏感任务可获得更早 deadline，提高响应性，同时长期仍由虚拟时间约束公平。
- 睡眠任务的 lag 处理和细节仍在演进，面试应给出版本基线而不是把 EEVDF 说成永恒固定实现。

## 04-nice权重
Q: nice 值如何影响普通任务的 CPU 份额？
A:
- nice 映射到调度权重，相邻级别按近似比例变化，不是“nice 加一就固定少运行一毫秒”。
- 同一竞争域内，任务份额约由自身权重占总权重比例决定；没有竞争时低权重任务仍可使用空闲 CPU。
- cgroup 调度实体会形成层级权重，进程 nice 与 cgroup `cpu.weight` 共同作用。
- nice 只影响公平类调度，不会把普通任务提升为实时任务。

## 05-per-CPU runqueue
Q: 为什么每个 CPU 有自己的 runqueue？
A:
- 每 CPU runqueue 降低全局调度锁竞争，让选择下一个任务主要在本地完成并保留缓存亲和性。
- SMP 负载均衡按调度域和 CPU 拓扑在队列间迁移任务，处理空闲拉取、周期平衡和唤醒放置。
- 完全均衡会破坏缓存热度，完全不迁移又会让 CPU 忙闲不均，调度器需要折中。
- CPU affinity、isolcpus、cpuset 和 NUMA 策略会限制可迁移范围。

## 06-抢占
Q: 哪些事件会让当前普通任务被抢占？
A:
- 时间/虚拟截止条件表明当前任务已运行过多，调度 tick 或其他调度点会设置 need_resched。
- 更应运行的任务被唤醒时，wakeup preemption 可能请求当前 CPU 尽快调度。
- 内核是否能立即抢占取决于 preemption model、当前是否禁抢占、持锁和中断上下文。
- 设置 need_resched 不等于在任意指令立即切换，真正调度要到安全点。

## 07-睡眠与等待队列
Q: 内核等待队列怎样避免“检查条件后刚好错过唤醒”？
A:
- 等待者先把自身加入 wait queue，设置可睡眠状态，再重新检查条件，确保条件变化与排队顺序受同步保护。
- 条件仍不满足才调用 schedule；生产者修改条件后调用 wake_up，把匹配任务转为可运行。
- 正确代码总是循环检查条件，因为唤醒可能是伪唤醒、多个等待者竞争或条件再次变化。
- 仅仅设置 task state 后直接睡眠而没有正确内存顺序，可能造成 lost wakeup。

## 08-实时调度
Q: `SCHED_FIFO`、`SCHED_RR` 和 `SCHED_DEADLINE` 有什么差别？
A:
- FIFO 实时任务在同优先级内可一直运行到阻塞、让出或被更高优先级抢占，没有普通时间片公平。
- RR 在同优先级 FIFO 语义上增加轮转时间片，让同优先级任务依次运行。
- DEADLINE 以 runtime、deadline、period 约束，使用 EDF/CBS 思想提供带准入控制的时限调度。
- 实时任务若不阻塞可饿死普通任务，应设置权限、CPU 预算和 watchdog，而不是用来“让服务快一点”。

## 09-load-average
Q: Linux load average 为什么不等于 CPU 使用率？
A:
- load average 统计一段时间内可运行任务以及特定不可中断等待任务的指数平滑数量。
- CPU 使用率低但大量线程处于 D 状态等待磁盘时，load 仍可能很高。
- 在多核机器上，load 需要与 CPU 数、runqueue、IO 等待和 PSI 共同解释。
- 1/5/15 分钟值不是三个窗口的简单算术平均，也不能单凭“load 大于 CPU 数”认定故障。

## 10-正确性审查
Q: 关于 Linux 调度，哪些旧说法需要更新？
A:
- “Linux 普通调度器就是 CFS 红黑树取最小 vruntime”对旧内核有解释力，但 6.6 起要补充 EEVDF 演进。
- “nice 代表固定时间片”错误；它主要映射权重并在竞争时影响份额。
- “D 状态说明 CPU 忙”错误；它常表示不可中断内核等待，可能造成高 load、低 CPU。
- “实时优先级更高所以业务服务都应使用”危险；失控实时线程能饿死系统维护和普通任务。
