# 上下文切换、地址空间切换与 CPU 迁移

> 基线：区分用户态/内核态切换、线程调度切换、地址空间切换和 CPU 迁移。四者成本来源不同。

## 01-切换对象
Q: 调度器切换两个 task 时需要保存和恢复什么？
A:
- 保存旧 task 的 CPU 寄存器、栈指针、指令位置和架构线程状态，并切换到新 task 的内核栈。
- 更新当前 task 指针、调度统计、TLS/FS-GS 等架构相关状态，必要时处理浮点与扩展寄存器。
- 如果地址空间不同，还要切换页表根或相应 MMU 上下文；内核线程可能借用前一个 `mm`。
- 切换汇编本身只是成本一部分，缓存、TLB 和分支预测器的后续冷启动常更昂贵。

## 02-mode-switch
Q: 用户态进入系统调用为什么不一定是 context switch？
A:
- mode switch 只是当前 task 从低特权代码进入内核入口，PID、调度实体和多数执行上下文仍是同一个。
- 若系统调用立即完成，内核直接恢复同一 task 回用户态，没有选择另一个任务。
- context switch 指调度器真正把 CPU 从 task A 交给 task B，需要保存/恢复调度上下文。
- 阻塞系统调用常同时经历 mode switch 和后续 context switch，但两者不能作为同义词。

## 03-地址空间
Q: 切换线程和切换进程在地址空间成本上有什么差别？
A:
- 同一线程组的线程通常共享 `mm_struct` 和页表，线程间调度不需要更换用户地址空间。
- 不同进程通常需要切换页表上下文，可能影响 TLB；现代 CPU 的 ASID/PCID 可让不同地址空间的部分 TLB 项共存。
- KPTI 等安全机制还可能让用户页表与内核页表入口发生额外切换，取决于架构和配置。
- 即使不刷新 TLB，两个线程的工作集不同也会污染数据缓存和分支预测状态。

## 04-主动与被动
Q: voluntary 和 involuntary context switch 分别从哪里来？
A:
- 主动切换发生在任务睡眠等待 IO、锁、定时器或显式 yield 时，任务自行离开可运行状态。
- 被动切换来自时间片/调度决策、优先级更高任务唤醒或 CPU 资源控制，当前任务仍可运行但被抢占。
- `/proc/<pid>/status`、`pidstat -w` 可观察计数，但高计数是否异常要结合每次工作量和延迟。
- 异步 IO 服务可能主动切换少但中断/软中断高，不能只用一个指标判断效率。

## 05-直接成本
Q: 一次上下文切换有哪些直接成本？
A:
- 调度器加锁和选择任务、保存恢复寄存器、切换内核栈与地址空间、更新 CPU 和进程统计。
- 安全缓解、调试跟踪、cgroup 记账、性能计数器和架构扩展状态会增加入口路径。
- 切换频率很高时，即使每次只有微秒或更低量级，累计 CPU 也可能显著。
- 具体成本依硬件、内核、工作集和切换类型变化，不能背一个固定纳秒数字。

## 06-间接成本
Q: 为什么 cache/TLB 冷却通常比保存寄存器更值得关注？
A:
- 新任务运行后，指令、数据和页表项可能不在本 CPU 缓存中，需要从更远层级加载。
- 共享缓存中的工作集会互相驱逐，跨核迁移还可能触发 cache line 所有权转移和 NUMA 远端访问。
- 分支预测与预取器历史也被不同执行流扰动，导致切换后的短期 IPC 下降。
- 因此减少过度线程、保持 CPU 亲和与按数据分片，往往比微调切换汇编更有效。

## 07-CPU迁移
Q: task 从 CPU0 迁移到 CPU1 有哪些额外影响？
A:
- 新 CPU 的私有 L1/L2 缓存没有原工作集，共享写数据还要通过一致性协议转移 cache line。
- NUMA 机器上，内存页可能仍位于 CPU0 所属节点，造成远端访存延迟和带宽占用。
- 调度器在负载均衡、亲和性、能耗和缓存热度之间折中，不会简单追求每个 CPU 队列长度完全相等。
- `taskset` 或 cpuset 可限制迁移，但绑定过度会造成热点和闲置，需要结合实际拓扑。

## 08-锁与切换
Q: 锁竞争怎样放大上下文切换？
A:
- 互斥锁未获得时线程进入等待队列并睡眠，持锁者释放后唤醒，至少增加睡眠和唤醒调度路径。
- 线程被唤醒后可能再次竞争失败，形成惊群、锁护送和 cache line 抖动。
- 自旋锁避免睡眠切换但消耗 CPU，适合极短不可睡眠临界区，不适合长等待。
- 优化应减少共享状态和临界区、按 key 分片或批处理，而不是只增加线程数。

## 09-观测
Q: 如何确认应用是否受上下文切换影响？
A:
- `pidstat -w` 看进程/线程主动和被动切换，`vmstat` 的 `cs` 看系统总量，必须按时间窗口和 CPU 数解释。
- `perf stat` 可结合 context-switches、cpu-migrations、cache-misses、cycles 和 instructions 判断代价。
- `perf sched`、调度 tracepoint 和 off-CPU 分析能定位谁让线程睡眠、等待多久、被谁唤醒。
- 在同负载基线下比较延迟分位数和 CPU，避免把正常异步服务的高切换数误判为故障。

## 10-正确性审查
Q: 关于上下文切换，哪些常见说法需要纠正？
A:
- “系统调用一次就上下文切换两次”错误；通常只是同一 task 的特权级往返。
- “线程切换没有成本”错误；即使共享页表，寄存器、栈、缓存和调度仍有成本。
- “进程切换一定清空全部 TLB”已不准确；ASID/PCID 等硬件机制可保留带地址空间标签的项。
- “context switch 越少越好”过度简化；适度阻塞让 CPU 执行其他工作，关键是吞吐与延迟而非单指标最小。
