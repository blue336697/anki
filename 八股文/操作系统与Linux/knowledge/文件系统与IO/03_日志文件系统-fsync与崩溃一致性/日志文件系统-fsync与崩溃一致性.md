# 日志文件系统、fsync 与崩溃一致性

> 基线：文件系统一致性保证元数据结构可恢复，不自动保证应用多文件事务。持久性必须覆盖应用、VFS、文件系统、块层和设备缓存。

## 01-崩溃窗口
Q: 文件更新为什么会在崩溃后出现“数据和元数据一半新一半旧”？
A:
- 一次逻辑写可能修改数据块、inode 大小、目录项、空闲位图和日志等多个物理位置。
- CPU、Page Cache、文件系统事务、块层队列和设备缓存会重排/延迟这些写入。
- 断电可能发生在任意阶段，若没有顺序和提交协议，磁盘结构可能引用未初始化块或丢失已写数据。
- 应用层看到 write/rename 返回只说明运行时操作完成，不自动定义断电后的状态。

## 02-journaling
Q: 文件系统 journal 如何把多次元数据写变成可恢复事务？
A:
- 先把本事务的元数据变更记录写入 journal，再写 commit record 表示日志事务完整。
- commit 持久后，即使 home location 尚未更新，重启可 replay journal 完成操作。
- 若 commit 未完成，恢复忽略该事务，避免部分元数据更新破坏结构。
- journal 是循环日志，需要 checkpoint 把已提交内容写回正式位置后复用空间。

## 03-ext4模式
Q: ext4 的 data=journal、ordered、writeback 模式有何取舍？
A:
- journal 模式把数据和元数据都写 journal，恢复语义强但写放大明显。
- ordered 常只 journal 元数据，同时要求相关新数据在元数据 commit 前提交，避免 inode 指向旧垃圾数据。
- writeback 对数据和元数据顺序保证更弱，吞吐可能高但崩溃后新文件内容更不可预测。
- 具体默认、DAX、delayed allocation 和发行版配置会变化，不能把模式名扩展为应用事务保证。

## 04-fsync链路
Q: `fsync(fd)` 为何不只是“调用一次磁盘 flush”？
A:
- 内核需找出该文件脏 page cache 与相关 inode 元数据，提交 writeback 并等待完成。
- 文件系统可能先提交包含该 inode 的 journal 事务，再确保数据和必要元数据按序到达块层。
- 块层/驱动根据缓存语义发出 flush/FUA 等命令，使设备报告完成达到要求的持久点。
- 任一层错误都应反馈给 fsync；忽略返回值会把持久化失败当成功。

## 05-fdatasync
Q: `fdatasync` 与 `fsync` 有什么差别？
A:
- fdatasync 重点持久化文件数据以及读取这些数据所必需的元数据，例如文件大小变化。
- fsync 还要求更多文件元数据如某些时间戳进入持久状态，可能写入更多内容。
- 如果写入扩展了文件，fdatasync 仍必须持久化 size，否则重启后数据不可访问。
- 性能差异依文件系统和变更类型，不能假设 fdatasync 永远显著更快。

## 06-rename
Q: rename 原子为什么不等于 rename 已持久化？
A:
- 同一文件系统内 rename 通常对并发观察者表现为旧名或新名，不暴露一半目录项状态。
- 系统崩溃后目录更新是否保留取决于 journal 提交和目录持久化；返回成功不等于设备已完成。
- 安全替换常是写临时文件、fsync 临时文件、rename 到目标，再 fsync 父目录。
- 跨文件系统 rename 不能作为单一原子操作，通常退化为复制与删除。

## 07-fsync目录
Q: 为什么创建、删除或 rename 后需要 fsync 目录？
A:
- 文件内容和 inode 持久化不自动保证父目录的“名字 -> inode”目录项已经持久。
- fsync 父目录要求目录项创建/删除/重命名进入文件系统提交路径，重启后名字仍可找到。
- 某些文件系统可能因实现顺带持久，但可移植崩溃协议不能依赖偶然行为。
- 多级目录操作可能需要对受影响目录分别处理，具体协议应通过故障注入验证。

## 08-delayed-allocation
Q: delayed allocation 提高性能的同时带来什么语义？
A:
- 文件系统先把数据留在 page cache，延后选择物理块，可聚合写、减少碎片并做更好布局。
- write 返回时甚至还没有最终物理块映射，ENOSPC 等错误可能推迟到 writeback/fsync。
- 应用必须检查 fsync/close/后续写错误，不能认为最初 write 成功就锁定了磁盘空间。
- 崩溃一致性依赖文件系统在分配、数据写与元数据提交之间建立正确顺序。

## 09-设备缓存
Q: 文件系统已经按顺序提交，为什么设备写缓存仍重要？
A:
- 磁盘/SSD 控制器可能把“完成”先用于易失缓存，并在内部重排真正介质写入。
- flush 命令要求先前缓存数据达到持久介质，FUA 可要求特定写绕过/落稳缓存，具体受设备支持影响。
- 设备或虚拟化层谎报 flush、无电池保护缓存，会破坏文件系统假设。
- 数据库可靠性测试必须覆盖真实存储栈和断电模型，而不是只在进程 kill 下验证。

## 10-正确性审查
Q: 关于日志文件系统和持久化，哪些说法需要纠正？
A:
- “有 journal 就绝不会丢用户数据”错误；journal 首先解决结构一致性，数据模式和 fsync 决定持久边界。
- “rename 原子所以不需要 fsync”错误；运行时原子可见性与崩溃持久性不同。
- “close 会自动等价 fsync”错误；正常 close 通常不保证脏数据已经持久。
- “fsync 只刷当前文件数据块”过度简化；还可能涉及 inode、journal、目录关系和设备缓存。
