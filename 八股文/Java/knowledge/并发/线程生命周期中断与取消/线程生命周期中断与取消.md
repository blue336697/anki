# 线程生命周期、中断与任务取消

## 01-线程状态
Q: Java Thread.State 六种状态怎样理解？BLOCKED 与 WAITING 有什么区别？
A:
- NEW 尚未启动；RUNNABLE 同时覆盖 JVM 视角的可运行和正在执行，不等于始终占用 CPU。
- BLOCKED 表示等待进入 `synchronized` monitor；它不用于描述 LockSupport 或 Condition 等等待。
- WAITING 是无期限等待，如 `Object.wait()`、`Thread.join()`、`LockSupport.park()`。
- TIMED_WAITING 是有期限等待，如 sleep、带超时 wait/join/park。
- TERMINATED 表示 run 已结束；Java 状态与操作系统线程状态不是一一对应。

## 02-interrupt协议
Q: `interrupt()` 实际做什么？为什么它不是强制杀死线程？
A:
- 中断是协作式取消信号：设置线程中断状态，并使部分阻塞 API 抛 InterruptedException 或提前返回。
- 线程必须在合适边界检查状态、传播 InterruptedException 或执行清理后退出。
- `Thread.interrupted()` 读取并清除当前线程中断状态；`isInterrupted()` 读取指定线程状态但不清除。
- sleep/wait/join 抛 InterruptedException 时通常会清除标志；若不能继续向上抛，应恢复标志 `Thread.currentThread().interrupt()`。
- 强制停止会破坏不变量和资源清理，因此 `Thread.stop` 已废弃。

## 03-取消任务
Q: Future.cancel、超时和线程中断是什么关系？
A:
- `cancel(false)` 尝试阻止尚未开始的任务，通常不打断已运行任务；`cancel(true)` 可请求中断执行线程。
- 是否真正停止取决于任务是否响应中断，以及底层 I/O 是否支持可中断取消。
- `Future.get(timeout)` 超时只停止等待者，不会自动取消后台任务；需要显式 cancel 或上层超时传播。
- 业务超时应沿 RPC、数据库和线程池边界传递 deadline，避免上游放弃而下游继续消耗资源。
- 取消后仍要处理资源关闭、幂等和部分副作用，线程结束不等于业务回滚。

## 04-停止服务
Q: ExecutorService 怎样优雅关闭？
A:
1. `shutdown()` 停止接收新任务，已提交任务继续执行。
2. 在预算时间内 `awaitTermination` 等待。
3. 超时后 `shutdownNow()` 请求中断正在执行任务并返回尚未开始的任务。
4. 再次等待并记录无法终止的任务；业务任务必须实现中断响应。
5. 关闭顺序应先停止流量和上游生产，再耗尽队列，最后关闭依赖资源。

## 05-正确性审查
Q: 中断与取消有哪些危险说法？
A:
- “interrupt 会立即终止线程”：错误，它是协作信号。
- “捕获 InterruptedException 后打印日志即可”：通常错误，会吞掉取消语义。
- “Future.get 超时会杀掉任务”：错误，只是等待超时。
- “shutdownNow 保证线程立刻停止”：错误，只是尝试中断并返回未启动任务。
- “volatile boolean 可替代所有中断”：不行，它不能唤醒 sleep/wait/park 和部分可中断阻塞。
