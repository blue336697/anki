# 虚拟线程与并发限制

> 基线：JDK 21/25，虚拟线程为正式特性。

## 01-调度模型
Q: 虚拟线程、carrier 线程和 continuation 之间是什么关系？
A:
- 虚拟线程是 Java Thread API 的轻量实现，由 JDK 调度器把大量虚拟线程映射到较少平台 carrier 线程。
- 阻塞点可把虚拟线程的 continuation 从 carrier 卸载，carrier 转而运行其他虚拟线程。
- continuation 的栈数据按需保存在堆中并可挂起/恢复，不为每个虚拟线程永久预留完整 OS 线程栈。
- 调度器通常基于 ForkJoinPool，但它不是让业务直接向 commonPool 提交的普通任务池。
- 虚拟线程仍有独立 Thread 身份、异常和 ThreadLocal 语义，只是调度资源模型不同。

## 02-适用场景
Q: 哪类负载适合虚拟线程？为什么 CPU 密集任务不会因此加速？
A:
- 大量相互独立、同步阻塞式、主要等待网络或数据库的任务最受益，可保持直观 thread-per-request 代码。
- CPU 密集任务吞吐受核心数限制，虚拟线程只增加任务数量，可能增加调度和竞争。
- 长时间持有全局锁、单连接池或远端限流时，虚拟线程无法消除真正串行瓶颈。
- 延迟收益取决于下游容量和并发控制；无限放大请求数可能把数据库打崩。
- 迁移应对照吞吐、尾延迟、内存、连接池等待和下游错误率，而不是只比较线程数。

## 03-pinning
Q: 什么是虚拟线程 pinning？怎样发现和治理？
A:
- 虚拟线程执行某些无法卸载的阻塞操作时，会把 carrier 一起占住，降低可扩展性。
- 历史上在 synchronized 临界区内阻塞是典型风险；JDK 新版本持续改进，具体行为必须按目标 JDK 验证。
- native/foreign 调用和不可感知阻塞也可能限制卸载。
- 通过 JFR 的虚拟线程事件、线程 dump 和压测观察 carrier 饥饿，不应仅凭代码里出现 synchronized 判定。
- 治理优先缩短临界区、避免持锁 I/O、升级 JDK/依赖，并验证真实热点。

## 04-不要池化虚拟线程
Q: 为什么不应创建固定大小“虚拟线程池”？并发上限怎样表达？
A:
- 虚拟线程本身很廉价，池化它们会把旧平台线程资源复用模型错误搬过来。
- `Executors.newVirtualThreadPerTaskExecutor()` 为每个任务创建虚拟线程，生命周期与任务一致。
- 数据库连接、远端 QPS、内存和业务配额仍有限，应通过连接池、Semaphore、RateLimiter 或有界入口限制。
- 并发限制应对应稀缺资源，而不是对应“线程”这个代理指标。
- 还要有超时、取消和背压，否则大量挂起任务仍会占堆和业务上下文。

## 05-ThreadLocal
Q: 虚拟线程下还能使用 ThreadLocal 吗？
A:
- 语义上可以，每个虚拟线程仍是 Thread；普通请求上下文通常不会在线程间意外共享。
- 海量线程会放大每线程大对象、缓存和 inheritable ThreadLocal 的内存成本。
- 不要把数据库连接、大缓冲或客户端实例作为 ThreadLocal 缓存；资源应显式管理或池化。
- Scoped Values 旨在改进只读上下文传播，但其稳定状态/API 必须按目标 JDK 核对。
- 迁移前盘点框架和业务 ThreadLocal，关注 remove、继承、线程切换与 observability 上下文。

## 06-正确性审查
Q: 虚拟线程有哪些常见误解？
A:
- “虚拟线程比平台线程执行更快”：不准确，优势主要是阻塞并发可扩展性。
- “用了虚拟线程就不需要连接池”：错误，下游连接仍是稀缺资源。
- “虚拟线程完全没有栈和内存成本”：错误，状态保存在堆中且任务上下文仍占内存。
- “应该按 CPU 核数建立虚拟线程池”：错误，那是 CPU 任务平台线程池的思路。
- “所有阻塞都会自动卸载 carrier”：错误，需关注 pinning 和不可感知阻塞。
