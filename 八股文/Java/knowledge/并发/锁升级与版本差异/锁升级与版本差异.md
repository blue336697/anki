# synchronized 锁升级与版本差异

## 概念卡
Q: synchronized 的锁状态升级想解决什么问题？

A:
- 目标是让不同竞争强度下的锁成本更匹配。
- 无竞争或单线程重复进入时，尽量减少原子指令和系统调用。
- 轻微竞争时，优先短暂自旋，避免线程挂起/唤醒。
- 激烈竞争时，膨胀为重量级锁，让等待线程阻塞，避免持续烧 CPU。

## 机制卡
Q: 偏向锁、轻量级锁、重量级锁分别靠什么降低成本？

A:
- 偏向锁：假设锁长期被同一线程使用，后续进入时尽量避免 CAS。
- 轻量级锁：通过栈上 Lock Record、对象头 Mark Word 和 CAS 尝试获取锁，失败时短暂自旋。
- 重量级锁：竞争激烈时把等待线程挂起，由操作系统/监视器机制协调唤醒。
- 升级方向体现的是竞争越来越强时的成本选择。

## 图示卡
Q: 锁升级流程复习时应该抓住哪条主线？

A:
- 主线不是死背标志位，而是“竞争程度上升，锁实现从便宜路径切到更稳路径”。
- 无锁/CAS：没有互斥，失败重试。
- 偏向锁：偏向同一线程，减少无竞争加锁成本。
- 轻量级锁：CAS + 自旋，避免挂起。
- 重量级锁：阻塞等待，避免高竞争下无限自旋。

## 边界卡
Q: 为什么说“锁升级不能降级”这句话要带限定？

A:
- 面试里可以说对象锁竞争过程中通常是从低成本形态向高成本形态膨胀，避免在竞争期反复来回切换。
- 但不要把它说成所有 JVM、所有时刻、所有实现都绝对不会做任何形式的优化回收。
- 更稳妥的表达是：HotSpot 的经典锁优化模型里，单个对象锁在竞争路径上以升级为主，目的是减少无效自旋和状态震荡。

## 版本审查卡
Q: 偏向锁在新 JDK 中还应该怎么讲？

A:
- 原文按 Java 6/7 的经典模型讲偏向锁，适合理解历史锁优化。
- 但 OpenJDK JEP 374 已在 JDK 15 默认关闭并废弃偏向锁相关选项。
- 所以面试表达要补一句：偏向锁是 HotSpot 曾经的重要优化，现代 JDK 中默认关闭/逐步退出，不能把它当作所有新版本的默认运行状态。
- 如果面试官问 Java 17/21 的 synchronized，不要只背“无锁→偏向锁→轻量级锁→重量级锁”。
