# JDK 11 到 25 的后端关键演进

> 基线：JDK 17、21、25 均为 LTS。区分正式、预览和孵化特性，不把 preview 当成稳定语言能力。

## 01-LTS主线
Q: 五年后端面试为什么应以 JDK 17、21、25 为主线，而不是背每个版本的功能清单？
A:
- LTS 决定多数生产升级节奏；JDK 17 是大量 Spring Boot 3 系统基线，21/25 承载更现代的并发与语言能力。
- 面试重点是能力解决了什么问题、运行时成本和迁移边界，而不是逐版本罗列 JEP。
- JDK 11 到 17 完成模块化后的生态迁移、GC 演进和多项语言增强；JDK 21 正式交付虚拟线程等关键能力。
- JDK 25 是新的 LTS，应关注 compact object headers 等运行时演进及 preview 边界，但不要假设所有项目已升级。
- 回答结构：当前生产版本 → 目标 LTS → 业务收益 → 依赖兼容与回滚计划。

## 02-语言能力时间线
Q: switch、record、sealed class、模式匹配分别何时成为正式特性？
A:
- Switch Expressions 在 JDK 14 正式交付，支持表达式返回值和箭头标签。
- Records 在 JDK 16 正式交付，适合透明数据载体，但不等于所有领域对象都应改为 record。
- Pattern Matching for `instanceof` 在 JDK 16 正式交付。
- Sealed Classes 在 JDK 17 正式交付，用 `permits`/模块或包边界限制可扩展类型集合。
- Pattern Matching for `switch` 在 JDK 17 首次预览，经过多轮预览后于 JDK 21 正式交付；“JDK 17 正式”是错误说法。

## 03-虚拟线程
Q: JDK 21 虚拟线程解决什么问题？它为什么不等于“所有代码自动更快”？
A:
- 虚拟线程把大量阻塞式并发任务映射到少量 carrier 平台线程，显著降低一请求一线程模型的线程资源成本。
- 它适合高并发、任务大部分时间等待网络/数据库的 thread-per-task 服务，不提升纯 CPU 计算吞吐上限。
- 阻塞操作若能被 JDK 感知，虚拟线程可卸载 carrier；某些 native/外部阻塞或 pinning 会限制调度收益。
- 不应池化虚拟线程来“限制数量”；并发限制应由 Semaphore、连接池或业务背压表达。
- ThreadLocal 仍可用但海量虚拟线程会放大复制/内存成本，需重新审视上下文传播与缓存用法。

## 04-JDK21并发边界
Q: Structured Concurrency、Scoped Values 在 JDK 21/25 中应怎样表述？
A:
- 它们用于让并发子任务生命周期和上下文传播更结构化，减少泄漏、丢失异常和 ThreadLocal 滥用。
- 在 JDK 21 中属于 preview；后续版本继续演进，API 和是否正式必须以目标 JDK 的 JEP 状态为准。
- 生产使用 preview 需要 `--enable-preview`，编译和运行版本强绑定，不适合作为跨版本库的默认 API。
- 面试可以讲设计动机和适用场景，但不能把某个 preview API 签名当作长期稳定契约。
- 虚拟线程在 JDK 21 已正式，Structured Concurrency/Scoped Values 的成熟状态不能与它混为一谈。

## 05-GC与运行时演进
Q: JDK 11 到 25 的 GC 主线有哪些真正影响生产选型的变化？
A:
- G1 在 JDK 9 成为 HotSpot 服务端常见默认收集器，并持续改进暂停预测、并发处理和 Region 管理。
- CMS 在 JDK 9 废弃、JDK 14 移除，现代选型不再包含 CMS。
- ZGC 从实验性能力逐步成熟，JDK 15 成为 product feature；JDK 21 交付 Generational ZGC。
- JDK 23 移除非分代 ZGC，使用 ZGC 的现代基线应以分代实现理解。
- Shenandoah 的可用性与支持范围取决于具体 OpenJDK 发行版；不能只看 Oracle JDK 的一个构建推断整个生态。

## 06-模块与封装迁移
Q: 从 JDK 8 升级到 17/21/25，为什么反射和内部 API 往往成为主要阻力？
A:
- JDK 9 引入模块系统和强封装，JDK 16/17 进一步收紧对 JDK 内部包的非法反射访问。
- 依赖 `sun.misc`、私有字段深反射或 `--add-opens` 的框架需要升级；启动参数只能作为过渡债务。
- `javax` 到 `jakarta` 是 Java EE/Jakarta EE 生态迁移，常与 Spring Boot 3 升级同时发生，但不是 JDK 模块化本身。
- 应先升级构建工具、测试框架、字节码库和 agent，再升级业务依赖；使用 `jdeps`、测试和真实流量验证。
- 多版本 JAR、module path 和 class path 混用可能带来 split package、可读性和服务发现问题。

## 07-JDK25视角
Q: 面试中怎样合理谈 JDK 25，而不追逐不稳定新特性？
A:
- 先确认它是 LTS，并说明团队升级价值来自安全支持、运行时改进和已正式特性，而非为了使用所有 preview。
- 重点评估框架、agent、字节码工具、JNI、容器镜像和 GC 行为兼容性。
- 对 compact object headers、值对象相关演进等实现能力必须标注正式/实验/preview 状态和启用条件。
- 新版本压测需覆盖启动、稳态吞吐、尾延迟、内存占用、GC 和故障恢复，不能只通过单元测试宣布兼容。
- 生产策略可采用“17/21 当前基线，25 验证与渐进迁移”，具体取决于组织支持周期。

## 08-正确性审查
Q: JDK 演进卡最容易出现哪些过时错误？
A:
- 把 JDK 17 的 switch pattern matching 写成正式；它在 JDK 21 才正式。
- 把 preview 当稳定 API，忽略 `--enable-preview` 和版本绑定。
- 把 JDK 17 当作“最新 LTS”；当前还应覆盖 21 和 25。
- 把虚拟线程说成更快的 CPU 线程池；它主要改善阻塞并发的可扩展性。
- 把 `javax`→`jakarta`、JPMS 模块化和 JDK 内部 API 强封装混成同一件事。
