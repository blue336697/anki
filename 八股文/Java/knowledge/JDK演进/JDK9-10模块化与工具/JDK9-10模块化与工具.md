# JDK 9–10 模块化、运行时映像与工具

## 01-JPMS目标
Q: JPMS 解决 classpath 的哪些结构性问题？
A:
- classpath 只有扁平搜索路径，缺少可靠依赖声明、强封装和重复模块诊断。
- `module-info.java` 声明 requires、exports、opens、uses、provides，让依赖与可见性进入编译/运行模型。
- 模块可读性决定是否能引用另一模块，exports 决定普通访问，opens 主要允许深反射。
- JPMS 提高大型系统和 JDK 自身可维护性，但不会自动消除 Maven 版本冲突。
- 未命名模块为 classpath 兼容提供过渡，迁移可以分阶段进行。

## 02-运行时映像
Q: JDK 9 为什么取消 `rt.jar`/`tools.jar`？类资源怎样访问？
A:
- JDK 自身被拆分为模块并存放在实现定义的运行时映像，不再把核心类集中在 `jre/lib/rt.jar`。
- `jrt:/` 文件系统提供遍历运行时模块、类和资源的标准访问入口。
- Bootstrap/Platform/Application ClassLoader 的职责随模块化调整，旧 Extension ClassLoader/扩展目录机制退出。
- 旧工具若扫描 rt.jar、依赖 `java.ext.dirs` 或内部目录布局，需要迁移到模块和标准 API。
- 模块化不意味着 JVM 启动时曾经会“把整个 rt.jar 全部加载进内存”；那是错误因果解释。

## 03-jlink
Q: `jlink` 与普通 JDK/JRE 部署有什么不同？
A:
- jlink 从一组模块及其依赖链接出定制运行时映像，只包含应用需要的 JDK 模块和资源。
- 收益是镜像更小、攻击面和无关模块更少，并可结合容器部署。
- 动态反射、ServiceLoader、JNI 和资源依赖若未正确声明，裁剪后可能在运行时失败。
- jdeps 可辅助分析依赖，但动态行为仍需集成测试。
- jlink 生成的是运行时映像，不等于 GraalVM native image，应用仍运行在 JVM 上。

## 04-var与局部推断
Q: JDK 10 的 `var` 能推断什么，不能推断什么？
A:
- var 只用于有初始化器的局部变量等允许位置，编译器仍生成静态确定类型。
- 它不是 JavaScript 式动态类型，后续赋值仍受推断类型约束。
- 不能用于字段、普通方法参数或无初始化局部变量。
- 适合类型显而易见或泛型极长的局部表达式；若隐藏关键领域类型会降低可读性。
- API 签名仍应显式表达稳定契约。

## 05-兼容风险
Q: 从 JDK 8 迁移到模块化 JDK，常见失败点是什么？
A:
- 使用已移除 Java EE/CORBA 模块、内部 `sun.*` API、扩展目录或 endorsed standards。
- 依赖深反射访问未 opens 的包，在强封装版本中失败。
- split package、自动模块名变化、module path/classpath 混用和重复模块。
- 老旧字节码工具、agent、测试框架无法识别新 class 版本或模块边界。
- `--add-opens/--add-exports` 可临时过渡，但应登记债务并推动依赖升级。

## 06-正确性审查
Q: JDK 9 模块化有哪些常见误解？
A:
- “模块化就是 Maven 依赖管理”：错误，二者分别处理运行时/语言模块边界与构建依赖。
- “JDK 8 会加载整个 rt.jar 所有类”：错误，jar 文件存在不等于全部类已加载。
- “exports 等于 opens”：错误，普通访问与深反射开放不同。
- “jlink 等于 native image”：错误，前者仍是 JVM 运行时映像。
- “迁移只需添加 module-info”：错误，内部 API、反射、工具链和动态资源都要验证。
