# Java 值传递与引用语义

## 01-参数传递
Q: Java 到底是值传递还是引用传递？
A:
- Java 方法调用只有值传递：形参获得实参值的一份副本。
- 基本类型复制数值；引用类型复制“引用值”，形参与实参可通过各自引用访问同一对象。
- 方法内修改对象字段会影响共享对象；把形参重新赋给新对象不会改变调用者变量保存的引用值。
- “传对象所以是引用传递”混淆了被复制的值是什么与传递机制。
- 验证时分别画变量槽、引用值和堆对象，避免把变量与对象画成同一个节点。

## 02-对象别名
Q: 什么是 aliasing？它为什么是可变对象 bug 的根源之一？
A:
- 多个变量保存指向同一可变对象的引用时，它们互为别名；任一路径修改对象，其他路径都能观察到。
- 防御性复制、不可变对象和清晰所有权可以减少别名导致的隐式耦合。
- 浅拷贝只复制顶层字段，嵌套引用仍共享；深拷贝需要定义对象图边界、循环和外部资源语义。
- 集合的 `unmodifiableList` 通常只是只读视图，底层集合被其他引用修改时视图仍变化。
- API 设计应说明入参/返回值是否借用、转移所有权或复制，不能只靠调用者猜测。

## 03-final引用
Q: `final` 引用、不可变对象和线程安全是什么关系？
A:
- final 引用不能重新指向另一对象，但被引用对象的字段仍可能变化。
- 不可变对象要求构造后可观察状态不再变化，通常还需类不可扩展、字段私有 final、对可变成员防御性复制。
- 正确构造的 final 字段有初始化安全语义，但不自动保护其指向对象的后续修改。
- 不可变对象天然便于并发共享；“final 集合”仍可能被并发修改。
- 面试必须把“引用不可变”“对象不可变”“线程安全”三个层次拆开。

## 04-返回值与逃逸
Q: 方法返回内部可变对象为什么会破坏封装？
A:
- 返回内部 List、数组、Date 等真实引用，会让调用者绕过校验直接修改对象内部状态。
- 可以返回不可变快照、复制品或受控接口；选择取决于对象大小、更新频率和一致性要求。
- 返回 Stream/Iterator 也可能间接暴露生命周期，底层资源关闭和并发修改边界需明确。
- 高性能场景不应无脑深拷贝，可通过只读数据结构、版本化快照或所有权协议控制成本。
- 单元测试应验证调用者修改返回值是否能反向污染对象。

## 05-正确性审查
Q: 值传递有哪些常见错误说法？
A:
- “Java 基本类型值传递、对象引用传递”：错误，二者都是值传递，只是值的种类不同。
- “修改形参对象等于修改实参”：不精确，修改的是双方引用共同指向的对象。
- “final 对象不能修改”：错误，final 约束变量重新赋值。
- “浅拷贝就是完全独立副本”：错误，嵌套引用通常仍共享。
- “不可修改视图等于不可变快照”：错误，视图可能随底层数据变化。
