# Spring 缓存、异步、事件与调度

## 01-共同代理边界
Q: `@Cacheable`、`@Async`、`@Scheduled` 与事务有哪些共同边界？
A:
- 多数注解能力由后处理器和代理/调度基础设施实现，不是注解本身改写方法体。
- 自调用、直接 new 对象、非容器 Bean 或不可代理方法可能绕过拦截。
- 多切面顺序会改变事务提交、缓存写入和异步线程切换时机。
- 线程切换后 ThreadLocal、SecurityContext、MDC 和事务资源默认不会天然完整传播。
- 应用必须用集成测试验证真实代理和线程边界。

## 02-缓存语义
Q: `@Cacheable` 能否保证缓存与数据库强一致？
A:
- Cache interceptor 通常在调用前查缓存，未命中才执行目标方法并按规则写入。
- 它不能自动让缓存写和数据库事务成为原子操作；回滚、并发 miss 和跨节点失效仍需设计。
- key 设计必须包含影响结果的全部维度，避免租户、权限或版本串数据。
- null、异常、条件缓存和序列化格式需要明确策略。
- 高并发击穿需单飞、分布式锁、逻辑过期或后端限流，不能只加注解。

## 03-Async
Q: `@Async` 为什么常出现线程池耗尽和异常丢失？
A:
- 调用经代理后把任务提交给指定 Executor，调用线程通常立即返回。
- void 异步方法异常不会回到调用者，需要 AsyncUncaughtExceptionHandler 或显式日志指标。
- Future/CompletableFuture 应由调用方处理异常、超时和取消。
- 默认/共享线程池不应承载所有业务；必须设置容量、队列、拒绝策略和监控。
- 异步不等于削峰，若入口无背压只是把压力移到内存队列。

## 04-事件
Q: Spring ApplicationEvent 是进程内消息队列吗？
A:
- 默认事件发布通常在调用线程同步执行 listener；慢 listener 会直接拖慢发布者。
- 配置异步 multicaster 或 `@Async` 后才发生线程切换，同时失去原线程事务/上下文的天然边界。
- TransactionalEventListener 可绑定事务阶段，但 after-commit 中继续写库需谨慎处理新事务。
- 进程崩溃会丢失普通内存事件，它不替代可靠 MQ/outbox。
- 事件适合模块解耦和生命周期通知，可靠跨服务交付要使用持久化机制。

## 05-Scheduled
Q: `@Scheduled` 任务在集群中为什么可能重复执行？
A:
- 每个应用实例都会注册并触发本地调度，扩容后同一任务会在多个实例执行。
- 需要单实例语义时使用分布式锁、调度平台或任务分片，并设计租约超时和 fencing。
- fixedRate、fixedDelay、cron 的下一次计算语义不同；长任务和时区/DST 会影响实际触发。
- 任务必须幂等、可重试、可观测，并有防重和补偿。
- 不要在默认 scheduler 上运行无限阻塞任务。

## 06-正确性审查
Q: 缓存、异步、事件和调度有哪些误区？
A:
- “加 @Async 就一定另起线程”：自调用或代理失效时不成立。
- “@Cacheable 保证数据库缓存一致”：错误。
- “Spring 事件默认异步”：错误，默认常为同步。
- “@Scheduled 集群只执行一次”：错误，每实例都会调度。
- “异步队列越大越安全”：错误，无界队列会隐藏过载并放大内存与超时。
