# Spring AOP 代理与拦截器链

## 01-代理选择
Q: Spring AOP 何时使用 JDK 动态代理或类代理？
A:
- JDK 动态代理基于接口生成代理，目标类型对外主要按接口暴露时适合。
- 类代理通过 CGLIB/字节码生成目标类子类，可代理未抽取接口的方法，但 final 类/方法有天然限制。
- Spring Boot/Framework 的默认选择受配置和版本影响，不能永远背“有接口必用 JDK”。
- 代理对象类型会影响按具体类注入、`getClass()`、序列化和反射行为。
- 选择应以契约和限制为核心，不应为了代理强行改变业务 API。

## 02-调用链
Q: 一次代理方法调用怎样经过 Advisor 和 MethodInterceptor？
A:
1. 代理根据目标方法和目标类匹配可用 Advisor/Pointcut。
2. 匹配结果转换成有序拦截器链。
3. `MethodInvocation.proceed()` 逐个调用 interceptor；每个 interceptor 可在前后增加行为、短路或抛异常。
4. 链末端通过反射/方法句柄等路径调用目标方法。
5. 事务、缓存、异步等功能本质上都可能以不同拦截器加入链，顺序会影响组合语义。

## 03-自调用
Q: 为什么同类 `this.method()` 常导致事务、缓存或异步失效？
A:
- 外部调用先进入代理，代理才有机会执行拦截器链。
- 目标对象内部 `this` 调用直接分派到自身方法，不重新经过外围代理。
- 解决方案优先拆分职责到另一个 Bean；也可使用代理自注入或 AspectJ，但会增加耦合/复杂度。
- 把方法改 public 只解决可代理性的一部分，不会让 `this` 调用自动穿过代理。
- 测试必须从容器获取 Bean 并走真实调用边界，直接 new 目标对象无法验证切面。

## 04-切面顺序
Q: 事务、重试、缓存等多个切面叠加时，顺序为什么会改变结果？
A:
- 外层 interceptor 包裹内层；谁先进入也通常最后退出，类似嵌套函数。
- “重试包事务”可让每次重试拥有新事务；“事务包重试”可能让所有尝试处于同一已回滚标记事务中。
- 缓存若在事务提交前写入，回滚后可能留下未提交结果对应的缓存。
- 顺序由 `Ordered`、`@Order` 和框架默认值共同决定，不能靠注解书写顺序猜测。
- 关键组合要写集成测试并观察实际 Advisor 链。

## 05-正确性审查
Q: Spring AOP 有哪些常见误解？
A:
- “AOP 修改了目标类源码”：错误，常见 Spring AOP 通过代理拦截调用。
- “private 方法加事务也生效”：通常不通过代理调用，不能这样依赖。
- “有接口一定是 JDK 代理”：取决于代理配置与版本。
- “自调用失效是事务独有问题”：错误，所有依赖同一代理边界的切面都可能受影响。
- “切面顺序无所谓”：错误，事务、重试、缓存组合尤其敏感。
