# Spring 事务拦截、传播与资源绑定

## 01-执行链
Q: `@Transactional` 方法从代理入口到提交的大体链路是什么？
A:
1. 事务 interceptor 解析方法/类上的 TransactionAttribute。
2. 根据 qualifier、数据源等选择 PlatformTransactionManager。
3. `getTransaction` 检查当前线程是否已有事务，并按传播行为加入、挂起或创建事务。
4. 调用目标方法；正常返回则按状态提交，异常则按 rollback rule 决定回滚或提交。
5. 最终清理线程绑定资源并恢复被挂起事务。

## 02-线程资源绑定
Q: Spring JDBC 事务为什么能让多个 DAO 复用同一连接？
A:
- DataSourceTransactionManager 从 DataSource 获取 Connection，并通过 TransactionSynchronizationManager 绑定到当前线程。
- DAO 经 DataSourceUtils 获取连接时会复用线程绑定的 Connection，而不是每次创建独立物理事务。
- 提交/回滚后事务管理器解绑并释放连接。
- 跨线程执行不会自动继承这个绑定；`@Async`、新线程和 CompletableFuture 常落入新事务边界。
- 连接池只负责复用物理连接，不等于自动建立 Spring 事务语义。

## 03-传播行为
Q: REQUIRED、REQUIRES_NEW、NESTED 的物理资源语义有什么区别？
A:
- REQUIRED 有现有事务就加入，没有则新建；内层设置 rollback-only 可能导致外层提交时 UnexpectedRollbackException。
- REQUIRES_NEW 挂起外层事务并获取独立事务/连接；高并发嵌套会增加连接池需求。
- NESTED 常借助同一物理事务的 savepoint，实现局部回滚后外层可继续；能力取决于事务管理器和资源。
- SUPPORTS/MANDATORY/NOT_SUPPORTED/NEVER 主要控制有无事务上下文，不应只背中文名称。
- 传播只在代理调用边界生效，同类自调用无法触发新的传播决策。

## 04-回滚规则
Q: Spring 默认为什么只对 RuntimeException/Error 回滚？怎样避免误用？
A:
- 默认规则沿用 unchecked exception 表达程序/业务失败、checked exception 可由调用者处理的传统。
- 业务若以 checked exception 表达必须回滚，应显式配置 rollbackFor 或统一异常策略。
- 捕获异常后正常返回，拦截器看不到失败；需要重新抛出或显式标记 rollback-only。
- 数据库已执行但外部消息/缓存操作不受本地事务自动保护，必须设计 outbox、幂等或补偿。
- 事务方法返回异步结果时，提交点与异步失败点可能分离，需要重新设计边界。

## 05-隔离与Spring
Q: `@Transactional(isolation=...)` 能否消除所有并发一致性问题？
A:
- 它请求数据库事务隔离级别，实际支持和行为由数据库、驱动和连接池决定。
- 隔离级别不代替唯一约束、乐观锁、幂等键和正确的业务不变量。
- 加入已有事务时，内层声明的隔离/只读/超时通常不能任意改变已经建立的物理事务。
- readOnly 多为优化提示和写保护协作，不是跨数据库一致的安全沙箱。
- 必须把 Spring 传播与数据库 MVCC/锁行为分层回答。

## 06-正确性审查
Q: Spring 事务哪些说法最危险？
A:
- “加注解一定生效”：代理边界、方法可见性、Bean 管理和异常处理都会影响。
- “REQUIRES_NEW 更安全”：它消耗额外连接并打破与外层原子性。
- “NESTED 等于新事务”：通常是同一物理事务 savepoint。
- “事务能回滚 MQ 和 HTTP”：本地数据库事务不会自动覆盖外部系统。
- “连接池有连接复用所以自动同一事务”：错误，关键是事务管理器的线程资源绑定。
