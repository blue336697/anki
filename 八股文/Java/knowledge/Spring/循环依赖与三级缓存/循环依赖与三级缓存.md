# Spring 循环依赖与三级缓存

## 01-适用边界
Q: Spring 能解决哪些循环依赖，哪些不能？
A:
- 经典三级缓存机制主要针对 singleton、setter/字段注入形成的属性循环。
- 构造器循环在实例化前双方都需要完整依赖，无法通过暴露半成品打破。
- prototype 循环通常不能自动解决，因为容器不维护 singleton 那套创建中缓存。
- Spring Boot 默认策略和是否允许循环引用会随版本/配置变化，工程上不应依赖“容器总能兜底”。
- 循环依赖往往暴露职责纠缠，应优先重构边界，而不是把三级缓存当设计模式。

## 02-三级缓存
Q: singletonObjects、earlySingletonObjects、singletonFactories 分别保存什么？
A:
- `singletonObjects` 保存完成创建、可正常使用的一级 singleton。
- `earlySingletonObjects` 保存已经提前暴露并被实际取用的早期引用。
- `singletonFactories` 保存可生成早期引用的 ObjectFactory，允许在真正需要时决定暴露原对象还是早期代理。
- 创建 A 时先注册 factory，再填充依赖 B；B 回查 A 时从三级获取早期引用并提升到二级。
- A 完成初始化后进入一级缓存并清理早期缓存状态。

## 03-为什么三级
Q: 为什么只用“成品缓存 + 半成品缓存”不够？
A:
- 关键不是缓存层数本身，而是延迟创建 early reference 的工厂。
- AOP 场景下，依赖方应尽量拿到与最终暴露一致的代理引用，不能先注入原对象、最后再换代理。
- `getEarlyBeanReference` 给自动代理创建器机会提前生成或记录代理。
- 如果没有循环依赖，factory 通常不会被调用，避免所有 Bean 都过早代理。
- 自定义后处理器若在早期与最终阶段返回不一致对象，仍可能触发 raw injection 或身份不一致问题。

## 04-代理冲突
Q: 循环依赖与 AOP 同时存在时为什么更危险？
A:
- B 可能在 A 完整初始化前拿到 A 的早期代理；A 的部分状态和其他依赖尚未完成。
- 若最终代理与早期引用不是同一身份，容器会检测到其他 Bean 已注入 raw/不同版本引用。
- 构造或初始化期间调用跨 Bean 方法，还可能绕过期望的切面或访问半初始化状态。
- 多个代理创建器、手工包装 BeanPostProcessor 会放大不一致风险。
- 最稳妥方案是打破依赖环，或抽取第三个协调组件/事件边界。

## 05-正确性审查
Q: 三级缓存有哪些错误口诀？
A:
- “三级缓存解决所有循环依赖”：错误，只覆盖特定 singleton 属性循环。
- “二级缓存存代理、三级缓存存原对象”：过度简化，三级保存 factory，二级保存实际早期引用。
- “循环依赖完全无害”：错误，半初始化暴露和代理身份都会增加风险。
- “加 @Lazy 一定解决”：它可能延迟依赖，但会改变失败时机且不一定消除设计耦合。
- “Spring 为了循环依赖才有所有缓存”：错误，一级 singleton 缓存首先承担正常单例管理。
