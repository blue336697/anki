# JVM 体系与类加载器

> 基线：JDK 21/25 HotSpot。涉及 JDK 8 的 `rt.jar`、Extension ClassLoader 等内容只作为历史差异。

## 01-JVM执行链
Q: 一段 Java 代码从源码到在 CPU 上执行，完整链路是什么？
A:
- `javac` 把源码编译为平台无关的 class 文件；class 文件保存常量池、字段、方法、字节码和验证所需的结构化元数据。
- 类加载子系统按需完成加载、验证、准备、解析和初始化，把类型元数据放入 JVM 管理的运行时结构。
- 解释器逐条解释热点尚不明确的字节码；分层编译器根据计数器和 profiling 把热点方法编译成本地机器码。
- 运行期间可能发生内联、逃逸分析、标量替换，也可能因假设失效去优化并退回解释执行。
- GC、Safepoint、线程调度和 JNI 与执行引擎协作；“Java 一次编译到处运行”依赖的是统一 class 语义与各平台 JVM，而不是 CPU 直接执行字节码。

## 02-JDK21类加载器层次
Q: JDK 21 中内置类加载器怎样分工？为什么不能再背 `rt.jar` 模型？
A:
- Bootstrap ClassLoader 由虚拟机实现，负责定义 `java.base` 等引导模块中的核心类；Java 层通常看到其父加载器为 `null`。
- Platform ClassLoader 加载平台模块及升级模块路径中的类，是 JDK 9 之前 Extension ClassLoader 的继任者。
- Application ClassLoader 通常从 class path 和 module path 为应用定义类；它不是“加载所有用户类”的绝对边界，自定义加载器仍可参与。
- JDK 9 起运行时类放在模块化运行时映像中，可通过 `jrt:/` 访问，不再位于 `JAVA_HOME/jre/lib/rt.jar`。
- 父子关系描述的是委派链，不等于 Java 类继承关系，也不意味着父加载器能看到子加载器定义的类。

## 03-双亲委派
Q: 双亲委派的实际加载流程是什么？它解决了什么问题？
A:
1. `ClassLoader.loadClass` 先查 `findLoadedClass`，避免同一加载器重复定义。
2. 未命中时通常先委派父加载器；父加载器找不到，当前加载器才调用 `findClass`。
3. Bootstrap 没有普通 Java 对象，委派到它常通过内部 native 路径完成。
4. 该策略让核心 API 优先由可信加载器定义，减少应用伪造 `java.lang.String` 等核心类型的机会。
5. 它也让公共依赖更容易共享，但不是完整安全边界；模块可读性、包封装、签名、Security Manager 历史机制属于其他层面。

## 04-类身份与隔离
Q: JVM 如何判断两个类是不是同一个类型？类加载隔离为什么会产生 ClassCastException？
A:
- 运行时类型身份由“二进制类名 + 定义它的 ClassLoader”共同决定，只比较全限定名不够。
- 同一份字节码若被两个互不相同的加载器分别定义，会得到两个不兼容的 `Class` 对象。
- 应用服务器、插件系统、热部署和测试隔离会利用这个能力实现版本隔离，也可能出现“明明类名相同却不能强转”。
- 跨加载器共享 DTO 或接口时，应把契约类放到共同父加载器可见的位置，或通过序列化、反射、标准协议跨越边界。
- 排障时同时打印类名、`getClassLoader()`、模块和 protection domain，不能只看异常里的类名。

## 05-打破委派与上下文加载器
Q: 哪些场景会打破普通父优先委派？线程上下文类加载器解决什么问题？
A:
- SPI 的接口常由平台或框架加载，但实现由应用提供；父加载器无法向下看到子加载器的实现。
- `ServiceLoader` 可使用线程上下文类加载器，从调用线程所在应用的可见范围发现提供方，实现“父层 API 调用子层实现”。
- Web 容器和插件框架可能采用 child-first 或局部父优先，以隔离应用依赖；这不是随意重写 `loadClass`，而是明确的可见性策略。
- OSGi/JPMS 还增加导出、读取和模块边界；类“能找到”不代表模块允许访问。
- 自定义加载器必须正确处理并发加载、包定义、资源关闭和卸载引用，否则会导致 LinkageError 或 Metaspace 泄漏。

## 06-类卸载
Q: 一个类什么时候才可能被卸载？为什么热部署常造成 Metaspace 泄漏？
A:
- 类卸载的核心前提是其定义 ClassLoader 不再可达；只让某个 `Class` 对象局部变量出作用域并不够。
- 加载器定义的类、静态字段和常量池通常形成一个生命周期集合；加载器活着，这批类型元数据通常也活着。
- 线程上下文加载器、ThreadLocal、定时任务、全局缓存、JDBC Driver、日志框架回调都可能从长生命周期对象反向引用旧加载器。
- 发生支持类卸载的 GC 周期后，JVM 才可能回收对应 Metaspace；是否立即发生取决于收集器与触发条件。
- 排障用 class histogram、JFR、heap dump 和 `jcmd VM.classloader_stats` 找仍存活的加载器及引用链。

## 07-正确性审查
Q: 类加载面试中哪些常见说法需要修正？
A:
- “Bootstrap 加载 `rt.jar`”：只适用于旧 JDK；JDK 9+ 使用模块化运行时映像。
- “双亲委派不能被破坏”：错误。它是默认约定，容器、SPI 和插件系统有受控的不同策略。
- “同名类就是同一个类”：错误，还必须由同一个定义加载器定义。
- “加载完成就执行静态代码”：错误。加载、链接与初始化是不同阶段，初始化还受主动使用规则约束。
- “类卸载等于对象回收”：错误。类卸载以定义加载器不可达为关键条件，通常整批发生。
