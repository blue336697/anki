# 类加载、链接与初始化状态机

> 基线：Java SE 21/25 规范语义与 HotSpot 实现。类生命周期阶段、初始化触发条件和失败状态分开回答。

## 01-完整生命周期
Q: 一个类从二进制名字到可执行类型，完整生命周期有哪些阶段？
A:
- 加载：根据二进制名字取得 class 二进制表示，创建 JVM 内部类型表示及对应 `Class` 镜像。
- 链接由验证、准备、解析组成；规范允许解析在首次主动使用前后按实现策略惰性发生。
- 初始化执行类或接口初始化方法 `<clinit>`，把静态初始化逻辑真正应用到类状态。
- 使用阶段包含实例创建、静态调用、反射、方法句柄和 JIT 编译等运行行为。
- 卸载以定义 ClassLoader 不可达为核心前提；不是某个实例回收后该类就立即卸载。

## 02-加载与defineClass
Q: ClassLoader 从字节流定义类时，JVM 做了哪些关键约束？
A:
1. `loadClass` 通常先查找已加载类，再按委派策略尝试父加载器，最后调用当前加载器的 `findClass`。
2. `findClass` 从文件、网络、加密包等来源取得字节，调用 `defineClass` 建立运行时类型。
3. JVM 检查二进制名字、受保护包、重复定义、包与签名信息，非法输入会产生 ClassFormatError、SecurityException 或 LinkageError。
4. 同一个定义加载器不能以同一二进制名字重复定义不同类；不同加载器可定义同名但类型身份不同的类。
5. `resolveClass` 可显式请求链接，但多数应用只需覆盖 `findClass`，不应随意破坏 `loadClass` 的并发与委派控制。

## 03-验证
Q: 字节码验证为什么不是“检查文件头”这么简单？
A:
- 文件格式验证检查 magic、版本、常量池索引、属性长度和结构合法性，防止解析越界或畸形 class。
- 类型与控制流验证确保操作数栈类型、局部变量类型、跳转目标、返回值和异常处理路径一致。
- 符号引用验证确保访问控制、字段/方法描述符和最终解析目标满足 JVM 约束。
- `StackMapTable` 给验证器提供控制流合流点的类型状态，减少从头推导数据流的成本。
- 验证保障 JVM 执行安全，但不证明业务逻辑正确，也不能替代依赖来源和供应链安全。

## 04-准备与解析
Q: 准备阶段和解析阶段分别改变什么？`static final` 为什么有时不等到 `<clinit>`？
A:
- 准备阶段为类变量建立存储并设置初始值；普通 `static int x = 10` 此时先是零值，赋 10 属于初始化逻辑。
- 带 `ConstantValue` 属性的编译期常量可在准备阶段得到常量值，例如基本类型或 String 的常量表达式。
- 解析把常量池中的类、字段、方法、接口方法等符号引用转换为运行时可直接定位的引用或解析结果。
- JVM 可按需惰性解析；因此“链接完成时所有被引用类都已加载解析”不是可靠结论。
- 解析失败常表现为 NoSuchFieldError、NoSuchMethodError、IllegalAccessError 等 LinkageError，通常指向编译期与运行时依赖不一致。

## 05-初始化触发
Q: 哪些行为会触发类或接口初始化？哪些只是被动使用？
A:
- `new`、`getstatic`、`putstatic`、`invokestatic` 首次主动使用声明目标类的非常量静态成员时会触发初始化。
- 反射调用、方法句柄/动态调用的特定首次使用、初始化启动主类，也会按规范触发相关初始化。
- 初始化子类前必须先初始化其父类；初始化类不会因此把所有实现接口或子类一起初始化。
- 读取编译期常量可能已被内联到调用方，不触发声明类初始化；创建引用类型数组也不初始化元素类型。
- 通过子类名读取父类声明的静态字段，通常只初始化真正声明该字段的父类。

## 06-clinit状态机
Q: 多线程同时初始化一个类时，JVM 怎样保证 `<clinit>` 只成功执行一次？
A:
- 每个类/接口有初始化状态与对应同步过程：未初始化、正在由某线程初始化、已初始化或初始化失败。
- 抢到初始化权的线程执行父类初始化和本类 `<clinit>`；其他线程等待状态转换。
- 同一线程在初始化过程中递归请求同一类时允许继续，避免单线程自递归死锁。
- 成功后状态变为已初始化，等待线程被唤醒，并获得初始化写入的可见性。
- 两个线程分别初始化 A、B，而各自 `<clinit>` 又等待对方类型，仍可能形成类初始化死锁。

## 07-初始化失败
Q: `<clinit>` 抛异常后，为什么后续访问常看到 NoClassDefFoundError？
A:
- 首次执行 `<clinit>` 的线程若抛出非 Error 异常，JVM 通常用 ExceptionInInitializerError 包装并标记该类初始化失败。
- 该 `Class` 在当前定义加载器命名空间中进入 erroneous 状态，不会在下一次访问时自动重新执行初始化。
- 之后其他线程主动使用该类通常得到 `NoClassDefFoundError: Could not initialize class`，它不是“找不到 class 文件”。
- 修复配置后若仍在同一 JVM/加载器中，失败状态不会自然重置；通常需要更换加载器或重启相应应用上下文/进程。
- 排障必须保留第一次初始化失败的原始异常，它通常比后续 NoClassDefFoundError 更接近根因。

## 08-接口初始化
Q: 接口初始化与类初始化有哪些关键差异？
A:
- 接口字段隐式为 `public static final`，但只有编译期常量可直接内联；运行期表达式仍需要接口初始化。
- 初始化一个类要求其父类先初始化，但不要求所有父接口先初始化；真正使用接口的非编译期静态成员时才初始化它。
- 初始化一个接口也不会自动初始化它的子接口或实现类。
- 接口可以因默认方法等规则影响类初始化前置集合，具体边界应以目标 Java SE 规范版本为准。
- 不能用“接口没有 `<clinit>`”概括；接口存在运行期静态初始化表达式时同样可生成初始化方法。

## 09-加载器约束与LinkageError
Q: 为什么依赖冲突有时不是 ClassNotFoundException，而是 LinkageError 或 ClassCastException？
A:
- ClassNotFoundException 通常表示显式加载请求的加载器无法找到二进制定义；NoClassDefFoundError 还可能表示曾找到但定义/初始化失败。
- NoSuchMethodError、NoSuchFieldError 常表示调用方按一个版本编译，运行时解析到另一个不兼容版本。
- ClassCastException 若显示两个相同类名，常是它们由不同定义加载器加载，运行时类型身份不同。
- Loader constraint violation 表示 JVM 为保证方法签名类型一致而发现两个加载器解析出了不兼容类型。
- 排障应输出类来源、模块、ProtectionDomain、定义加载器和依赖树，而不是只补一个 jar 重试。

## 10-类卸载与验证
Q: 怎样证明类能够卸载，并定位 ClassLoader 泄漏？
A:
- 卸载要求定义 ClassLoader 不再被线程、静态字段、ThreadLocal、JNI、缓存或框架注册表引用。
- 一个加载器通常连带其定义的整组类和静态状态一起存活或卸载。
- 触发支持类卸载的 GC 后，用 `jcmd VM.classloader_stats`、JFR、class histogram 和 heap dump 对比加载器数量。
- heap dump 中追踪旧加载器到 GC Roots 的路径，常见保留者是线程上下文加载器、定时任务、DriverManager 和日志/序列化缓存。
- “Class 对象没业务引用”不足以证明可卸载；关键是定义加载器及其整张对象图是否不可达。

## 11-正确性审查
Q: 类生命周期有哪些必须纠正的面试口诀？
A:
- “加载、验证、准备、解析、初始化严格连续一次完成”：不严谨，解析可按需惰性发生。
- “访问 static final 一定不初始化类”：错误，只有编译期常量可被内联；运行期表达式仍触发初始化。
- “初始化失败下次会自动重试”：错误，同一 Class 通常保持失败状态。
- “ClassNotFoundException 与 NoClassDefFoundError 都只是缺 jar”：错误，后者还可能来自链接或初始化失败。
- “类的唯一性只看全限定名”：错误，还要看定义它的 ClassLoader。
