# JIT 分层编译、优化与去优化

## 01-解释与编译
Q: HotSpot 为什么同时需要解释器和 JIT？
A:
- 解释器启动快、无需等待编译，适合冷代码和收集运行时 profile。
- JIT 对热点方法/循环编译成本地代码，用运行时类型、分支概率和调用频率进行激进优化。
- 分层编译在启动速度、profile 质量和峰值性能之间折中，典型地由 C1/C2 等层级协作。
- 方法调用计数和回边计数触发编译，但阈值与策略是版本实现细节。
- AOT/原生镜像减少暖机但失去部分动态 profile 优化能力，是不同成本模型。

## 02-内联
Q: 方法内联为什么是 JIT 最关键的优化之一？
A:
- 内联消除调用开销，更重要的是把调用者与被调用者放入同一优化范围。
- 内联后可继续常量传播、死代码消除、逃逸分析和循环优化。
- 是否内联受方法大小、调用热度、类型 profile、多态程度和编译预算影响。
- 巨大方法、调用点高度多态或频繁变化会降低内联机会。
- 不应通过手工复制代码“帮助内联”；应使用编译日志/JITWatch验证瓶颈。

## 03-推测优化与去优化
Q: JIT 为什么敢基于“当前只有一个实现类”优化？假设失效怎么办？
A:
- JVM 收集运行时 profile，在调用点当前单态时可做推测内联和类型检查消除。
- 新类加载或实际类型变化使假设失效时，JVM 会使相关 nmethod 失效并触发 deoptimization。
- 执行状态通过调试/作用域元数据重建为解释器可继续执行的帧。
- 反复编译和去优化会造成性能抖动，常见于类型形态不稳定或类动态生成。
- “JIT 编译后机器码永远不变”是错误的，动态适应正是 JVM 性能模型的一部分。

## 04-逃逸与锁消除
Q: JIT 能怎样消除对象和锁？
A:
- 对不逃逸对象可做标量替换，把字段拆成局部标量并消除分配。
- 对只在线程内可见的锁对象可做锁消除，避免无意义 monitor 操作。
- 优化依赖完整编译图和 profile；反射、复杂调用、多态和去优化会限制效果。
- 即使源码写了 new 或 synchronized，最终机器码也可能不存在对应动作。
- 基准测试必须使用 JMH，避免死代码消除、常量折叠和未暖机结果。

## 05-CodeCache
Q: Code Cache 满了会发生什么？怎样识别？
A:
- JIT 生成的本地代码、stubs 和相关数据存放在 Code Cache 的不同区域。
- 空间紧张可能导致编译受限或停止，应用退回较低层级/解释执行并出现吞吐下降。
- 动态生成大量类/方法、agent 和长时间运行服务可能增加压力。
- 通过 `jcmd Compiler.codecache`、JFR 和编译日志观察使用量、编译失败和 sweeping。
- 不应看到 Code Cache 高就盲目增大；先确认动态代码和编译行为是否异常。

## 06-正确性审查
Q: JIT 面试有哪些错误结论？
A:
- “Java 代码只解释执行”或“启动时全部编译”：都错误，HotSpot 动态分层执行。
- “热点代码只按调用次数判断”：过度简化，还有回边计数、profile 和编译策略。
- “对象一定真实分配在堆”：JIT 可能标量替换或消除。
- “内联只是减少方法调用开销”：不完整，它打开跨方法优化空间。
- “机器码生成后永久有效”：错误，推测假设失效会去优化和重编译。
