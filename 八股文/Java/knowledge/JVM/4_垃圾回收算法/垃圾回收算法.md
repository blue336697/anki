# 可达性分析与垃圾回收算法

> 基线：JDK 21/25 HotSpot；算法名是设计模型，具体收集器通常组合多种技术。

## 01-GC Roots
Q: JVM 如何判断对象是否存活？常见 GC Roots 有哪些？
A:
- 主流 JVM 使用可达性分析：从一组 Roots 沿引用关系遍历，不可达对象才进入可回收候选。
- 常见 Roots 包括线程栈和寄存器中的引用、类静态字段引用、JNI 全局/局部句柄、JVM 内部数据结构。
- 引用计数无法独立解决循环引用，因此不是 HotSpot 判活的主体算法；某些辅助计数不改变这个结论。
- Roots 枚举需要准确知道某个位置是引用还是普通数值，HotSpot 借助 OopMap 等元数据避免保守扫描全部内存。
- “不可达”不等于马上释放，实际回收还取决于引用处理、收集周期和清理队列。

## 02-引用类型与清理
Q: 强、软、弱、虚引用在 GC 中分别有什么边界？
A:
- 强引用可达时对象不会因普通 GC 被回收；业务缓存若一直保留强引用就可能形成逻辑泄漏。
- SoftReference 的回收受内存压力和 JVM 策略影响，不适合做可预测容量缓存。
- WeakReference 在发现仅弱可达后通常会被清除，常用于规范化映射或与 ReferenceQueue 配合清理元数据。
- PhantomReference 的 `get()` 始终返回 null，用于获知对象进入特定清理阶段并管理堆外资源。
- 资源释放优先使用 `try-with-resources`/显式 `close`；Cleaner/虚引用是兜底，不能依赖 GC 时机保证及时释放。

## 03-三类基础算法
Q: 标记-清除、复制、标记-整理各自的成本模型是什么？
A:
- 标记-清除只回收死亡对象，但会留下碎片；分配器需要空闲链或其他结构寻找可用块。
- 复制/疏散把存活对象搬到新区域并更新引用，分配端可获得连续空间，成本与存活对象量更相关。
- 标记-整理在标记后移动存活对象消除碎片，移动和更新引用可能带来较长暂停。
- 现代收集器常按 Region 局部疏散、并发标记并配合转发表/屏障，不能只贴单一算法标签。
- 选择取决于存活率、暂停目标、吞吐、堆大小、内存余量和并发阶段的 CPU 成本。

## 04-三色标记与屏障
Q: 并发标记为什么需要写屏障？SATB 与增量更新分别保护什么？
A:
- 三色抽象中白色未发现、灰色已发现但子引用未扫描、黑色及其子引用已扫描。
- 应用线程并发修改引用可能让一个本应存活的白对象从标记图中消失，造成漏标，这是必须防止的正确性问题。
- SATB 记录被覆盖前的旧引用，近似保留并发标记开始时的对象图；可能保留本轮产生的浮动垃圾。
- 增量更新关注黑对象新指向白对象的写入，把相关对象重新纳入扫描。
- 写屏障是引用写入周围的 JVM 代码片段，不等于 CPU 内存屏障；不同 GC 的 remembered set、marking barrier 和 load barrier 作用不同。

## 05-RememberedSet与卡表
Q: 分代/分区 GC 为什么需要卡表和 Remembered Set？
A:
- 回收某个年轻代或部分 Region 时，不能每次扫描整个老年代寻找跨区引用，否则局部回收失去意义。
- 写屏障把发生引用写入的内存小区间标为 dirty card，收集时重点扫描这些卡对应区域。
- Remembered Set 逻辑上记录“其他区域可能指向本区域”的信息；G1 的具体结构和精度会随版本演进。
- 卡表通常是粗粒度摘要，会有假阳性，因此减少扫描范围但不是精确对象引用集合。
- 高频跨代写会增加屏障、并发精化和扫描成本，解释了某些引用密集型负载的 GC CPU 上升。

## 06-安全点与根扫描
Q: 为什么 GC 经常需要 Stop-The-World？并发收集是否代表没有停顿？
A:
- 某些阶段需要得到一致的线程状态、枚举 Roots、重定位对象或处理无法与应用并发的全局状态。
- JVM 让 Java 线程到达可描述执行状态的 Safepoint；现代 HotSpot 也用 Thread-Local Handshake 执行部分单线程操作。
- 并发 GC 只把大部分工作与应用线程重叠，初始标记、重标记或最终重定位等阶段仍可能暂停。
- 停顿时间还受 Roots 数量、脏卡、类卸载、引用处理和操作系统调度影响，不只由堆大小决定。
- 面试指标应同时看暂停分位数、并发 GC CPU、分配速率、回收余量和吞吐，而不是只问“是不是低延迟 GC”。

## 07-正确性审查
Q: 垃圾回收算法有哪些常见错误说法？
A:
- “GC 用引用计数”：不严谨，HotSpot 主体是可达性分析。
- “并发 GC 没有 STW”：错误，只是显著缩短或迁移部分暂停工作。
- “标记-清除只用于 CMS”：错误，这是通用算法模型；CMS 本身已在 JDK 14 移除。
- “写屏障就是 volatile 的内存屏障”：错误，GC 屏障用于维护收集器元数据和并发标记正确性。
- “对象不可达立即执行清理”：错误，引用处理、Cleaner 和实际回收都没有业务实时性保证。
