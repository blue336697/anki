# JVM 性能诊断、监控与调优方法论

> 基线：JDK 21/25。先建立业务症状和时间线，再选择低开销证据；调参是验证后的最后一步。

## 01-诊断闭环
Q: JVM 性能问题应按什么闭环处理，为什么不能先改参数？
A:
1. 定义症状与 SLO：吞吐下降、p99 抖动、CPU 高、内存增长、线程池堆积还是启动慢。
2. 建立时间线，把请求、发布、流量、GC、Safepoint、CPU throttle、磁盘和下游错误对齐。
3. 先收集低开销持续指标，再针对假设采集 JFR、线程 dump、heap dump 或 profiler。
4. 形成可证伪假设，单变量修改代码/容量/参数，在相同负载下对照验证。
5. 上线后观察长期回归并保留回滚；“一次压测变快”不等于生产问题已解决。

## 02-观测工具分工
Q: jcmd、JFR/JMC、jstack、jstat、heap dump、NMT 和 profiler 各适合回答什么问题？
A:
- `jcmd` 是统一诊断入口，可查看 VM flags、线程、类加载、堆、JFR、NMT 等目标 JVM 能力。
- JFR 低开销记录 CPU sample、分配、锁、线程、GC、Socket/File I/O 等时间事件，JMC 用于关联分析。
- thread dump/jstack 给出线程瞬时栈和锁关系，适合死锁、线程池耗尽和阻塞定位，但单次快照不能证明长期热点。
- jstat 提供 GC/类加载等计数趋势，适合快速观察，不应仅凭某列上涨就宣布泄漏。
- heap dump/MAT 解释堆对象与保留关系；NMT 解释 JVM native memory 分类；async-profiler 等采样器适合 CPU、wall、alloc、lock 火焰图。

## 03-CPU高
Q: Java 进程 CPU 高时怎样区分业务热点、GC、锁自旋和系统调用？
A:
- 先看进程 CPU、容器 quota/throttle、load 和核数，确认是持续饱和还是短时突发。
- 用 JFR/采样 profiler 获取一段时间的 CPU 火焰图；不要只依赖某一时刻的线程 dump。
- 若必须用线程 ID 对齐，记录多次 `top -H`/系统线程统计，再把 native tid 转换后匹配 dump 中 `nid`。
- 同时看 GC CPU 和日志：高分配率可能让 GC 占用 CPU；锁竞争或自旋会在 lock/线程事件中出现。
- native 方法、正则回溯、序列化、大量日志和异常创建都可能成为热点，最终要回到调用路径和输入数据验证。

## 04-尾延迟
Q: 请求 p99 抖动时，怎样判断是不是 GC 或 Safepoint？
A:
- 把请求 trace 时间戳与 `-Xlog:gc*,safepoint`、JFR pause/GC 事件对齐，相关不等于因果但可缩小范围。
- 区分到达 Safepoint 的时间、VM operation 执行时间和 GC 各阶段；长暂停不一定由 GC 触发。
- 停顿恢复后的队列拥塞、锁竞争、连接池等待和重试风暴会把 20ms VM pause 放大成更长业务尾延迟。
- 若 GC pause 很短但请求仍慢，检查并发 GC 抢 CPU、allocation stall、容器 throttle 和下游等待。
- 至少比较无事件窗口与事件窗口的分布，不用一条日志解释所有慢请求。

## 05-堆泄漏
Q: 怎样用趋势、Histogram 和 Dominator Tree 证明 Java 堆泄漏？
A:
1. 观察多次 GC 后 live set 是否在相似负载下持续抬升，排除缓存预热和正常流量增长。
2. 比较多个时间点的 class histogram，找实例数/字节持续增长的候选类。
3. 在 heap dump 中看 retained size 与 dominator tree，定位谁支配了大对象图。
4. 沿 path to GC roots 找静态集合、ThreadLocal、队列、监听器或 ClassLoader 等保留者。
5. 回到业务所有权证明对象何时应释放，修复后用相同时间窗口验证 live set 平台化。

## 06-HeapDump边界
Q: 线上获取 heap dump 有哪些风险？`-live` 是否总是更准确？
A:
- dump 可能触发明显停顿、额外 GC、大量磁盘写和临时空间占用，堆越大风险越高。
- `-live` 为只保留存活对象通常需要先做 Full GC，会改变现场、延长停顿并清掉短命分配证据。
- OOM 自动 dump 更接近故障时刻，但也要预留磁盘、权限、采集和加密传输流程。
- dump 含用户数据、凭据和业务对象，应按敏感数据管控。
- 分配热点更适合 JFR allocation events/profiler；heap dump 适合解释某一时刻“谁还活着、被谁保留”。

## 07-NativeMemory
Q: Heap 使用稳定但 RSS 上升，怎样分析 native memory？
A:
- 先拆分 Metaspace、Compressed Class Space、Code Cache、线程栈、Direct Buffer、GC 辅助结构、JNI/native library 和 allocator 碎片。
- NMT 需在启动时开启，使用 `jcmd VM.native_memory baseline` 与 `summary.diff/detail.diff` 比较 JVM 已跟踪分类。
- NMT 不覆盖所有第三方 native 分配和操作系统页状态，需联合 `/proc`、容器 RSS、pmap、线程数和 direct buffer pool。
- 大量平台线程会以每线程栈消耗 native 地址空间/提交内存；大量虚拟线程主要改变为堆内 continuation 成本。
- 增大 Xmx 可能挤压 native 余量，不能把所有进程内存问题都当堆容量问题。

## 08-线程池与锁
Q: 应用“CPU 不高但响应卡死”时，线程与锁证据怎样收集？
A:
- 连续获取多份 thread dump，找稳定重复的 BLOCKED、park、Socket read、连接池等待和同一栈聚集。
- 死锁可由 JVM 检测，但线程饥饿、资源池耗尽和锁队列过长不一定形成形式死锁。
- 结合线程池 active、queue size、oldest task age、reject、任务耗时和下游连接池指标。
- JFR lock/park/socket 事件或 wall-clock profiler 能说明时间花在哪里，优于把所有 WAITING 都当异常。
- 修复可能是缩短临界区、拆锁、设置超时与背压、隔离线程池或扩下游容量，而非单纯增加线程数。

## 09-GC调优顺序
Q: 已确认 GC 是瓶颈后，调优顺序是什么？
A:
- 先减少不必要分配、大对象、重复序列化和无界缓存，确认 live set 与 allocation rate。
- 再校准堆与容器总内存余量，避免堆太小频繁回收或太大挤压 native memory。
- 按目标选择 G1、Generational ZGC 或 Parallel，并用默认策略建立可复现基线。
- 只有日志显示明确阶段问题时才调整少量收集器参数，每次保留吞吐、暂停、GC CPU 和业务延迟对照。
- 不复制 CMS 参数和旧版本固定阈值；具体 flag 必须核对目标 JDK 是否存在、是否 product/experimental。

## 10-基准测试
Q: 为什么普通循环计时常得出错误的 JVM 性能结论？JMH 解决什么？
A:
- JIT 暖机、分层编译、内联、常量折叠、死代码消除和逃逸分析会让源码操作与实际机器码不同。
- OSR、GC、CPU 频率、NUMA、容器干扰和数据分布也会污染短测试。
- JMH 用 fork、warmup、measurement、Blackhole 和统计框架降低常见微基准错误。
- 微基准只能回答局部操作成本，不能替代真实服务的队列、I/O、锁和尾延迟压测。
- 结果必须记录 JDK、flags、硬件、数据规模和置信区间，不能只贴一个 ns/op。

## 11-生产安全
Q: 线上诊断如何避免“为了排障把服务打死”？
A:
- 从指标、已有 GC 日志、短 JFR 和低频 thread dump开始，再逐步提高采样深度。
- 评估 heap dump、class histogram、NMT detail 和高频 profiler 的暂停、CPU、磁盘及敏感数据成本。
- 设定采集时长、文件轮转、磁盘上限和自动停止；在单实例/影子流量先验证。
- 故障节点已接近极限时，优先摘流、保留必要证据和恢复服务，不执着于采齐所有现场。
- 所有临时参数和诊断 agent 都要有撤销记录，避免永久留在生产。

## 12-正确性审查
Q: JVM 性能排障有哪些必须拒绝的经验主义结论？
A:
- “老年代使用量上涨就是泄漏”：错误，要看多次回收后的 live set、负载和引用链。
- “GC 时间占比超过某个固定百分比就一定泄漏”：没有跨业务通用阈值。
- “一份 thread dump 能证明 CPU 热点”：只能提供瞬时证据，应多次采样或用 profiler。
- “heap dump 越大越该看 shallow size”：泄漏定位更关注 retained size、dominator 和 GC Roots。
- “性能问题最终都靠 JVM 参数解决”：多数根因在分配、锁、队列、I/O、下游容量和业务算法。
