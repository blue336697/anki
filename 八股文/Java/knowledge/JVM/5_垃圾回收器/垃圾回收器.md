# HotSpot 垃圾回收器选型与机制

> 基线：JDK 21/25。CMS 仅保留历史原理，不作为现代生产选型。

## 01-收集器谱系
Q: JDK 21/25 常见 HotSpot 收集器怎样定位？
A:
- Serial 以单线程完成主要 GC 工作，结构简单，适合小堆、单核或对资源占用极敏感的场景。
- Parallel GC 以吞吐为主要目标，用多线程完成年轻代和 Full GC，适合批处理和对暂停不敏感的任务。
- G1 是服务端常用默认选择，以 Region、并发标记和可预测暂停目标管理中大堆。
- ZGC 以极低暂停和大堆扩展性为目标；JDK 21 提供 Generational ZGC，JDK 23 起非分代 ZGC 已移除。
- Shenandoah 同样强调并发压缩/疏散和低暂停，但是否随发行版提供、默认实现细节应按所用 JDK 验证。

## 02-G1Region布局
Q: G1 为什么使用 Region？Humongous 对象为什么容易带来问题？
A:
- 堆被切分为等大小 Region，每个 Region 在某阶段承担 Eden、Survivor、Old 或 Humongous 角色。
- 年轻代大小可动态变化；回收时选择一组 Region 构成 Collection Set，而不是要求连续的新老年代。
- 大于约半个 Region 的对象通常按 Humongous 路径占用一个或多个连续 Region，可能产生尾部浪费和连续 Region 压力。
- G1 使用 remembered set/card table 跟踪跨 Region 引用，使局部回收无需扫描全堆。
- Region 化提高回收选择灵活性，但 RSet、并发精化和屏障会消耗额外内存与 CPU。

## 03-G1周期
Q: G1 从 Young GC 到 Mixed GC 的核心状态链是什么？
A:
1. Young GC 疏散 Eden/Survivor 中的存活对象，部分进入新的 Survivor 或晋升 Old。
2. 老年代占用达到 IHOP 相关条件后启动并发标记；初始标记通常借助一次 Young GC 完成。
3. 并发标记期间应用继续运行，SATB 屏障维护快照语义；Remark 完成剩余标记和引用处理。
4. Cleanup 统计各 Region 存活率并回收完全空 Region，随后若有收益进入若干 Mixed GC。
5. Mixed GC 同时回收年轻 Region 和收益较高的老 Region；若疏散空间不足可能发生 evacuation failure，严重时退化到 Full GC。

## 04-ZGC机制
Q: ZGC 为什么能把暂停压得很低？它把哪些成本移到了并发路径？
A:
- ZGC 让标记、重定位和多数引用修复与应用并发，暂停阶段主要处理 Roots 等有限工作。
- 通过 colored pointers/指针元数据、load barrier 及转发表，让应用读取引用时能够参与修复或重映射。
- Generational ZGC 分离年轻代与老年代，利用对象年龄分布减少每轮扫描和重定位工作。
- 低暂停不等于零成本：load/store barrier、并发 GC 线程、额外内存余量和更高 CPU 都可能影响应用吞吐。
- 若分配速度长期超过并发回收速度，仍可能出现 allocation stall；选型必须看延迟 SLO、CPU 预算和 headroom。

## 05-选型方法
Q: 面向线上服务怎样选择 G1、ZGC 或 Parallel，而不是背固定堆大小阈值？
A:
- 先定义目标：吞吐、最大/分位暂停、尾延迟、容器内存、CPU 限额、启动时间和部署密度。
- 用真实流量压测获取分配速率、对象存活率、晋升量、大对象分布和 GC CPU，而不是仅按“几 GB 堆”做选择。
- 一般服务先从发行版默认 G1 建立基线；暂停目标严格且堆较大时评估 Generational ZGC；批处理优先评估 Parallel。
- 给并发收集器预留 CPU 与堆余量；容器 CPU throttle 会使并发周期跟不上，单纯加堆可能只延后故障。
- 每次只调整少量参数并保留对照，优先修复对象分配和缓存容量问题，再做高级 GC 参数微调。

## 06-CMS历史卡
Q: CMS 的核心机制和历史价值是什么？现代面试应怎样回答？
A:
- CMS 以并发标记清除降低老年代停顿，典型阶段包括初始标记、并发标记、重标记和并发清除。
- 它不压缩老年代，存在碎片、浮动垃圾和 concurrent mode failure；失败后可能退化为代价很高的串行 Full GC。
- CMS 在 JDK 9 被标记废弃，并在 JDK 14 由 JEP 363 移除；现代 HotSpot 不能把它当作可选生产收集器。
- 面试可以用 CMS 解释 SATB/增量更新、碎片与并发回收余量，但选型答案应转向 G1/ZGC/Shenandoah。
- 老系统运行旧 JDK 时才讨论 CMS 参数，且应把升级 JDK 和迁移收集器作为治理方向。

## 07-失败模式
Q: G1/ZGC 的低延迟承诺会在哪些情况下失效？
A:
- 分配速率超过回收速度、晋升突增或堆余量不足，会触发 evacuation failure、allocation stall 或 Full GC。
- Humongous/大对象持续产生会制造 Region 压力；类卸载、引用处理、Roots 激增也会扩大暂停。
- 容器 CPU 被限流时并发标记和重定位线程得不到调度，墙钟时间变长，即使 GC CPU 指标看似合理。
- native memory、direct buffer 或线程栈耗尽不是增加 `-Xmx` 能解决的，反而可能挤压进程余量。
- 选择低延迟 GC 后仍需监控暂停分位数、allocation rate、live set、GC CPU、stall 和进程总内存。

## 08-正确性审查
Q: 收集器选型有哪些需要拒绝的固定口诀？
A:
- “低延迟选 CMS”：过时，CMS 已移除。
- “小于 6GB 用 CMS，大于 6GB 用 G1”：没有可靠通用性，应基于 SLO 与真实负载。
- “ZGC 没有 STW”：错误，它有短暂停阶段，只是大部分工作并发化。
- “G1 一定比 Parallel 吞吐高”：错误，低暂停和并发维护有成本，批处理场景 Parallel 可能更合适。
- “只要把暂停目标调小就能降低延迟”：错误，过激目标可能增加 GC 频率和 CPU，甚至降低整体稳定性。
