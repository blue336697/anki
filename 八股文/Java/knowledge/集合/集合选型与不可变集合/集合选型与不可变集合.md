# 集合选型、视图与不可变集合

## 01-选型维度
Q: 选择 Java 集合时应先问哪些问题？
A:
- 语义：是否允许重复、是否要求 key/value、是否要求排序、插入顺序或双端操作。
- 复杂度：按索引、按 key、范围查找、头尾操作、遍历分别是否是热点。
- 数据规模与内存：节点对象、装载因子、装箱和缓存局部性可能比大 O 更影响实际性能。
- 并发：单线程、外部锁、弱一致遍历、写时复制或无界并发结构的需求不同。
- API 边界：是否需要 null、可变性、快照、序列化和稳定迭代顺序。

## 02-不可变工厂
Q: `List.of`、`Set.of`、`Map.of` 与 `Collections.unmodifiableXxx` 有什么差异？
A:
- `of` 家族创建不可修改集合，通常拒绝 null；Set/Map 还拒绝重复元素或重复 key。
- `unmodifiableXxx` 返回现有集合的只读视图，调用者若仍持有底层引用并修改，视图会同步变化。
- `copyOf` 可表达“基于当前内容得到不可修改结果”，但实现可能复用已知不可变输入，不承诺总是深拷贝。
- 所有这些只约束集合结构，元素对象仍可能可变。
- 需要时间点快照时，应先切断底层集合别名，并评估元素是否也需复制。

## 03-subList与视图
Q: `subList`、`keySet`、`entrySet` 为什么容易引发意外修改和内存问题？
A:
- 它们通常是原集合的视图而不是独立副本；对视图的结构修改可能反映到原集合。
- 原集合在视图预期之外发生结构修改，迭代和后续操作可能抛 ConcurrentModificationException。
- 旧实现或长期持有小视图可能间接保留大底层结构；需要独立生命周期时显式复制。
- Map 的 Entry 可能允许 `setValue` 回写；不能把 entrySet 当成普通值快照。
- API 返回视图时应在契约中明确其可变性和生命周期。

## 04-并发选型
Q: 读多写少、生产消费、按 key 原子更新分别选什么集合？
A:
- 读极多写极少且规模可控，可评估 CopyOnWriteArrayList；每次写复制数组，不适合大集合或高频写。
- 生产消费需要阻塞与背压用 BlockingQueue；只需高并发非阻塞队列可看 ConcurrentLinkedQueue。
- 按 key 并发读写和复合原子操作使用 ConcurrentHashMap 的 compute/merge 等 API。
- 有序并发导航可使用 ConcurrentSkipListMap/Set，代价高于无序哈希结构。
- 集合线程安全不保护元素内部状态，也不自动让跨多个集合的操作成为事务。

## 05-正确性审查
Q: 集合选型有哪些常见机械结论？
A:
- “LinkedList 插入一定比 ArrayList 快”：忽略定位成本、对象分配和缓存局部性。
- “不可修改集合就是深度不可变”：错误，元素仍可变。
- “subList 是新数组”：错误，通常是视图。
- “线程安全集合让所有复合操作原子”：错误，必须使用专门原子 API 或外部同步。
- “HashMap O(1) 所以总是最快”：忽略碰撞、扩容、内存和有序/范围语义。
