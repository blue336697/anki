# CAS 的原理与边界

## 概念卡
Q: CAS 是什么？它解决的是哪类并发问题？

A:
- CAS 是 Compare-And-Swap/Compare-And-Set，一次原子性的“比较并更新”操作。
- 它读取内存当前值，与期望值比较；相等才写入新值，不相等说明期间被其他线程改过，本次更新失败。
- Java 原子类和 AQS 中大量使用 CAS，把一些读-改-写操作从“加锁互斥”转成“失败重试”。
- 面试表达重点：CAS 是硬件原子指令能力在 JVM/库层面的使用，不是 Java 语法层面的魔法。

## 机制卡
Q: CAS 更新共享变量的基本流程是什么？

A:
1. 线程先读取共享变量旧值，记为 expected。
2. 基于 expected 计算 newValue。
3. 执行 CAS：如果内存当前值仍等于 expected，就原子地改成 newValue。
4. 如果不相等，说明发生并发修改，通常进入自旋重试或返回失败。

## 边界卡
Q: CAS 的三个典型问题是什么？分别怎么处理？

A:
- ABA：值从 A 变成 B 又变回 A，CAS 只看当前值会误以为没变；可用版本号/时间戳，例如 `AtomicStampedReference`。
- 自旋成本：高竞争下反复失败会消耗 CPU；需要退避、限次重试，或改用锁/队列化同步器。
- 多变量原子性：单次 CAS 天然只保护一个内存位置；多个变量要封装成一个引用对象后 CAS，或使用锁/事务化方案。

## 对比追问卡
Q: CAS 和 synchronized 最大的差异是什么？

A:
- CAS 偏乐观：先尝试更新，失败后重试；无竞争或低竞争时开销小。
- synchronized 偏悲观：进入临界区前先获得互斥权；能保护一段复合逻辑。
- CAS 不会自动提供临界区互斥，也不适合无限制地在高竞争热点上自旋。
- synchronized 的能力更强，CAS 的优势在合适场景下更轻。

## 正确性审查卡
Q: 原文中关于 CAS 的表述需要怎么修正得更严谨？

A:
- “把数据更新到主内存时再次读取主内存变量”可以改成“对某个内存位置执行原子的比较并交换”，不要把 JMM 的主内存/工作内存模型和 CPU 缓存细节混成一个物理过程。
- “解决 ABA 就加时间戳”是对的，但更准确说是“加入版本维度”，时间戳只是版本的一种实现。
- “多个变量合并成一个共享变量”建议表达为“把多个字段封装到不可变对象引用里，再对引用做 CAS”。
