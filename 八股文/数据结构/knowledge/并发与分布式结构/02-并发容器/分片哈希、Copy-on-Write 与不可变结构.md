# 分片哈希、Copy-on-Write 与不可变结构

> 基线：并发容器的关键是线性化、发布、扩容协作和迭代语义，不是简单地“加一把锁”。

## 01-全局锁
Q: 给普通哈希表加全局互斥锁能得到什么，又失去什么？
A:
- 所有 get/put/remove/resize 在同一锁下可复用单线程不变量，容易实现线性一致和原子复合操作。
- 不相交 key 也被串行化，热点锁造成排队、上下文切换和 convoy；持锁线程暂停会阻塞所有访问。
- 只给写加锁而让读无锁不自动安全，读可能看到迁移一半的桶、未发布 entry 或陈旧字段。
- 若读多写少可考虑读写锁，但读锁元数据本身也会争用，写者饥饿策略需明确。

## 02-分片哈希
Q: Lock Striping/分片哈希怎样提高并发度？
A:
- 根据 hash 的高/低位把 key 映射到多个 segment，每片拥有独立桶数组、size 和锁，不同片可并行更新。
- 分片数决定最大锁并发和元数据开销；热点 key 或坏 hash 仍会集中到单片。
- 单片扩容只阻塞该片，简化全表迁移；但全局 size、快照迭代和跨 key 原子操作需锁多个片。
- 多片加锁必须规定固定顺序以避免死锁，或明确 API 不提供跨片事务语义。

## 03-桶级同步
Q: 桶级锁或 CAS 更新比固定分片更细时，会增加哪些复杂度？
A:
- 不同桶可并发写，冲突范围更小；桶头可用 CAS 插入，链/树内部再用锁或不可变节点。
- 扩容时 key 会从旧桶迁到新桶，访问方必须识别桶状态、帮助迁移或跳转到新表。
- 锁对象若每桶一个会占大量内存，常把锁状态编码在桶头或复用较少的 stripe。
- 删除、树化和迭代必须与迁移协议组合验证，局部原子不代表全表一致。

## 04-协作扩容
Q: 并发哈希表怎样让多个线程协作 resize 而不重复搬迁？
A:
- 发布 nextTable 和全局迁移游标，线程领取一段桶区间，把 entry 搬到新表后将旧桶标记为 forwarded。
- 其他线程遇到 forwarded 可去新表查询或帮助迁移；每桶必须只完成一次可验证的状态转换。
- 迁移期间 put 要确保更新落到权威位置，不能同时在新旧表产生两个不一致副本。
- 最后一个完成者原子发布新 table 并清理迁移元数据；失败线程可退出但不能留下永远无人完成的区间。

## 05-弱一致迭代
Q: 并发容器的 weakly consistent iterator 意味着什么？
A:
- 迭代不必冻结全表，可与更新并行，通常不会抛结构修改异常，也不保证某个瞬间的精确快照。
- 它可能看到迭代开始后新增的部分元素，也可能看不到；但不应返回破损 entry、重复到违反契约或陷入循环。
- 若业务需要审计快照，必须显式复制、版本化或加锁，不能把弱一致遍历结果当事务视图。
- API 文档应区分 fail-fast、weakly consistent 与 snapshot iterator。

## 06-Copy-on-Write
Q: Copy-on-Write 容器的更新和读取路径是什么？
A:
- 读者只读取一个不可变数组/根指针，无需结构锁；写者持锁复制当前结构、在副本修改，再原子发布新引用。
- 已开始的读者继续持有旧版本，天然获得稳定快照；新读者看到新版本。
- 每次写 O(n) 复制并产生垃圾，所以只适合元素不多、读极多写极少、遍历频繁的配置/监听器列表。
- value 若可变，COW 只保证容器结构快照，不自动深复制对象内部状态。

## 07-持久化结构
Q: 持久化不可变数据结构怎样避免每次更新复制全部内容？
A:
- 用宽分支树、HAMT 或 Radix 等结构共享未变化子树，只复制从根到修改点的 O(log_B n) 个节点。
- 原子替换 root 即可发布新版本，读者无需锁；旧版本在无人引用后回收。
- 与 COW 整数组相比写放大更小，但每次查询多层指针，节点与 bitmap 元数据增加。
- 它的“持久化”指版本长期可访问，不等同磁盘 durability；要落盘仍需日志和恢复协议。

## 08-复合操作
Q: 为什么线程安全容器的 get 与 put 分别安全，不代表 `if absent then put` 安全？
A:
- 两个线程可同时 get 到不存在，再各自创建并 put，产生重复副作用或后写覆盖。
- 需要容器提供 `putIfAbsent`、`compute`、CAS replace 等单一线性化操作，把检查和更新绑定。
- 回调可能在锁内执行、被重复调用或禁止递归修改容器，必须阅读契约；副作用应可幂等。
- 涉及多个 key 或多个容器时，单 key 原子 API 仍不足，需要锁顺序、事务或更高层协议。

## 09-选型
Q: 全局锁、分片、无锁和 COW 应如何选择？
A:
- 先测读写比例、key 热度、容器大小、是否需要快照/跨 key 原子，再确定一致性级别。
- 小表低竞争优先简单锁；大量独立 key 更新可分片；读极多写极少可 COW/不可变根。
- 无锁适合对阻塞和系统进展有明确要求且团队能维护内存序与回收证明的核心路径。
- 任何方案都应测高分位延迟、扩容和 GC，不应只比较无竞争微基准。
