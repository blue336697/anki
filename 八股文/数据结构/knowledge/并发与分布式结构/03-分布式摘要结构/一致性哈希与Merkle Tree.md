# 一致性哈希与 Merkle Tree

> 基线：一致性哈希负责“key 应归谁”，Merkle Tree 负责“哪一段状态不同”；二者都不能替代复制一致性协议。

## 01-取模分片问题
Q: `hash(key)%N` 在节点增减时为什么会大规模迁移？
A:
- N 改变后，几乎所有 key 的余数映射都可能改变；从 N 到 N+1 时只有少量偶然仍落原节点。
- 大规模 cache miss、数据搬迁和后端回源会叠加，扩容瞬间容易形成雪崩。
- 取模在 N 固定、节点同质且中心化路由简单时仍可用；问题不是 hash，而是映射直接依赖节点总数。
- 可用固定分片数再映射节点，或一致性哈希把成员变化限制到局部区间。

## 02-哈希环
Q: 一致性哈希环怎样映射节点和 key？
A:
- 把 hash 输出空间视为首尾相接的环，节点和 key 都映射到环上；key 通常归顺时针遇到的第一个节点。
- 新增节点只接管其前驱到自身区间，删除节点的区间转给后继，理想迁移比例约为节点份额。
- 环只是逻辑排序，可用有序数组二分后继或平衡树查 ceiling，超过末尾则回到首节点。
- hash seed 和成员视图必须一致，否则不同客户端会把同 key 路由到不同节点。

## 03-虚拟节点
Q: 为什么一致性哈希需要虚拟节点，虚拟节点如何表示？
A:
- 物理节点数量少时随机点间距方差大，负载可能严重不均；每台机器映射多个 token/virtual node 能细分区间。
- 环上 entry 保存 token→physical node，同一物理节点拥有多个不连续小区间，负载更接近期望。
- 异构机器可分配不同 token 数实现权重，但 key 热度不均仍可能造成热点。
- token 越多路由表和迁移计划越大，现代系统也可使用固定分区/均匀 token 代替纯随机虚拟点。

## 04-副本放置
Q: 一致性哈希怎样选择多个副本，为什么不能简单取后续虚拟节点？
A:
- 基本做法从主 token 顺时针找后继，但必须跳过属于同一物理节点的其他 token，直到收集不同故障域节点。
- 还应考虑机架、可用区和地域，避免多个副本在同一故障域；这需要拓扑感知放置规则。
- 成员变动后的迁移要限速、校验并处理并发写，哈希环本身不解决复制期间的一致性。
- 读写 quorum、版本冲突和 hinted handoff 属于上层复制协议，不能由“有三个副本”自动推出。

## 05-有界负载
Q: 一致性哈希为什么仍可能过载，bounded-load 思想解决什么？
A:
- hash 只按 key 数近似均衡，value 大小、请求频率和机器容量可能不同，热门 key 会让单节点过载。
- bounded-load 路由在首选节点超过容量阈值时继续寻找候选，把负载偏差限制在平均值某个因子内。
- 这会改变纯环的固定归属并增加协调/观测需求，缓存命中和迁移量也受影响。
- 热 key 还需复制、拆分或请求合并；增加虚拟节点不能拆开同一个 key。

## 06-Merkle结构
Q: Merkle Tree 的叶子和内部节点保存什么？
A:
- 叶子对数据块或 key-range 内容计算 hash，内部节点 hash 由子节点 hash 按固定顺序组合得到，根是全量摘要。
- 任一数据变化会沿祖先传播并改变根；相同根在抗碰撞假设和相同编码规则下表示内容一致。
- 树可为二叉或更高分支，叶分区、排序、序列化和 hash 算法必须两端完全一致。
- 它保存摘要而非业务数据，无法仅从根恢复缺失内容。

## 07-差异定位
Q: 两个副本如何用 Merkle Tree 定位不一致范围？
A:
- 先比较根；相同则无需继续，不同则比较子摘要，只递归进入 hash 不同的分支。
- 若差异很少，通信和计算集中在 O(k log N) 附近的路径，而不必逐条比较全部数据。
- 到叶范围后仍需交换 key/version 或实际数据完成修复；hash 只告诉“这一块不同”。
- 若树构建时数据仍在变化，需要快照、版本水位或增量维护，否则比较到的是不同时间点。

## 08-Merkle Proof
Q: Merkle Proof 如何证明某条数据属于一个已知根？
A:
- 提供目标叶内容/hash，以及从叶到根每一层的兄弟 hash 和左右位置。
- 验证者逐层重算父 hash，最终与可信根比较；二叉树证明大小 O(log N)。
- 可信根必须通过共识、签名或安全渠道获得，否则攻击者可同时伪造根和证明。
- 不包含证明需排序树、稀疏 Merkle Tree 或相邻边界等额外结构，普通成员证明不能直接证明不存在。

## 09-边界与组合
Q: 一致性哈希和 Merkle Tree 在分布式存储中怎样组合，分别不解决什么？
A:
- 环/分区表先决定某 key range 的责任副本，Merkle Tree 再对同一 range 的副本摘要做反熵比较。
- 节点变化触发 range 迁移，迁移完成后可用摘要校验并针对差异修复，避免全量反复传输。
- 一致性哈希不保证副本内容相同，Merkle 也不决定哪个版本正确；仍需版本、冲突解决和复制协议。
- 面试若把二者都概括为“保证一致性”是不准确的，应分别说明路由、摘要、修复和仲裁职责。
