# Trie、Radix Tree 与 Patricia Trie

> 基线：Trie 按 key 的符号序列走路径，复杂度与 key 长度相关；压缩变体用边标签减少单子节点。

## 01-Trie节点
Q: Trie 节点在内存中通常保存什么，核心不变量是什么？
A:
- 节点表示一个前缀，保存 children 映射、终止标志，可选 value、频次或子树统计；边对应字符/字节/bit。
- 从根沿 key 的符号依次走边，走完且终止标志存在才表示完整 key；仅有路径可能只是其他 key 前缀。
- 查询和插入是 O(L)，L 为 key 长度，与已存 key 数 n 关系较弱。
- children 可用固定数组、排序小数组或哈希表，不同字母表和稀疏度决定空间与查找成本。

## 02-插入删除
Q: Trie 插入和删除如何保持共享前缀？
A:
- 插入沿已有边前进，缺边时创建剩余链，末节点设置 terminal/value；共同前缀节点只存一份。
- 删除先取消 terminal；只有节点无 value 且无孩子时才可向上回收，不能删掉仍服务其他 key 的共享前缀。
- 若同 key 允许多值或计数，删除需减少计数而非立即清终止标志。
- Unicode 必须明确按 UTF-8 字节、code point 还是规范化 grapheme 切分，否则视觉相同字符串可能走不同路径。

## 03-前缀查询
Q: Trie 如何实现 autocomplete 和前缀统计？
A:
- 先用 O(P) 定位前缀节点，再 DFS/BFS 枚举其子树，输出 k 个结果至少需要 Ω(k)。
- 若每节点维护 top-N 热门候选，可快速返回建议，但每次词频更新要沿祖先维护缓存。
- 保存 subtree count 可 O(P) 回答前缀下 key 数，并支持按字典序寻找第 k 个 key。
- 热门缓存、计数和原始结构是冗余状态，更新失败必须防止它们不一致。

## 04-空间问题
Q: 普通 Trie 为什么可能非常耗内存？
A:
- 每个符号可能生成一个节点；短 value 配上对象头、父子指针和稀疏 children 容器，元数据远大于字符本身。
- 固定 256/65536 子指针数组查询快，但多数为空；哈希 children 节省空槽却增加节点和 hash 开销。
- 单孩子长链重复保存节点边界，尤其 key 很长、公共前缀短时浪费明显。
- Radix 压缩、紧凑节点类型、arena 分配和 LOUDS 等 succinct 表示分别从路径、布局和指针方面压缩。

## 05-Radix压缩
Q: Radix Tree 如何压缩 Trie，查询时发生什么？
A:
- 将没有 value 且只有一个孩子的节点链合并为一条带字符串标签的边，节点只保留真正分叉点。
- 查询需比较边标签与 key 剩余部分的最长公共前缀；完全匹配才进入子节点。
- 插入若只匹配边标签一部分，要在分歧点拆边，创建中间节点并挂旧后缀与新后缀。
- 节点数显著减少，但边标签比较使一步不再只是单字符索引，且标签所有权/切片生命周期要明确。

## 06-Patricia
Q: Patricia Trie 的核心思想是什么，它与一般 Radix Tree 有何关系？
A:
- Patricia 是压缩基数树的一类，常针对 bit/string key，只保留真正发生分歧的位或前缀。
- 二进制版本节点可记录判别 bit 位置，查询按该位选择分支；路径跳过所有不产生区分的位。
- 它保持按前缀/位搜索能力并减少单分支节点，适合路由前缀和紧凑字典。
- 文献命名并不完全统一，面试应描述实际节点字段和边语义，而不是只凭 Patricia 名称推实现。

## 07-最长前缀匹配
Q: Trie/Radix 如何做 IP 路由的 Longest Prefix Match？
A:
- 按地址 bit 从根向下，每遇到带路由 value 的节点就记录为当前最佳，直到无边或地址耗尽。
- 返回最后一次记录，而不是最后访问节点，因为更深路径可能存在但没有路由条目。
- 路径压缩后边带 prefix/skip length，必须验证跳过位段确实匹配；IPv4/IPv6 的位宽和 mask 规则不同。
- 高性能路由还会使用多 bit stride、LC-trie 或硬件 TCAM，在内存、更新与查找步数间权衡。

## 08-持久化Radix
Q: 不可变/持久化 Radix Tree 如何支持快照？
A:
- 更新时只复制根到变更点路径，其余未变子树通过指针共享，称 path copying 或 structural sharing。
- 新根代表新版本，旧根仍可无锁读取；成本与 key 路径和分裂节点数相关，不必复制整棵树。
- 共享节点必须不可变，并通过 GC、引用计数、epoch 等方式管理生命周期。
- 它适合路由表、配置快照和 MVCC 式读，但频繁小更新会产生临时节点和内存回收压力。

## 09-选型
Q: Trie、哈希表和有序树在字符串 key 场景如何选择？
A:
- 精确查找且无需顺序/前缀时，哈希表期望 O(1) 且通常更简单；Trie 的 O(L) 会逐字节访问。
- 需要前缀枚举、最长前缀匹配或共享大量前缀时，Trie/Radix 直接表达问题。
- 需要全局有序范围、前驱后继且 key 很长时，比较树每次比较也可能读多个字符，实际成本需测量。
- 数据静态且极大时可考虑 minimal DFA/FST 等更强压缩；更新复杂度和构建成本会显著上升。
