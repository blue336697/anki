# 哈希函数、桶数组与哈希表扩容

> 基线：哈希表的常数时间来自均匀分布与低负载，不是由语法或接口保证。

## 01-内部表示
Q: 一个通用哈希表内部至少有哪些组成部分？
A:
- 核心是桶/槽数组、当前元素数 size、容量 capacity、装载因子阈值以及冲突处理所需的节点或控制元数据。
- 每个 entry 至少关联 key、value 和用于定位的 hash；有的实现缓存 hash，避免扩容或比较时重新计算。
- 不变量是每个 key 必须能沿当前冲突策略从 `index(hash)` 找到，且逻辑上不能出现重复 key。
- 迭代顺序通常不稳定；扩容、随机种子或删除都可能改变槽位，不能把观察到的顺序当接口契约。

## 02-哈希函数要求
Q: 好的哈希函数需要满足什么，为什么“hash 相等”不能代表 key 相等？
A:
- 它应确定、快速，并把实际 key 分布均匀扩散到输出位；小输入差异最好影响多个输出位。
- 输出空间有限而 key 空间通常更大，鸽巢原理决定不同 key 必然可能同 hash，因此命中 hash 后必须再做 equality。
- 哈希与相等契约要求 `a==b` 时 hash 必须相等，反向不成立；可变 key 入表后改变参与字段会让元素“失踪”。
- 安全场景需防 hash-flooding，可使用进程随机种子或抗碰撞哈希，但密码哈希与普通表哈希目标不同。

## 03-索引映射
Q: 哈希值怎样映射到桶下标，容量为什么常取 2 的幂或质数？
A:
- 一般映射是 `index = hash mod capacity`；容量为 2 的幂时可用 `hash & (capacity-1)`，速度快但依赖低位已充分混合。
- 若 key 的 hash 低位模式差而直接按位与，会集中到少数桶，因此常先做 xor-shift 等二次扰动。
- 质数模能削弱某些周期性输入与容量的公因子关系，但整数除法较贵，扩容和探测设计也更复杂。
- 关键不是背某个容量规则，而是让 hash 混合方式、容量和探测步长共同覆盖并均匀使用槽位。

## 04-装载因子
Q: 装载因子 α=size/capacity 如何影响哈希表性能？
A:
- 拉链法 α 可大于 1，但平均链长随 α 增长；开放寻址必须留空槽，α 接近 1 时探测长度急剧恶化。
- 降低 α 用更多内存换更少碰撞；提高 α 节省内存，却增加比较、cache miss 和尾延迟。
- 阈值不是普适常数，取决于槽布局、探测策略、hash 质量和读写目标；紧凑控制字节实现可承受更高负载。
- 监控平均值不够，最大桶长或探测长度分位数更能暴露攻击与长尾。

## 05-拉链法
Q: Separate Chaining 的桶内结构如何工作，链表、树和小数组各有什么差异？
A:
- 桶保存冲突 entry 的集合，查询先定位桶，再逐个比较 hash 与 key；期望成本约为 O(1+α)。
- 链表插删简单但指针跳转多；小型连续数组局部性好；平衡树能将严重碰撞从 O(n) 降至 O(log n)。
- 树化需要 key 可比较或提供稳定 tie-break，并且小桶上树节点开销可能得不偿失，所以通常设进入与退化阈值。
- 扩容时重新分配桶并迁移节点；若容量翻倍，旧 hash 的某一位可决定留在原桶还是移动固定偏移。

## 06-查询与更新
Q: 哈希表 get/put/remove 的完整路径是什么？
A:
- get 计算 hash 和桶下标，沿冲突结构先比 hash 再比 key，相等才返回 value；空槽或链尾表示不存在。
- put 若命中相等 key 则更新 value，否则插入新 entry、增加 size，并在超过阈值时触发扩容。
- remove 除了定位，还要修复链、探测簇或墓碑状态；开放寻址不能简单清空槽，否则会截断其他 key 的查找路径。
- 用户提供的 hash/equality 若抛异常、耗时或在比较中修改表，会破坏简单复杂度与可重入假设。

## 07-扩容过程
Q: 哈希表扩容为什么昂贵，stop-the-world 式和渐进式 rehash 有何区别？
A:
- 新容量改变索引映射，通常要申请新数组并把所有元素重新分桶，单次成本 O(n)，还会产生峰值双份内存。
- 一次性 rehash 实现简单，但大表可能形成明显延迟尖峰；即便每次 put 摊还 O(1)，尾延迟仍不可忽略。
- 渐进式保留 old/new 两张表，每次普通操作搬迁少量桶；查询迁移期间可能需要检查两张表。
- 渐进迁移要定义更新、删除和迭代语义，避免元素重复或漏查；它把暂停摊开但增加常态分支与内存周期。

## 08-缩容与抖动
Q: 哈希表删除很多元素后为什么不一定立刻缩容？
A:
- 缩容同样需要 O(n) 迁移，且高低阈值太接近会在临界工作负载下反复扩缩，造成时间和内存抖动。
- 常采用迟滞：在较低装载因子才缩，缩后仍保留足够余量；也可只在显式 trim/compact 时执行。
- 服务更关注稳定尾延迟时，宁愿暂时保留容量；批处理工具可能更关注释放内存。
- 开放寻址表还可能因大量墓碑而需要同容量重建，元素数没变也要清理探测路径。

## 09-正确性边界
Q: 关于哈希表，哪些面试说法必须补充边界？
A:
- “查询 O(1)”应说在哈希均匀、负载受控条件下期望 O(1)，最坏可能 O(n) 或树化后的 O(log n)。
- “扩容只是数组变大”错误；必须重新建立 key 到槽的可达关系，并处理旧引用和迭代器失效。
- “碰撞说明哈希函数坏”错误；碰撞不可避免，坏的是分布异常或冲突策略无法承受。
- “线程安全只需给 put 加锁”错误；get、扩容、发布和迭代都涉及可见性与结构一致性。
