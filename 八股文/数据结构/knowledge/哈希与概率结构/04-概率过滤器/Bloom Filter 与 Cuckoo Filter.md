# Bloom Filter 与 Cuckoo Filter

> 基线：概率过滤器回答“可能存在/一定不存在”，不能替代保存真实数据的索引。

## 01-Bloom结构
Q: Bloom Filter 的内部数据结构和插入查询过程是什么？
A:
- 它由 m 位 bit array 和 k 个哈希位置生成函数组成，不存原始 key 和 value。
- 插入 key 时计算 k 个位置并全部置 1；查询时若任一位为 0 则一定未插入，全部为 1 只表示可能存在。
- 多个 key 会共享位，无法从位图反推出成员；普通 Bloom 也不能安全清除某个 key 对应位。
- 实现常用双重哈希派生 k 个位置，避免真正计算 k 个昂贵独立哈希，但仍需保证分布质量。

## 02-假阳性与假阴性
Q: Bloom Filter 为什么有假阳性却在正确实现下没有假阴性？
A:
- 查询 key 的 k 位可能被其他元素共同置 1，因此未插入 key 也可能返回“可能存在”，形成 false positive。
- 已插入 key 的 k 位不会自行变回 0，所以它们必然都为 1，不会 false negative。
- 位数组损坏、错误并发非原子更新、直接删除或两端哈希配置不一致会人为制造假阴性。
- 系统只能用 Bloom 跳过确定不存在的慢查询；“可能存在”必须访问权威存储确认。

## 03-误判率
Q: Bloom Filter 的误判率由哪些参数决定，如何估算？
A:
- 插入 n 个元素、m 位、k 个哈希时，一位仍为 0 的概率近似 `e^(-kn/m)`，误判率近似 `(1-e^(-kn/m))^k`。
- 给定 m/n，最优 k 约为 `(m/n) ln2`；哈希过少位利用不足，过多则更快把位图填满并增加 CPU。
- 设计必须预估最大 n 和可接受误判率，超容量后误判率会远高于初始目标。
- 公式假设哈希近似独立均匀，真实 key 分布和实现缺陷需通过压测校准。

## 04-容量规划
Q: 如何从预计元素数和目标误判率规划 Bloom Filter？
A:
- 经典近似为 `m≈-n ln(p)/(ln2)^2`，再取 `k≈(m/n)ln2` 并按机器字、页或分片边界取整。
- 除 bit array 还要计入元数据、对齐、版本和副本；分布式场景需统一 hash seed 与序列化格式。
- n 不确定时可用 scalable Bloom：多个容量层逐步追加，但查询需检查多层且总误判率要分配。
- 监控实际插入计数、bit 填充率和抽样误判，达到上限应重建或增加层，而不是继续无界写入。

## 05-Counting Bloom
Q: Counting Bloom Filter 怎样支持删除，代价和风险是什么？
A:
- 每个位换成小计数器；插入对 k 个计数器加一，删除减一，查询要求都大于零。
- 多个 key 共享计数器时，删除自己的贡献不会清掉别人的贡献，因此理论上可安全删除已确认存在的 key。
- 若删除一个从未插入或已删除的 key，会错误减掉共享计数并制造假阴性；计数器溢出/下溢也需处理。
- 每槽从 1 bit 增到数 bit，空间显著增加；频繁删除场景也可考虑 Cuckoo Filter。

## 06-Cuckoo结构
Q: Cuckoo Filter 内部保存什么，查询为何只检查两个桶？
A:
- 它保存 key 的短 fingerprint，而非原 key；每个 bucket 有固定数量槽位。
- 第一个桶由 key hash 得到，第二个桶由 `i1 XOR hash(fingerprint)` 得到；这种对称关系允许搬迁后反推出另一候选桶。
- 查询只需在两个桶中匹配 fingerprint，缓存局部性好；短指纹碰撞导致假阳性。
- fingerprint 不能取特殊空值，长度影响误判率；删除必须删除匹配指纹中的一个，但重复语义需计数或约束。

## 07-Cuckoo插入
Q: Cuckoo Filter 插入失败和踢出链是怎样发生的？
A:
- 若两个候选桶有空槽直接插入；否则随机选择一个 fingerprint 踢出，把被踢者搬到它的另一个桶。
- 重复踢出最多执行限定次数；若形成循环或表太满仍无空槽，则扩容、重建或返回失败。
- 插入不是始终 O(1) 确定时间，接近负载上限时尾延迟和失败率上升。
- 并发实现需让踢出链原子可见或加桶锁，否则查询可能在迁移间隙产生假阴性。

## 08-Bloom与Cuckoo对比
Q: Bloom Filter 和 Cuckoo Filter 应如何选择？
A:
- Bloom 结构最简单、只置位，静态或追加型集合通常空间效率好；普通版本不支持删除。
- Cuckoo 支持删除，查询只访问两个局部桶，在某些目标误判率下更紧凑，但插入可能失败且实现更复杂。
- Bloom 的多个随机 bit 访问可能跨 cache line；blocked Bloom 把位置限制在块内以改善缓存，代价是误判分析变化。
- 两者都不枚举成员、不保存 payload，也都不能把“可能存在”当真值。

## 09-缓存穿透应用
Q: 用 Bloom Filter 防缓存穿透时，完整数据流和一致性边界是什么？
A:
- 请求先查过滤器；明确不存在则直接拒绝，可能存在再查缓存/数据库，数据库仍是权威来源。
- 新增 key 必须在可接受窗口内写入过滤器，否则真实数据会被错误挡住；通常先更新权威数据再可靠地传播过滤器。
- 删除 key 后残留只增加一次无效后端查询，是假阳性；错误清位造成真实 key 被挡住则是假阴性，危害更大。
- 热点恶意 key 即使被过滤，也可能消耗哈希和网关资源，还需限流、负缓存和鉴权配合。
