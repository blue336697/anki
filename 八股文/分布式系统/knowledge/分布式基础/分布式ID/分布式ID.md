# 分布式ID

## 目标卡
Q: 分布式 ID 生成需要满足哪些核心目标？
A:
- 全局唯一，不能因为多节点并发生成而冲突
- 高可用，不能让 ID 服务成为业务写入链路单点
- 高性能，生成 ID 通常在核心写路径上，延迟要低
- 趋势递增，便于数据库索引写入和范围查询
- 可治理，最好能承载业务、机房、时间等排障信息，但要避免泄漏敏感规模

## 方案对比卡
Q: 常见分布式 ID 方案如何对比？
A:
- UUID 本地生成、无中心依赖，但太长、无序，对数据库聚簇索引不友好
- 数据库自增简单可靠，但吞吐和可用性受数据库限制
- 号段模式批量从数据库取号，本地发号性能高，但需要处理号段耗尽和浪费
- Snowflake 类方案本地生成、趋势递增、性能高，但依赖时钟和 workerId 管理
- Redis INCR 简单高性能，但要考虑持久化、主从切换和可用性

## 号段模式卡
Q: 号段模式生成分布式 ID 的机制和优缺点是什么？
A:
- 服务从数据库申请一段 ID，例如 `[max_id + 1, max_id + step]`
- 业务实例在内存中顺序发号，用完后再申请下一段
- 优点是数据库访问频率低，吞吐高，ID 趋势递增
- 缺点是服务宕机会浪费未使用号段，步长过小会频繁访问数据库
- 工程实践通常用双 buffer 预加载下一段，避免号段切换时阻塞业务请求

## Snowflake卡
Q: Snowflake 类分布式 ID 的组成和关键风险是什么？
A:
- 典型结构是时间戳、机房/机器标识、序列号
- 同一毫秒内通过序列号区分多个 ID
- workerId 必须全局唯一，常通过配置中心、数据库或注册中心分配
- 最大风险是时钟回拨，可能导致同一 worker 生成重复 ID
- 面试表达：Snowflake 的本质是把全局唯一问题拆成时间唯一、节点唯一和节点内序列唯一

## 时钟回拨卡
Q: Snowflake 遇到时钟回拨应该怎么处理？
A:
- 小幅回拨可以等待时间追平，但会增加请求延迟
- 大幅回拨可以拒绝发号并报警，避免生成重复 ID
- 可以记录上次发号时间到本地或注册中心，启动时检测系统时间是否异常
- 多时钟序列、备用 workerId、逻辑时钟等方案可以降低回拨影响
- 面试边界：不要简单说“使用 NTP 就没问题”，NTP 只能降低概率，不能消除回拨风险

## 正确性审查卡
Q: 分布式 ID 有哪些常见误区？
A:
- “UUID 一定最好”：错误。它唯一性好，但长度和无序性会影响索引局部性
- “数据库自增不能用”：不完整。小规模或单库场景很实用，问题在扩展性
- “Snowflake 保证绝对递增”：错误。它通常是趋势递增，跨节点不保证严格全局递增
- “ID 越短越好”：不完整。还要看唯一性、容量、可读性和未来扩展
- “ID 暴露业务规模无所谓”：错误。连续订单号可能泄漏订单量和增长趋势
