# 访问方法与成本优化

## AccessMethod卡
Q: MySQL 常见单表访问方法有哪些？
A:
- `const` 用主键或唯一索引等值匹配，最多一行
- `ref` 用普通索引等值匹配，可能多行
- `range` 用索引范围扫描
- `index` 扫描整个索引树
- `ALL` 全表扫描，通常成本最高但在返回大量数据时也可能被选择

## 成本卡
Q: MySQL 优化器为什么有时不走你期望的索引？
A:
- 优化器基于统计信息估算不同计划的成本
- 二级索引需要考虑回表成本
- 如果选择率差或返回行太多，全表扫描可能更便宜
- 统计信息不准时，优化器可能选错索引
- 可通过 `analyze table`、改写 SQL、调整索引或必要时 hint 干预

## IndexDive卡
Q: Cardinality、index dive 和统计信息在索引选择中有什么作用？
A:
- Cardinality 表示索引列不同值数量的估计
- index dive 通过访问索引边界估算范围行数
- 统计信息采样不准确会导致行数估算偏差
- 数据分布倾斜时，平均估算更容易出错
- 面试表达：优化器选错索引的根因常是成本模型基于错误估算做了正确流程

## 正确性审查卡
Q: MySQL 成本优化有哪些常见误区？
A:
- “有索引就一定走索引”：错误。成本高时可能全表扫描
- “force index 是常规解法”：不建议滥用。数据分布变化后可能变成负优化
- “explain rows 就是真实行数”：错误。它是估算
- “统计信息永远准确”：错误。采样和数据变化都会影响准确性
- “ALL 一定最差”：不一定。小表或返回大量数据时可能合理
