# 死锁检测、Victim 选择与排查

## 结构定位
Q: InnoDB 如何检测死锁，wait-for graph 中节点和边是什么？
A:
- 节点是事务，边 `T1→T2` 表示 T1 的锁请求被 T2 持有的不兼容锁阻塞。
- 新锁等待形成时，检测器沿依赖边搜索环；发现环后选择一个 victim 回滚以打破循环。
- victim 通常倾向选择回滚代价较小的事务，事务权重与修改/锁定工作量有关，不保证永远回滚“后来的”。
- 关闭 `innodb_deadlock_detect` 后依赖 `innodb_lock_wait_timeout`，高热点场景可减少检测 CPU 但恢复更慢。

## 死锁结构
Q: 为什么只有两条 UPDATE 也可能因二级索引、gap 或唯一检查死锁？
A:
- 一条 SQL 可按执行计划锁多条聚簇/二级记录，不是一个业务行只对应一把锁。
- 不同事务访问相同资源但顺序相反，形成经典环。
- INSERT 的 duplicate check、insert intention 与 gap/next-key 相互作用可形成非直观环。
- 扫描范围、页分裂和并发时序会影响复现概率，因此要看实际死锁报告。

## 检测处理链
Q: 检测到死锁后 InnoDB 做什么，应用又必须做什么？
A:
1. 检测器确认闭环并选 victim。
2. victim 收到 deadlock error，其事务回滚并释放锁，其他等待者被唤醒重试授予。
3. MySQL 记录最近一次死锁；开启 `innodb_print_all_deadlocks` 可写全部到错误日志。
4. 应用把死锁视为正常并发结果，对整个事务做有界、带抖动的幂等重试。

## 超时差异
Q: Deadlock 和 lock wait timeout 有什么本质差异？
A:
- 死锁是等待图成环，不取消任何事务就永远无法前进；检测通常快速选 victim。
- 超时可能只是长等待链，没有环；等待资源最终可能释放。
- `innodb_rollback_on_timeout` 配置会影响超时是否只回滚当前语句还是整个事务，应用不能假设相同。
- 两者都说明延迟和事务设计需治理，但处理日志与重试边界不同。

## 排查与治理
Q: 怎样从死锁报告推导根因并修复？
A:
- 提取每个事务已持有/等待的 index、key、模式和 SQL，画出获取顺序，不只看最后两行语句。
- 用 EXPLAIN 与表数据还原扫描范围，检查缺索引、非唯一范围和事务内更早语句。
- 统一资源访问顺序、缩小批次、建立精准索引、缩短事务；热点可串行化或分片。
- 监控死锁率和重试成功率；零死锁不是目标，持续高频或重试风暴才是问题。
