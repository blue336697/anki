# 不同 SQL、索引条件与加锁范围

## 结构定位
Q: 决定一条 DML 锁多少记录的四个关键变量是什么？
A:
- 隔离级别：RR 与 RC 对 gap/不匹配记录处理不同。
- 访问路径：聚簇等值、唯一二级、非唯一 range、全表扫描会产生不同锁集合。
- 语句类型：一致性读、锁定读、UPDATE/DELETE、INSERT、唯一/外键检查语义不同。
- 实际扫描记录：锁跟执行器访问路径走，不仅跟 SQL 文本的最终结果走。

## 二级索引加锁
Q: 通过二级索引 UPDATE 一行时通常为什么既锁二级记录又锁聚簇记录？
A:
- 二级记录用于搜索并保护该 key 的范围/唯一性；真正行数据和版本位于聚簇记录。
- 修改非索引列仍需聚簇 X 锁；修改索引列还会锁旧/新二级 key 及相关 gap。
- 唯一二级 key 含 NULL 时 SQL 唯一语义允许多个 NULL，不能总按完整唯一等值的最窄锁推导。
- 外键父子检查可能继续访问并锁另一张表的索引。

## INSERT链路
Q: INSERT 新记录时的锁与检查顺序大致是什么？
A:
1. 获得表 IX 和必要 MDL，定位各唯一索引插入位置。
2. 对目标 gap 申请 insert intention，以允许不同位置并发插入。
3. 扫描潜在冲突 key，重复键/外键检查可能申请 S/记录或 gap 相关锁。
4. 成功后插入聚簇与各二级记录并持有新记录 X 语义至提交。

## 无索引代价
Q: `UPDATE t SET ... WHERE non_index_col=?` 会真正锁表吗？
A:
- InnoDB 仍创建记录锁而非自动转换成一个表 X 锁，但全表扫描可能给大量扫描记录加锁，效果上阻塞很广。
- RR next-key 还可能覆盖许多 gap；RC 可较早释放不匹配记录锁，但扫描和 CPU 成本仍在。
- LIMIT 不一定让锁集合总是很小，取决于找到目标前扫描多少行和排序/计划。
- 最根本措施是建立能精确定位写集合的索引并缩短事务。

## 验证与边界
Q: 面试回答加锁题时怎样避免背错“固定答案”？
A:
- 先声明 MySQL/InnoDB 版本、隔离级别、表结构与索引数据，再画 key 区间。
- 明确执行计划，区分二级与聚簇锁、record 与 gap、返回行与扫描行。
- 用双会话实验和 Performance Schema 验证；不同补丁版本优化可能改变边界细节。
- 最后给工程结论：索引、访问顺序、事务大小和重试策略比背某个区间更重要。
