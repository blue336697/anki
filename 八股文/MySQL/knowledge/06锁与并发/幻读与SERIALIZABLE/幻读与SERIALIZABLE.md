# 幻读、谓词保护与 SERIALIZABLE

## 结构定位
Q: MVCC 与 next-key lock 分别怎样处理幻读？
A:
- RR 一致性读复用 Read View，让后来提交的新行在快照中不可见，提供“快照层不出现”。
- 锁定范围读/写使用 next-key lock 阻止其他事务在受保护索引范围插入，提供“当前读层不被改变”。
- MVCC 不阻止他人插入，只决定看不看得见；next-key 才是并发写入约束。
- 没有合适索引时谓词范围无法精确映射，锁定读会扩大扫描锁范围。

## 异常边界
Q: 为什么说 InnoDB RR “解决幻读”需要限定语境？
A:
- 两次纯一致性读通常结果稳定，但事务自己 DML 后能看到自己的版本，可能得到混合快照现象。
- 第一次快照读、第二次当前读本来就采用不同可见性模型，结果变化不违反各自规则。
- 业务谓词如“余额总和不低于 0”可能发生 write skew，单行 MVCC/锁不自动保护跨行不变量。
- 需要把 ANSI 现象、实现机制和业务一致性分别说明。

## SERIALIZABLE机制
Q: InnoDB SERIALIZABLE 相比 RR 增加了什么？
A:
- 在典型显式事务中，普通 SELECT 被转换为共享锁定读，读写冲突和范围保护更强。
- 多事务效果更接近某个串行顺序，但并发下降、锁等待与死锁增多。
- autocommit 单语句等边界应以官方语义验证，不能只背“SELECT 自动 FOR SHARE”。
- SERIALIZABLE 仍需要应用处理死锁/超时，并不提供分布式系统全局串行化。

## 保护算法
Q: 如何用数据库锁保护“范围内不能再出现新行”的业务规则？
A:
1. 建立能表达业务谓词的索引。
2. 在短事务中对该索引范围执行 `SELECT ... FOR UPDATE`/FOR SHARE。
3. 检查条件后执行插入或更新，并提交；并发插入会被 gap/next-key 阻塞。
4. 再加唯一约束或汇总行锁作为最终不变量保护，避免仅靠应用先查后写。

## 验证与实践
Q: 哪些方案比直接把全库改 SERIALIZABLE 更可控？
A:
- 对冲突资源建立唯一约束、版本号 CAS、库存行锁或按业务 key 的互斥记录。
- 对队列使用 SKIP LOCKED，对计数使用原子 UPDATE，对跨行规则锁定明确的 guard row。
- 只在需要稳定快照的报表使用一致性快照，避免长事务阻止 purge。
- 用并发测试证明不变量，应用必须重试死锁与锁超时。
