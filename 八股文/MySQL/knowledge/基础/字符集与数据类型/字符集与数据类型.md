# 字符集与数据类型

## 字符集卡
Q: MySQL 中字符集和 collation 分别控制什么？
A:
- 字符集决定字符串如何编码存储，例如 `utf8mb4`
- collation 决定字符串如何比较和排序，例如是否大小写敏感
- 字符集可在服务器、库、表、列、连接多个层级设置
- 连接层有 `character_set_client/results/connection` 等变量，影响客户端和服务端转换
- 面试表达：乱码和关联异常常常不是 SQL 错，而是字符集与比较规则不一致

## utf8mb4卡
Q: 为什么 MySQL 中通常推荐使用 utf8mb4 而不是 utf8？
A:
- MySQL 早期 `utf8` 实际是 `utf8mb3`，最多存 3 字节字符
- `utf8mb4` 才能完整支持 4 字节 Unicode 字符，例如 emoji
- 新系统应优先统一库、表、列和连接字符集为 `utf8mb4`
- collation 选择会影响排序、唯一索引判断和大小写敏感
- 面试边界：不仅要改表字符集，还要关注连接字符集和已有数据转换

## 类型卡
Q: varchar、text、timestamp 等类型在建表时要注意什么？
A:
- `varchar(n)` 的 n 表示字符数，不是字节数，但行大小受字节限制
- `text` 不适合频繁排序和索引，通常只做前缀索引或单独拆表
- `timestamp` 受时区转换影响，`datetime` 更像原样存储日期时间
- 金额不要用浮点类型，应使用 `decimal` 或整数分单位存储
- 字段类型越小越利于索引页容纳更多记录，但不能牺牲业务范围

## 正确性审查卡
Q: 字符集和数据类型有哪些常见误区？
A:
- “utf8 就一定支持所有字符”：在 MySQL 中通常错误，应使用 `utf8mb4`
- “varchar 长度越大越安全”：不完整。会影响行大小、临时表和内存估算
- “text 可以随便建索引”：错误。通常需要前缀索引，且选择性要评估
- “timestamp 和 datetime 没区别”：错误。时区语义不同
- “隐式类型转换无所谓”：错误。可能导致索引失效或比较结果异常
