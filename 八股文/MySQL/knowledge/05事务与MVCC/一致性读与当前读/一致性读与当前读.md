# 一致性读、当前读与锁定读

## 结构定位
Q: 普通 SELECT、SELECT FOR UPDATE 和 UPDATE 分别读取哪种版本？
A:
- RC/RR 下普通 SELECT 默认是一致性非锁定读，通过 Read View 返回可见历史版本，不阻塞普通写。
- `FOR SHARE/FOR UPDATE` 是锁定当前读，读取最新可用版本并对扫描到的索引记录/间隙加相应锁。
- UPDATE/DELETE 在定位待修改行时也是当前读，并获取 X 锁。
- SERIALIZABLE 会把普通 SELECT 的锁语义加强，具体还受 autocommit 等条件影响。

## 锁定范围
Q: `SELECT ... FOR UPDATE` 锁的是返回行，还是扫描过程遇到的索引范围？
A:
- InnoDB 对实际扫描的索引记录及必要 gap 加锁，范围由执行计划和隔离级别决定，不只由最终返回集决定。
- 有唯一索引完整等值命中时可退化为 record lock；非唯一/范围在 RR 常是 next-key。
- 未命中范围也可能锁住 gap，防止插入造成幻影。
- 无合适索引会扫描并锁更多记录，甚至表现接近锁住整表业务范围。

## 执行算法
Q: 锁定读遇到未提交版本时为什么不能像普通 SELECT 一样直接读 undo 旧值？
A:
1. 当前读目标是获得可修改/保护的最新逻辑记录，旧版本不能被加锁。
2. 若最新记录由其他事务持有不兼容锁，请求进入 lock wait。
3. 对方结束后重新检查记录、条件与可见状态，再获取锁。
4. 普通一致性读则可忽略记录锁，沿 undo 返回快照版本。

## NOWAIT与SKIP LOCKED
Q: NOWAIT 和 SKIP LOCKED 的语义边界是什么？
A:
- NOWAIT 遇到锁立即报错，适合应用自行重试或选择其他任务。
- SKIP LOCKED 跳过已锁记录，结果不是一致业务快照，适合多消费者任务队列而非财务汇总。
- 两者只作用于行级锁定读，不绕过 MDL、表锁或其他资源等待。
- 使用时必须有稳定索引与状态更新协议，否则任务可能饥饿、遗漏或重复。

## 验证与实践
Q: 怎样正确实现数据库工作队列的“抢任务”？
A:
- 用可选择的状态/时间联合索引，短事务执行 `FOR UPDATE SKIP LOCKED LIMIT n`，随后在同事务更新 owner/status。
- 任务处理与抢占事务通常分离，靠租约、幂等键和超时重试处理消费者崩溃。
- 监控跳过率、租约超时、重复执行和长事务；SKIP LOCKED 只降低等待，不提供 exactly-once。
- 用 data_locks 验证锁范围，避免缺索引使每个消费者扫描大量已锁记录。
