# READ COMMITTED 与 REPEATABLE READ

## 结构定位
Q: InnoDB RC 与 RR 最核心的实现差异是什么？
A:
- RR 下同一事务的普通一致性读复用首次建立的 Read View；RC 下每条一致性读使用较新的视图。
- RR 对搜索和索引扫描通常使用 next-key locking 抑制幻影；RC 多数场景禁用 gap lock，仅保留外键/重复键检查等例外。
- 当前读读取最新可锁版本，不遵循普通 SELECT 的旧快照，所以同一事务内两种读可能看到不同结果。
- MySQL InnoDB 默认隔离级别是 RR，但应用、云服务或驱动可能覆盖，必须查询实际变量。

## 现象对比
Q: RC、RR 下不可重复读和幻读分别怎样出现？
A:
- RC 两次普通 SELECT 之间他人已提交更新，第二次新 Read View 可看到新值，产生不可重复读。
- RR 两次一致性读复用视图，通常保持旧结果；但事务自己的写以及当前读会看到最新可锁版本。
- RR 的锁定范围读通过 next-key lock 防止他人在范围中插入；仅靠 MVCC 是“看不见新行”，不是阻止写入。
- 对“幻读是否发生”必须说明一致性读还是当前读、事务是否自己修改，不能一句“RR 完全解决”概括。

## 执行链
Q: RR 事务先快照读、再 UPDATE 范围、再快照读时为什么容易让人困惑？
A:
1. 第一次普通 SELECT 建立旧 Read View。
2. UPDATE 是当前读，搜索最新记录并加锁，可能修改快照建立后他人已提交的行。
3. 事务自己的新版本总是可见，因此后续普通 SELECT 会看到自己改过的行。
4. 未被自己修改的其他行仍可能按旧 Read View 显示，结果组合未必对应数据库曾存在的单一时刻。

## 选择权衡
Q: 业务应怎样选择 RC 或 RR？
A:
- RC 减少 gap lock 与锁冲突，快照更新，适合能接受语句级一致性且显式处理并发写冲突的系统。
- RR 提供事务级稳定快照，适合多次一致性读取；范围写锁更强，也更容易出现 gap 等待。
- 隔离级别不能替代唯一约束、幂等、版本号 CAS 或业务锁。
- 变更隔离级别必须回归死锁、复制格式、报表一致性和 ORM 行为。

## 验证与排障
Q: 隔离级别相关问题应如何复现和取证？
A:
- 明确 autocommit、事务起止、每条语句类型和提交时点，写出双会话时间线。
- 查询 `@@transaction_isolation`，用 `data_locks` 验证 record/gap 锁，而不是依据等待现象猜测。
- 记录每次 SELECT 是普通、FOR UPDATE 还是 DML 内部读取。
- 使用最小表和确定索引复现；缺索引会扩大扫描与锁范围，改变结论。
