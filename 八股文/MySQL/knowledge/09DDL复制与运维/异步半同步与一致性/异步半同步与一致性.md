# 异步、半同步复制与读写一致性

## 结构定位
Q: 异步复制和半同步复制分别对主库 commit 提供什么保证？
A:
- 异步在本地提交后即可返回，不等待副本；主机永久丢失时最新 binlog 可能尚未复制。
- 半同步等待至少一个副本确认已接收并写入 relay log/相应持久层后再返回，具体 ACK 点受插件配置。
- ACK 不等于事务已由副本 applier 执行，也不等于多个副本形成共识。
- 超时后半同步通常退化为异步以保可用性，必须监控状态。

## ACK边界
Q: AFTER_SYNC 与 AFTER_COMMIT 类等待点为什么影响故障语义？
A:
- 更早/更严格地在主库对外可见前完成 binlog sync 与副本 ACK，可减少旧主本地可见但故障切换丢失的窗口。
- 不同等待点影响主库锁释放、客户端延迟和“返回前至少一份远端日志”的含义。
- 无论哪种，副本应用延迟仍存在，读副本可能看不到刚提交事务。
- 8.4 使用 source/replica 新术语和对应半同步插件，配置应核对实际变量。

## 读己之写
Q: 应用写主读从怎样实现 read-your-writes？
A:
1. 写成功后获取/记录事务 GTID 或一致性 token。
2. 读副本前等待该副本 executed set 包含 token，或在短窗口内路由主库。
3. 超时按业务选择回主、失败或接受旧读。
4. 仅 sleep 固定时间无法适应延迟波动，也不提供证明。
5. Token 必须随用户请求链路传播；负载均衡器随机换副本时，每个候选都要满足该执行集合边界。

## CAP边界
Q: 半同步是否等于强一致/不丢数据？
A:
- 不是。只要确认副本随后也故障、ACK 未持久、超时退化或错误选主，仍可能丢失/分叉。
- 网络分区下继续接受写与保证唯一主/零丢失存在权衡，需要选主仲裁和 fencing。
- 跨地域 RTT 直接进入 commit p99，半同步副本位置是可用性与延迟选择。
- 更强保证可用 Group Replication/共识类系统，但也有 quorum 与性能成本。

## 验证
Q: 如何验证半同步配置真正工作？
A:
- 观察半同步 status、等待事务数、超时/退化次数和 commit latency。
- 故障注入断开副本、延迟 fsync、杀主库，检查 ACK 后事务是否存在于候选。
- 区分 received 与 executed GTID，测试写后立即读副本。
- 告警必须覆盖“插件加载但当前已 OFF/退化”的状态。
