# 并行复制、依赖跟踪与延迟治理

## 结构定位
Q: MySQL 副本并行应用怎样保证有冲突的事务仍按正确顺序？
A:
- coordinator 从 relay log 读取事务，根据主库提交依赖/写集合等元数据分配 worker。
- 无依赖事务可并行执行，有依赖事务必须等待前序；worker commit 还可配置保持提交顺序。
- 主库 group commit 和 write set extraction 提供可并行性信息。
- 增加 worker 只提高可并行部分上限，单热点 key/大事务仍串行。

## 依赖结构
Q: LOGICAL_CLOCK 与 WRITESET 思路分别利用什么并行性？
A:
- logical clock 利用主库提交组或 last_committed/sequence_number，认为无依赖窗口事务可并行。
- writeset 对事务修改 key 做 hash，检测冲突，能发现跨提交组的独立事务。
- hash 冲突会保守串行，不会破坏正确性；缺主键/大事务会降低效果和增加跟踪成本。
- 具体变量与默认值随 8.x 演进，应查询当前实例。

## 应用算法
Q: 一个并行复制事务如何从 coordinator 到 commit？
A:
1. coordinator 解析事务边界与依赖元数据。
2. 等待依赖满足后派给 worker，worker 在副本 InnoDB 执行 row events。
3. 若保持提交顺序，执行完成还可能等待 sequence 前序事务 commit。
4. 更新 executed GTID 与 worker checkpoint，relay 位置向前推进。

## 延迟边界
Q: worker 开很多为什么可能更慢？
A:
- worker 竞争 CPU、Buffer Pool、redo fsync、锁和热点页；上下文切换上升。
- commit-order 等待导致已执行 worker 堆积内存，最慢事务形成队头阻塞。
- 副本硬件或持久参数弱于主库时，瓶颈在 I/O 而非调度。
- 大事务无法在事务内部自动拆分，会独占一个 worker。

## 验证与治理
Q: 复制延迟应怎样分层治理？
A:
- 先分网络 receive lag、relay backlog、worker apply 和 commit-order wait。
- 修主库大事务、无主键、热点更新与 DDL；确保副本硬件/持久配置能承载源端日志率。
- 再调 worker、writeset 与 preserve commit order，并压测读负载共存。
- 建立 GTID lag/bytes lag/oldest transaction age 告警，不依赖单一 Seconds_Behind_Source。
