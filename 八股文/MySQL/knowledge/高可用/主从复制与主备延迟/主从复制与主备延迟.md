# 主从复制与主备延迟

## 复制卡
Q: MySQL 主从复制的基本流程是什么？
A:
- 主库提交事务后写 binlog
- 从库 IO 线程拉取主库 binlog 写入 relay log
- 从库 SQL 线程或 worker 重放 relay log
- row 格式下从库按行变更重放，语义更确定
- 面试表达：复制本质是从库持续获取并重放主库提交日志

## 延迟卡
Q: 主备延迟通常由哪些原因导致？
A:
- 主库写入并发高，从库重放能力不足
- 大事务或大 DDL 导致从库长时间应用
- 从库机器性能、IO、网络弱于主库
- 从库并行复制粒度不够，无法充分利用多核
- 从库承担读流量过大，也会拖慢回放

## 切换卡
Q: 主库故障时如何理解可靠性优先和可用性优先？
A:
- 可靠性优先会尽量等待从库追上主库，减少数据丢失
- 可用性优先更快切换，但可能丢失未复制事务
- 半同步复制能降低事务已提交但未复制的窗口
- 切换后要处理旧主恢复、脑裂和数据补偿
- 面试表达：高可用不是只切 VIP，还要讲数据一致性和故障窗口

## 正确性审查卡
Q: 主从复制有哪些常见误区？
A:
- “从库一定实时同步”：错误。异步复制天然可能延迟
- “读写分离一定提升性能”：不一定。延迟读会带来一致性问题
- “半同步绝对不丢数据”：不完整。要看确认时机、故障组合和配置
- “复制延迟只和网络有关”：错误。从库回放能力和大事务也很关键
- “切换后旧主直接加回来”：危险。要先确认数据差异和复制位点
