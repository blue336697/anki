# 访问方法与成本模型

## 结构定位
Q: EXPLAIN 的 system/const/ref/range/index/ALL 表示什么层次？
A:
- 它们描述表的访问方法，不是整条查询的绝对性能排名。
- const 用唯一 key 常量定位至多一行，ref 用非唯一等值，range 扫若干索引区间。
- index 是扫描整棵索引，ALL 是扫描表/聚簇索引；index 若很宽或大量回表也可能慢。
- 8.x TREE 还会直接显示 index lookup/range scan/table scan 等更具体节点。

## 成本组成
Q: 优化器比较索引回表和全表扫描时成本由什么组成？
A:
- 估算读取页/行数乘 I/O 与 CPU 单位成本，加上条件计算、回表、排序、临时表等代价。
- `mysql.server_cost/engine_cost` 可配置部分成本常数；默认模型只是硬件近似。
- Buffer Pool 是否热、顺序/随机 I/O 与并发缓存污染难被完美预测。
- 所以“cost 更小”是模型内相对值，不能跨不同服务器直接当毫秒。

## 路径选择
Q: 为什么优化器有时宁愿全表扫描也不用低选择性索引？
A:
1. 统计估计索引会返回大量主键。
2. 二级扫描加随机回表的页访问成本高于顺序聚簇扫描。
3. 若查询取多数列且无小 LIMIT，覆盖与提前停止优势不存在。
4. 选择 ALL 是合理候选；若估算错误再用 ANALYZE 证明并修统计/索引。
5. 若强制索引只在热缓存测试中更快，冷缓存或高并发下可能反而恶化，不能据一次执行固化 hint。

## 边界与版本
Q: `rows × filtered` 能精确预测上层输出吗？
A:
- 它们是估算且受显示舍入，连接 loops 会放大误差。
- filtered 是剩余条件预计通过比例，不包含所有算子语义。
- Hash join、materialize、sort 等树算子在传统表格中难以按一行公式还原。
- 用 EXPLAIN ANALYZE 的 actual rows/loops/time 对照模型。

## 实践
Q: 优化器选错索引时正确治理顺序是什么？
A:
- 校验 SQL 参数类型、统计、直方图、索引和数据分布。
- 对比候选 plan 的真实 I/O/CPU/尾延迟，确认不是偶发缓存。
- 再考虑改索引、重写 SQL或成本配置；hint 可临时止血。
- 记录版本升级前计划基线，因为 optimizer 与 cost model 会演进。
