# Histogram 与数据倾斜

## 结构定位
Q: MySQL 8 histogram 补充了索引基数统计的什么缺陷？
A:
- 普通基数多用平均分布估算，无法知道某个具体值特别热或范围分布不均。
- histogram 在数据字典 `column_statistics` 中保存桶分布，帮助无合适索引列或非均匀谓词估行。
- singleton 适合 distinct 较少，equi-height 把近似相同记录数分桶。
- 通过 `ANALYZE TABLE ... UPDATE HISTOGRAM` 创建，INFORMATION_SCHEMA.COLUMN_STATISTICS 查看。

## 桶结构
Q: 等高直方图一个桶大致表达什么？
A:
- 保存下界、上界、累计频率和桶内 distinct 估计，使范围/等值选择率不再只按全局均匀分布。
- 桶数越多通常能表达更多细节，但采样、存储和维护成本增加。
- 它主要描述单列边际分布，不能天然表达多列相关性。
- 数据变化后 histogram 不自动像实时计数器一样精确，需治理更新周期。

## 估算算法
Q: 优化器怎样用 histogram 估算 `col BETWEEN x AND y`？
A:
1. 找到 x/y 所在桶及完全覆盖的中间桶。
2. 完整桶使用累计频率差，边界桶按桶内分布假设插值。
3. 将选择率乘表行数，作为该谓词基数估算的一部分。
4. 再与其他谓词按可用相关性模型组合，所以多条件仍可能偏差。
5. 若边界值集中在桶内少数热点，均匀插值仍会失真；增加桶或改变数据建模后必须用 actual rows 验证。

## 边界与代价
Q: 有索引的列还需要 histogram 吗？
A:
- 某些索引 range 估算可直接探测索引，histogram 可能不被使用；是否有益要看计划和版本。
- 高频变化列直方图很快陈旧，维护成本可能高于收益。
- 增加桶不能修复列间强相关和参数化 SQL 的所有计划问题。
- histogram 影响计划但不加速执行本身，最终仍需合适访问路径。

## 验证
Q: 如何验证 histogram 改善而未引入 plan regression？
A:
- 保存更新前后的 JSON/TREE EXPLAIN、estimated/actual rows、耗时和 optimizer trace。
- 用热点、冷门、范围边界多组参数测试，不只测一个值。
- 需要回退时 `DROP HISTOGRAM` 并重新验证计划。
- 把 histogram DDL 纳入变更管理和版本升级回归。
