# InnoDB 持久统计与基数估算

## 结构定位
Q: 优化器为什么依赖统计信息，而不能执行前精确数每个条件的行数？
A:
- 精确扫描本身可能与执行查询同样昂贵，优化器必须用低成本估算比较大量候选。
- InnoDB 持久统计保存表行数、索引页、不同前缀基数等近似值，可跨重启复用。
- 统计通常通过采样索引页获得，`innodb_stats_persistent_sample_pages` 影响精度和 ANALYZE 成本。
- 估算进入访问方法、连接顺序、join buffer、排序和物化决策。

## 统计结构
Q: 联合索引的 n_diff_pfx 与选择率怎样关联？
A:
- `n_diff_pfx01...` 估计索引前 1、2...列的不同值数，等值命中行数可近似 rows/distinct。
- 平均值无法描述热点倾斜和列间相关性；`tenant_id,status` 的独立假设可能严重错误。
- NULL、删除标记、采样页和快速变化数据都会引入偏差。
- 统计是计划输入而非正确性数据，不能用估算 rows 当精确业务计数。

## 更新算法
Q: `ANALYZE TABLE` 做了什么，为什么可能改变计划？
A:
1. 读取/采样索引页并重新估计基数和页信息。
2. 更新持久统计表与内存缓存。
3. 后续语句重新优化时使用新估值，访问索引或连接顺序可能变化。
4. 它不“整理索引数据页”，也不保证计划一定更好；采样误差仍存在。
5. 已执行中的语句不会因统计更新在中途换计划；需要重新优化的新执行才会消费新统计。

## 边界与代价
Q: 自动统计何时可能不及时或不稳定？
A:
- 大表少量但分布关键的变更可能未达到自动重算条件。
- 采样页少时不同 ANALYZE 结果波动；分区/热点数据分布更复杂。
- ANALYZE 需读取页并取得必要元数据锁，生产应评估负载。
- Plan regression 要保存前后统计、EXPLAIN 和变量，不能只回滚 SQL 文本。

## 验证与治理
Q: 发现 estimated rows 与 actual rows 差几个数量级怎么办？
A:
- 先确认谓词类型、隐式转换、数据倾斜和列相关性，再更新统计。
- 单列倾斜可建 histogram，列相关可改联合索引/生成列，不能只无限提高采样。
- 用 EXPLAIN ANALYZE 找最早的估算爆炸节点，因为上层误差会乘法传播。
- 临时 hint 固定路径时设置回收条件，长期修复统计或数据模型。
