# 内部临时表、GROUP BY 与 DISTINCT

## 结构定位
Q: 哪些执行场景会创建内部临时表？
A:
- GROUP BY、DISTINCT、UNION、某些 ORDER BY、窗口函数、derived/CTE materialization 和 semijoin weedout。
- MySQL 8 默认内部 TempTable 引擎处理多数内存临时表，超过限制或含特定列时可转磁盘。
- “Using temporary”表示计划需要中间物化，不等于创建用户可见 TEMPORARY TABLE。
- 临时表可建内部索引用于去重或后续 lookup。

## 聚合结构
Q: GROUP BY 可通过哪几类路径执行？
A:
- 利用索引顺序流式分组，连续相同 key 聚合，内存较小。
- Loose index scan 跳过组内多数记录，适合特定 MIN/MAX 或分组形态。
- 先扫描并用临时表/hash-like 结构累计，再排序/输出。
- 具体 8.4 iterator 路径以 TREE/ANALYZE 为准，不能一概说“GROUP BY 必排序”。

## 物化算法
Q: 一个 derived table materialization 如何执行？
A:
1. 执行子查询并把结果写 TempTable，必要时去重。
2. 优化器可能为物化结果添加临时索引。
3. 外层把它当表扫描或 lookup；若只使用一次也可能延迟到真正需要时才物化。
4. 若满足 merge 条件，优化器可消除物化并把谓词下推。
5. 物化结果的列宽、行数和被重复探测次数共同决定收益；只看子查询是否“大”不足以判断。

## 内存与落盘
Q: 临时表何时落盘，为什么不能只调大 `tmp_table_size`？
A:
- 受 `tmp_table_size`、`temptable_max_ram`、行宽、并发和 TempTable mmap/磁盘策略共同影响。
- 单表不落盘不代表安全：大量并发临时表的总内存可能很高。
- BLOB/TEXT 与具体版本支持会影响路径，旧“有 TEXT 必落盘”口诀可能过时。
- 减少中间行和行宽通常比全局放大阈值更有效。

## 验证
Q: 怎样排查 GROUP BY/DISTINCT 导致的抖动？
A:
- ANALYZE 找物化节点实际 rows、loops 与耗时，观察 created_tmp_tables/disk_tables 的增量。
- 关联 tmpdir I/O、内存和并发，而非只看一条 SQL。
- 考虑匹配过滤+分组顺序的索引、预聚合、分批和结果缓存。
- 任何阈值调整要按“每查询 × 并发”做峰值预算。
