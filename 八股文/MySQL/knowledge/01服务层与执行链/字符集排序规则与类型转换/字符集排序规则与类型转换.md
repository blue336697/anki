# 字符集、排序规则与隐式类型转换

## 结构定位
Q: MySQL 中 character set、collation、connection charset 分别决定什么？
A:
- character set 定义字符到字节的编码；collation 定义比较、排序、大小写和重音是否敏感等规则。
- 列有持久化字符集/排序规则；连接有 client、connection、results 三组字符集，服务端按它们解码 SQL 与编码结果。
- 比较表达式会依据 coercibility 和兼容性选择共同排序规则，必要时转换一侧，结果可能影响索引可用性。
- MySQL 的 `utf8mb3` 最多 3 字节且已弃用方向；现代业务通常使用 `utf8mb4`。

## 编码与索引布局
Q: utf8mb4 为什么会影响 InnoDB 行大小和索引设计？
A:
- `VARCHAR(n)` 的 n 是字符数，但页内实际占用取决于字节长度；utf8mb4 最坏每字符 4 字节，还要加长度字段和记录开销。
- B+ 树索引按排序权重比较 key；不同 collation 的权重长度、大小写规则会改变选择性与唯一性语义。
- 索引 key 有字节上限，长字符列常需前缀索引、生成列哈希或重新设计键；不能只按字符数估算。
- DYNAMIC 行格式可把长列放到溢出页，但索引列本身仍受最大索引长度约束。

## 转换算法
Q: 字符串与数字或不同字符集比较时，隐式转换为什么可能让索引失效或结果意外？
A:
1. 解析/类型推导阶段先确定比较的共同类型与 collation。
2. 如果对索引列施加函数或把列转换为另一类型，原 B+ 树顺序通常不能直接用于 range 定位。
3. 例如字符列与数字比较可能按数值语义转换多个不同字符串为同一数，既影响结果也可能扫描更多行。
4. 最稳妥做法是参数类型与列类型一致，跨字符集时显式校正并用 EXPLAIN 验证转换发生在哪一侧。

## 版本与边界
Q: `utf8mb4_general_ci`、`utf8mb4_0900_ai_ci` 和二进制排序规则该怎么选？
A:
- 8.0 默认 `utf8mb4_0900_ai_ci` 基于较新的 Unicode 排序，`ai/ci` 表示不区分重音/大小写；旧 general 规则更粗糙。
- `_bin` 或 binary collation 更接近按编码值比较，但“字节完全相同”还要区分 CHAR 尾空格等 SQL 语义。
- 排序规则影响唯一索引：在不区分大小写规则下，`A` 与 `a` 可能冲突。
- 修改列 collation 可能重建表和索引，并改变查询结果；必须先做重复值检测和容量评估。

## 边界与验证
Q: 排查中文乱码、比较异常和字符串索引不生效时怎样验证？
A:
- 查看 `SHOW CREATE TABLE`、`character_set_%`、`collation_%`，同时检查驱动连接参数，不能只看数据库默认值。
- 用 `HEX(col)` 区分“存储字节已错”与“展示解码错”；前者仅改连接字符集无法修复。
- 用 `EXPLAIN FORMAT=TREE` 和 optimizer trace 检查是否对列做了 cast/collation conversion。
- 迁移前在副本或快照上验证排序、唯一冲突、索引长度、重建耗时与回滚方案。
