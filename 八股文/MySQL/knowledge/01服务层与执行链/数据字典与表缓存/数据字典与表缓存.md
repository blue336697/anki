# MySQL 8 数据字典与表缓存

## 结构定位
Q: MySQL 8 的事务数据字典解决了 5.7 时代什么问题？
A:
- 8.0 起表、列、索引、权限等元数据集中存入 InnoDB 数据字典表，替代 `.frm` 等分散且缺少事务一致性的文件。
- DDL 的字典变更、存储引擎变更和 binlog 可以纳入原子提交，崩溃后不会轻易出现“定义已改、数据未改”的半状态。
- 用户通过 INFORMATION_SCHEMA 视图访问字典，不能把内部 `mysql.*` 字典表当普通业务表直接修改。
- 源码锚点：`sql/dd/`、`sql/dd/cache/`、InnoDB `dict0dict.*`。

## 缓存结构
Q: 数据字典缓存、table definition cache 和 table open cache 有什么区别？
A:
- Dictionary Client/cache 缓存 schema、table、column 等 DD 对象，减少反复读取字典表。
- Table Definition Cache 复用 `TABLE_SHARE` 这类解析后的共享定义；Table Open Cache 复用已打开的 `TABLE`/handler 实例。
- 同一张表可有一个共享定义和多个会话打开实例；缓存条目仍受 MDL 与版本校验约束，不能绕过 DDL 一致性。
- 缓存过小会造成频繁 open/close，过大则增加内存和字典维护成本。

## DDL一致性链
Q: 原子 DDL 在崩溃安全上如何协同数据字典、InnoDB 和 binlog？
A:
1. 服务层取得 MDL，准备新的字典对象和引擎操作。
2. InnoDB 在内部事务中完成表/索引元数据及必要的数据文件变更，并记录 redo/DDL log。
3. 数据字典修改与引擎事务按原子 DDL 协议提交，同时写入 binlog，成功后使新定义可见。
4. 崩溃恢复依据 redo、DDL log 和字典状态完成或回滚未完成操作，目标是让 DDL 对外只呈现旧或新状态。

## 代价与版本
Q: “MySQL 8 DDL 都是事务性的，因此可以 ROLLBACK”为什么错误？
A:
- 原子 DDL 指单条受支持 DDL 的崩溃原子性，不等于像 PostgreSQL 那样允许用户在多条 DDL 之间随意事务回滚。
- 多数 DDL 会隐式提交当前事务；成功后不能靠用户 `ROLLBACK` 撤销。
- INSTANT、INPLACE、COPY 描述执行算法与并发能力，和“是否原子”是不同维度。
- 临时表、非 InnoDB 引擎或某些账户管理语句存在各自边界，必须查具体语句支持矩阵。

## 边界与验证
Q: 表频繁打开、DDL 卡住或元数据不一致时看哪些证据？
A:
- 用 `performance_schema.metadata_locks` 看 MDL 持有与等待，用 `sys.schema_table_lock_waits` 关联阻塞会话。
- `Opened_tables` 持续快速增长且 `table_open_cache_hits` 低，才考虑 table open cache；不要只看表数量。
- DDL 后用 `SHOW CREATE TABLE`、INFORMATION_SCHEMA 和错误日志核对定义；异常恢复问题结合 DDL log/redo 恢复日志。
- 长事务即使不访问目标表，也可能因已持有的 MDL 或未结束语句阻塞 DDL，所以必须沿等待链定位。
