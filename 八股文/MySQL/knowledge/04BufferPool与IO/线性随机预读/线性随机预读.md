# 线性预读、随机预读与扫描

## 结构定位
Q: InnoDB read-ahead 想解决什么问题，线性预读如何触发？
A:
- 单页同步读取无法充分利用顺序存储吞吐；read-ahead 提前异步读取未来可能访问的 extent 页。
- 线性预读观察同一 extent 中按页号顺序访问的页数，达到 `innodb_read_ahead_threshold` 后预取下一个 extent。
- 随机预读依据同一 extent 多页被访问推测其余页也会用到；现代版本默认配置需以实际变量为准。
- 预读页进入 Buffer Pool old 区，避免立即污染最热区域。

## 逻辑物理关系
Q: B+ 树范围扫描逻辑连续时，为什么预读不一定有效？
A:
- 叶子页通过 next 链逻辑连续，但页分裂后物理 page no 可能离散，线性页号模式不足。
- 过滤率高、LIMIT 小或缓存已命中时，预读出的页可能从未使用。
- 云盘/SSD 随机读差距较小，但高并发下队列与带宽仍会影响收益。
- 预读浪费会占 I/O、Buffer Pool 和解压 CPU，必须基于 workload 判断。

## 触发流程
Q: 一次范围扫描如何与异步 I/O 和 Buffer Pool 协作？
A:
1. 游标沿叶子链请求下一页，命中直接读取。
2. 访问模式达到阈值后，read-ahead 提交一批异步页读。
3. I/O 线程完成校验并把页加入 Buffer Pool，前台到达时若已完成即可避免同步等待。
4. 未被使用的预读页最终从 old LRU 淘汰，相关计数用于评估浪费。

## 代价与调参
Q: 为什么不能看到磁盘吞吐低就直接调低 read_ahead_threshold？
A:
- 阈值低会更激进预读，可能放大无用 I/O；吞吐低也可能是随机点查、队列深度不足或被 fsync 限制。
- 阈值只影响线性模式，不能修复逻辑页物理碎片和缺失索引。
- Buffer Pool 太小、扫描并发高时，预读更容易挤出热点。
- 首先用 `Innodb_buffer_pool_read_ahead` 与 `read_ahead_evicted` 判断命中质量。

## 验证与工程实践
Q: 哪些场景适合用顺序扫描能力，哪些应避免？
A:
- 大范围导出、校验和分析可在副本上按聚簇主键分段，利于叶子链与预读。
- OLTP 主库的无界扫描应通过索引、分区裁剪、限流或离线数仓转移。
- 比较逻辑读、物理读、预读页、未使用淘汰、设备吞吐和热点查询延迟。
- 预热与预读不是一回事：前者主动建立工作集，后者由访问模式预测未来页。
