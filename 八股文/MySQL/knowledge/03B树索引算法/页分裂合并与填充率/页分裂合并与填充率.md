# B+ 树页分裂、合并与填充率

## 结构定位
Q: InnoDB 叶子页插不下新记录时为什么需要分裂？
A:
- B+ 树必须保持 key 有序并让每页不超过容量；页内重组仍无足够连续空间时，需分配新页并重分配记录。
- 新旧页更新叶子前后链，父页插入新的 node pointer；父页也满时分裂可向上传播，根分裂使树高增加。
- 所有结构变化在 latch 保护下由 mini-transaction 记录 redo，保证崩溃恢复后树结构一致。
- 分裂是局部结构操作，不等同于 SQL 事务提交。

## 内部状态
Q: 顺序插入和随机插入导致的分裂形态为什么不同？
A:
- 顺序插入多发生在最右页，可按右边界策略保留较好填充和局部性。
- 随机插入落在全树中间，页通常被拆成两个并留下未来空间，造成更多页、随机写和缓存工作集。
- 删除留下页内空间可供后续复用；物理页不会因每次 DELETE 立即归还文件。
- `MERGE_THRESHOLD` 控制低填充页何时尝试与邻页合并，具体行为是版本实现细节。

## 分裂算法
Q: 一次页分裂需要修改哪些持久化关系？
A:
1. 分配并初始化新页，确定 split point，把部分记录移动到新页。
2. 修正旧页、新页及相邻页的 prev/next。
3. 在父页插入指向新页的最小分隔 key；必要时递归分裂父页。
4. 更新 segment、页头和可能的自适应哈希条目，并生成相应 redo。

## 代价与误区
Q: 页分裂的成本为什么不只是“多写一个页”？
A:
- 需要 latch 多页、移动记录、写 redo、修改父页，可能触发级联分裂。
- 新页降低缓存密度并增加后续扫描页数；脏页最终还要 doublewrite 与数据文件落盘。
- 二级索引也分别分裂，所以随机长主键会同时放大各二级索引记录与聚簇写入。
- “自增永不分裂”错误；右侧页满同样分裂，只是模式更可预测。

## 验证与治理
Q: 怎样判断索引碎片或页分裂值得治理？
A:
- 结合页数、数据量、索引大小、写放大、Buffer Pool 命中与范围扫描耗时，不能只看文件大。
- 重建索引/表可提高填充率并回收独立表空间，但需要额外空间、redo/binlog、复制容量和 MDL 窗口。
- 首选修正随机宽主键、冗余索引与删除归档模式；周期性无差别 OPTIMIZE 常把问题变成维护抖动。
- 在同样数据分布下压测重建前后真实 p95/p99，确认收益大于重建风险。
