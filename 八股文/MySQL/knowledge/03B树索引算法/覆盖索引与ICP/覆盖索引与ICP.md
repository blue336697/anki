# 覆盖索引与 Index Condition Pushdown

## 结构定位
Q: 覆盖索引和 ICP 分别减少哪一部分工作？
A:
- 覆盖索引表示查询所需列都能从当前索引记录取得，可避免为取列访问聚簇索引。
- ICP 把可用索引列判断的部分 WHERE 下推给存储引擎，在二级索引扫描时先过滤，再决定是否回表。
- 覆盖解决“取数据是否回表”，ICP 解决“哪些候选值得回表”；两者可以独立出现。
- EXPLAIN 常以 `Using index` 和 `Using index condition` 分别提示。

## 执行边界
Q: 哪些条件适合 ICP，哪些仍要在 Server 层判断？
A:
- 只依赖当前索引记录可取得列、且引擎可执行的谓词适合下推。
- 涉及未包含列的条件必须先回表；存储函数、子查询、触发器相关表达式等存在下推限制。
- ICP 主要对二级索引减少聚簇查找；聚簇索引已经读取完整行，收益形态不同。
- 下推不会改变 range 边界，只过滤 range 扫描得到的候选。

## 执行算法
Q: 二级 range + ICP 的逐行链路是什么？
A:
1. range iterator 定位下一条二级索引记录。
2. InnoDB 从该记录取可用字段，执行 pushed index condition。
3. 条件失败则直接移动到下一二级记录；成功才按主键读取聚簇记录。
4. server 再执行剩余条件、投影与上层算子。

## 代价权衡
Q: 为什么不能无限追加列构造“万能覆盖索引”？
A:
- 索引越宽，单页记录越少、树更大，Buffer Pool 命中下降，插入/更新/redo/binlog 成本上升。
- 可变长大列和低频查询的覆盖收益往往抵不过全局写成本。
- 列顺序还服务 range 与排序；只为覆盖把大列放入 key 可能破坏更重要的访问需求。
- 应围绕稳定高频查询建立少量索引，并通过真实读写 workload 验证。

## 边界与验证
Q: EXPLAIN 显示 Using index 就能断言零回表吗？
A:
- 通常表示计划层面可覆盖，但 InnoDB MVCC 在某些并发版本场景可能仍回聚簇记录确认可见性。
- EXPLAIN 是估算，不能告诉你真实扫描数和缓存 miss；需配合 ANALYZE 与 I/O 指标。
- SELECT * 几乎破坏覆盖并增加网络与对象创建；应明确投影。
- 隐式类型转换或 collation 变化还可能让预期 range 退化，即使索引包含所有列。
