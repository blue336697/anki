# 索引选择性、冗余与设计审查

## 结构定位
Q: 什么是索引选择性，它为什么不是决定索引价值的唯一指标？
A:
- 选择性近似 `distinct_values / rows`；越高通常每次等值命中越少。
- 但索引价值还取决于查询频率、联合前缀、范围、排序、覆盖、LIMIT 与回表成本。
- 低选择性状态列与高选择性租户/时间组合后可能形成非常有效的联合索引。
- 优化器使用采样统计与直方图估行，不会直接扫描全表计算精确选择性。

## 冗余关系
Q: `(a,b,c)` 建立后，哪些单列/联合索引可能冗余，为什么不能机械删除？
A:
- 在同方向普通 B-tree 下，`(a)`、`(a,b)`常可由左前缀替代。
- 但较窄索引页更少，某些高频只查 a 的查询可能成本更低；UNIQUE、前缀长度、排序方向和覆盖语义也可能不同。
- `(b)`不能由 `(a,b,c)`常规替代，除非优化器使用代价可接受的 skip scan。
- 删除前应结合 `sys.schema_redundant_indexes`、使用统计和完整 workload，不要只看 DDL 前缀。

## 设计流程
Q: 为一组 SQL 设计索引时应按什么顺序推导？
A:
1. 归一化高频 SQL，列出等值、IN、范围、连接、排序、分组、投影与 LIMIT。
2. 选择能形成窄扫描区间的稳定等值前缀，再安排范围和顺序列。
3. 仅加入少量高价值覆盖列，检查是否可合并已有索引。
4. 用代表性分布测试计划与写入代价，再通过 invisible index/灰度上线。

## 写入代价
Q: 每增加一个二级索引，DML 内部增加哪些工作？
A:
- INSERT 要构造并插入一条二级记录、检查唯一性、可能页分裂，并写 redo/undo/binlog。
- UPDATE 若改变索引列，表现为旧 key delete-mark 与新 key insert；即便不改 key，宽索引也占缓存。
- DELETE 对每个索引标记并最终 purge；备份、复制和 DDL 重建数据量也增加。
- change buffer 只缓冲部分非唯一二级页修改，不能消除索引写成本。

## 边界与验证
Q: 如何安全删除“长期未使用”的索引？
A:
- Performance Schema 使用计数自实例启动或重置后累计，可能漏掉月末任务、故障切换和约束用途。
- 先确认是否支撑外键、唯一约束、关键 ORDER BY 和应急查询。
- MySQL 8 可先 `ALTER INDEX ... INVISIBLE`，让优化器默认不选但保留维护，观察完整业务周期后再删除。
- invisible 索引仍占空间并参与 DML，适合可回退验证，不是长期免费保留。
