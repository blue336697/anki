# 联合索引、最左前缀与范围边界

## 结构定位
Q: 联合索引 `(a,b,c)` 的“最左前缀”本质是什么？
A:
- B+ 树按 `(a,b,c,主键补充列)` 的字典序排列；只有先固定或限定前导列，后续列才形成连续可定位区间。
- 可用前缀包括 `a`、`a,b`、`a,b,c`，也可能在跳过前导列时使用 skip scan，但那是额外枚举算法而非改变排序。
- 索引是否“使用到某列”要区分 range 定位、ICP 过滤、覆盖返回和排序，不能只看 key 名。
- 比较还受 ASC/DESC、NULL 和 collation 影响。

## 区间结构
Q: `a=1 AND b>10 AND c=3` 为什么 c 通常不能继续缩小单一扫描区间？
A:
- 索引 key 区间是 `[(1,10,-∞),(1,+∞,+∞)]`；在 b 的不同值之间，c=3 的记录并不连续成一个更小区间。
- c 仍可由 ICP 在二级索引记录上过滤，避免部分回表，但扫描的 b 范围没有消失。
- 若业务主要按 a、c 等值再按 b 范围，索引 `(a,c,b)` 可能更合适。
- 8.x range optimizer 可构造多个区间，但不能违反 B+ 树字典序的连续性。

## 区间推导
Q: 优化器怎样从 WHERE 条件构造联合索引 ranges？
A:
1. 抽取可 sargable 的等值、IN、比较、BETWEEN、IS NULL 等谓词。
2. 按索引列顺序组合前缀；等值/小 IN 可继续展开下一列，首个宽范围通常终止连续前缀扩展。
3. 合并重叠区间并估算命中行数，选择 range/ref 等访问方法。
4. 未进入边界的条件留给 ICP 或 server filter，EXPLAIN 的 key_len 只能辅助判断。

## 设计代价
Q: 联合索引列顺序应只按“区分度最高放最左”吗？
A:
- 不应。先满足真实查询的等值前缀、范围、排序/分组和覆盖需求，再比较选择性。
- 高选择性列若查询不提供，也无法直接定位；低选择性租户列放最左可能是必要的隔离前缀。
- 一条宽联合索引可能替代若干前缀索引，但会增加写放大与页占用；冗余判断需考虑排序方向和覆盖列。
- 索引设计是 workload 设计，不存在脱离 SQL 集合的固定口诀。

## 边界与验证
Q: 怎样验证联合索引实际用了哪几层能力？
A:
- 看 EXPLAIN 的 access type、key/key_len、rows、filtered、Extra，再用 TREE/ANALYZE 看实际 range 与过滤。
- `Using index` 表示覆盖，`Using index condition` 表示 ICP，二者不是“用了索引/没用索引”的二选一。
- 对参数分布倾斜的 SQL 分别验证高频值和低频值；同一索引可能因成本不同被放弃。
- 生产加索引前使用 invisible index 或副本验证，并检查写 TPS、空间和复制延迟。
