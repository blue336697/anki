# 索引顺序、范围扫描与 ORDER BY

## 结构定位
Q: 什么条件下 MySQL 能直接利用 B+ 树顺序完成 ORDER BY？
A:
- 访问路径输出顺序必须与 ORDER BY 的列序、方向和前导常量约束兼容。
- 联合索引中被等值固定的前导列可跳过；后续排序列必须形成一致的索引序。
- MySQL 8 支持降序索引和反向扫描，但混合 ASC/DESC 仍需与索引定义的 homogeneity 匹配。
- 多表连接时，排序列是否来自连接顺序中的首个非 const 表也会影响能否保序。

## 物理顺序
Q: 聚簇索引“按主键有序”是否意味着磁盘文件中的页物理连续？
A:
- 只保证 B+ 树叶子逻辑顺序和页内 key 顺序；分裂后相邻逻辑页可能位于文件不同位置。
- 范围扫描沿叶子 next 指针读取，Buffer Pool 与 read-ahead 可缓解物理离散。
- 二级索引对二级 key 排序，相同 key 再按主键区分，因此特定 ORDER BY 可利用该隐含次序。
- SQL 未写 ORDER BY 时结果顺序没有契约，即使某次碰巧按索引返回也不能依赖。

## TopN算法
Q: `WHERE a=? ORDER BY b LIMIT 20` 用 `(a,b)` 为什么通常高效？
A:
1. a 等值把搜索限定到一个连续前缀。
2. 叶子记录已按 b 排序，从下界开始顺序读取。
3. 找到 20 个满足剩余条件的可见行即可停止，避免读取全量再 filesort。
4. 若还要大量回表或过滤率极低，实际读取可能远超 20，应从 ANALYZE 的 rows/loops 验证。

## 边界与代价
Q: 为什么“加了 ORDER BY 列索引”优化器仍可能选 filesort？
A:
- 使用排序索引可能要扫描大量低选择性记录并回表；选择过滤性更强的索引再排序可能成本更低。
- SELECT 列太宽、LIMIT 大、过滤条件与排序索引不匹配都会改变成本。
- ORDER BY 表达式、不同 collation、非连续联合前缀或多表输出可能破坏索引序。
- filesort 是排序算法名称，不一定写磁盘；小结果可完全在内存。

## 验证与实践
Q: 排查 ORDER BY 慢时应怎样区分扫描问题与排序问题？
A:
- `EXPLAIN ANALYZE` 对照 sort 前输入行数、sort 输出行数和耗时；先减少输入通常比盲调 sort_buffer 更有效。
- 看是否出现 filesort、临时表、回表与深 OFFSET；验证实际排序 key 和索引方向。
- keyset pagination 用最后一个唯一排序键继续范围扫描，避免 OFFSET 重扫。
- 排序键必须加唯一 tie-breaker，否则翻页在并发写入下可能重复或漏行。
