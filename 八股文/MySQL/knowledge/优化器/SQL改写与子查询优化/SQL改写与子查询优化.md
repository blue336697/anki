# SQL改写与子查询优化

## 规则优化卡
Q: MySQL 基于规则的优化常见有哪些？
A:
- 条件化简，例如常量折叠、恒真恒假判断
- 外连接消除，在 where 条件使外连接语义等价于内连接时改写
- 谓词下推，减少中间结果规模
- 子查询改写为半连接、物化表或连接
- 派生表合并，避免不必要的物化

## 子查询卡
Q: MySQL 如何优化 IN、EXISTS 等子查询？
A:
- 非相关子查询可能先执行并物化结果
- IN 子查询可转换为 semi join
- EXISTS 关注是否存在匹配记录，常可提前停止
- 相关子查询可能被反复执行，成本较高
- 优化效果取决于子查询类型、索引、数据量和可改写性

## 外连接卡
Q: 外连接消除为什么要谨慎？
A:
- 外连接会保留驱动表中没有匹配的行，并用 NULL 填充被驱动表列
- 如果 where 条件要求被驱动表列非 NULL，外连接可能等价于内连接
- 优化器可利用这种语义缩小搜索空间
- 但错误改写会改变结果集，尤其要注意 NULL 语义
- 面试表达：SQL 改写必须保持语义等价，不是看到 left join 就随便改 inner join

## 正确性审查卡
Q: SQL 改写有哪些常见误区？
A:
- “子查询一定比 join 慢”：不一定。优化器可能改写，且 EXISTS 在某些场景更合适
- “left join 都能改 inner join”：错误。要看 where 条件是否消除 NULL 扩展行
- “优化器改写一定符合业务意图”：它只保证 SQL 语义，不理解业务语义
- “物化一定慢”：不完整。小结果集物化可能更快
- “SQL 写法不同结果一样性能就一样”：错误。可优化空间和统计估算可能不同
