# 联合索引与最左前缀

## 最左前缀卡
Q: 联合索引的最左前缀原则是什么？
A:
- 联合索引按定义列顺序组织，例如 `(a,b,c)` 先按 a，再按 b，再按 c 排序
- 查询条件从最左列连续匹配时，才能充分利用索引
- 如果跳过最左列，后续列通常无法用于定位索引范围
- 范围条件之后的列通常不能继续用于索引范围定位
- 面试表达：最左前缀本质来自 B+ 树复合 key 的排序方式

## 排序分组卡
Q: 联合索引如何帮助 order by 和 group by？
A:
- 如果排序列顺序和索引顺序一致，可能避免额外 filesort
- where 等值条件固定前导列后，后续列仍可用于排序
- 排序方向、字段顺序、范围条件都会影响是否能利用索引有序性
- group by 也可利用索引顺序减少排序或临时表
- 覆盖索引还能减少回表，进一步降低排序和扫描成本

## 列顺序卡
Q: 设计联合索引时列顺序怎么考虑？
A:
- 高选择性列适合放前面，但不是唯一标准
- 等值条件列通常放在范围条件列前面
- 要结合查询模式、排序分组需求和覆盖索引一起设计
- 频繁用于排序的列顺序要与 order by 尽量一致
- 不要为每条 SQL 单独堆索引，要合并相近查询的公共前缀

## 正确性审查卡
Q: 联合索引有哪些常见误区？
A:
- “最左前缀就是最左列必须出现在 select 中”：错误。关键是 where/order/group 的使用
- “范围条件后的列完全没用”：不完整。可能不能定位，但可用于覆盖索引或 ICP
- “选择性最高的一定放第一”：不一定。排序、范围和业务查询频率也重要
- “联合索引可以替代所有单列索引”：不一定。要看查询是否匹配前缀
- “索引顺序无所谓”：错误。顺序决定可利用的查询模式
