# 二级索引记录、回表与二级 MVCC

## 结构定位
Q: InnoDB 二级索引叶子记录具体保存哪些内容？
A:
- 保存二级索引定义列，加上尚未包含的聚簇主键列；主键充当稳定行定位符而不是物理页地址。
- 唯一二级索引的“唯一”只针对显式索引列，附加主键用于定位，不改变业务唯一语义。
- 索引包含的生成列或前缀是物化后的 key；覆盖查询能直接从二级记录返回所需字段。
- 非叶子节点也需要足够 key 区分子树，内部可能包含主键成分保证记录顺序唯一。

## 回表链路
Q: 二级索引回表为何不是简单的一次额外 O(1) 访问？
A:
1. 先沿二级 B+ 树定位叶子 range，得到若干二级 key 与主键。
2. 对每个候选主键再搜索聚簇 B+ 树；若访问次序随机，可能产生大量离散页访问。
3. 读取聚簇记录后做 MVCC、剩余谓词和投影；不满足条件的回表也是成本。
4. MRR 可先收集/排序主键以改善聚簇页局部性，ICP 可在二级索引阶段提前过滤。

## MVCC细节
Q: 二级索引记录没有 DB_TRX_ID 时，一致性读如何判断它是否可见？
A:
- InnoDB 会利用二级记录上的删除标记和页级最大事务信息做快速判断；无法确定时回聚簇记录。
- 聚簇记录通过 `DB_TRX_ID + DB_ROLL_PTR` 重建 read view 可见版本，再判断该旧版本对应的二级 key 是否匹配。
- 因而即使 SELECT 只取二级索引列，在并发更新下也可能需要访问聚簇记录；“覆盖索引绝不回表”不是绝对实现保证。
- purge 清理旧版本与 delete-mark 前，也要确保没有活跃 Read View 仍可能需要它。

## 成本模型
Q: 优化器怎样比较二级索引回表与全表扫描？
A:
- 估算 range 命中行数、二级页访问、每行聚簇查找成本、过滤率和顺序/随机 I/O 成本。
- 低选择性条件返回大量行时，回表次数与随机性可能让全表扫描更便宜。
- 覆盖索引、MRR、Buffer Pool 命中和 LIMIT 会改变盈亏点；不存在通用“超过 20% 就不用索引”的硬阈值。
- 统计基数或数据倾斜错误会让估算严重偏离，应通过 EXPLAIN ANALYZE 验证。

## 边界与验证
Q: 如何确认慢查询真正慢在回表？
A:
- 对比原查询与只选索引列的覆盖版本，观察 `EXPLAIN ANALYZE` 的实际 rows、loops 和聚簇查找耗时。
- 看 handler 读计数、Buffer Pool 随机读、MRR/ICP 是否启用；`Using index` 与 `Using index condition`含义不同。
- 可增加包含必要列的索引，但要计算索引宽度、写放大和缓存污染；不要为了一个查询复制大字段。
- 深分页即使走索引也可能先扫描并回表大量被 OFFSET 丢弃的行，应改用 keyset pagination。
