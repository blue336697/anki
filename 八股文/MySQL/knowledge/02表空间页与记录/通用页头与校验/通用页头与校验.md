# InnoDB 通用页头、页类型与校验

## 结构定位
Q: 一个 InnoDB 页的通用物理布局是什么，FIL header/trailer 用来做什么？
A:
- 页前部 `FIL_PAGE_HEADER` 保存 checksum、page number、前后页指针、LSN、page type、flush LSN 和 space id；后部 trailer 保存校验相关信息。
- 中间 payload 由页类型解释：索引页、undo 页、inode、XDES、LOB 等使用不同专用头和内容。
- 页头 LSN 表示最近修改该页的日志位置，恢复和刷脏会用它判断 WAL 与页新旧。
- 源码锚点：`fil0fil.h`、`page0page.h`、`buf0checksum.*`。

## 字段与链路
Q: FIL_PAGE_PREV/NEXT 是不是整棵 B+ 树所有页的父子指针？
A:
- 不是。它们通常连接同一索引同一层级的逻辑相邻页，支持叶子范围扫描，也可用于其他页链。
- B+ 树父子关系存放在非叶子节点记录中的 child page number；根页和层级由数据字典/index 元数据定位。
- 页号只在同一 space 内有意义，所以排障必须同时记录 space id 与 page no。
- 页链是持久化结构，Buffer Pool 中另有 hash、LRU、flush 等内存链表，两者不能混同。

## 校验与恢复
Q: InnoDB 读取一个页时如何发现 torn page 或错误页？
A:
1. I/O 完成后核对 page id、page type 和 checksum；校验算法受 `innodb_checksum_algorithm` 影响。
2. checksum 或页头/trailer 不一致说明页可能被部分写、介质损坏或读到错误位置。
3. 若启用 doublewrite，恢复可从 doublewrite 文件找到完整副本，再用 redo 前滚到目标 LSN。
4. redo 解决“页落后”，doublewrite 解决“单页本身被撕裂”；二者职责不同。

## 版本与代价
Q: 为什么把“页就是 16KB”当成绝对协议会出错？
A:
- 16KiB 是默认值，实例可在初始化时选择 4K、8K、16K、32K、64K；具体支持和压缩限制按版本判断。
- 页大小影响 B+ 树扇出、单页浪费、I/O 粒度、Buffer Pool 页数和最大索引长度。
- 更大页并不必然更快：随机点查可能读放大，更小页也可能增加树高和管理开销。
- 分析 `.ibd` 必须读取真实实例页大小，硬编码 16KiB 会错位解析。

## 验证与边界
Q: 错误日志出现 page corruption 时正确处理顺序是什么？
A:
- 先停止扩大损坏：保留错误日志、故障文件和存储告警，不要直接反复重启或覆盖原盘。
- 验证备份可恢复性和副本完整性，优先从健康副本/备份重建；`innodb_force_recovery` 只用于尽量导出，不是修复。
- 检查 OS、文件系统、RAID/云盘和内存错误，同时确认 checksum/doublewrite 配置。
- 逻辑一致性检查与物理 checksum 是两层问题；页能读不代表索引与约束一定一致。
