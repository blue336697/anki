# 表空间、区、段与页寻址

## 结构定位
Q: InnoDB 为什么用“表空间→区→页”管理磁盘，而 B+ 树又需要“段”？
A:
- 表空间是逻辑地址空间，页是 Buffer Pool 与磁盘 I/O 的基本单位；默认 `innodb_page_size` 为 16KiB，实例初始化后不能普通在线修改。
- 默认一个 extent 含 64 个连续页，16KiB 页时为 1MiB；extent 便于批量分配并提高大对象顺序局部性。
- 段是某个索引叶子页或非叶子页的逻辑页集合，可跨多个 extent；每棵 B+ 树通常分别维护 leaf/non-leaf segment。
- 文件偏移可由 `page_no × page_size` 定位，但 `(space_id,page_no)` 才是 InnoDB 的逻辑页地址。

## 管理结构
Q: 表空间怎样记录哪些区和页空闲，inode segment 又保存什么？
A:
- 表空间头页的 FSP header 保存 space id、size、free limit 和 extent 链表；XDES entry 用位图记录 extent 内各页状态。
- extent 可处于 FREE、FREE_FRAG、FULL_FRAG 或属于某 segment；小对象先用碎片页，增长后再整区分配。
- segment inode 保存 segment id、已分配页统计以及 FREE/NOT_FULL/FULL extent 链表，索引根页记录两个 segment header。
- 源码锚点：`fsp0fsp.h/.cc`、`fseg0fseg.h/.cc`。

## 分配算法
Q: 一棵索引从小到大增长时，页分配策略如何变化？
A:
1. 初始索引页可从 fragment extent 领取单页，避免小表独占整区。
2. segment 增长到一定规模后申请完整 extent，并把页挂入 leaf 或 non-leaf segment。
3. 顺序插入时分配器尽量获取相邻页以改善预读和扫描；页分裂仍可能让逻辑相邻页物理不连续。
4. 删除记录通常只产生页内空闲；能否回收页、区或文件空间取决于页合并、表空间类型和重建/截断。

## 文件边界
Q: system、file-per-table、general、undo 和 temporary tablespace 有何边界？
A:
- system tablespace 保存系统级 InnoDB 数据及可选用户表；file-per-table 通常每表一个 `.ibd`，便于回收和迁移。
- general tablespace 可容纳多表，删除单表不一定让操作系统文件缩小。
- undo tablespace 保存 undo，临时表空间保存用户/内部临时对象；它们的生命周期和恢复语义不同。
- “DROP 后磁盘一定立刻归还”只对可删除的独立文件较接近，不能泛化到共享表空间。

## 验证与排障
Q: 表很大但业务行数不多时，怎样判断空间耗在什么地方？
A:
- 对照 `INFORMATION_SCHEMA.TABLES` 的 DATA_LENGTH/INDEX_LENGTH、`INNODB_TABLESPACES` 与实际文件大小。
- 检查二级索引数量、长主键、页填充率、历史版本、LOB 溢出页和已删除但未重用空间。
- `OPTIMIZE TABLE` 往往等价重建，可能回收 file-per-table 空间但需要额外磁盘、时间与 MDL；不可直接在线执行。
- 精确页分析应在备份副本使用 `innodb_space` 类工具，生产直接扫页会产生额外 I/O。
