# COMPACT 记录格式与隐藏列

## 结构定位
Q: InnoDB COMPACT/DYNAMIC 行记录从低地址到高地址包含哪些部分？
A:
- 记录额外信息依次包含变长字段长度数组、NULL bitmap 和固定 5 字节 record header，随后才是各列真实数据。
- 变长长度与 NULL 位按内部列顺序逆序存放，解析时需要数据字典提供列类型、nullable 和长度。
- 聚簇记录还含必要的系统列：6 字节 `DB_TRX_ID`、7 字节 `DB_ROLL_PTR`；无合适主键时还有 6 字节 `DB_ROW_ID`。
- DYNAMIC 继承 COMPACT 的基本记录组织，但长列的 off-page 策略不同。

## 字节细节
Q: VARCHAR 长度字段、NULL bitmap 和 CHAR 存储为什么不能用固定公式粗算？
A:
- 变长字段实际长度较短时用 1 字节，否则可能用 2 字节，其中最高位还可表示外部存储。
- 只有允许 NULL 的列占 NULL bitmap 位；NULL 字段通常不在数据区存实际值。
- CHAR 是否固定字节受字符集最大/实际长度和行格式影响；多字节字符集下可能按变长处理。
- 行大小还包括主键、系统列、记录头、各二级索引副本和页目录摊销，不能只累加 DDL 字段长度。

## 写入算法
Q: INSERT 一行时 SQL 值怎样变成聚簇索引记录？
A:
1. Server 按字段类型和字符集完成值转换、默认值与生成列表达式，handler 接收 MySQL 行缓冲。
2. InnoDB 构造内部 tuple，补齐主键及系统字段，计算 NULL 位和各变长字段长度。
3. B+ 树游标定位叶子页，检查唯一约束并申请锁；空间足够则在页内插入，否则触发重组或分裂。
4. 页修改由 mini-transaction 加 latch、生成 redo；事务 undo 记录支持回滚和旧版本。

## 大小边界
Q: 为什么会出现 Row size too large，即使表里很多 VARCHAR 实际值很短？
A:
- DDL 校验既考虑最大可能行内长度，也受页可容纳记录比例、索引 key 和行格式限制。
- 变长列可 off-page 不代表所有字节都消失：仍需页内保存外部引用，某些格式还保留前缀。
- 大量 nullable/变长列、超长主键和多索引会共同放大空间。
- 应拆分垂直大字段、使用 DYNAMIC、审查类型，而不是简单把所有 VARCHAR 改成 TEXT。

## 验证与误区
Q: 怎样验证一行真正占用，而不是背诵“VARCHAR(n) 占 n+2 字节”？
A:
- 根据 `SHOW CREATE TABLE` 的真实字符集、行格式、nullable、主键与索引先算最坏和典型值。
- 用测试表插入代表性数据，观察页数、平均行长和 `.ibd` 增量；必要时在副本离线解析记录。
- `LENGTH()` 返回字节数、`CHAR_LENGTH()` 返回字符数，可验证业务数据分布但不含记录元数据。
- “n+1/2”只是长度字段近似，忽略字符集、NULL、off-page 和页管理会误导容量设计。
