# 正反向代理、四七层负载均衡与健康检查
## 01-代理方向
Q: Forward Proxy 与 Reverse Proxy 的“方向”指什么？
A:
- 正向代理代表客户端访问外部，服务端看到代理来源；用于出口控制、匿名、缓存等。
- 反向代理代表服务端集群接收客户端，客户端只看到统一入口；用于 TLS、路由、缓存和负载均衡。
- 两者都可能终止连接并建立新连接，源 IP/协议信息需显式传递。
- “正向在客户端、反向在服务端”是部署习惯，本质看它代表哪一方。
## 02-四层负载
Q: L4 load balancer 如何转发 TCP/UDP 流量？
A:
- 依据 IP、端口和协议做连接/流转发，不需解析 HTTP；可用 NAT、DR、TUN 或代理模式。
- 状态型 NAT 需维护连接映射和对称回程；DSR 让后端直接回客户端以减少 LB 回程压力。
- 粒度通常是一条连接，HTTP/2 长连接上请求不会再由 L4 分散。
- 优点是通用、开销低，缺点是不能按 URL/header/业务语义路由。
## 03-七层负载
Q: L7 reverse proxy 为什么能做内容路由，代价是什么？
A:
- 它终止 TLS/HTTP，解析 host/path/header/cookie 后选择 upstream，可做鉴权、重写、限流和缓存。
- 客户端与代理、代理与后端是两条独立连接，超时、缓冲、拥塞和重试也分成两段。
- 解析/加密消耗 CPU，并可能改变流式/backpressure；代理故障会成为统一爆炸半径。
- HTTP/2、WebSocket、gRPC 等需正确处理升级、stream 和 trailer 语义。
## 04-调度算法
Q: Round Robin、Least Connections、hash 和 EWMA 各适合什么？
A:
- RR 适合实例近似同质和请求成本稳定；weighted RR 表达容量差异。
- least-connections 对长短连接差异有帮助，但连接数不等于在途请求/CPU；HTTP/2 更明显。
- consistent/hash 提供会话亲和和缓存局部性，实例变化会迁移部分 key；热点 key 仍可能倾斜。
- EWMA/least-request 结合延迟与在途量更自适应，但反馈滞后可能振荡。
## 05-健康检查
Q: 为什么 TCP 端口健康不等于服务健康？
A:
- TCP connect 只证明监听栈可握手，线程池、数据库、依赖和业务初始化可能已经失败。
- HTTP readiness 应检查是否能接新流量，但不宜同步探测所有下游导致级联；liveness 只判断是否需重启。
- unhealthy 阈值、间隔和 slow start 防瞬时抖动频繁摘挂与新实例流量冲击。
- 被动检查使用真实请求错误补充主动探测，二者需避免同一故障误判。
## 06-重试放大
Q: 代理重试为什么可能把局部故障放大成雪崩？
A:
- 多层客户端、网关和服务各重试，单请求尝试数相乘；故障后端/健康实例承受更多流量。
- 非幂等请求重试会重复副作用，已发送 body/已收到部分响应后能否重试受协议状态限制。
- 应使用总 deadline、单层有限重试、指数退避+jitter、retry budget 和熔断。
- 记录 attempt/upstream/错误阶段，区分连接失败、首字节超时和响应中断。
