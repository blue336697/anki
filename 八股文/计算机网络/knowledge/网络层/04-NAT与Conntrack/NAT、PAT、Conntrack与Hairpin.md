# NAT、PAT、Conntrack 与 Hairpin

## 01-NAT类型
Q: SNAT、DNAT 和 PAT 分别改写什么？
A:
- SNAT 改源地址，常让私网主机共享公网出口；DNAT 改目的地址，常把 VIP/公网端口映射到后端。
- PAT/NAPT 还改传输层端口，使多个内部连接可共享一个公网 IP。
- 改写后需增量或重新计算 IP/TCP/UDP checksum，并让回程按反向映射恢复。
- NAT 是地址/端口转换，不等同防火墙；是否允许连接由独立策略和状态跟踪决定。

## 02-状态表
Q: 有状态 NAT 的 conntrack 表通常保存什么？
A:
- 以原始/回复方向五元组、协议和 zone 标识连接，保存转换后的 tuple、状态、超时和辅助信息。
- 首包创建状态，后续包走 fast path 查表；回程必须经过能访问同一状态的设备。
- TCP 状态和超时比 UDP 伪连接更复杂；表容量耗尽会让新连接失败。
- 集群 NAT 需会话亲和、状态同步或确定性映射，否则非对称回程会绕过映射。

## 03-端口耗尽
Q: 大量出站连接为什么会耗尽 NAT 端口？
A:
- 一个公网源 IP 到特定协议可用端口有限，活跃和 TIME_WAIT 映射占据不同源端口组合。
- 高 QPS、长连接、连接风暴或过长 UDP timeout 会让分配失败，即使 CPU/带宽仍空闲。
- 增加公网 IP、连接复用、合理超时和扩大可用端口范围可缓解。
- 单纯启用端口复用可能引入四元组冲突和旧包污染，必须遵循协议栈安全条件。

## 04-Hairpin
Q: 内网客户端访问同一网络的公网 VIP 时为什么可能需要 Hairpin NAT？
A:
- DNAT 把 VIP 改到内网后端，但后端若直接用私网地址回复客户端，回包绕过 NAT，客户端看到源地址不符。
- Hairpin 通常同时 SNAT 客户端源，使后端回程必经 NAT，再反向还原双向 tuple。
- 代价是丢失真实客户端 IP，需要 PROXY protocol/X-Forwarded-For 等上层传递。
- Split-horizon DNS 让内网解析私网地址是另一方案，但会产生内外解析差异。

## 05-穿透边界
Q: NAT 为什么妨碍 P2P，STUN/TURN/ICE 如何处理？
A:
- 外部主机通常不能主动知道或创建内部映射，不同 NAT 对源/目的 tuple 的复用限制也不同。
- STUN 让客户端发现外部映射，hole punching 尝试双方同时发包建立状态；某些对称 NAT 下失败。
- TURN 通过公网中继转发，成功率高但增加带宽成本和时延；ICE 组织候选与连通检查择优。
- NAT traversal 不能绕过企业 ACL 和认证，业务仍需安全握手。

## 06-排障
Q: 如何证明连接失败发生在 NAT/conntrack 而不是服务端？
A:
- 在 NAT 前后同时抓包对比 tuple，检查是否创建状态、DNAT/SNAT 是否匹配和回包是否回来。
- 查看 conntrack 使用率、insert_failed、invalid、超时与端口分配失败，确认是否表满。
- 若后端收到 SYN 并回 SYN-ACK，但客户端侧没有，重点查回程路由和反向 NAT。
- 应记录真实客户端标识链，避免代理/NAT 后只看到一个源 IP 而误判热点。
