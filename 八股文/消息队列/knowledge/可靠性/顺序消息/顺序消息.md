# 顺序消息

## 顺序卡
Q: MQ 如何保证消息顺序？
A:
- 全局顺序通常成本很高，需要单队列或单分区串行消费
- 更常见的是按业务 key 保证局部顺序，例如同一订单有序
- 生产者把同一业务 key 路由到同一队列或分区
- 同一队列或分区由单线程或同一消费者顺序处理
- 面试表达：顺序消息通常是“分区内有序”，不是全局有序

## 乱序卡
Q: 消息为什么会乱序？
A:
- 多分区并行发送和消费会打乱全局顺序
- 生产者重试可能让后发消息先到
- 消费失败重试可能让旧消息晚于新消息处理
- 消费者并发线程处理同一业务 key 也会乱序
- 顺序要求越强，并发能力通常越低

## 工程卡
Q: 订单状态流转这类场景如何设计顺序消息？
A:
- 用订单 ID 作为 sharding key
- 同一订单消息进入同一队列或分区
- 消费端对同一队列串行消费或按 key 单线程处理
- 业务侧仍要用状态机校验合法流转
- 如果乱序到达，可暂存或拒绝非法状态，等待补偿

## 正确性审查卡
Q: 顺序消息有哪些常见误区？
A:
- “MQ 默认保证所有消息有序”：错误。通常只保证队列/分区内有序
- “提高消费者数量不影响顺序”：不一定。同一分区并发处理会破坏顺序
- “顺序消息不用业务校验”：错误。状态机仍然必要
- “重试不影响顺序”：错误。重试可能导致旧消息晚处理
- “全局顺序适合高吞吐系统”：通常不适合，会严重限制并发
