# RocketMQ Producer 发送链路与故障语义

> 基线：以经典 Java Producer 直连 Broker 的同步发送链路为主，并指出异步、单向和 5.x 接入差异。

## 01-客户端启动
Q: Producer 启动时建立了哪些关键运行状态？
A:
- 校验 ProducerGroup、NameServer 地址、实例名和发送参数，并把客户端实例注册到共享 MQClientInstance。
- 启动网络客户端、路由更新、心跳等后台任务；同一进程内兼容配置的 Producer 和 Consumer 可能复用客户端基础设施。
- Producer 本地维护 TopicPublishInfo，包含可写 Queue 与 Broker 地址映射，用于快速选择发送目标。
- 启动成功不代表某个业务 Topic 已有合法路由，首次发送仍可能因 Topic 未创建、权限或路由不可达失败。

## 02-路由获取
Q: Producer 如何得到并刷新 Topic 路由？
A:
- 首次没有可用 TopicPublishInfo 时，客户端向 NameServer 请求 TopicRouteData，并转换为可发布 Queue 列表。
- 路由缓存在本地并周期更新；发送异常、Broker 变化或管理操作后，客户端可能再次刷新。
- 生产环境应显式创建 Topic 和 Queue 数，避免依赖默认 Topic 自动创建造成各 Broker 配置不一致。
- 路由只是“可以尝试发送到哪里”，实际 Broker 是否可写、磁盘是否健康仍需由发送响应判断。

## 03-队列选择
Q: 普通消息和顺序消息的 Queue 选择策略有什么不同？
A:
- 普通消息通常在可写 Queue 中轮转，并可结合最近失败或延迟故障信息规避异常 Broker。
- 顺序消息必须根据稳定 sharding key 使用确定性选择，把同一业务键持续映射到同一 Queue。
- 如果重试时换到其他 Queue，虽然提高成功率，却会破坏该业务键的存储顺序；可靠与有序之间需要显式策略。
- 选择器不能使用进程内随机 hash 或会变化的对象哈希，扩容 Queue 后也要评估映射迁移。

## 04-同步异步单向
Q: 同步、异步和单向发送分别保证什么？
A:
- 同步发送阻塞等待 Broker 响应，便于立即处理 SendStatus 和异常，但线程延迟受网络、刷盘和复制影响。
- 异步发送通过回调得到成功或失败，吞吐更高但必须限制在途请求、处理回调异常并保证进程退出前完成。
- 单向发送只把请求写出而不等待业务响应，无法确认 Broker 是否接受，适合允许丢失的日志类数据。
- 三者改变客户端等待方式，不自动改变 Broker 的持久化和副本策略。

## 05-Broker处理链路
Q: Broker 收到 SendMessageRequest 后做哪些关键检查和写入？
A:
- 请求处理器校验 Broker 是否可写、Topic 配置、QueueId、消息大小、事务或延迟属性以及磁盘存储状态。
- 组装内部 MessageExtBrokerInner，计算系统属性和队列信息，然后调用 MessageStore 追加消息。
- 存储层序列化记录并顺序追加 CommitLog，返回物理 Offset、消息 ID 与追加状态。
- Broker 再根据刷盘、复制结果和具体异常映射响应码；客户端看到成功前已经跨过哪些持久化点取决于配置。

## 06-发送状态
Q: `SEND_OK`、刷盘超时、Slave 不可用等状态应该怎样理解？
A:
- `SEND_OK` 表示满足当前 Broker 策略定义的成功条件，不代表消费者已处理，也不能脱离刷盘复制配置解释。
- 同步刷盘超时可能表示追加已完成但等待落盘确认超时；客户端重试前必须接受原消息可能仍然有效。
- 同步复制等待超时或 Slave 不可用说明副本确认条件未满足，Master 本地是否已有消息需要结合返回状态判断。
- 对关键消息应记录业务键、目标 Broker、Queue、Offset 和返回状态，供超时后的查询、去重与审计使用。

## 07-重试与重复
Q: Producer 重试为什么可能产生重复，怎样降低风险？
A:
- Broker 写入成功但响应在网络中丢失时，客户端只看到超时；重发会在 CommitLog 中追加第二条消息。
- 普通同步发送可尝试其他 Broker，但跨 Queue 重试会改变物理位置，不能由 Broker 全局识别为同一业务事实。
- 使用稳定业务键、限制重试总时长、记录发送结果并让消费者幂等，才能把不确定结果变为可恢复。
- 不应在 SDK 已重试的外层再无限重试，否则故障期间会形成重试风暴和更多重复。

## 08-背压与限流
Q: Producer 侧如何避免在 Broker 或网络异常时把自己拖垮？
A:
- 对异步发送设置在途请求上限、超时和有界缓冲，缓冲满时阻塞、降级或拒绝，不能无界堆积对象。
- 对系统繁忙、流控和超时采用有抖动退避，设置整体 deadline，而不是每层各自完整重试。
- 大批量业务可合并消息，但要受单条/批次大小限制，并评估一批失败后的重试和幂等粒度。
- 发送延迟、失败率、重试次数和本地待发送量必须纳入监控，不能只统计调用次数。

## 09-大消息与批量
Q: 为什么不应把大对象直接塞进 RocketMQ？
A:
- 大消息增加序列化、网络、CommitLog 写入、Page Cache 污染、复制时延和消费者内存压力，并放大重试成本。
- 通常把大文件存对象存储，只在消息中发送不可变地址、校验值、大小和业务元数据。
- 批量消息能摊薄协议开销，但一批共享发送结果，失败重试可能重复整个批次，消费者仍要逐业务项幂等。
- 具体大小上限受 Broker 和客户端版本配置约束，应以目标集群参数为准，避免背诵单一默认值。

## 10-正确性审查
Q: 关于 Producer 发送，哪些面试回答容易误导？
A:
- “同步发送就绝不丢消息”错误；还取决于业务双写、Broker 刷盘、副本和客户端超时处理。
- “发送超时说明 Broker 没收到”错误；超时代表结果未知，正是重复产生的主要窗口。
- “异步发送一定比同步可靠性低”错误；可靠性取决于是否处理回调、在途状态和 Broker ACK 语义。
- “重试越多越可靠”错误；无边界重试会放大故障，可靠方案必须结合幂等、退避和对账。
