# RocketMQ 核心架构与路由发现

> 基线：经典 4.x 重点理解 NameServer、Producer、Consumer、Broker；5.x 新客户端通常经 Proxy 接入，自动主从切换可使用 Controller 或 DLedger 等部署形态。

## 01-组件职责
Q: RocketMQ 的核心组件分别负责什么？
A:
- Producer 从路由服务获取 Topic 路由，选择 MessageQueue 并把消息发送到对应 Broker。
- Broker 接收消息、写入存储、建立逻辑队列索引、维护消费进度并响应拉取、重试和管理请求。
- NameServer 保存 Broker 注册上来的集群、Broker 地址、Topic 与 Queue 路由，供客户端发现；它不承载消息数据。
- Consumer 按 Group 订阅 Topic，从 Broker 拉取消息、执行监听器并提交消费结果或 Offset。
- RocketMQ 5.x 的 Proxy 可为 gRPC 新客户端提供接入、协议转换和消息级负载均衡能力，但不是所有 4.x 部署都必须存在。

## 02-NameServer数据结构
Q: NameServer 中保存的路由关系可以怎样理解？
A:
- Broker 维度维护 `clusterName -> brokerName` 集合，以及 `brokerName -> master/slave地址` 的 BrokerData。
- Topic 维度维护多个 QueueData，包含所在 brokerName、读写队列数量、权限和同步标识等路由元数据。
- Broker 定期注册并携带 Topic 配置，NameServer 更新内存路由；客户端按需拉取并在本地缓存 TopicRouteData。
- NameServer 不保存 CommitLog、消费 Offset 或业务消息，因此路由节点故障不会直接丢消息。

## 03-路由一致性
Q: 多个 NameServer 之间如何保持一致？会有什么短暂异常？
A:
- 经典 NameServer 节点彼此独立，Broker 分别向每个节点注册；它们不通过共识协议同步路由。
- 某个节点可能暂时拥有旧路由，客户端也有本地缓存，因此扩缩容和 Broker 故障后存在最终一致窗口。
- Producer 发送失败会刷新路由或重试其他 Broker，Consumer 也会周期更新订阅与路由信息。
- 不能把 NameServer 当成强一致注册中心；它用无共享、可水平部署换取简单和可用性。

## 04-Broker分组
Q: cluster、brokerName、brokerId 在经典部署中是什么关系？
A:
- 一个 Cluster 包含多个逻辑 Broker 组；同一 `brokerName` 标识同一组副本，组内节点保存相同逻辑数据。
- 经典约定中 `brokerId=0` 通常表示 Master，非零表示 Slave；读写能力和复制方式还由配置共同决定。
- 不同 brokerName 共同承载一个 Topic 的多个 MessageQueue，实现分片和水平吞吐。
- brokerName 不是单台机器的随意标签，错误复用会破坏副本关系与路由语义。

## 05-请求链路
Q: Producer 第一次向一个 Topic 发送消息时，请求经过哪些节点？
A:
1. Producer 启动后连接 NameServer，查询 TopicRouteData；无路由时可能尝试默认 Topic 自动创建逻辑，但生产环境通常预创建 Topic。
2. 客户端根据路由与队列选择策略挑选 Broker 和 Queue，建立到 Broker 的 Remoting 连接。
3. Broker 校验权限、Topic、消息属性和存储状态，把消息追加到 CommitLog，并按刷盘、复制策略确定 ACK 时机。
4. 后续发送复用本地路由和连接，路由会周期刷新；NameServer 不处于每条消息的数据路径上。

## 06-消费链路
Q: Consumer 消费一条消息时，NameServer 和 Broker 分别参与什么？
A:
- Consumer 从 NameServer 获取 Topic 到 Broker 的路由，再根据 Group 成员与负载均衡结果确定应处理的 Queue 或消息。
- 实际拉取、长轮询、ACK、重试和 Offset 请求直接发送给 Broker，消息体不经过 NameServer。
- 经典 PushConsumer 本质上由客户端后台 Pull 服务持续拉取，再交给本地消费线程池。
- 路由不可用时，已有 Broker 连接与缓存路由可能暂时维持收发；但长期无法刷新会影响故障转移和新 Topic 发现。

## 07-Controller与自动切换
Q: Controller 模式解决了经典主从架构的什么问题？
A:
- 经典 Master-Slave 复制中，Master 故障后角色切换往往依赖外部运维或特定 HA 方案，恢复写入不够自动。
- Controller 维护副本存活、主节点选择和同步副本集合等控制面元数据，使 Broker 角色可以动态选举和切换。
- Controller 自身需要通过可靠的复制或共识部署保证控制面可用；它不替代 Broker 的消息存储副本。
- 面试应区分 NameServer 的路由发现与 Controller 的副本选主，它们不是同一个组件。

## 08-Proxy与5.x客户端
Q: RocketMQ 5.x 引入 Proxy 后，经典架构发生了什么变化？
A:
- Proxy 为新一代多语言 gRPC 客户端提供统一接入，可独立部署，也可与 Broker 组合部署，具体取决于发行版与拓扑。
- 它可承担客户端会话、鉴权、协议转换、消息级负载均衡和消费状态相关请求，降低客户端对 Broker 内部拓扑的感知。
- 经典 Remoting Java 客户端仍可直接连接 Broker，不能把“5.x 一定所有流量经过 Proxy”当成普遍结论。
- 排障时必须先确认客户端类型和接入模式，否则对 Rebalance、重试和可见性语义的判断可能完全错误。

## 09-可用性故障域
Q: 设计 RocketMQ 部署时为什么要同时考虑 NameServer、Broker组和机房故障域？
A:
- 多 NameServer 解决路由节点单点，但不会增加某个 Broker 组中消息数据的副本数。
- 一个 Topic 的 Queue 分散到多个 brokerName 可分摊机器故障；同组副本应跨独立宿主机和故障域部署。
- 复制副本存在不等于可自动写切换，还要核对选主模式、ACK 策略、同步差距和客户端路由刷新。
- 跨机房部署还会增加复制延迟、网络分区和脑裂决策成本，应从 RPO、RTO 而不是节点数量倒推方案。

## 10-正确性审查
Q: 关于 RocketMQ 架构，哪些常见表述不够准确？
A:
- “NameServer 是注册中心且强一致”错误；经典实现是独立节点接收 Broker 注册，路由具有最终一致窗口。
- “Producer 每次先请求 NameServer 再发 Broker”错误；客户端缓存路由，NameServer 不在每条消息数据路径上。
- “有 Slave 就一定自动故障转移且不丢数据”错误；还取决于复制、ACK、选主和同步状态。
- “RocketMQ 5.x 完全推翻 4.x”也不准确；核心日志与 Queue 模型延续，但客户端、Proxy、消费状态和 HA 能力有重要演进。
