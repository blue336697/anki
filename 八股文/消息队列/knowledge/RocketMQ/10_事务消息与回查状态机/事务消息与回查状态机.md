# RocketMQ 事务消息与回查状态机

> 基线：事务消息协调的是 Producer 本地事务与消息是否对消费者可见，提供最终一致性；它不覆盖消费者本地事务。

## 01-解决的问题
Q: RocketMQ 事务消息解决哪一个原子性缺口？
A:
- 目标是让“Producer 本地事务提交”最终对应“消息可投递”，本地事务回滚则消息最终不可见。
- 普通先落库后发消息会漏发，先发后落库会产生幽灵消息；事务消息用 Half 状态推迟消息对消费者可见。
- Broker 与数据库仍不是同一个事务资源，协议依靠状态记录、二次确认和回查达到最终一致。
- 消费者处理仍是至少一次，需要自己的幂等和本地事务。

## 02-发送流程
Q: 事务消息的标准发送流程是什么？
A:
1. Producer 先向 Broker 发送 Half Message，Broker 持久化成功后消息暂不可被普通消费者看到。
2. Producer 收到 Half 成功后执行本地数据库事务，得到 commit、rollback 或 unknown。
3. Producer 向 Broker 发送 EndTransaction 请求；commit 使消息进入可投递状态，rollback 使其不再投递。
4. EndTransaction 丢失或 unknown 时，Broker 稍后回查 Producer，由本地事务事实决定最终状态。

## 03-HalfMessage
Q: Half Message 为什么对普通消费者不可见？
A:
- 经典实现会把事务准备消息转换到内部 Half Topic，并在 properties 中保存真实 Topic、Queue 等恢复信息。
- 普通业务 Consumer 不订阅内部 Topic，因此在事务状态明确前不会收到该消息。
- Commit 时 Broker 根据保存的原始属性恢复并重新投递到真实 Topic；Rollback 则记录完成而不发布。
- 内部 Topic 名称和操作细节属于实现，不应由业务代码直接依赖或手工消费。

## 04-Op标记
Q: 经典事务实现中的 Op 记录有什么作用？
A:
- Broker 需要知道哪些 Half Message 已经被 commit 或 rollback 终结，避免回查服务反复扫描已完成事务。
- EndTransaction 会为对应 Half Offset 写入内部操作标记，回查时把 Half Queue 与 Op Queue 进行匹配。
- Op 记录更像完成索引，消息真实业务结果仍由本地事务表和最终真实 Topic 消息共同验证。
- 异常恢复中 Half 与 Op 都可能存在派发延迟，所以扫描逻辑必须容忍暂时不一致。

## 05-本地事务监听器
Q: `executeLocalTransaction` 中应该怎样写本地事务？
A:
- 用数据库事务更新业务表，并记录可供回查的事务状态或业务版本；两者必须在同一事务提交。
- 返回 COMMIT 前应确保本地事务已经可靠提交，返回 ROLLBACK 表示确定失败，结果不确定时返回 UNKNOWN。
- 不要在回调里执行无法查询结果的长链路远程调用，否则回查无法判定真实状态。
- 事务监听器可能因网络和客户端行为面对重复调用，业务更新自身也应幂等。

## 06-事务回查
Q: Broker 回查时 Producer 应依据什么返回状态？
A:
- 只能查询本地权威事务记录，例如订单状态、事务日志或 Outbox 行，不能依赖进程内变量。
- 查到已提交返回 COMMIT，明确回滚或业务不存在返回 ROLLBACK，数据库暂时不可用或仍处理中返回 UNKNOWN。
- 回查接口必须快速、幂等且可监控；长时间 UNKNOWN 会增加 Broker 扫描和回查压力。
- ProducerGroup 要稳定，并保证至少有可处理回查的实例在线，否则消息会长期悬而未决。

## 07-回查上限
Q: 一直返回 UNKNOWN 会怎样，为什么需要业务兜底？
A:
- Broker 会按版本和配置在一定间隔后继续回查，并记录消息已检查次数。
- 超过最大检查次数后的处理由版本、配置和实现决定，不能假设平台会永久保留并无限回查。
- 业务必须监控 Half 消息年龄、回查失败和事务状态缺失，并通过对账重新发布或人工处理。
- 本地事务表保留时间应覆盖最长回查与排障窗口，不能业务提交后立即清理。

## 08-故障窗口
Q: 事务消息协议中各故障点如何恢复？
A:
- Half 发送失败：不执行本地事务或按明确协议处理，避免本地成功而消息不存在。
- 本地事务执行中崩溃：数据库事务决定提交或回滚，Broker 回查后由持久状态判定。
- 本地事务成功但 EndTransaction 丢失：回查返回 COMMIT，消息最终可见，可能只是延迟。
- Commit 后消费者重复：事务消息不解决消费幂等，仍按业务键和状态机吸收。

## 09-与Outbox对比
Q: RocketMQ 事务消息与 Outbox 各自适合什么场景？
A:
- 事务消息由 Broker 提供 Half、EndTransaction 和回查协议，适合已深度使用 RocketMQ且本地事务可查询的系统。
- Outbox 把待发布记录与业务表同事务写入，平台无关、审计清晰，但需要可靠发布器、扫描或 CDC。
- 两者都可能重复，都需要消费者幂等和对账；差异主要在谁负责调度与状态协调。
- 不应同时叠加两套协议却没有明确权威状态，否则故障时会出现重复发布和责任不清。

## 10-正确性审查
Q: 关于 RocketMQ 事务消息，哪些表述是错误的？
A:
- “事务消息实现分布式强一致事务”错误；它保证本地事务与消息投递的最终一致。
- “Half Message 只在 Producer 内存中”错误；Broker 要持久化它才能在 Producer 故障后回查。
- “本地事务成功后消息一定立刻可见”错误；EndTransaction 丢失时要等待回查。
- “使用事务消息后消费者不需要幂等”错误；消费端仍存在 ACK 丢失、超时和重试。
