# 缓存一致性

## 模式卡
Q: 缓存和数据库一致性常见更新模式有哪些？
A:
- Cache Aside：应用先读缓存，未命中读 DB 后写缓存
- 更新时通常先更新 DB，再删除缓存
- Read/Write Through 由缓存层代理读写 DB
- Write Behind 先写缓存异步落库，性能好但一致性风险高
- 后端业务最常见的是 Cache Aside

## 删除卡
Q: 为什么常说更新数据库后删除缓存，而不是直接更新缓存？
A:
- 删除缓存让下次读取从 DB 重新加载，避免复杂对象重算不一致
- 直接更新缓存可能和其他并发写乱序覆盖
- 删除失败会造成缓存脏读，需要重试或订阅 binlog 补偿
- 高并发下还可能出现 DB 更新和缓存重建交错问题
- 工程上常用延迟双删、消息重试或 Canal/binlog 订阅兜底

## 一致性边界卡
Q: 缓存一致性为什么很难做到强一致？
A:
- 缓存和数据库是两个系统，没有天然原子提交
- 网络失败、进程崩溃、重试乱序都会产生不一致窗口
- 强一致方案通常需要牺牲性能和可用性
- 多数缓存场景接受最终一致，并通过 TTL、重试和补偿控制窗口
- 面试表达：缓存一致性是取舍题，不是单条命令能解决

## 正确性审查卡
Q: 缓存一致性有哪些常见误区？
A:
- “先删缓存再更新 DB 一定安全”：错误。并发读可能重建旧值
- “更新 DB 后删缓存就绝对一致”：不绝对。删除失败和并发重建仍有窗口
- “加 TTL 就不用管一致性”：不完整。TTL 只是最终兜底
- “分布式事务能轻松解决”：成本高，通常不适合高频缓存
- “所有数据都适合缓存”：错误。强一致、低命中或高变更数据不一定适合
