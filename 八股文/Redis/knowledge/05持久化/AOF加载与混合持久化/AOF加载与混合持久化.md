# AOF加载与混合持久化

> 版本基线：Redis 7.4 OSS。答案中的结构体与函数名以官方源码为准；版本差异会显式标注。

## 01-加载顺序

Q: Redis 启动时有 AOF 和 RDB 时优先加载谁？

A:
- 开启 AOF 时通常以 manifest 指定的活动 AOF 集合作为恢复源，因为它一般包含比独立 RDB 更新的数据。
- 先加载 BASE，再按序加载所有 INCR；BASE 若是 RDB preamble 就走 RDB loader，后续 RESP 命令走伪客户端重放。
- 独立 dump.rdb 不会再叠加到同一状态上，否则会重复数据。
- 实际行为取决于 appendonly 配置、manifest 完整性和文件版本。

## 02-伪客户端重放

Q: AOF 命令加载为什么要通过 fake client 执行？

A:
- AOF 保存的是 Redis 命令语义，加载器解析 RESP argv 后用无网络连接的伪客户端走命令实现。
- 这样复用 SET/HSET/ZADD 等正常数据结构构建逻辑、编码转换和错误检查。
- 加载路径会设置特殊标志，避免把重放命令再次追加 AOF/复制，形成递归传播。
- 恢复时间与命令数量和构建成本有关，这也是 RDB preamble 加速 BASE 的原因。

## 03-尾部截断

Q: AOF 最后一条命令被截断时能否自动恢复？

A:
- 若仅是崩溃导致尾部不完整且配置允许 `aof-load-truncated yes`，Redis 可警告并忽略/截掉不完整尾巴后加载。
- 中间损坏、错误 RESP 或 manifest 缺失不是同一问题，贸然截尾可能丢失后续有效数据。
- `redis-check-aof --fix` 会修改文件，操作前必须备份整个 AOF 目录和 manifest。
- 先区分“尾部半条写入”与“磁盘/人为破坏”，再决定修复。

## 04-RPO与WAIT

Q: AOF everysec + 主从复制能否保证绝不丢数据？

A:
- AOF everysec 仍有本机掉电窗口；异步复制在主节点确认后也可能尚未到 replica。
- `WAIT` 只等待指定副本确认复制 offset，降低故障丢失概率，不把 Redis 变成强一致共识系统。
- replica 确认收到不等于其数据已 fsync；新主选举、网络分区和双写窗口仍影响结果。
- 更严格需求要组合 WAITAOF（版本支持时）、持久化、拓扑和上层幂等/对账，而不是靠单一命令。

## 05-恢复演练

Q: 一套可用的 Redis 持久化方案为什么必须做恢复演练？

A:
- 文件存在不等于可加载：可能有 manifest 不一致、权限、磁盘损坏、模块缺失或恢复时间超 SLA。
- 演练应复制完整 RDB/AOF 目录，在隔离实例校验启动、key 数、关键业务校验和与耗时。
- 同时测试尾部截断、旧版本升级、磁盘满和最后一个 base/incr 缺失场景。
- RPO 由最后可恢复数据点验证，RTO 由真实加载与业务切换时间验证。
