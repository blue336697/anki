# RDB生成与Fork

> 版本基线：Redis 7.4 OSS。答案中的结构体与函数名以官方源码为准；版本差异会显式标注。

## 01-BGSAVE状态机

Q: BGSAVE 从收到命令到文件替换的完整流程是什么？

A:
1. 检查是否已有互斥子进程/持久化任务，记录调度状态。
2. 主进程 fork；子进程遍历 fork 时刻的地址空间快照，写临时 RDB。
3. 子进程 fsync/关闭并原子 rename 临时文件为目标 dump.rdb。
4. 父进程通过 pipe/SIGCHLD 获知结果，更新 lastsave、状态和 COW 统计。
5. 失败保留旧可用 RDB，不应先覆盖正式文件再写。

## 02-快照一致性

Q: 父进程继续写时，子进程为什么仍能得到 fork 时刻的一致快照？

A:
- fork 创建相同虚拟地址视图，页表指向同一物理页并标 COW。
- 父进程修改页面时获得复制页，子进程仍看到旧页；子进程自己的写不改变父进程对象。
- 一致性边界是 fork 成功的时刻，不是子进程最后写完文件的时刻。
- 这避免了全局长时间停写锁，但把代价转成 fork 页表和后续 COW。

## 03-fork停顿

Q: 为什么 fork 本身仍会暂停 Redis 主线程？

A:
- 创建子进程要复制页表和内核进程元数据，数据集/映射页越多，耗时通常越高。
- fork 系统调用在主线程执行，返回前事件循环不能处理其他请求。
- 慢 fork 常见于大内存、内存页多、虚拟化/容器环境、THP 和系统压力。
- 用 `latest_fork_usec` 与 latency monitor 关联 p99；不能只看子进程写盘阶段。

## 04-COW放大

Q: BGSAVE 期间哪些写模式最容易产生 COW 放大？

A:
- 高频随机更新覆盖大量页面，比集中更新少数热页复制更多物理页。
- 大对象原地修改、rehash、过期/淘汰、active defrag 会触碰广泛页面。
- 数据集越接近物理内存上限，COW 越可能导致 swap 或 OOM。
- 生产上把持久化压测与峰值写流量结合，监控 `rdb_current_bgsave_time_sec` 和 `rdb_last_cow_size`。

## 05-save配置

Q: save 规则是“每隔 N 秒必定保存”吗？

A:
- 规则含义是“在 N 秒窗口内至少发生 M 次修改时触发后台保存”，多个规则任一满足即可。
- serverCron 检查 dirty 与上次保存时间，并受已有子进程、失败重试间隔等条件影响。
- `save ""` 可关闭自动 RDB，但复制全量同步仍可能需要 RDB/无盘快照路径。
- 备份策略不能只依赖进程内自动规则，还要复制文件、做异地保留并实际演练恢复。
