# RDB文件格式

> 版本基线：Redis 7.4 OSS。答案中的结构体与函数名以官方源码为准；版本差异会显式标注。

## 01-文件分段

Q: RDB 文件从头到尾大致由哪些部分组成？

A:
- 头部是 `REDIS` 魔数与版本；随后是 opcode/类型驱动的数据流。
- AUX 字段可保存版本、创建时间、used memory 等辅助信息；SELECTDB、RESIZEDB 切换 DB 并给装载预分配提示。
- 每个 key 前可有过期时间 opcode，然后写对象类型、key 和按编码序列化的 value。
- EOF 后带校验和（配置允许关闭）；加载时按 RDB 版本兼容解析。
- 源码锚点：`src/rdb.c`、`src/rdb.h`。

## 02-长度编码

Q: RDB 如何紧凑表示长度、整数和字符串？

A:
- 长度字段前几位区分 6-bit、14-bit、更宽固定长度或特殊编码，短长度只用一个字节。
- 字符串可能直接写原始字节，也可能用整数编码或 LZF 压缩，加载时还原为对象。
- 容器会按 RDB 对象类型写其元素，不等于把进程内指针/allocator 内存原样 dump。
- 因此 RDB 是逻辑序列化快照，可跨进程地址和一定版本范围加载。

## 03-编码兼容

Q: RDB 会不会把当前内存编码完全原样保存？

A:
- 某些紧凑结构可用专门 RDB type 保存，但加载器仍根据版本、配置和安全校验决定创建/转换对象。
- 旧 RDB 类型如 ziplist 需要新版本兼容读取并转换，不能把 RDB 当 C 结构体内存镜像。
- 保存/加载都要验证长度和元素，损坏文件可能在 redis-check-rdb 或启动加载时报错。
- 模块类型使用模块自定义序列化回调和 encoding version。

## 04-加载流程

Q: Redis 启动加载 RDB 时怎样处理过期 key 和错误？

A:
- 按 opcode 切 DB、读取可选 expire、key 和 value；校验类型与长度后加入临时/目标数据库。
- 作为主节点加载持久化时，已经超过绝对过期时间的 key 通常直接丢弃。
- 加载期间服务未就绪，大数据集恢复时间与磁盘吞吐、CPU 解压/对象构建和 key 数有关。
- 校验和或结构损坏会中止加载，恢复前应先复制文件并用 redis-check-rdb 检查。

## 05-RDB优缺点

Q: 为什么 RDB 适合备份和快速恢复，却有时间窗口数据丢失？

A:
- 单文件紧凑、顺序 I/O，加载时直接构建最终对象，通常比重放大量文本命令快。
- BGSAVE 只在某些时间点生成快照；故障发生在两次快照之间，之后写入不在文件中。
- fork/COW 让主线程继续服务，但带来 fork 停顿、内存峰值和磁盘竞争。
- 正确表述是“恢复点粒度由 save/BGSAVE 周期决定”，不是笼统说固定丢 5 分钟。
