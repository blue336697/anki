# intset整数集合

> 版本基线：Redis 7.4 OSS。答案中的结构体与函数名以官方源码为准；版本差异会显式标注。

## 01-结构布局

Q: intset 的内存结构为什么只有 encoding、length、contents？

A:
```c
typedef struct intset {
    uint32_t encoding;
    uint32_t length;
    int8_t contents[];
} intset;
```
- `contents` 实际按 encoding 解释为连续的 int16/int32/int64 数组，并保持升序。
- 不需要逐元素类型、指针或哈希 entry，因此纯整数小集合非常省内存。
- 字段以小端序辅助函数读写，不能直接假设宿主字节序。
- 源码锚点：`src/intset.h`、`src/intset.c`。

## 02-查找与插入

Q: intset 查找和插入的算法复杂度是什么？

A:
- 查找先判断值是否超出当前最小/最大，再对有序数组二分，O(log N)。
- 插入先二分得到位置，然后扩容并 memmove 后半段，写入新值，O(N)。
- 删除同样二分定位并搬移尾部，O(N)。
- 所以 intset 依赖“小集合”前提；它省空间，不代表写入复杂度优于 hash table。

## 03-升级算法

Q: 加入一个超出现有位宽的整数时，intset 如何升级而不覆盖数据？

A:
- 先根据新值选择 int32 或 int64 新编码并扩容整块内存。
- 从旧数组尾部向前读取旧编码值，再写到新编码的对应位置，避免宽元素写入覆盖尚未读取的旧字节。
- 新值若为负且小于当前最小值，放在头部；若为正且大于最大值，放在尾部。
- 一次升级 O(N)，但每种位宽最多升级一次，因此不形成频繁来回转换。

## 04-为什么不降级

Q: 删除大整数后，intset 为什么不自动从 int64 降回 int32？

A:
- 降级必须扫描并重写整个数组，是 O(N)；频繁加入/删除边界值会造成编码抖动。
- 保持较宽编码浪费一部分空间，但换取稳定写延迟和更简单的实现。
- Redis 多数紧凑编码转换也偏单向：达到阈值升级为通用结构后，不因短暂缩小立即降级。
- 容量治理应避免依赖“删除几个元素后内存马上按最紧凑编码回落”。

## 05-转哈希表

Q: Set 何时不能继续使用 intset？

A:
- 加入非整数成员时必须转换；整数成员数超过 `set-max-intset-entries`（7.4 默认 512）也会转换。
- Redis 7.2+ 小集合还可能使用 listpack；具体目标取决于成员类型、数量、长度和配置。
- hashtable 平均成员查找 O(1)，但每成员内存开销显著增加。
- 用 `OBJECT ENCODING key` 实测，不要根据命令类型武断认为 Set 一定是 intset 或 hashtable。
