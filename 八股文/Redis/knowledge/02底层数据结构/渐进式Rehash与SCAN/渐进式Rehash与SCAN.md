# 渐进式Rehash与SCAN

> 版本基线：Redis 7.4 OSS。答案中的结构体与函数名以官方源码为准；版本差异会显式标注。

## 01-Rehash启动

Q: 渐进式 rehash 启动时发生了什么？

A:
- 为 `ht_table[1]` 分配目标容量，保留旧 `ht_table[0]`，设置 `rehashidx=0`。
- 不会一次搬完所有 entry；这样把 O(N) 停顿拆到后续操作和定时任务中。
- rehash 期间读需要查两表，写入目标表，删除可能在两表中定位。
- 代价是短期双表内存、读路径多一次检查和状态复杂度。

## 02-单步迁移

Q: dictRehash(d,n) 一次具体迁移多少，如何限制空桶扫描？

A:
- `n` 表示计划迁移的非空 bucket 数，不是 entry 数；一个 bucket 的整条冲突链会一起迁移。
- 从 `rehashidx` 向后找非空桶，把每个 entry 按新 mask 重新挂到 table 1，并清空旧桶。
- 为防大量空桶导致一次调用失控，最多访问 `n*10` 个空 bucket；因此一次调用不保证一定迁移 n 个非空桶。
- table 0 used 归零后释放旧 bucket 数组，把 table 1 提升为 table 0，并把 `rehashidx` 设回 -1。

## 03-触发推进

Q: 哪些路径会推进渐进式 rehash？

A:
- 普通字典增删查可能调用 `_dictRehashStep(d)`，每次迁移一个 bucket，让活跃字典顺带完成迁移。
- server cron 还会按微秒预算调用 `dictRehashMicroseconds`，避免低访问字典永远卡在迁移中。
- 安全迭代器或明确 pause 时 `pauserehash>0`，单步迁移暂停，防止迭代中的指针失效。
- 所谓“渐进”不是后台独立线程搬迁，而是主线程在受控预算内分摊工作。

## 04-SCAN游标

Q: SCAN 为什么使用位反转游标，而不是 bucket 下标简单加一？

A:
- 表容量是 2 的幂，扩缩容改变的是 hash 的低位掩码；位反转后递增相当于优先遍历高位组合。
- 当容量从 2^n 变化到 2^(n+1) 时，旧 bucket 对应的新 bucket 能在游标序列中被覆盖，避免漏掉整个分支。
- rehash 时同时扫描较小表对应 bucket，以及较大表由掩码差异展开出的多个 bucket。
- 源码锚点：`src/dict.c::dictScan` 的长注释与 `rev()` 游标变换。

## 05-SCAN语义

Q: SCAN 能保证什么，为什么可能返回重复元素？

A:
- 从游标 0 开始并最终回到 0 的完整迭代中，持续存在的元素不会被系统性漏掉。
- 元素在迭代期间移动、插入或删除时，可能重复，也可能对短暂存在元素不给确定保证。
- COUNT 是每轮工作量提示，不是严格返回条数；紧凑编码的小集合甚至可能一次返回全部。
- 调用方必须容忍重复并用幂等处理；生产上仍要控制 COUNT，SCAN 不是“完全不消耗 CPU 的 KEYS”。
