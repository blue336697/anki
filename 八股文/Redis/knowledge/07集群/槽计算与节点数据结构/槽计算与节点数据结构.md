# 槽计算与节点数据结构

> 版本基线：Redis 7.4 OSS。答案中的结构体与函数名以官方源码为准；版本差异会显式标注。

## 01-为什么16384槽

Q: Redis Cluster 为什么在 key 和节点之间增加 16384 个 hash slot？

A:
- key 先映射到固定槽，槽再归属 master；迁移只需改变槽归属和搬该槽 key，不必为每个 key 维护全局路由。
- 16384 = 2^14，槽号可紧凑放在 14 位；节点用 2048 字节 bitmap 表示自己负责的槽。
- 数量足够细化负载，又控制 gossip 消息中槽 bitmap 大小；不是因为 CRC16 只能产生 16384 值。
- 源码常量：`CLUSTER_SLOTS (1<<14)`。

## 02-槽算法

Q: 一个 key 的槽号如何计算，hash tag 在哪一步生效？

A:
- 若 key 含第一个非空 `{...}`，只对花括号内子串计算；否则对完整 key。
- 使用 CRC16 后与 16383 做按位与，得到 0–16383。
- `{user:42}:profile` 与 `{user:42}:orders` 同槽，可执行多 key 命令/Lua；空 `{}` 或无闭合括号不生效。
- tag 过度集中会把大量业务压到单槽/单节点，跨槽问题解决了但热点更严重。

## 03-clusterState

Q: clusterState 需要保存哪些全局路由信息？

A:
- 节点字典保存 node id → clusterNode；`slots[16384]` 或槽映射保存每槽当前 owner。
- migrating_slots_to/importing_slots_from 记录本节点正在迁出/导入的对端。
- currentEpoch、lastVoteEpoch、myself、cluster state、size 等支持配置传播和选举。
- 节点各自维护最终一致的拓扑视图，没有中心路由服务器。

## 04-clusterNode

Q: clusterNode 里为什么同时有 slots bitmap、配置 epoch 和链接状态？

A:
- slots bitmap 表示该节点宣称负责哪些槽；numslots 用于统计。
- configEpoch 决定槽所有权冲突时哪个配置更新，epoch 更高者获胜。
- flags 表示 master/replica/PFAIL/FAIL/handshake/noaddr 等角色和故障状态。
- ping_sent、pong_received、data_received 与 clusterLink 负责故障检测；slaveof/replicas 表示复制拓扑。

## 05-路由验证

Q: 客户端和运维怎样验证槽映射？

A:
- `CLUSTER SHARDS`/`CLUSTER SLOTS` 获取面向客户端的槽范围与节点；`CLUSTER NODES` 看 node id、flags、epoch 和 link state。
- `CLUSTER KEYSLOT key` 验证 hash tag；不要自己实现错 CRC/tag 规则。
- cluster-aware 客户端维护本地 slot→node 表，并在 MOVED 或拓扑刷新时更新。
- 任一节点都可能返回拓扑，但分区期间视图会暂时不同，客户端需处理重定向。
