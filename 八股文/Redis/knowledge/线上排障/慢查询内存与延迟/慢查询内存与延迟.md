# 慢查询内存与延迟

## 慢查询卡
Q: Redis 慢查询应该如何排查？
A:
- 使用 slowlog 查看执行时间长的命令
- 重点关注大 key 操作、复杂集合操作、Lua 脚本和 keys 命令
- 区分命令执行慢和网络/排队/客户端处理慢
- 查看 Redis 单线程是否被阻塞
- 配合 latency monitor、monitor、客户端埋点和系统指标定位

## 内存卡
Q: Redis 内存问题通常从哪些角度排查？
A:
- 查看 used_memory、maxmemory、mem_fragmentation_ratio
- 分析 key 数量、TTL 分布、大 key 和数据类型
- 检查淘汰策略是否符合业务预期
- 关注 fork 时写时复制带来的额外内存
- 使用 scan、bigkeys、memory usage 等工具分批定位

## 延迟卡
Q: Redis 延迟尖刺常见原因有哪些？
A:
- 大 key 删除或读取阻塞主线程
- RDB/AOF fork、fsync 或重写带来抖动
- 主从全量同步、Cluster 迁移、网络抖动
- CPU 打满、内存碎片整理、操作系统调度
- 客户端批量请求过大也会造成长尾延迟

## 正确性审查卡
Q: Redis 线上排障有哪些常见误区？
A:
- “slowlog 没记录就说明 Redis 不慢”：不完整。网络和排队不一定计入命令执行时间
- “内存够就不会有延迟”：错误。fork、碎片、大 key 都可能导致延迟
- “keys 命令线上查问题很方便”：危险。应使用 scan
- “只看 Redis 指标就够”：不够。还要看客户端、网络、系统和下游
- “重启能根治 Redis 问题”：通常只是止血，根因还要回到数据模型和访问模式
