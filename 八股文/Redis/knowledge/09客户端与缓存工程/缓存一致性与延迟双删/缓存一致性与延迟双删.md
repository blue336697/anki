# 缓存一致性与延迟双删

> 版本基线：Redis 7.4 OSS。答案中的结构体与函数名以官方源码为准；版本差异会显式标注。

## 01-旁路缓存

Q: Cache Aside 的标准读写链是什么？

A:
- 读：先读缓存，miss 后查数据库，再写缓存；并发 miss 需防击穿。
- 写：先更新数据库，成功后删除缓存；下一次读从数据库回填新值。
- 通常选择删除而不是直接更新缓存，因为缓存可能是派生结构、更新成本高，且并发写顺序容易倒置。
- Redis 不是真相源时，数据库事务成功才是业务写成功边界。

## 02-先删后写竞态

Q: 为什么“先删缓存，再更新数据库”会写回旧值？

A:
1. 写线程删缓存。
2. 读线程 miss，数据库尚未更新，读到旧值。
3. 写线程提交数据库新值。
4. 读线程把旧值回填缓存，旧缓存可持续到 TTL。
- 这就是先删后写的典型并发窗口；延迟双删试图在提交后再删一次，但仍需失败重试。
- 若没有第二次删除或版本校验，旧值会一直存活到 TTL，自然过期前持续污染读结果。

## 03-先写后删竞态

Q: 先更新数据库再删缓存是否绝对不会不一致？

A:
- 常见窗口更小，但不是绝对：一个早先 cache miss 的慢读先读到旧 DB，写线程提交新值并删缓存，慢读随后把旧值写回。
- 删除缓存还可能因网络/Redis 故障失败；数据库已提交不能简单回滚。
- 给回填加版本号/逻辑时间并用 Lua 只允许新版本覆盖，可缩小慢读覆盖。
- 更可靠做法是 outbox/CDC 驱动可重试失效消息，缓存 TTL 作为最终兜底。

## 04-延迟双删

Q: 延迟双删的第二次延迟应该怎样理解？

A:
- 写前删一次，数据库提交后等待大于典型“旧读查询+回填”时长，再删第二次，清掉窗口内旧回填。
- 延迟不是拍脑袋固定 500ms，要覆盖数据库 p99、线程调度和缓存写延迟，并考虑极端长尾。
- 进程在第二次删除前崩溃会失效，因此需要可靠延迟消息/任务，而非内存 sleep。
- 它是概率性补救；版本化缓存或 CDC 通常更可审计。

## 05-一致性等级

Q: 如何向面试官准确描述缓存一致性目标？

A:
- 先明确是否允许短暂旧读、最大陈旧时间、是否允许读到不存在、写后读是否必须同会话一致。
- Cache Aside + TTL 通常是最终一致，不是强一致；TTL 决定失败时陈旧上界之一。
- 对强一致关键数据应读主数据库/带版本校验，或把 Redis 降为可丢弃加速层。
- 方案评估还要覆盖删除失败、消息重复/乱序、回源失败和缓存重建，而非只画正常时序。
