# 穿透击穿雪崩内部机制

> 版本基线：Redis 7.4 OSS。答案中的结构体与函数名以官方源码为准；版本差异会显式标注。

## 01-缓存穿透

Q: 缓存穿透为什么会持续打数据库，空值缓存和 Bloom Filter 各解决什么？

A:
- 请求 key 在缓存和数据库都不存在，每次都 miss 并回源；攻击随机 key 时数据库承受无效查询。
- 空值缓存把“不存在”也缓存短 TTL，适合真实查询后确定不存在；会占 key，并有新数据创建后的短暂陈旧。
- Bloom Filter 在入口用位数组和 k 个 hash 判断“可能存在/一定不存在”；无假阴性（集合未错误维护时），有假阳性。
- Bloom 删除困难、需容量和误判率规划，不能代替权限校验和限流。

## 02-Bloom数学

Q: Bloom Filter 的位数组大小、hash 数和误判率如何关联？

A:
- n 个元素、m 位、k 个 hash 时，误判率近似 `(1-e^{-kn/m})^k`。
- 给定 m/n，最优 k 约为 `(m/n) ln2`；k 太少位利用不足，太多则计算高且更快把位打满。
- 容量超出设计 n 后误判率会快速升高；必须监控填充率并重建/分层。
- 误判只会让少量不存在 key 继续查库，不能让存在 key 被拦截，前提是过滤器更新不漏。

## 03-缓存击穿

Q: 热点 key 到期时 singleflight/互斥重建内部怎样避免并发回源？

A:
- miss 后只有第一个请求通过本机 future/Redis 锁获得“重建者”身份，其余等待、返回旧值或快速失败。
- 重建者查询 DB、写缓存后唤醒等待者；锁必须有租约与 owner token，失败路径要释放/超时。
- 分布式锁减少跨实例回源，但锁本身故障和等待队列会抬高尾延迟；本机 singleflight 只能合并单进程。
- 热点可采用逻辑过期：物理缓存保留旧值，一个后台线程刷新，换取短暂旧读。

## 04-缓存雪崩

Q: 雪崩与击穿的区别是什么，为什么 TTL 抖动不是全部答案？

A:
- 击穿通常是单个极热 key 失效；雪崩是大量 key 同期失效或整个缓存层故障，回源总量暴涨。
- TTL 随机化只解决“同批 key 同时自然到期”，不能解决 Redis 集群不可用、网络隔离或全量 flush。
- 还需要多级缓存、限流/熔断、回源并发配额、降级数据、预热和数据库容量保护。
- 恢复时也要限速回填，避免缓存刚恢复又被重建流量打垮。

## 05-失败矩阵

Q: 这三类问题的设计验证应该覆盖哪些失败场景？

A:
- 不存在 key 高频随机访问、Bloom 超容量/重建期间、新数据刚创建。
- 热点 key 重建者超时/崩溃、锁过期、DB 慢查询、等待者超时与重试风暴。
- 批量 TTL、Redis 整体不可用、节点切换、客户端连接池耗尽、数据库保护阈值。
- 指标至少含 cache hit、回源 QPS/并发、每 key 合并率、拒绝/降级数和数据库 p99。
