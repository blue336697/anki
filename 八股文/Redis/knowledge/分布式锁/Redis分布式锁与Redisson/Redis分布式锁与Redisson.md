# Redis分布式锁与Redisson

## 基础卡
Q: Redis 分布式锁的基本正确写法是什么？
A:
- 加锁使用 `SET key value NX PX ttl` 保证互斥和过期
- value 要用唯一随机值标识锁持有者
- 解锁时用 Lua 脚本先校验 value 再删除 key
- TTL 防止客户端崩溃后锁永不释放
- 面试表达：加锁原子性、持有者标识、超时释放、原子解锁缺一不可

## 风险卡
Q: Redis 分布式锁有哪些风险？
A:
- 业务执行时间超过 TTL，锁过期后可能被别人拿到
- 主从异步复制下，主节点宕机可能丢失锁写入
- 客户端 STW、网络抖动会导致锁持有时间不可控
- 锁只能保护临界区入口，资源侧最好有幂等或 fencing token
- 对强一致要求很高的场景，应考虑数据库锁、ZooKeeper/etcd 等方案

## Redisson卡
Q: Redisson 分布式锁做了哪些增强？
A:
- 提供看门狗机制，业务未完成时自动续期
- 支持可重入锁、公平锁、读写锁、联锁等高级形式
- 解锁时也会校验线程和锁标识
- 简化使用，但不能消除 Redis 异步复制和极端网络问题
- 面试表达：Redisson 提升工程易用性，不等于锁语义变成强一致

## 正确性审查卡
Q: Redis 分布式锁有哪些常见误区？
A:
- “setnx 后 expire 两步就够”：错误。两步之间崩溃会死锁
- “del key 解锁即可”：错误。可能删掉别人的锁
- “TTL 设置很长就安全”：不完整。故障恢复慢，且仍有过期/并发风险
- “Redisson 一定可靠”：不绝对。要看部署、复制和业务幂等
- “有锁就不用幂等”：错误。锁失败、重试和超时都可能发生
