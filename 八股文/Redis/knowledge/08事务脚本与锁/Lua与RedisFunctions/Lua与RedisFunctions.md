# Lua与RedisFunctions

> 版本基线：Redis 7.4 OSS。答案中的结构体与函数名以官方源码为准；版本差异会显式标注。

## 01-原子执行

Q: Lua 脚本为什么能原子执行，它的原子性边界是什么？

A:
- 脚本在 Redis 执行上下文中运行，脚本主动让出前，其他普通命令不能插入其 Redis 调用之间。
- 因而读 key、计算、写 key 可形成单实例原子序列，无需 WATCH 重试。
- 原子不等于可回滚：脚本前半已写，后半运行错误时，已发生写入不会自动撤销。
- 脚本访问外部网络/数据库不在原子边界内，Redis Lua 也不允许任意外部 I/O。

## 02-确定性与传播

Q: 脚本复制为什么关注确定性？

A:
- 若把脚本文本交给 replica 各自执行，时间、随机数或数据遍历差异可能产生不同结果。
- 现代 Redis 通常传播脚本产生的具体写命令，或对脚本 API/随机行为施加规则，保证复制与 AOF 可重放。
- 脚本必须通过 `KEYS[]` 声明访问键，Cluster 才能校验同槽并正确路由；动态拼未知 key 是坏实践。
- 版本间脚本复制模式有演进，回答要以当前官方文档和源码为准。

## 03-缓存与Functions

Q: EVALSHA 和 Redis Functions 分别怎样解决脚本分发？

A:
- SCRIPT LOAD 把脚本放入实例脚本缓存，以 SHA1 标识；EVALSHA 只发送摘要，NOSCRIPT 后客户端需回退加载。
- 脚本缓存不是可靠持久业务注册表，重启、故障切换或 SCRIPT FLUSH 后可能消失。
- Redis 7 Functions 用 FUNCTION LOAD 把命名函数库装入数据库并随持久化/复制管理，FCALL 按函数名调用。
- Cluster 中每个分片节点仍需具备相应库/脚本，部署系统要管理版本。

## 04-超时与kill

Q: 长 Lua 为什么会阻塞，SCRIPT KILL 为什么不总能杀？

A:
- 脚本与普通命令共享主执行线程；大循环或大量 Redis 调用会阻塞所有客户端。
- `lua-time-limit` 到达后 Redis 进入 busy script 状态并允许管理命令介入，但不会神奇地抢占并回滚脚本。
- 尚未执行写命令的脚本可 SCRIPT KILL；已经写过的数据脚本不能安全 kill，只能等待或强制关闭实例，避免留下无法解释的部分效果。
- 因此必须限制输入规模、循环上限，并压测脚本最坏路径。

## 05-脚本工程化

Q: 一段面试级 Lua 方案还必须说明哪些工程细节？

A:
- 所有 key 显式放 KEYS，参数放 ARGV；Cluster 中 key 必须同槽。
- 返回码要区分业务失败、重试和系统异常；脚本内部先校验再写，减少运行期错误后的部分修改。
- 使用整数/字符串规则避免浮点与序列化歧义，限制日志和返回体。
- 监控 script/function 耗时，设置版本化部署、回滚和 NOSCRIPT 处理，而不是只给一段 EVAL 命令。
