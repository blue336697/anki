# MULTI与EXEC内部状态

> 版本基线：Redis 7.4 OSS。答案中的结构体与函数名以官方源码为准；版本差异会显式标注。

## 01-事务队列

Q: 客户端进入 MULTI 后，命令保存在什么结构里？

A:
- `client.flags` 加上 `CLIENT_MULTI`；普通命令不执行，而由 `queueMultiCommand` 复制到 `client.mstate`。
- `multiState.commands` 是 `multiCmd` 数组；每项保存 argv、argc、argv_len 和 `redisCommand *cmd`。
- 队列复制参数并增加对象引用，确保客户端后续输入缓冲移动时事务参数仍有效。
- EXEC/DISCARD/连接释放会清理队列和引用；排队大量命令会直接消耗客户端内存。

## 02-两类错误

Q: 为什么事务排队阶段错误和 EXEC 阶段错误结果不同？

A:
- 未知命令、参数个数错误等可在排队时发现，标记 `CLIENT_DIRTY_EXEC`；EXEC 返回 EXECABORT，整队不执行。
- 类型错误、数值溢出等依赖运行时数据，只能在 EXEC 执行对应命令时返回该项错误；其他已排队命令仍继续。
- Redis 事务没有自动 rollback/undo log，不能把“原子执行”误解为“任一子命令失败全部回滚”。
- 客户端必须检查 EXEC 数组中每一项结果。

## 03-EXEC执行

Q: EXEC 怎样保证队列不被其他普通命令插入？

A:
- 主线程开始 EXEC 后顺序调用队列中每个命令，期间不会在这些命令之间切换去执行另一个客户端的普通命令。
- 执行前处理 WATCH 脏标记、ACL/命令变化等检查；执行中临时切换 client argv/cmd，完成后恢复。
- 整个事务的写传播可使用 MULTI/EXEC 包装，使 AOF/replica 重放保持同一原子序列。
- 事务越长，其他客户端等待越久；原子性来自主线程串行，也意味着大事务是延迟风险。

## 04-无回滚原因

Q: Redis 为什么不为事务实现关系数据库式回滚？

A:
- Redis 命令错误通常可在排队期发现，运行期错误不会破坏内部数据结构一致性。
- 实现 undo log 需为每种数据结构保存反向操作，增加内存、写放大和主线程复杂度。
- Redis 选择简单快速的批量原子执行；业务原子读改写更常用 Lua/Functions。
- 跨 Redis 与数据库的事务仍需 outbox、幂等、补偿等分布式方案，MULTI 只覆盖单实例命令队列。

## 05-持久化边界

Q: 事务写进 AOF 就一定要么全有要么全无吗？

A:
- 正常传播用 MULTI、子命令、EXEC 包裹，重放时保持事务边界。
- 进程在 AOF 尾部写到一半时可能留下不完整事务；启动加载会识别截断/错误并按配置处理，必要时 redis-check-aof。
- fsync 策略仍决定掉电窗口，事务原子执行不等于事务已持久化。
- replica 异步传播也可能在故障提升时缺失整个事务或尾部，需结合 WAIT/持久化理解。
