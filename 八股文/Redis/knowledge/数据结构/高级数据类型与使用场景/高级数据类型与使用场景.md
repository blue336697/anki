# 高级数据类型与使用场景
## 类型选择卡
Q: Redis 常见数据类型应该如何选型？
A:
- String 适合缓存值、计数器、分布式锁标记
- Hash 适合对象字段缓存，但字段过多也会形成大 key
- List 适合简单队列，但复杂消息场景更推荐 Stream 或 MQ
- Set 适合集合去重、交并差
- ZSet 适合排行榜、延迟队列、按 score 范围查询

Q: Bitmap、HyperLogLog、GEO 分别适合什么场景？
A:
- Bitmap 用 bit 表示状态，适合签到、在线状态、布尔统计
- HyperLogLog 用于基数估算，例如 UV 统计，误差换空间
- GEO 基于有序集合和 geohash，适合附近位置查询
- 这些结构都不是万能存储模型，要看精度、范围和更新频率
- 面试表达：高级类型的价值是用更低空间或更合适的操作表达业务

## Stream卡
Q: Redis Stream 和 Pub/Sub 有什么区别？
A:
- Pub/Sub 是实时广播，消息没有持久保存，消费者离线会丢
- Stream 消息持久化在 Redis 数据结构中
- Stream 支持消费组、消息确认和 pending 列表
- Stream 更像轻量消息队列，但不等价于 Kafka/RabbitMQ
- 选择时要看可靠性、堆积能力、消费语义和运维成本

## 正确性审查卡
Q: Redis 数据类型使用有哪些常见误区？
A:
- "Hash 一定比 String 省内存"：不一定。取决于字段数量、编码和访问模式
- "HyperLogLog 能精确计数"：错误。它是近似统计
- "List 就能替代消息队列"：不完整。确认、重试、堆积和可观测性较弱
- "ZSet 延迟队列绝对可靠"：不完整。还要处理并发抢占、失败重试和持久化
- "Redis 类型只看功能"：还要看内存、时间复杂度和大 key 风险
