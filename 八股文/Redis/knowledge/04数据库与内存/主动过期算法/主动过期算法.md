# 主动过期算法

> 版本基线：Redis 7.4 OSS。答案中的结构体与函数名以官方源码为准；版本差异会显式标注。

## 01-快慢周期

Q: activeExpireCycle 的 FAST 和 SLOW 两种周期在哪里运行？

A:
- SLOW 周期由 serverCron 定期调用，允许占用一定比例 CPU；FAST 周期可在 beforeSleep 中短时补扫。
- Redis 7.4 默认基础常量：每 DB 每轮采样 20 key、fast 时长 1000 微秒、slow 最大约占 CPU 25%、可接受 stale 约 10%。
- `active-expire-effort` 1–10 会同时调整采样数、时间预算和可接受过期比例。
- 这些是算法预算，不是保证某 key 在到期后多少毫秒内物理删除。

## 02-采样流程

Q: 一次主动过期循环怎样选择数据库和 key？

A:
1. 从保存的 current DB/游标继续，而非每轮从 DB0 全表开始。
2. 对 expires 结构采样有限数量，检查绝对过期时间并删除到期 key。
3. 维护平均 TTL 和过期比例；若采样中仍有较高比例已过期，在预算允许时继续该 DB。
4. 达到时间上限则退出，把工作留给下一轮，保证主线程不会无限清理。

## 03-为什么用采样

Q: 为什么 Redis 不用一个按时间排序的最小堆管理所有 TTL？

A:
- 堆能快速找到最早过期项，但每次设置/更新/删除 TTL 都要维护 O(log N) 索引并增加节点内存。
- Redis 用 expires 哈希表保持 TTL 更新平均 O(1)，再通过惰性访问和主动随机/游标采样回收。
- 这是精确删除时刻、写入成本、内存和实现复杂度之间的折中。
- Redis 7.4 对 hash field expiration 引入了额外 ebuckets 机制，不能把 key 级算法机械套到字段级过期。

## 04-过期风暴

Q: 大量 key 同时到期时，主动过期为什么会造成抖动？

A:
- 采样命中率很高会持续使用更多周期预算；删除对象、通知、AOF/复制传播和 allocator 释放都消耗主线程/后台资源。
- 即使每轮有时间上限，连续多轮也会抬高 CPU 和尾延迟，随后淘汰/回源又可能冲击下游。
- TTL 加随机抖动应基于业务容忍窗口，避免同一批次整数秒集中失效。
- 监控 expired_keys 速率、CPU、latency event、命中率和后端 QPS，不能只看 Redis 是否存活。

## 05-参数取舍

Q: active-expire-effort 调高会得到什么，又牺牲什么？

A:
- 更积极采样和更长时间预算能降低过期垃圾占用，适合 TTL 密集且内存紧张的场景。
- 代价是主线程更多 CPU 花在回收而非处理请求，p99 可能上升。
- 若根因是 TTL 设计集中、对象巨大或内存容量不足，单纯调高 effort 只是改变症状。
- 应先压测 1–10 不同值，并同时观测 stale 内存、吞吐和尾延迟。
