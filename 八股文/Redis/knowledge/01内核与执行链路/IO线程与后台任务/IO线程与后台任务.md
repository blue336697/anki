# IO线程与后台任务

> 版本基线：Redis 7.4 OSS。答案中的结构体与函数名以官方源码为准；版本差异会显式标注。

## 01-IO线程边界

Q: Redis 6+ I/O threads 具体并行了什么，没有并行什么？

A:
- 可并行处理网络写；配置 `io-threads-do-reads yes` 后也可分担读取与协议解析相关工作。
- 普通命令对 keyspace 的执行仍主要回到主线程串行完成，不能因此宣称 Redis 已经多线程并行执行命令。
- 主线程把待处理 client 分发到各线程列表，通过状态变量协调本轮读/写任务，再汇总到主线程继续执行。
- 默认 `io-threads 1`、读线程关闭；只有网络 I/O 成为瓶颈且 CPU 核足够时才有收益。

## 02-BIO线程

Q: BIO 后台线程解决哪些主线程不能做的工作？

A:
- BIO 把可能阻塞或耗时的后台工作放入队列，例如 AOF fsync、关闭文件、lazy free。
- `UNLINK`/异步 FLUSH 会先把对象从 keyspace 摘除，再让 lazy-free 线程递归释放底层内存，从而缩短主线程停顿。
- “异步删除”只把释放成本后移；内存不会在命令返回瞬间完全归还，释放队列过长仍会造成 used_memory/RSS 滞后。
- 源码锚点：`src/bio.c`、`src/lazyfree.c`。

## 03-fork子进程

Q: RDB 和 AOF rewrite 为什么使用子进程，而不是普通线程？

A:
- fork 后子进程拥有父进程地址空间的页表快照，可遍历一致视图而不与主线程共享可变对象锁。
- 实际物理页依靠 Copy-On-Write 共享；父进程修改页面时才复制，因此并非立即复制整个数据集。
- 代价是 fork 页表开销、COW 内存放大、内存带宽和磁盘 I/O 竞争；写流量越大，COW 越严重。
- Linux 应关注 `latest_fork_usec`、`rdb_last_cow_size`/`aof_last_cow_size`、透明大页和可用内存。

## 04-何时开IO线程

Q: 什么现象说明该考虑 I/O threads，而不是盲目增加线程？

A:
- 单核接近满载但命令 CPU 本身低、网络收发/协议处理占比高、包率很大，才可能受益。
- 若瓶颈是 O(N) 命令、Lua、fork、内存碎片、带宽上限或客户端连接池，增加 I/O 线程不会解决根因。
- 线程数通常不应超过可用物理核，并要给主线程、后台线程和系统留核；官方配置示例强调 8 核常从 2–3 个 I/O 线程试起。
- 通过同一数据集压测 p50/p99、CPU 分布和吞吐，再决定是否开启读线程。

## 05-常见误区

Q: 如何回答“Redis 6 之后是不是就不再单线程了”这一追问？

A:
- 先区分三个层次：进程内一直有后台线程；持久化常有子进程；Redis 6 新增可配置网络 I/O 线程。
- 再给结论：核心 keyspace 命令执行模型仍以主线程串行为主，原子性和无锁数据结构修改主要来自这个边界。
- 最后补限制：模块、后台任务和未来版本可能扩展并行能力，不能把“主线程串行”外推成所有代码都不并行。
- 源码验证：`src/networking.c::IOThreadMain` 与 pending read/write 调度路径。
