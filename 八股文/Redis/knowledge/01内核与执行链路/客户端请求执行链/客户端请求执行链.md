# 客户端请求执行链

> 版本基线：Redis 7.4 OSS。答案中的结构体与函数名以官方源码为准；版本差异会显式标注。

## 01-输入缓冲

Q: 客户端字节从 socket 进入 Redis 后存在哪里？

A:
- accept 后创建 `client`，连接读处理器设置为 `readQueryFromClient`。
- 读回调把字节追加到 SDS 类型的 `client.querybuf`，`qb_pos` 标记已经解析到的位置，避免每解析一条就整体搬移。
- 大 bulk 参数可走专门路径并使用 non-greedy 扩容，降低预分配浪费；query buffer 受客户端缓冲上限保护。
- 源码锚点：`src/networking.c::readQueryFromClient`、`client.querybuf`。

## 02-RESP解析

Q: RESP 请求怎样被解析成 argc/argv？

A:
- `processInputBuffer` 根据首字节区分 inline 与 multibulk；常规客户端使用 RESP 数组格式。
- `processMultibulkBuffer` 先解析 `*argc`，再逐个解析 `$len\r\n<payload>\r\n`，为参数构造 robj。
- 数据不完整时保留解析状态并返回，等下一次读事件继续；不会假设一次 read 就得到完整命令。
- 超大参数时会尽量避免重复复制，但仍必须受 `proto-max-bulk-len` 和 client query buffer 限制。

## 03-命令查找与校验

Q: 真正执行命令前 Redis 做哪些检查？

A:
- `processCommand` 先按命令名查 `redisCommand`，校验 arity、认证/ACL、集群槽与重定向、内存淘汰、磁盘错误、复制只读状态等。
- MULTI 中的普通命令不会立即执行，而是复制 argv 和命令元数据到 `multiState` 队列。
- 通过检查后进入 `call()`，调用 `cmd->proc`；执行耗时、dirty 计数、slowlog、命令统计也围绕 call 更新。
- 写命令的传播目标由命令属性和执行结果决定，不是“收到写命令就无条件写 AOF/复制”。

## 04-传播与回包

Q: 写命令执行后怎样进入 AOF、复制流和客户端输出缓冲？

A:
- 命令修改数据后，`propagate`/alsoPropagate 路径把规范化后的命令送往 AOF 和 replica；某些命令会被重写为确定性形式。
- 回复先写入客户端固定小缓冲，放不下时追加 `clientReplyBlock` 链表；主线程不必在命令内把所有字节同步发完。
- pending write clients 在 beforeSleep 阶段批量尝试发送，未写完的连接注册 writable 事件继续发送。
- 输出缓冲超过 soft/hard limit 会被关闭，Pub/Sub 和 replica 客户端尤其要防慢消费者。

## 05-延迟拆解

Q: 一条 Redis 请求的端到端延迟应该拆成哪几段？

A:
- 客户端排队/连接池等待 → 请求编码与网络发送 → 服务端 socket/querybuf 排队 → RESP 解析与安全检查。
- 命令主线程等待 → 命令实际执行 → AOF fsync/复制等待类命令造成的额外等待 → reply buffer 排队。
- 服务端写 socket → 网络返回 → 客户端 event loop 解码和业务线程调度。
- SLOWLOG 主要覆盖命令执行，不覆盖上述全部阶段；排障必须同时看客户端指标、Redis latency events、CPU、网络和输出缓冲。
