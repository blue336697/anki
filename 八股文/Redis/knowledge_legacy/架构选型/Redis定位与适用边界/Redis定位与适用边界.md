# Redis定位与适用边界

## 01-母题输出卡
Q: 面试官问“为什么用 Redis，不用本地缓存或数据库”，应该怎样结构化回答？

A:
- 先说业务目标：降低读延迟、减少数据库压力、提供共享原子数据结构，而不是因为“Redis 快”
- 本地缓存延迟最低但实例间不共享、一致失效困难；Redis 提供跨实例共享状态和集中治理
- 数据库是事实源并擅长持久事务与复杂查询；Redis 用内存和受限模型换低延迟
- Redis 适合可重建缓存、短状态、计数、排行和轻量协调，不适合无限数据、复杂关系查询和强一致事实账
- 决策必须带数据规模、读写比、陈旧容忍、故障降级、RPO/RTO 和成本

## 02-为什么快卡
Q: Redis 的低延迟来自哪些组合条件，哪些条件一旦破坏就不再快？

A:
- 热数据在内存，避免常规磁盘随机 IO；数据结构和编码针对常用操作优化
- 事件驱动和短命令降低线程切换与锁竞争，pipeline 可摊薄网络 RTT
- value 过大、O(N) 命令、长 Lua、网络大回复会占住执行路径
- 内存不足、fork/COW、AOF fsync、复制和迁移都会制造尾延迟
- 所以“快”是数据模型、命令规模和资源水位共同保证的运行结果

## 03-不适用边界卡
Q: 哪些场景不应该把 Redis 作为核心事实源？

A:
- 不能接受异步复制丢失窗口且缺少外部对账的余额、账务和关键状态
- 数据规模远超可承受内存，访问又不具备明显冷热分布
- 需要复杂关联、临时查询、强 schema 和多行事务的业务
- 单 value 或集合会无界增长，必须频繁全量扫描与大范围计算
- 团队无法提供持久化、备份、故障转移、容量和客户端治理时

## 04-部署选型卡
Q: 单机、主从+Sentinel 和 Cluster 应怎样选择？

A:
- 可丢失、易重建且规模小的缓存可从单机开始，但仍需监控与降级
- 数据量单机可承载、需要自动主从切换时可用 Sentinel
- 数据量或吞吐需要水平分片时选择 Cluster，同时接受客户端路由和跨槽限制
- 部署形态不能替代容量模型；热点 key 和大 key 在 Cluster 中仍是单节点问题
- 所有方案都要明确故障域、RPO/RTO、备份和客户端重连

## 05-项目决策卡
Q: 如何用可验证数据说明“这个项目确实需要 Redis”？

A:
- 给出数据库基线 QPS、P95/P99、热点查询比例和目标延迟
- 估算缓存命中后的数据库降载、Redis 内存、网络和峰值 OPS
- 定义允许陈旧时间、缓存 miss/Redis 故障时的降级路径
- 通过压测比较无缓存、本地缓存、Redis 的吞吐与尾延迟
- 上线后用命中率、回源 QPS、错误率和成本复盘，而不是只展示平均响应时间

## 06-十分钟闭卷验收卡
Q: 怎样闭卷完成 Redis 架构选型连续追问？

A:
- 从业务目标对比数据库、本地缓存与 Redis
- 解释 Redis 快的条件和破坏这些条件的操作
- 举出不适合作为事实源的场景
- 对比单机、Sentinel、Cluster 的能力边界
- 用容量、延迟、命中率和故障降级证明选型
- 只能回答“内存快、分布式缓存”，应按未掌握处理
