# 事务WATCH与Lua

## 01-母题输出卡
Q: Redis 需要把多条命令组合执行时，MULTI/EXEC、WATCH 和 Lua 分别解决什么问题？

A:
- MULTI/EXEC 负责把已入队命令连续执行，期间不会插入其他客户端命令，但不提供关系数据库式回滚
- WATCH 给 EXEC 增加条件：被观察 key 在提交前发生变化，整个事务放弃，由客户端重新读取和重试
- Lua 把“读、判断、写”放到服务端一次原子执行，适合短小且需要依赖前一步结果的逻辑
- pipeline 只减少网络往返，不保证原子性；它和事务、Lua 解决的是不同问题
- 选型核心是依赖关系、冲突率、脚本时长、Cluster 槽约束和失败后的业务语义

## 02-MULTI错误语义卡
Q: MULTI/EXEC 的“原子执行”具体保证什么？命令报错时为什么不会自动回滚？

A:
- MULTI 后命令先入队，EXEC 时按顺序执行；执行这批命令期间不会插入其他客户端命令
- 语法、参数数量等可在入队时发现的错误，会使事务不能正常执行
- 类型不匹配等运行时错误只让对应命令失败，前后其他命令仍可能已经执行
- Redis 不维护通用 undo log，放弃自动回滚换取实现简单和执行性能
- 所以它保证的是执行隔离与顺序，不是数据库 ACID 的完整语义；业务补偿仍由应用设计

## 03-WATCH冲突卡
Q: WATCH 如何实现乐观 CAS？高冲突时会发生什么？

A:
1. 客户端先 WATCH 相关 key，再读取当前值并在应用侧计算新值
2. 客户端进入 MULTI，把写命令入队后调用 EXEC
3. 如果 WATCH 到的 key 在此期间被修改、过期或淘汰，EXEC 返回失败而不执行队列
4. 客户端必须重新读取、重新计算，并按有限次数和退避策略重试
- 高冲突下大量事务会反复失败，CPU 和网络成本上升；此时应考虑原子命令、Lua、串行化入口或改变数据模型

## 04-Lua原子性边界卡
Q: Lua 脚本为什么适合原子“读改写”，又为什么不能承载复杂业务？

A:
- 脚本在 Redis 执行上下文中连续运行，可把读取、判断和写入合成一次不可插入的操作
- 它减少客户端与 Redis 的多次 RTT，也避免读完后被并发修改的窗口
- 脚本运行期间会占用主执行路径，长循环、大集合遍历或复杂计算会阻塞所有客户端
- 脚本不能把 Redis 与数据库、MQ 的写入变成一个分布式事务
- Cluster 中脚本涉及的 key 必须满足同槽约束；动态 key 应通过 KEYS 显式声明和校验

## 05-工程选型卡
Q: 库存扣减、限流和状态更新分别怎样选择 Redis 原子能力？

A:
- 单 key 计数优先使用 `INCR`、`DECR`、`SET NX` 等原生命令，语义清楚且成本最低
- 令牌桶、滑动窗口等需要多步读改写时，可用短 Lua 脚本并限定 key 数、数据规模和执行时长
- 低冲突配置更新可用 WATCH CAS；高冲突场景不要依赖无限客户端重试
- 涉及数据库事实源的库存或余额，Redis 原子扣减只能做前置控制或派生状态，最终正确性仍需数据库约束、幂等与对账
- 所有方案都要定义超时、重试、重复执行和脚本升级期间的兼容策略

## 06-十分钟闭卷验收卡
Q: 不看答案，怎样证明自己能应对 Redis 事务与 Lua 的连续追问？

A:
- 先对比 pipeline、MULTI/EXEC、WATCH、Lua 四者各自解决的问题
- 推演一次 MULTI 中运行时命令报错，说明哪些命令已经生效以及为何不回滚
- 推演 WATCH 冲突后的客户端重试，并解释高冲突退化
- 说明 Lua 的原子性来自哪里、为什么长脚本会拖死实例、Cluster 有何限制
- 用库存或限流案例给出选型，同时明确数据库事实源、幂等和对账边界
- 只会说“事务不回滚、Lua 原子”而不能进行故障推演，应按未掌握处理
