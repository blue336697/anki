# Key设计TTL与容量规划

## 01-母题输出卡
Q: Redis 上线前怎样从 key 设计推导容量，而不是等内存告警后再扩容？

A:
- 先定义 key schema、租户/业务维度、数据类型、平均与 P99 value 大小、TTL 和最大元素数
- 容量不能只算 value，还要包含 key、对象头、底层编码、过期字典、复制/客户端缓冲和碎片
- 用每日新增量、存活时间和访问分布估算稳态 key 数，再叠加峰值写入与增长余量
- 同时预留 fork COW、AOF 重写、全量复制和故障转移所需临时内存
- 设置扩容水位、增长率告警和数据清理责任人，容量规划才形成闭环

## 02-Key规范卡
Q: 一个可治理的 Redis key schema 应包含什么，哪些命名方式会制造风险？

A:
- 推荐表达业务域、租户、实体与用途，例如 `risk:{tenantId}:rule:{version}`
- key 不能无意义过长，但过度缩写会失去归属和排障能力
- 多租户必须把隔离维度放进 key；涉及 Cluster 原子操作时谨慎设计 hash tag
- 禁止把高基数随机维度无限拼接而没有 TTL 与数量上限
- key 规范要配 owner、数据分类和迁移版本，不能只靠文档约定

## 03-TTL治理卡
Q: TTL 应怎样根据业务语义设计，为什么“统一 24 小时”通常不合理？

A:
- TTL 应由数据变化频率、允许陈旧时间、重建成本和访问热度共同决定
- 大批同源数据要加入抖动，热点 key 还需主动刷新或逻辑过期
- 空值 TTL 通常更短，防止新数据创建后长期不可见
- 永不过期数据必须有明确 owner、容量上限和主动失效链路
- 监控无 TTL key 比例、TTL 分布和集中到期时间，防止配置悄悄失控

## 04-容量估算卡
Q: 如何粗略估算一个 Redis 数据集的稳态内存与峰值内存？

A:
- 稳态 key 数约等于单位时间新增量 × 平均存活时间，再按业务保有量校准
- 基础数据内存用样本 `MEMORY USAGE` 分布乘 key 数，而不是只用序列化 value 大小
- 再加复制/客户端缓冲、过期元数据、allocator 碎片和安全余量
- 峰值还要叠加 fork COW、AOF rewrite、全量同步与流量突增
- 用压测或影子数据校验估算，并按增长率计算到达扩容水位的日期

## 05-扩容与清理卡
Q: 内存持续上涨时，怎样判断是扩容、缩短 TTL、清理数据还是修改模型？

A:
- 先区分正常业务增长、无 TTL 泄漏、大 key 增长、客户端缓冲和碎片
- 可重建冷数据优先优化 TTL/淘汰；无界集合要修改分桶、归档或长度上限
- 业务确实增长且模型合理时再扩容，并验证热点与槽分布是否均衡
- 清理必须限速、可审计并评估复制/AOF，不能在线直接大批 `DEL`
- 每次处置后复核命中率、数据库回源、内存增长率和 P99

## 06-十分钟闭卷验收卡
Q: 怎样闭卷完成 Redis 容量治理连续追问？

A:
- 设计一个含租户、实体、版本的 key schema，并指出 hash tag 风险
- 根据陈旧容忍和重建成本制定 TTL，而不是给统一数字
- 从新增率、存活时间、MEMORY USAGE 和碎片估算稳态容量
- 加上 fork、rewrite、复制缓冲得到峰值余量
- 面对内存上涨给出诊断、清理、模型修改和扩容决策
- 只会说“设置 maxmemory 和淘汰策略”，应按未掌握处理
