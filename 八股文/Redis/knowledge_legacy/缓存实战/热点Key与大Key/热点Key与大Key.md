# 热点Key与大Key

## 01-母题输出卡
Q: 热点 key 和大 key 有什么区别，为什么 Cluster 不能自动解决它们？

A:
- 热点 key 的核心是访问集中，瓶颈可能出现在单节点 CPU、网卡、连接或热点过期
- 大 key 的核心是 value 体积或集合元素过多，风险覆盖执行时间、网络、删除、复制、持久化和迁移
- 一个 key 只属于一个 slot；Cluster 扩容不会把单个热点或大 value 自动拆到多个节点
- 同一个 key 可以既热又大，排障时必须同时看访问分布和数据规模
- 治理原则是发现、限流/拆分、平滑迁移和持续防回归，而不是临时删除

## 02-热点治理卡
Q: 一个读热点把单节点打满时，本地缓存、复制 key 和读副本怎样选择？

A:
- 短 TTL 本地缓存可分散读流量，但要接受多实例陈旧和失效广播复杂度
- 把只读热点复制成多个带后缀 key 可分散槽位，应用负责路由和一致更新
- 读副本能扩展读取，但受复制延迟影响，不能承接强 read-after-write
- 热点数据可提前预热、请求合并和限流，避免过期瞬间变成击穿
- 先确认瓶颈是 Redis 还是客户端/网络，不能因 QPS 高就盲目拆 key

## 03-大Key风险卡
Q: 为什么大 key 不只是“占内存”，一次读写会怎样影响整条链路？

A:
- 读取或遍历需要在主执行路径处理大量元素，并生成大回复占用输出缓冲和带宽
- 同步删除可能长时间释放对象；即使用 `UNLINK`，后台释放仍消耗 CPU 和内存带宽
- RDB/AOF、主从复制、Cluster 迁移都会搬运大对象，放大 fork、网络和全量同步压力
- 大集合上的单条 O(N) 命令会阻塞其他客户端，平均延迟可能正常但 P99 激增
- 数据模型应限制单 key 最大字节数和集合元素数，并提供分页/分片接口

## 04-发现与处置卡
Q: 线上怎样安全发现并处理大 key，而不让排查动作本身拖垮 Redis？

A:
- 先从 `MEMORY USAGE`、采样工具、业务 key 规范和监控估算，避免全库阻塞扫描
- 必须遍历时使用 `SCAN` 系列、小批次和限速，在低峰观察实例延迟
- 删除优先 `UNLINK`；集合可按 `HSCAN/SSCAN/ZSCAN` 分批清理后再删 key
- 处置前评估读写流量、复制 backlog、AOF 和迁移影响，必要时先让业务停止写入
- 删除只是止血，还要修复无界增长的数据模型和上游写入约束

## 05-容量与观测卡
Q: 怎样把热点 key、大 key 治理做成长期机制？

A:
- 统一 key schema，记录业务归属、类型、预计元素数、TTL 和最大 value 大小
- 监控 top key QPS、网络字节、慢命令、输出缓冲、大对象数量和增长速度
- 对集合写入设置长度上限或分桶规则，对异常增长触发告警而非等到内存满
- 发布前压测最坏数据规模，验证读取、删除、持久化和故障转移延迟
- 建立旁路本地缓存、限流和降级开关，热点突发时能够快速止血

## 06-十分钟闭卷验收卡
Q: 怎样闭卷完成热点 key 与大 key 的连续追问？

A:
- 先区分访问热点和数据体积，并解释 Cluster 为何不能自动拆单 key
- 对比本地缓存、key 复制、读副本的收益与一致性代价
- 推演大 key 对主线程、网络、复制、持久化和迁移的放大链
- 给出安全扫描、分批删除、`UNLINK` 和业务停写步骤
- 最后设计 key 上限、监控和应急开关
- 只会回答“热点加缓存、大 key 用 UNLINK”，应按未掌握处理
