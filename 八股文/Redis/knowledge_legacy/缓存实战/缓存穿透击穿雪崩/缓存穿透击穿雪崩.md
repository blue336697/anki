# 缓存穿透击穿雪崩

## 01-母题输出卡
Q: 缓存穿透、击穿和雪崩分别是什么？回答时怎样从故障链而不是定义列表展开？

A:
- 穿透是请求的数据根本不存在，缓存无法沉淀结果，请求持续落到数据库
- 击穿是单个热点 key 失效，大量并发同时重建同一份数据
- 雪崩是大量 key 同时失效或缓存整体不可用，数据库遭遇面状流量冲击
- 三者表象都是回源激增，但治理分别侧重无效请求拦截、单 key 重建合并和全链路限流降级
- 所有方案的最终目标都是保护事实源，而不是只提高缓存命中率

## 02-穿透闭环卡
Q: 对恶意或异常请求造成的缓存穿透，空值缓存和布隆过滤器怎样组合？

A:
- 先做参数、权限和业务边界校验，明显非法请求不应进入缓存层
- 对确认不存在但可能重复查询的 key 缓存空值，并使用较短 TTL 防止长期污染
- 数据创建后要主动失效对应空值，否则新数据可能在空值 TTL 内不可见
- 布隆过滤器适合大规模存在性预判：可能误判存在，但不会把已加入元素误判为不存在
- 过滤器更新延迟、重建和误判仍会放行请求，因此还需限流、风控和数据库保护

## 03-击穿时序卡
Q: 热点 key 过期时，互斥重建和逻辑过期各自怎样工作、如何取舍？

A:
- 互斥重建让一个请求获得重建资格，其余请求等待、快速失败或返回兜底，保证数据库只承受一次查询
- 锁必须有 TTL，重建也要有超时；持锁请求失败时要允许后续请求接管
- 逻辑过期把“是否陈旧”写进 value，陈旧时先返回旧值并异步刷新，优先保证可用性
- 逻辑过期会主动服务旧数据，不适合不能容忍陈旧的权限、余额等场景
- 选择依据是热点程度、允许陈旧时间、重建成本和等待超时，而不是统一使用分布式锁

## 04-雪崩防护卡
Q: Redis 整体不可用或大量 key 同时过期时，怎样构建多层防护？

A:
- TTL 加随机抖动只能缓解集中到期，无法解决 Redis 节点故障
- 应具备主从/Cluster 高可用、容量水位和热点预热，降低缓存自身故障概率
- 应用侧要限流、熔断、请求合并和分级降级，防止所有流量同时穿透到数据库
- 数据库侧还需连接池上限、只读保护和慢查询治理，不能让缓存故障拖垮事实源
- 恢复时分批预热和逐步放量，避免 Redis 恢复瞬间再次击穿数据库

## 05-观测与演练卡
Q: 怎样区分穿透、击穿和雪崩，并验证防护真的有效？

A:
- 穿透常表现为大量不同不存在 key、缓存与数据库都 miss；要看非法参数和空值命中
- 击穿表现为少数热点 key 在失效点回源并发陡升；要看单 key QPS 与重建次数
- 雪崩表现为全局命中率下降、Redis 错误率或大量 TTL 同时到期，数据库连接池快速耗尽
- 压测应包含热点过期、Redis 超时、批量 TTL 到期和恢复预热，而不只是正常命中路径
- 核心指标是数据库回源 QPS、连接池等待、降级比例和恢复时间

## 06-十分钟闭卷验收卡
Q: 怎样闭卷完成缓存三大问题的连续深挖？

A:
- 不看术语，分别画出不存在请求、热点到期、缓存整体故障的流量路径
- 解释空值和布隆过滤器的更新边界
- 对比互斥重建与逻辑过期，并说出旧值服务的业务风险
- 给出从 Redis、应用到数据库的雪崩防线
- 设计监控与故障演练，说明怎样判断系统已经收敛
- 只会背“穿透空值、击穿加锁、雪崩随机 TTL”，应按未掌握处理
