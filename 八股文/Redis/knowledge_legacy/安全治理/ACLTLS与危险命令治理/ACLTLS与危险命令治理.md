# ACLTLS与危险命令治理

## 01-母题输出卡
Q: Redis 安全治理为什么不能只设置一个密码？

A:
- 安全边界包括网络可达性、身份认证、命令授权、传输加密、凭证管理和审计
- Redis 不应直接暴露公网，应通过私网、安全组和最小入口限制访问
- ACL 按应用身份限制 key pattern 与命令类别，避免所有服务共享超级账号
- TLS 保护传输中的凭证和数据，但不替代权限控制
- 高危命令、配置修改和批量扫描应从运行账号剥离，并记录审计

## 02-ACL最小权限卡
Q: 怎样为不同应用设计 Redis ACL，而不是复制 default 用户权限？

A:
- 每个应用或能力域使用独立用户，权限可单独轮换和吊销
- 只允许所需命令类别，并用 key pattern 限制可访问业务前缀
- 普通业务账号禁止管理、调试、危险和全库扫描类命令
- 发布前用真实命令清单验证权限，避免为了修复一次 NOPERM 直接放开 `+@all`
- 定期清理闲置账号并检查权限漂移

## 03-危险命令卡
Q: `KEYS`、`FLUSHALL`、`CONFIG`、`EVAL` 等命令应怎样治理？

A:
- `KEYS` 和大范围扫描会阻塞或放大负载，业务账号应禁用并提供受控 SCAN 工具
- `FLUSHALL/FLUSHDB` 可造成不可逆数据损失，只允许隔离管理流程执行
- `CONFIG`、复制和 Cluster 管理命令会改变实例行为与拓扑，应与业务账号分离
- `EVAL` 只允许受审脚本与受限 key，避免任意长脚本占住主线程
- 命令重命名不能替代 ACL、网络隔离和审计，只能作为附加防线

## 04-凭证与TLS卡
Q: Redis 凭证轮换和 TLS 上线时，怎样避免全量客户端同时断开？

A:
- 使用双凭证或新旧用户重叠窗口，先发布客户端新凭证，再撤销旧凭证
- 检查连接池中的长连接是否会自动重连并使用新配置
- TLS 上线要验证证书链、主机名、到期告警和性能开销
- 凭证不得写入仓库或日志，应由密钥系统下发并支持审计
- 演练错误证书、过期证书和权限撤销，确认客户端快速失败而非无限重试

## 05-事件响应卡
Q: 怀疑 Redis 凭证泄露或执行了危险命令时，如何响应？

A:
- 立即限制网络入口、吊销相关用户或凭证，并保护仍需运行的关键链路
- 保存 ACL、连接、命令审计、慢日志和基础设施日志，确定时间窗与影响 key
- 对数据做事实源对账，不能因 Redis 当前看似正常就认定没有篡改
- 轮换关联凭证、修复过宽权限和泄露渠道，再分阶段恢复流量
- 事后补充最小权限、异常命令告警和恢复演练

## 06-十分钟闭卷验收卡
Q: 怎样闭卷完成 Redis 安全治理连续追问？

A:
- 从网络、认证、ACL、TLS、凭证和审计六层给出防线
- 为两个业务设计不同 key pattern 与命令权限
- 解释危险命令为什么不能只靠口头规范
- 设计一次不中断服务的凭证轮换
- 推演凭证泄露后的隔离、取证、对账和恢复
- 只会说“设密码、不开放公网”，应按未掌握处理
