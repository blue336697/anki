# Cluster槽与重分片

## 01-母题输出卡
Q: Redis Cluster 如何同时实现分片和高可用？它的核心边界是什么？

A:
- key 空间被划分为 16384 个 hash slot，主节点分别负责一组槽，key 通过 CRC16 结果映射到槽
- 分片单位是槽而不是单个请求；迁移槽即可扩缩容，不必重新定义整个 key 路由算法
- 每个主节点可配置从节点，节点间通过 Cluster Bus/Gossip 传播拓扑和故障信息
- 主节点失败后由其从节点参与选举并接管槽，但底层异步复制仍存在已确认写丢失窗口
- Cluster 不代理请求，客户端必须理解槽映射和 MOVED/ASK 重定向
- 单个热点 key、大 key、跨槽多 key 操作和网络分区是主要边界

## 02-槽与客户端路由卡
Q: 客户端怎样把命令路由到正确节点，为什么不能每次都随机访问？

A:
- 客户端根据 key 或 hash tag 计算 slot，再查本地 slot-to-node 映射
- 正常请求直接发送给负责该槽的节点，避免通过中心代理增加跳数
- 收到 MOVED 后更新稳定槽映射；拓扑变化时还要主动或定期刷新
- 批量命令应按 slot 分组，分别发送到对应节点并合并结果
- 槽缓存过旧、刷新风暴和错误重试会放大故障，因此客户端能力是 Cluster 稳定性的一部分

## 03-重分片时序卡
Q: 一个槽从源节点迁到目标节点时，为什么会出现 ASK？

A:
1. 目标节点把槽标记为 importing，源节点把槽标记为 migrating
2. 槽内 key 逐个从源节点迁移，迁移期间并非所有 key 同时完成
3. 源节点仍有该 key 时直接服务；key 已在目标节点时返回 ASK 指向目标
4. 客户端向目标节点先发送 `ASKING`，再执行这一次命令
5. 槽正式归属目标后，访问旧节点会收到 MOVED，客户端再更新长期映射
- 迁移期间要限制并发与带宽，热点槽和大 key 会显著拉长窗口

## 04-故障转移卡
Q: Cluster 怎样判定主节点失败并提升从节点？网络分区下有什么代价？

A:
- 节点通过 Gossip 交换 PFAIL 信息，足够主节点形成共识后标记 FAIL
- 故障主节点的从节点根据复制进度、延迟和选举规则争取晋升
- 获胜从节点成为新主并接管原槽，拓扑逐步传播到其他节点和客户端
- 少数派侧通常停止服务相关槽，以避免长期双写，但会牺牲局部可用性
- 异步复制意味着故障前未传播的写仍可能丢失，Cluster 目标不是强一致

## 05-扩缩容治理卡
Q: Redis Cluster 扩容为什么不是“加机器就线性变快”，应该怎样安全实施？

A:
- 新节点加入后没有槽就不承载数据，必须规划槽迁移和容量均衡
- 迁移速度受 key 数、大 key、热点流量、网络和目标节点内存限制
- 迁移期间监控 ASK/MOVED、P99、网络、复制延迟和客户端重试，必要时限速或暂停
- 多 key 业务与 hash tag 可能形成热点槽，按槽均衡不等于负载均衡
- 缩容前确保槽和副本迁完，验证故障域分布，避免主从落在同一故障域

## 06-十分钟闭卷验收卡
Q: 怎样闭卷完成 Redis Cluster 连续追问？

A:
- 先解释 16384 槽、客户端路由、主从副本和 Cluster Bus 的整体关系
- 画出 migrating/importing、key 迁移、ASK、MOVED 的时序
- 推演主节点故障、从节点晋升和异步复制丢写
- 解释跨槽多 key、hash tag、热点槽和大 key 的边界
- 设计一次扩容迁移的限速、监控和回滚条件
- 只会背“CRC16 和 16384”，应按未掌握处理
