# MOVED-ASK与HashTag

## 01-母题输出卡
Q: MOVED、ASK 和 hash tag 在 Redis Cluster 中分别解决什么问题？

A:
- MOVED 表示槽的稳定归属与客户端认知不一致，客户端应重定向并刷新长期槽缓存
- ASK 表示槽迁移中的临时路由，客户端只对本次请求向目标节点发送 `ASKING`，不永久改槽映射
- hash tag 让 `{}` 中相同内容的 key 落到同一槽，以支持部分多 key 操作
- 三者共同反映 Cluster 不做服务端代理：路由、重定向和批量拆分主要由客户端承担
- hash tag 解决同槽约束，却可能制造热点槽，必须与负载均衡一起设计

## 02-MOVED处理卡
Q: 客户端收到 MOVED 后，为什么不能只重试一次就结束？

A:
- MOVED 告诉客户端该 slot 当前负责节点，通常意味着稳定拓扑已变化
- 客户端应先把本次请求发往新节点，再更新或刷新本地槽位缓存
- 大量并发同时刷新拓扑可能形成风暴，需要去重、限频和后台刷新
- 若继续随机请求旧节点，会反复重定向，增加 RTT、日志和服务端压力
- 重试写命令前仍要考虑连接是否已发送成功和业务幂等，不能把 MOVED 当安全重试证明

## 03-ASK时序卡
Q: ASK 为什么要求先发送 `ASKING`，又为什么不能更新长期槽缓存？

A:
- ASK 发生在槽迁移中，目标节点尚未正式拥有该槽，只临时接收已经迁移的 key
- `ASKING` 告诉目标节点允许执行紧随其后的这一次命令
- 同一槽的其他 key 可能仍在源节点，因此永久切换槽缓存会把未迁移 key 路由错
- 迁移完成后由 MOVED 反映稳定归属，客户端再更新长期映射
- ASK 激增说明迁移窗口或热点问题，应监控而不是把重定向当正常无成本行为

## 04-HashTag边界卡
Q: hash tag 什么时候有价值，什么时候会破坏 Cluster 扩展性？

A:
- 事务、Lua 或多 key 命令确实要求同槽时，可把业务聚合 ID 放入 `{}` 中
- 例如 `order:{123}:base` 与 `order:{123}:items` 同槽，便于原子处理同一订单
- 若所有租户共用 `{order}`，大量 key 会集中到一个槽和节点，失去分片意义
- tag 粒度应既满足原子边界又能分散负载，通常选择实体 ID 或合理分桶 ID
- 上线前统计槽分布、热点 QPS 与单槽数据量，不能只验证命令“不再 CROSSSLOT”

## 05-批量命令卡
Q: Cluster 下需要批量读取不同槽 key，客户端应该怎样做？

A:
- 先按 slot 对 key 分组，每组对对应节点执行 MGET 或 pipeline
- 各节点请求可受控并发，最后按原始 key 顺序合并结果和错误
- 批次要限制 key 数与返回字节，避免一个慢节点决定整体长尾
- 部分失败要定义重试和降级语义；写批次尤其需要幂等
- 不能为省客户端逻辑而滥用 hash tag，把所有 key 强行挤进同一槽

## 06-十分钟闭卷验收卡
Q: 怎样闭卷完成 MOVED、ASK 与 hash tag 的连续追问？

A:
- 对比稳定重定向与临时重定向，画出客户端槽缓存变化
- 解释 ASKING 的一次性语义和迁移期间 key 分布
- 设计一个正确与一个错误的 hash tag 方案
- 给出跨槽 MGET 的分组、并发、合并和部分失败处理
- 说明重定向风暴、热点槽和重试幂等的监控
- 只会说“MOVED 永久、ASK 临时”，应按未掌握处理
