# 慢查询内存与延迟

## 01-母题输出卡
Q: Redis P99 突然升高时，怎样分层排查而不是先看 slowlog？

A:
- 先确认客户端观测：请求量、命令类型、超时、连接池等待、重试和 DNS/网络是否变化
- 再看 Redis 执行：slowlog、latency monitor、主线程 CPU、大 key 和长 Lua
- 检查后台事件：fork、COW、AOF fsync/rewrite、全量复制、槽迁移和主动过期
- 检查系统资源：CPU steal、内存交换、NUMA、磁盘抖动和网络丢包
- 最后关联变更与时间线，用对照指标验证根因；重启只能止血，不能当结论

## 02-Slowlog边界卡
Q: slowlog 没有记录，为什么请求仍可能很慢？

A:
- slowlog 主要记录命令在服务端执行阶段的耗时，不包含客户端排队、网络传输和回复读取
- 连接池耗尽、事件循环前排队或客户端 GC 都可能让端到端很慢
- 大回复的网络发送和客户端反序列化可能占主要时间，但命令计算本身不慢
- fork、系统调度和网络抖动也可能形成延迟尖刺
- 必须把客户端 trace、Redis latency 事件和系统指标按同一时间轴关联

## 03-内存排查卡
Q: used_memory 正常但 RSS 很高，或者内存突然翻倍，应该想到什么？

A:
- RSS 高于逻辑使用量可能来自 allocator 碎片和内存页未及时归还操作系统
- RDB/AOF fork 后父子进程共享页，写流量会触发 COW，短时增加实际内存
- 大 key、输出缓冲、复制缓冲和客户端积压不一定完全体现在业务 value 估算中
- 检查 `used_memory`、RSS、fragmentation、fork/COW、buffer 和 swap，而不是只看 maxmemory
- 容器环境还要核对 cgroup 限额，防止宿主机看似有内存但实例被 OOM

## 04-延迟尖刺卡
Q: 周期性延迟尖刺通常怎样从时间特征反推原因？

A:
- 与 RDB/AOF 周期一致，优先检查 fork、fsync、rewrite 和磁盘
- 与整点或批任务一致，检查 TTL 集中到期、预热、统计任务和大批 pipeline
- 与主从断线一致，检查全量同步、backlog 和网络带宽
- 与发布后持续上升一致，检查新命令复杂度、key 规模和客户端重试
- 与系统噪声一致，检查 CPU steal、swap、透明大页和虚拟化调度

## 05-处置闭环卡
Q: Redis 延迟事故中，止血、定位、修复和防复发分别做什么？

A:
- 止血：限流或关闭高成本接口、旁路非关键缓存、暂停迁移/批任务，保护数据库
- 定位：保留 slowlog、latency、INFO、客户端 trace 和系统快照，不要重启后丢证据
- 修复：拆大 key、限制批次、优化命令、调整持久化/复制资源或客户端超时
- 验证：回放同等流量，对比 P50/P99、错误率、CPU、网络和内存
- 防复发：命令审查、key 上限、容量预测、故障演练和自动告警

## 06-十分钟闭卷验收卡
Q: 怎样闭卷完成 Redis 线上排障连续追问？

A:
- 从客户端、Redis 执行、后台任务、操作系统四层给出排查树
- 解释 slowlog 的计时边界
- 区分逻辑内存、RSS、碎片和 fork COW
- 根据周期性、突发性和发布相关性反推候选根因
- 给出止血、证据保留、修复验证和防复发闭环
- 只会说“查 slowlog 和 bigkeys”，应按未掌握处理
