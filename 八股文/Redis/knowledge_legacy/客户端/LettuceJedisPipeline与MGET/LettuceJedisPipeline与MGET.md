# LettuceJedisPipeline与MGET

## 01-母题输出卡
Q: Redis 客户端选型为什么不能只比较 Jedis 和 Lettuce 的 API？

A:
- 要比较连接并发模型、同步/异步能力、Cluster/Sentinel 拓扑刷新、超时重试和可观测性
- Jedis 传统同步连接通常由线程独占或经连接池管理；Lettuce 基于 Netty，连接可线程安全共享并支持异步/响应式
- “可共享”不代表所有命令都应走一个连接，阻塞命令、大回复和订阅需要隔离
- 客户端重试、连接池和拓扑缓存配置不当，故障时可能比 Redis 本身更先雪崩
- 选型应以业务并发模型、故障演练和团队运维能力为准

## 02-超时重试卡
Q: Redis 客户端需要区分哪些超时？为什么写命令超时不能无脑重试？

A:
- 连接超时控制建连，命令超时控制请求完成，池等待超时控制获取连接，拓扑刷新也有独立时限
- 命令超时只说明客户端没及时拿到结果，不证明服务端没有执行
- 对 `INCR`、扣减、入队等非天然幂等写直接重试，可能重复生效
- 重试应限定错误类型、次数并加入退避抖动，同时配业务幂等键或结果查询
- 故障期间要限制总并发和连接创建速率，避免重试与重连风暴

## 03-Pipeline机制卡
Q: pipeline 为什么能提升吞吐，批次过大又为什么会变慢？

A:
- pipeline 连续发送多条命令再批量读取回复，把多次 RTT 和系统调用摊薄
- 命令仍按 Redis 执行路径处理，pipeline 不提供事务原子性
- 服务端需要暂存未发送回复，客户端也要保存请求与结果，批次越大内存越高
- 一个慢命令或大回复会拉长整批完成时间，形成 head-of-line blocking
- 应按命令成本和返回字节压测批次，而不是固定追求“越多越快”

## 04-Cluster批量卡
Q: Redis Cluster 下 MGET/pipeline 跨槽时怎样正确实现？

A:
- 先按 slot 分组，同槽 key 才能组成原生多 key 命令
- 不同节点的子批次可受控并发，完成后按原始 key 合并结果
- hash tag 可让强相关 key 同槽，但过度集中会造成热点槽
- 需要处理 MOVED/ASK、部分节点超时和拓扑刷新，不能只返回第一处异常
- 总超时应覆盖分组与并发，但不能被单个慢节点无限拖住

## 05-连接隔离卡
Q: 为什么 Lettuce 连接线程安全仍可能需要连接池或独立连接？

A:
- 线程安全只说明并发调用不会破坏客户端状态，不保证延迟隔离
- 阻塞命令、Pub/Sub、事务状态和超大回复会占用连接或造成队头阻塞
- 同步高并发场景可能需要连接池限制并发；异步场景更要限制 in-flight 数量
- 普通命令、阻塞命令、订阅和大批处理应按用途隔离连接
- 监控连接数、池等待、pending 命令、超时和重连次数，才能判断模型是否合适

## 06-十分钟闭卷验收卡
Q: 怎样闭卷完成 Redis 客户端连续追问？

A:
- 从并发模型而不是品牌偏好对比 Jedis 与 Lettuce
- 区分四类超时并推演一次“服务端已执行但客户端超时”
- 解释 pipeline 的 RTT 收益、内存成本和队头阻塞
- 设计 Cluster 跨槽 MGET 的分组与部分失败
- 说明连接共享、池化与用途隔离的边界
- 只会说“Jedis 阻塞、Lettuce 异步”，应按未掌握处理
