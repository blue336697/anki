# Redis分布式锁与Redisson

## 01-母题输出卡
Q: 面试官问“Redis 分布式锁怎么设计才安全”，请用 90 秒讲清保证、实现和边界。

A:
- 单实例基本写法是 `SET lockKey token NX PX ttl`：一次命令完成互斥获取和租约过期
- token 必须唯一，释放时只有持有者才能删除；旧版本通常用 Lua 校验再删，Redis 8.4+ 可关注条件删除命令
- TTL 解决持有者崩溃后的活性问题，但同时意味着锁只是有期限的租约，不是永久所有权
- 业务超过 TTL、STW、网络分区和主从故障都可能让两个客户端先后认为自己有资格操作资源
- Redisson 看门狗能续期并提供可重入等工程能力，但不能消除异步复制和租约失效的根本边界
- 高正确性场景还要靠 fencing token、资源侧幂等/版本校验，必要时改用数据库或共识型协调系统

## 02-正确加解锁卡
Q: Redis 锁为什么必须“原子加锁、唯一 token、条件解锁”三个条件同时成立？

A:
- `SETNX` 后再单独 `EXPIRE` 之间若进程崩溃，可能留下永不过期的死锁
- 没有唯一 token，就无法判断当前 key 是否仍属于最初的持有者
- 客户端 A 超时后锁已被 B 获得，A 若直接 `DEL` 会误删 B 的锁
- 正确释放要在一个原子步骤中比较 token 并删除，旧版本常用 Lua 完成
- TTL 要覆盖正常临界区但不能无限大；获取、续期、释放都必须有超时和失败记录

## 03-租约失效时序卡
Q: 即使加锁和解锁写法正确，业务执行超过 TTL 时为什么仍可能并发写资源？

A:
1. 客户端 A 获得租约并开始处理，但发生长 GC、网络暂停或下游阻塞
2. 锁 TTL 到期，Redis 自动释放锁
3. 客户端 B 获得同一锁并开始更新资源
4. A 恢复后并不知道自己已经失去资格，也继续提交旧操作
5. 此时 Redis 锁本身无法阻止资源接受 A 的迟到写入
- 结论：锁只能控制进入临界区的资格窗口，资源侧仍要拒绝过期持有者

## 04-Redisson看门狗卡
Q: Redisson 看门狗如何续期？它解决了什么，又没有解决什么？

A:
- 未显式指定固定 leaseTime 时，Redisson 可在持锁线程仍存活时周期性延长 TTL
- 续期降低正常业务耗时不可预测导致的锁过期概率，并支持可重入、读写锁等封装
- 如果进程长时间暂停、网络隔离或续期任务本身得不到调度，租约仍可能失效
- 显式指定 leaseTime 的使用方式可能不走无限续期语义，必须结合具体 API 和版本确认
- 看门狗改善易用性和活性，不把 Redis 主从复制变成强一致，也不能替代资源侧保护

## 05-FencingToken卡
Q: fencing token 如何阻止“旧持有者恢复后继续写”的问题？

A:
- 每次成功获得锁时同时取得单调递增的序号，例如 101、102
- 客户端把序号随写请求发送给真正的资源服务或数据库
- 资源侧记录已接受的最大序号，只接受更大的 token，拒绝迟到的旧请求
- 这样 A 即使恢复并持有旧 token 101，也无法覆盖 B 已提交的 102
- fencing 必须由资源侧执行校验；只在 Redis 客户端里比较无法保护外部资源

## 06-方案选型卡
Q: 单实例锁、Redlock、数据库锁和 ZooKeeper/etcd 应怎样选？

A:
- 可容忍极小并发窗口、操作幂等的场景，可用单 Redis 实例锁换取简单和低延迟
- Redisson 适合 Java 工程化封装，但仍要评估实际部署、续期和故障模型
- Redlock 依赖多个独立主节点、时钟漂移和多数派假设；高正确性场景必须理解争议并配 fencing
- 资源本就在数据库且事务较短时，唯一约束、行锁或乐观版本往往更直接
- 需要强协调、会话语义和明确顺序时，ZooKeeper/etcd 等共识系统通常更合适
- 决策依据不是“哪个组件高级”，而是错误一次的损失、可用性目标和运维复杂度

## 07-十分钟闭卷验收卡
Q: 不看答案，怎样完成一次 Redis 分布式锁的连续深挖？

A:
- 写出原子加锁和条件解锁，并解释少任一条件会发生什么
- 推演 TTL 过期、旧持有者恢复、误删新锁三条故障时序
- 解释看门狗续期机制及其失效条件
- 用 fencing token 说明资源侧怎样拒绝迟到写
- 对比 Redis 单实例、Redlock、数据库锁和 ZooKeeper/etcd 的适用场景
- 最后落到自己的项目：说明锁保护什么、资源幂等怎么做、监控哪些超时与续期指标
