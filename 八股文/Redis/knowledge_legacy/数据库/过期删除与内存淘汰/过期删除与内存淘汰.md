# 过期删除与内存淘汰

## 01-母题输出卡
Q: Redis 的过期删除和内存淘汰有什么本质区别？

A:
- 过期由业务 TTL 决定 key 何时失效；淘汰由 `maxmemory` 压力决定必须释放哪些 key
- key 到期不代表物理内存瞬间释放，Redis 结合访问时的被动过期和周期性主动过期
- 内存超过限制后按 `maxmemory-policy` 选择 key；`noeviction` 会让新增写入报错而不是自动扩容
- volatile 系列只在带 TTL 的 key 中选，allkeys 系列面向全部 key
- 两套机制都要与业务事实源、缓存命中率和容量规划一起设计

## 02-过期机制卡
Q: 为什么 Redis 不为每个 TTL 建独立定时器，而采用被动加主动过期？

A:
- 每 key 定时器会带来大量调度和内存成本，不适合海量 key
- 被动过期在访问 key 时检查时间，到期则删除，CPU 成本按访问分摊
- 只靠被动过期会让不再访问的过期 key 长期占内存，所以后台周期抽样主动清理
- 主动过期在 CPU 与回收及时性之间动态取舍，不能保证到点立即释放
- 从业务视角到期 key 应视为不可见，不应依赖“内存里还在”继续读取

## 03-淘汰策略卡
Q: LRU、LFU、volatile 和 allkeys 应怎样选，Redis 的 LRU 为什么是近似的？

A:
- 通用纯缓存常从 allkeys-lru 或 allkeys-lfu 评估；存在稳定热点时 LFU 可能更合适
- volatile 策略要求候选 key 带 TTL，没有可淘汰候选时可能退化为写失败
- `volatile-ttl` 更偏向先淘汰剩余 TTL 短的 key，适合业务已表达价值差异的场景
- Redis 通过抽样近似 LRU/LFU，避免维护精确全局顺序的内存与 CPU 成本
- 选型要用真实命中率、淘汰率和访问分布验证，不靠策略名称猜测

## 04-集中到期卡
Q: 大量 key 同时过期会怎样从 Redis 扩散到数据库？

A:
- 主动过期会集中消耗 CPU，大量删除也影响 AOF、复制和内存释放
- 缓存命中率骤降后，回源请求同时涌入数据库，连接池和慢查询进一步放大排队
- TTL 抖动可打散同批数据，但热点 key 还要请求合并、互斥重建或逻辑过期
- Redis 故障造成的全量 miss 需要限流、降级和数据库保护，随机 TTL 无法解决
- 恢复阶段应分批预热，避免一次性把数据库和网络再次打满

## 05-生产选型卡
Q: 缓存与持久数据混在同一 Redis 实例时，淘汰策略为什么难以安全配置？

A:
- allkeys 策略可能淘汰不应丢的持久数据，volatile 策略又可能因候选不足导致写失败
- 两类数据的 TTL、价值、容量和故障恢复目标不同，共享水位会相互影响
- 更清晰的方案是按用途拆实例或至少拆独立资源池和监控
- 必须设置 maxmemory、告警水位、增长率预测和恢复演练，不能依赖淘汰兜底容量
- Redis 被当数据库使用时还要同时回答持久化、备份、复制和误删恢复

## 06-十分钟闭卷验收卡
Q: 怎样闭卷完成过期与淘汰连续追问？

A:
- 先区分业务 TTL 与内存压力两套触发条件
- 解释被动和主动过期为何组合、为什么到点不等于立即释放
- 根据访问分布选择 LRU/LFU、volatile/allkeys，并说明近似算法
- 推演集中到期到数据库雪崩的链路
- 解释缓存与持久数据混部为何危险并给出容量水位
- 只会列策略名称，应按未掌握处理
