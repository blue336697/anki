# 事件驱动与单线程模型

## 01-母题输出卡
Q: 面试官问“Redis 为什么快，单线程为什么还能扛高并发”，请用 90 秒讲出完整主线。

A:
- 快的前提不是“内存”三个字，而是内存访问、紧凑数据结构、事件驱动和短命令共同作用
- Redis 用 IO 多路复用监听大量连接，不需要为每个连接绑定一个工作线程
- 核心命令执行长期以串行模型为主，省掉共享数据结构上的锁竞争，也让单条命令的原子性更容易推理
- 单线程的代价是一个慢命令会阻塞后续所有请求，所以数据规模和命令复杂度比线程数更重要
- Redis 6 起可用 IO 线程分担部分网络读写；后台持久化、异步释放等也会使用其他线程或进程
- 结论：Redis 擅长大量短小操作，不适合把大计算、大结果集或长脚本塞进主执行路径

## 02-事件循环机制卡
Q: 一个客户端命令从 socket 就绪到返回结果，Redis 事件循环大致经历什么？

A:
1. 多路复用器等待 socket 的可读、可写事件，把就绪连接交给事件分派逻辑
2. Redis 读取并解析 RESP 请求，形成待执行命令
3. 主执行路径按顺序操作内存数据结构，生成回复
4. 回复进入客户端输出缓冲区，socket 可写时再发送
5. 时间事件穿插执行 serverCron 等周期任务，处理过期、统计和维护工作
- 所以“并发连接很多”不等于“命令同时修改数据”，连接并发与命令执行模型要分开回答

## 03-版本边界卡
Q: “Redis 是单线程的”这句话在 Redis 6+ 应该怎样准确表达？

A:
- 经典结论指核心命令执行和数据结构修改主要串行完成，不代表进程里只有一个线程
- Redis 6 引入可配置 IO 线程，主要分担网络读写和协议处理，命令本身不会因此随意并行修改同一份数据
- RDB/AOF 后台任务常涉及 fork 子进程；lazy free、部分磁盘 IO 和维护任务也可能使用后台线程
- 开启 IO 线程只对网络处理成为瓶颈的场景有帮助，慢命令和大 key 不会因此消失
- 面试时先说明版本，再落回关键性质：慢操作仍可能占住主执行路径并放大所有请求延迟

## 04-阻塞传播卡
Q: 哪些操作会阻塞 Redis 主执行路径，为什么一个请求会拖慢所有客户端？

A:
- 对大集合执行 `HGETALL`、集合聚合、排序或一次返回海量元素，会同时消耗 CPU 和输出缓冲
- `KEYS` 扫描全库、长 Lua 脚本和不受控模块命令会长时间占用执行线程
- 大 key 的同步删除、编码转换和内存分配可能制造明显延迟尖刺
- fork 本身、AOF fsync、内存压力和操作系统调度虽然不全是命令计算，也会形成停顿或排队
- 因为请求串行经过主执行路径，前一个任务不让出执行权，后面的短命令也只能等待

## 05-工程治理卡
Q: 线上怎样防止“单线程被拖死”，并证明治理有效？

A:
- 上线前审查命令时间复杂度和返回规模；集合接口必须分页，禁止无界 `KEYS`、`HGETALL` 和全量聚合
- 使用 `SCAN` 系列分批遍历，删除大 key 优先 `UNLINK` 或分批删除成员
- 同时观察 slowlog、latency monitor、主线程 CPU、事件循环延迟和客户端 P99，不能只看平均耗时
- 限制 pipeline 批次、Lua 执行时长和客户端输出缓冲，避免把网络优化变成内存与长尾问题
- 慢分析任务放副本或离线系统，但必须接受副本延迟，不能让业务误以为读到强一致数据

## 06-十分钟闭卷验收卡
Q: 不看答案，怎样完成一次“Redis IO 模型”连续追问并判断自己真正掌握？

A:
- 先讲 Redis 快的组合原因，再画出 socket 就绪、解析、执行、回复的事件循环
- 解释连接并发与命令串行的区别，以及为什么串行模型减少锁但放大慢命令
- 说清 Redis 6+ IO 线程改变了什么、没有改变什么
- 连续举出大 key、长脚本、全量扫描、fork/fsync 四类延迟来源
- 给出从命令设计、批次限制、监控到应急旁路的治理闭环
- 只能回答“因为内存和 epoll”而讲不出阻塞传播与版本边界，应按未掌握处理
