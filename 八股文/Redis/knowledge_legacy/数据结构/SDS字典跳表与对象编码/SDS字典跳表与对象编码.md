# SDS字典跳表与对象编码

## 01-母题输出卡
Q: Redis 的“数据类型”和“底层编码”为什么必须分开理解？

A:
- String、Hash、List、Set、ZSet 是对外语义，同一类型可按规模和内容选择不同内部编码
- 小对象常使用连续紧凑结构节省指针和提升缓存局部性，超过阈值后转换为通用结构
- 这种转换体现 CPU、内存和操作复杂度的取舍，也解释了某些写入为何出现延迟尖刺
- Redis 7 起很多旧 ziplist 场景改用 listpack；具体编码必须结合版本和 `OBJECT ENCODING`
- 面试重点不是背结构名，而是说明访问模式、转换条件和大 key 风险

## 02-SDS机制卡
Q: SDS 相比 C 字符串解决了哪些 Redis 核心需求？

A:
- 显式记录长度，获取长度无需扫描，追加前也能判断容量
- 二进制安全，value 中可以包含 `\0`，不依赖终止字符表达内容
- 记录容量并采用扩容策略，减少连续追加导致的频繁内存重分配
- API 能基于容量做边界检查，降低缓冲区溢出风险
- SDS 仍受单 value 大小和大对象复制成本约束，不代表 String 可无限增长

## 03-渐进Rehash卡
Q: Redis 字典为什么使用两张哈希表渐进 rehash，迁移期间读写怎样进行？

A:
- 一次性搬迁大哈希表会长时间阻塞主执行路径，所以迁移被拆到多次操作和周期任务中
- rehash 开始后保留旧表和新表，逐步把旧桶元素移动到新表
- 查询需要按状态检查两张表；新写通常进入新表，删除也要处理迁移状态
- 渐进迁移削平单次延迟，但增加临时内存与每次操作的少量额外成本
- 大量 key 与内存压力下仍要关注 rehash 进度和容量余量

## 04-ZSet跳表卡
Q: ZSet 为什么通常同时需要字典和跳表，而不是只保留一种结构？

A:
- 字典提供 member 到 score 的平均 O(1) 定位，适合判断与更新成员
- 跳表按 score 和 member 维持顺序，支持范围、排名和顺序遍历
- 跳表平均查找、插入、删除为 O(log N)，范围扫描实现自然
- 两份索引用额外内存换取两类访问能力，单个超大 ZSet 仍会成为大 key
- 小 ZSet 可能使用紧凑 listpack 编码，超过阈值后才转换为通用结构

## 05-版本与转换卡
Q: ziplist、listpack、quicklist、intset 等编码在面试中怎样避免背成过时结论？

A:
- 先说编码是版本和阈值相关实现细节，不能把 API 类型永久等同于某一种结构
- Redis 7+ 的小 Hash/ZSet/List 广泛使用 listpack；List 的通用组织仍围绕 quicklist
- 纯整数小 Set 可使用 intset，现代版本还可能对小 Set 使用 listpack
- 超过元素数或单元素大小阈值会自动转换，转换通常不可因删除简单逆转
- 用 `OBJECT ENCODING` 和目标版本配置验证，不引用陈旧默认值作为架构保证
