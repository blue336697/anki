# 高级数据类型与使用场景

## 01-母题输出卡
Q: 面试官让你为业务选择 Redis 数据类型，应该按什么维度回答？

A:
- 先描述需要的操作：按 key 取值、字段更新、队列、去重、排序、范围查询、近似统计还是事件流
- 再看时间复杂度、内存编码、单 key 最大规模和是否会形成大 key
- 还要明确原子边界、TTL 粒度、Cluster 同槽约束和持久化可靠性
- String/Hash/List/Set/ZSet 只是 API 类型，不能脱离访问模式机械套场景
- 最后给出增长上限、分页方式、监控和数据迁移策略

## 02-基础类型选型卡
Q: String、Hash、List、Set、ZSet 分别适合什么，最常见的误用是什么？

A:
- String 适合整体对象、计数和标记；大 JSON 每次整体改写会放大网络与内存
- Hash 适合字段级读写；字段无限增长仍会成为大 key，且 TTL 通常按 key 管理
- List 适合简单两端队列；需要 ACK、重试和消费组时应考虑 Stream 或专业 MQ
- Set 适合去重和集合关系；大集合交并集可能阻塞主线程
- ZSet 适合排行榜、范围查询和调度索引；score 精度、并发抢占和大 key 要额外治理

## 03-BitmapHLLGEO卡
Q: Bitmap、HyperLogLog 和 GEO 的空间收益分别以什么能力或精度为代价？

A:
- Bitmap 用位表示布尔状态，用户 ID 稠密时极省空间；ID 稀疏会浪费大片位区间
- HyperLogLog 用固定级别空间估算基数，适合 UV 趋势，不适合精确计费或集合成员判断
- GEO 基于地理索引支持附近与距离查询，适合初筛，不替代专业 GIS 的复杂几何能力
- 三者都应明确数据范围、误差和更新模式，不能因为“高级类型”就默认更优
- 上线前用真实数据分布验证空间与精度

## 04-Stream能力卡
Q: Stream 的消费组、PEL 和 ACK 怎样组成至少一次消费链路？

A:
- 生产者 `XADD` 追加有序 ID，消费者组用 `XREADGROUP` 分摊消息
- 已投递未确认消息进入 Pending Entries List，成功处理后用 `XACK` 移除 pending 状态
- 消费者故障后用 `XPENDING` 发现超时消息，并通过 `XCLAIM/XAUTOCLAIM` 转移
- 这形成 at-least-once 语义，消费者必须幂等；ACK 不能证明业务副作用一定成功
- 还需设置 trimming、积压水位、死信和重试上限，防止内存无限增长

## 05-数据模型验收卡
Q: 设计一个 Redis 数据模型时，哪些问题必须在上线前回答？

A:
- key schema、租户隔离、类型、TTL 与最大 value/元素数分别是什么
- 每个接口的命令复杂度、最坏返回字节和是否涉及跨槽多 key
- 数据事实源在哪里，Redis 丢失或陈旧时业务怎样降级与重建
- 热点、大 key、内存增长和过期集中如何监控
- 未来扩容、编码转换和结构迁移怎样双写、校验与回滚

## 06-十分钟闭卷验收卡
Q: 怎样闭卷完成 Redis 数据类型选型连续追问？

A:
- 从业务操作反推基础类型，并指出每种类型的大 key 风险
- 对比 Bitmap、HLL、GEO 的空间、精度和数据分布边界
- 画出 Stream 消费组、PEL、ACK、claim 和幂等链路
- 给出 key schema、TTL、容量上限、Cluster 与重建方案
- 用一个真实业务说明为什么没有选择另一种结构
- 只会列“String 缓存、ZSet 排行榜”，应按未掌握处理
