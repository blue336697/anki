# RDB与AOF

## 01-母题输出卡
Q: Redis RDB、AOF、复制和备份分别解决什么，怎样按 RPO/RTO 选型？

A:
- RDB 是时间点快照，文件紧凑、恢复快，但两次快照之间可能丢较多数据
- AOF 记录写操作，fsync 策略决定性能与丢失窗口，文件和恢复成本通常更高
- 复制提供在线副本和快速切换，不提供历史版本；错误删除也会同步
- 备份用于误操作和灾难恢复，必须离机保存并定期验证可恢复
- 选型要同时回答允许丢多少数据 RPO、多久恢复 RTO、写延迟和内存/磁盘余量

## 02-RDB与COW卡
Q: BGSAVE 怎样生成一致快照，fork 和 COW 为什么可能造成延迟与内存峰值？

A:
- 主进程 fork 子进程，子进程基于 fork 时的数据视图写临时 RDB，完成后原子替换旧文件
- 父进程继续服务写请求；被修改的内存页触发 Copy-on-Write
- 数据集越大，fork 页表成本越高；写流量越大，COW 额外内存越多
- 内存余量不足可能导致 OOM，慢磁盘会延长子进程和 COW 窗口
- 生产应监控 fork 时长、COW 大小、RDB 耗时和失败，而不是只确认“开了 bgsave”

## 03-AOF策略卡
Q: AOF 的 always、everysec、no 怎样取舍，客户端收到成功是否等于已落盘？

A:
- always 每次写都等待 fsync，耐久性更强但写延迟和吞吐成本最高
- everysec 通常由后台每秒 fsync，在性能与约一秒级窗口之间折中
- no 把刷盘更多交给操作系统，性能好但故障丢失窗口更不可控
- 客户端成功只代表对应配置语义下写被接受，不应脱离 fsync 策略宣称“绝不丢”
- 还要考虑磁盘满、fsync 卡顿、AOF 损坏与重启加载时间

## 04-AOF重写版本卡
Q: AOF 重写为什么能压缩文件，Redis 7 的多段 AOF 与旧模型有什么区别？

A:
- 重写依据当前内存状态生成等价最小命令集，不是简单压缩旧日志
- Redis 7 前常用“重写期间增量缓冲 + 完成后拼接”的经典解释
- Redis 7+ 使用 base AOF、incremental AOF 和 manifest 管理多段文件，父进程在重写期间继续写新的增量文件
- 切换时通过 manifest 组织新文件集合，降低旧模型的一些内存与管理压力
- 面试应先声明版本，不要把“重写缓冲区拼接单文件”当成所有现代版本的唯一实现

## 05-恢复演练卡
Q: 怎样证明 Redis 持久化真的可用，而不是配置文件里写了 appendonly yes？

A:
- 定期验证 RDB/AOF 生成、文件大小、校验、磁盘空间和失败告警
- 在隔离环境执行恢复，记录加载时间、最后可见数据点和业务校验结果
- 同时开启 RDB 与 AOF 时，重启通常优先使用更完整的 AOF 数据集
- 备份要离开实例和故障域，并覆盖误删、文件损坏和整机丢失场景
- 演练磁盘满、AOF 尾部损坏、fork 失败和慢恢复，形成明确 RPO/RTO

## 06-十分钟闭卷验收卡
Q: 怎样闭卷完成 Redis 持久化连续追问？

A:
- 从 RPO/RTO 对比 RDB、AOF、复制和备份
- 画出 fork、子进程快照、父进程写入和 COW
- 解释三种 fsync 策略与成功响应的耐久性边界
- 区分 Redis 7 前后 AOF 重写模型
- 设计一次恢复演练和磁盘满处置
- 只会背“RDB 快、AOF 安全”，应按未掌握处理
