# 主从复制与PSYNC

## 01-母题输出卡
Q: 面试官问“Redis 主从复制如何工作，能否保证不丢数据”，请用 90 秒完整回答。

A:
- Redis 复制用于数据冗余、读扩展和 Sentinel/Cluster 故障转移的基础，但默认是异步复制
- 初次或无法续接时做全量同步：主节点生成快照并传输，从节点加载后再追赶同步期间的增量
- 断线重连优先用 PSYNC，根据 replication ID、offset 和 backlog 补发缺失命令
- backlog 覆盖不了断线窗口、复制历史变化或从库状态不匹配时，会退化成成本更高的全量同步
- 主节点确认写成功时从节点可能尚未收到；主故障切换后，已确认写仍存在丢失窗口
- 工程上用延迟监控、backlog 容量、`min-replicas-*`、`WAIT` 和业务幂等降低风险，但不能轻易承诺强一致

## 02-全量同步卡
Q: Redis 全量复制经历哪些阶段，为什么它会同时给主从节点带来压力？

A:
1. 从节点发起同步，主节点准备当前数据集的 RDB 快照
2. 主节点 fork 子进程生成快照，同时继续处理新写并保留后续增量
3. RDB 通过网络发送，从节点清空或替换旧数据并加载快照
4. 主节点再发送快照期间积累的写命令，从节点追赶到接近当前进度
- 主节点承担 fork、COW 内存、网络和复制缓冲压力；从节点承担加载期间的 CPU、内存和暂时不可服务风险
- 多个从节点同时全量同步会形成 fork/带宽风暴，应错峰、限并发并保证磁盘与内存余量

## 03-PSYNC机制卡
Q: PSYNC 怎样判断可以部分重同步？backlog 应该如何估算？

A:
- 每条复制历史由 replication ID 和 offset 标识，从节点记录自己已处理的位置
- 重连时从节点提交旧 replication ID 与 offset，主节点判断是否仍属于可续接历史
- 若缺失区间仍保存在 replication backlog 中，主节点只补发这段数据
- backlog 太小、断线太久、写流量过高或复制历史已变化时，只能重新全量同步
- 容量估算至少考虑峰值写入字节率 × 目标可容忍断线时间，并留出波动余量，而不是只背默认值

## 04-延迟与丢失卡
Q: 主从异步复制会产生哪些业务可见问题？`WAIT` 能把它变成强一致吗？

A:
- 读从库可能看到旧值，read-after-write、会话状态和刚更新配置容易出现反直觉结果
- 主节点在写入尚未传播时故障，晋升的从节点可能缺少已确认数据
- `WAIT` 可让客户端等待指定数量副本确认某个复制 offset，显著缩小丢失概率
- 但 `WAIT` 不是跨故障模型的强一致事务；超时、分区和后续故障仍需业务处理
- `min-replicas-to-write` 与最大延迟可在副本不足时拒绝写入，用可用性换数据安全

## 05-复制延迟排障卡
Q: 发现 replica lag 持续升高，应怎样定位而不是直接重启从库？

A:
- 先看主从 offset 差、复制链路状态、backlog 命中和全量同步次数，确认是网络、处理还是反复重同步
- 检查主节点写入字节率与网络带宽，从节点 CPU、磁盘、慢命令和大 key 是否跟不上
- 关注输出缓冲、复制缓冲和内存水位，避免缓冲被挤爆后断线再触发全量同步
- 排查从库承担的大查询、持久化和容器限额；读扩展不应把副本压到无法复制
- 处置时先限流慢查询、扩容 backlog/带宽或新增副本，重启只能作为止血且可能加重全量同步

## 06-部署边界卡
Q: 主从复制、持久化和故障转移分别解决什么，为什么三者不能互相替代？

A:
- 复制解决在线副本和快速接管，但错误写入和删除也会被复制，不能代替备份
- RDB/AOF 解决进程或机器重启后的恢复，但单机持久化不能自动提供在线切换
- Sentinel/Cluster 负责发现故障和提升副本，但切换仍受异步复制的数据窗口影响
- 备份提供历史恢复点，必须离机保存并定期演练恢复
- 完整设计要同时回答 RPO、RTO、可用区故障、误操作恢复和客户端重连，而不是只说“一主两从”

## 07-十分钟闭卷验收卡
Q: 不看答案，怎样证明自己真正掌握 Redis 复制？

A:
- 先讲全量同步和部分重同步各自触发条件，并画出快照加增量的时序
- 用 replication ID、offset、backlog 解释 PSYNC，而不是只背三个名词
- 根据峰值写字节率估算 backlog，并说明过小如何引发全量同步风暴
- 推演读从库旧读与主故障丢写，解释 `WAIT` 和 `min-replicas-*` 的边界
- 给出 replica lag 的分层排查路径
- 最后区分复制、持久化、故障转移和备份四种能力
