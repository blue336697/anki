### **分布式ID生成**

名词解释

- TP999：通常表示"第999个百分位"（the 999th percentile），意味着在所有请求中，有99.9%的请求的响应时间低于或等于这个值。这是一个衡量系统在极端情况下性能的指标，用于了解在几乎所有情况下用户可以期待的最长响应时间。

> 例如，在一个Web服务中，如果TP999响应时间是500毫秒，这意味着在所有请求中，有99.9%的请求被处理的时间不会超过500毫秒。这个指标帮助开发者和系统管理员理解在高负载或极端情况下系统的表现，确保系统能够在大多数情况下提供快速响应。
> 
- 可用性5个9：99.999%的可用性意味着在一年（365天，或者8760小时）中，服务最多只允许有约5.26分钟的停机时间。

> 99%（两个9）：停机时间最多为3.65天。
> 
> 
> 99.9%（三个9）：停机时间最多为8.76小时。
> 
> 99.99%（四个9）：停机时间最多为52.56分钟。
> 
> 99.999%（五个9）：停机时间最多为5.26分钟。
> 
- SLA代表：服务级别协议”(Service Level Agreement)。它是服务提供者和客户之间的正式协议，明确规定了服务的质量、可用性、责任范围等标准。SLA通常包括服务的具体指标，如响应时间、故障恢复时间、系统可用性百分比等，以及不达标时的补偿措施。这些协议帮助确保客户可以期待一致的服务水平，并为服务提供者设定了明确的性能标准。
- NTP同步：指的是使用网络时间协议（Network Time Protocol，简称NTP）来同步计算机系统的时钟与世界标准时间（如UTC）之间的时间。NTP是一种广泛使用的协议，能够让网络中的计算机通过互联网或局域网与一个或多个NTP服务器进行通信，以校准它们的系统时钟。

> NTP同步的过程大致如下：
> 
> 1. **请求时间**：客户端（需要校时的计算机）向NTP服务器发送一个时间请求。
> 2. **接收时间**：NTP服务器接收到请求后，会根据其自身的系统时钟返回当前的时间信息。
> 3. **计算延迟**：客户端接收到服务器的时间信息后，会计算往返延迟时间，并据此调整自己的系统时钟，以尽可能准确地同步到服务器的时间。
> 4. **定期同步**：为了保持系统时钟的准确性，客户端会定期（例如每隔几分钟或几小时）重复这个过程。
> 
> NTP能够在网络环境中自动选择最佳的时间源，并使用复杂的算法来补偿网络延迟，从而实现高精度的时间同步。在许多需要时间精确同步的应用场景中，如金融交易、日志记录、网络安全等，NTP同步是非常关键的。
> 

#### **UUID**

uuid是比较经典的标识字段生成手段，拥有5种生成方式，形成8-4-4-4-12，共36个字符，每一个字符都是16进程的数

> 优点：本地生成，速度很快
> 
> 
> 缺点：
> 
> - 占用空间大，16字节128位，通常以36长度的字符串表示
> - 数据不连续，对DB存储以及查询压力大
> - 信息不安全，可通过UUID反推生成的MAC物理地址

#### **类snowflake方案**

上文介绍的UUID其实就是这种方案的一种思想，就是信息的组成分成几段，每一段的生成依据都来源不同，例如时间戳+机房ID+物理机器ID+自增序列ID等；在mongDB中的objectID就是一个例子

> 优点：
> 
> - 整体递增
> - 以服务的方式提供，稳定速度快
> - 可以通过业务分配不同BIT位的表达含义
> 
> 缺点：强依赖于机器的时钟，如果往回拨容易冲突
> 

#### **数据库生成**

这个就很显而易见了，也是小型项目的常用方式，用数据库的自增ID来满足

> 优点：简单易上手易维护
> 
> 
> 缺点：
> 
> - 分布式ID的生成性能依赖于数据库部署的机器
> - 生成强依赖于数据库，如果数据库挂了整个服务都会有问题

#### **主从数据库ID分段生成**

比如有两台机器。设置步长step为2，TicketServer1的初始值为1（1，3，5，7，9，11…）、TicketServer2的初始值为2（2，4，6，8，10…）。

> 生成公式由机器数量即步长（N）决定，以此类推
> 
> - 0，N+0，2N+0——步长为1
> - 1，N+1，2N+1——步长为2

优缺点：

> 缺点：
> 
> - 随着部署的节点越来越多，新增的步长对于水平扩展来说将会是灾难级的，例如现在只有一个，步长是1，占用的ID为1、2、3。。。当新加入的另一台，那么步长为2，此时就要从远离机器一长时间不会增常到的ID数开始增加，同时将机器一为偶数的ID全部删除，只保留奇数，所以当水平数量来到一定时将会非常困难
> - 没有了单调递增，前面调用获取的ID可能会比后面调用的ID要大
> - 读写压力大，每次还需要与DB进行交互才能获取ID

#### **Leaf-segment方案**

这个方案字面意思就很明了，通过预占用的方式和切割业务，将某个业务需要在一段时间内占用的ID全部加载到缓存中，业务与拿到的一段ID的关系可以通过一个映射表来维护，如下面代码

- biz_tag：业务标识
- max_id：这个业务当前用完所有段内ID后的最大ID
- step：段内ID数量

```java
+-------------+--------------+------+-----+-------------------+-----------------------------+
| Field       | Type         | Null | Key | Default           | Extra                       |
+-------------+--------------+------+-----+-------------------+-----------------------------+
| biz_tag     | varchar(128) | NO   | PRI |                   |                             |
| max_id      | bigint(20)   | NO   |     | 1                 |                             |
| step        | int(11)      | NO   |     | NULL              |                             |
| desc        | varchar(256) | YES  |     | NULL              |                             |
| update_time | timestamp    | NO   |     | CURRENT_TIMESTAMP | on update CURRENT_TIMESTAMP |
+-------------+--------------+------+-----+-------------------+-----------------------------+
```

---

当使用完这个段内所有ID，那么就把max_id更新为max_id+step即可

```java
Begin
UPDATE table SET max_id=max_id+step WHERE biz_tag=xxx
SELECT tag, max_id, step FROM table WHERE biz_tag=xxx
Commit
```

优缺点：

> 优点：
> 
> - 响应快
> - 很容易水平扩展
> - ID不会太长满足数据库ID自增的要求
> - 容灾性好，某个节点即便宕机也不影响服务
> - max_id可自定义大小
> 
> 缺点：
> 
> - ID太过连续，不够随机
> - TP999太过依赖于更新max_id的一次操作，会出现间隙的峰顶（尖刺）
> - 保存映射关系的DB如果宕机则会影响业务

如何优化：

- 双buffer优化

> 对于第二个缺点，当服务在更新max_id时发生阻塞，那么将会是毁灭性的，那么这个取号阶段如何优化成异步的呢，其实设置一个阈值，在每次取号时都会判断当前号段是否消耗到设定的阈值，如果达到了就提前把下一段的值更新上去，相当于把写的操作提前了，这样当DB挂了以后，保存在Leaf阶段的段还能撑一段时间；同时由于是每次取号都会判断所以偶尔的网络波动不会影响号段的更新
> 
- Leaf高可用容灾

> 对于第三个缺点，可采用一主两从配合是否是一个IDC来优化

#### **Leaf-snowflake方案**

上面的方案虽然简单易用，但是号码的总体上递增且ID本身非常简单，这就会使公司的一些信息泄漏出去，例如拿某一天最开始的订单ID和最后的订单ID相减就能得到一天的订单量

现在这个方案就是用类snowflake的方式去生成ID，当集群数量过大时，分布式的维护成本越来越大，所以引入配置中心如zookeeper，去简单维护一个workId，这个worker是每个节点的标识位，相当于使用节点本身来切割，前面也有用业务来切割的，同时这个workId也可以在服务本身缓存一份，当配置中心宕机还可以允许一段时间，启动描述如下：启动leaf节点连接zookeeper，检查是否注册过，如果注册过直接拿自己的workId，如果没有则生成一个全局唯一的

时钟问题如何解决：
