### **美团街景理解中视觉分割技术的探索与应用**

街景理解语义的结果形式：

- 点：最细分化的形式，将物体的各种特征点、要素等提取出来
- 线：以提取线条会主要目标，例如车道线、地平线和各种曲线等
- 面：以提取点和线组成的二维平面的位置信息、轮廓等
- 体：体积则是在二维的基础上扩充为三维，包含深度信息、虚拟三维重建等

![](https://p1.meituan.net/travelcube/1a5b6069d26f3d13607c490284df71a63104713.png)

目前视觉分割技术的难点在于：

- 在图片中由于物体形状的多样性、透视成像时物体远近时形状的巨大差异等问题导致算法天然的具有局限性，这就要求算法要具有鲁棒（健壮、健康）的复杂精准分割能力
- 由于天气等恶劣条件造成的识别困难
- 由于媒体的多样性，如果把多种算法的结果进行补足，以及如何利用有限的系统资源去调用算法这都是急需解决的问题

### **美团外卖推荐关于用户新颖体验优化的技术探索**

各种专用名词解释：

- feed：一种数据载体，常见于购物外卖平台，即一个小的商品展示或者外卖商家的单元格展示
- PRM：交易效率，千次展示收入
- UV_RPM：单一用户的千次展示收入
- GMV(Gross Merchandise Volume)：成交金额
- LBS(Location Based Services)：基于位置的服务
- Novelty/Unexpectedness：新颖性
- Serendipity：惊喜度
- Embedding：嵌入、植入
- PCA(Principal Component Analysis)：即主成分分析技术，又称主分量分析技术，旨在利用降维的思想，把多指标转化为少数几个综合指标。
- CGN(Graph convolution Network)：图卷积神经网络
- DNN(Deep Neural Network)：深度神经网络
- MLP(Multilayer Perceptron)：多层感知前馈神经模型

目前主流的推荐步骤为：

- 召回：是推荐系统中的第一步，其目标是从大规模的候选池中快速筛选出一小部分潜在的推荐项。在召回阶段，通常使用一些高效的算法或规则来进行快速筛选，以保证推荐的覆盖率和多样性。在召回步骤中，常常受冷启动和长尾问题困扰。目前主流的召回策略为I2I（物品到物品）和U2I（用户到物品），前者是基于用户某个维度选择一个商品时进行相似的东西进行召回；后者是基于用户的兴趣和行为进行召回

> 长尾问题（Long Tail Problem）是指在一个系统或市场中，少数热门项目或产品占据了大部分的关注和销售量，而大量的非热门项目或产品只有少量的关注和销售量。这种现象在许多领域都存在，如电影、音乐、图书、商品销售等。长尾问题的特点是热门项目或产品的销售量呈现出明显的头部，而非热门项目或产品的销售量则呈现出较长的尾部。
> 
> 
> 冷启动问题（Cold Start Problem）是指在一个系统或平台刚刚启动或新增了新的项目或产品时，由于缺乏足够的历史数据或用户反馈，导致系统无法准确预测或推荐给用户最相关的项目或产品。冷启动问题常见于推荐系统、搜索引擎、社交媒体平台等领域。解决冷启动问题需要通过收集更多的数据、利用其他相关信息或采用特定的算法和策略来进行推荐或预测。
> 
- 精排：是在召回阶段的基础上，对召回的候选项进行更加精细的排序和筛选。在精排阶段，通常会使用更加复杂的算法或模型，考虑更多的特征和用户行为，以提高推荐的准确性和个性化程度。
- 混排：是将召回阶段和精排阶段的结果进行合并和调整，以得到最终的推荐列表。在混排阶段，可以根据不同的策略和权重，将召回和精排的结果进行融合，以平衡推荐的多样性和准确性。

### **深入解析String#intern**

intern的作用：将字符串的内容放到字符串常量池中，如果常量池已经存在该字符串内容，则把字符串指向常量池中的地址

intern的优点：可以节省字符串的空间，因为字符串常量池的内部实现是hashTable，默认大小为1009长度（后面可通过`-XX:StringTableSize=99991来指定大小`），如果存储过多的常量会造成严重的冲突，性能急剧下降；但在没有冲突下搜索常量池中是否已经有某字符串的时间可以忽略不计，比没有使用intern方法造了很多字符串对象后长时间不使用GC的时间要短很多

背景：

- 字符串常量池（StringTable）在JDK6时存储在方法区（永久代）中，使用的是JVM内存，占用很小的一部分
- 在JDK7中StringTable被移动到了JVM堆中，可占用内存进一步提高，并且由于在堆中，原先相同的字符串对象如果是相同的值是无法替换的，但现在对象和StringTable都在堆中，就可以替换
- 在JDK8中StringTable被移动到了元空间，堆中存储元空间的引用，而元空间使用的则是本地内存

正确使用intern的例子：

```java
static final int MAX = 1000 * 10000;
static final String[] arr = new String[MAX];
 
public static void main(String[] args) throws Exception {
    Integer[] DB_DATA = new Integer[10];
    Random random = new Random(10 * 10000);
    for (int i = 0; i < DB_DATA.length; i++) {
        DB_DATA[i] = random.nextInt();
    }
    long t = System.currentTimeMillis();
    for (int i = 0; i < MAX; i++) {
        //arr[i] = new String(String.valueOf(DB_DATA[i % DB_DATA.length]));   //2160ms
         arr[i] = new String(String.valueOf(DB_DATA[i % DB_DATA.length])).intern();  //826ms
    }
 
    System.out.println((System.currentTimeMillis() - t) + "ms");
    System.gc();
}
```

### **分布式因果推断（反事实推断）**

因果推断

> 传统机器学习算法更关注预测问题，而因果推断提供了更佳的反事实推断能力。
> 
> 
> **以营销活动为例，我们不仅需要知道当前优惠券金额下，订单数是多少（预测问题），还要知道在改变金额的情况下，订单数会发生怎样的变化（反事实问题）。**
> 

损失函数

> 损失函数（Loss Function）是在机器学习、统计学和数学优化中使用的一个概念。它用于衡量模型预测值与真实值之间的差异。损失函数的值越小，说明模型的预测效果越好。
> 

决策树——CART输

> CART是一棵二叉树，每一次分裂会产生两个子节点。CART树分为分类树和回归树。
> 
> 
> 分类树主要针对目标标量为分类变量，比如预测一个动物是否是哺乳动物。
> 
> 回归树针对目标变量为连续值的情况，比如预测一个动物的年龄。
> 

泛化性能

> 泛化性能是指一个模型对未知数据的预测能力。在机器学习中，我们通常通过训练数据来训练模型，然后使用测试数据来评估模型的泛化性能。如果一个模型在训练数据上表现良好，但在测试数据上表现差，那么我们通常会说这个模型的泛化性能差，这可能是由于过拟合（过拟合是指为了得到一致假设而使假设变得过度严格）造成的。相反，如果一个模型在训练数据和测试数据上都表现良好，我们会说这个模型的泛化性能好。
>

### **Docker自动化部署、Linux资源管理之cgroups简介**

docker自动化部署流程：将编译打包的工作交给docker，然后容器完成工作后可销毁可不销毁，同时还解决了以下问题：

- 不同应用的构建环境在同一个虚拟机上，需要解决环境冲突和隔离的问题
- 多个应用同时构建会竞争发布机的CPU和IO资源，让构建变慢
- 应用的构建脚本运行在公共发布机上，脚本的bug可能会影响到发布机的正常运行

cgroups（control groups）是linux提供的一款可以隔离资源的工具，是用于限制线程级别的资源问题，同时可以对CPU、内存做精细控制，也是docker实现中所用到的

- 原理：将系统中每一种的可控制资源作为一个子系统，例如：cpu子系统、memory子系统，同时限制不是单独考某个子系统完成的，而是子系统与功能模块之间配合完成的，例如cpu子系统与进程模块配合

> 图中所说的结构就是字面意义上的函数结构体，在每一个 cgroups 层级结构（子系统与子系统连接-attach即形成了层级结构）中，每一个节点（cgroup 结构体）可以设置对资源不同的限制权重。比如上图中 cgrp1 组中的进程可以使用60%的 cpu 时间片，而 cgrp2 组中的进程可以使用20%的 cpu 时间片。
>

### **分布式队列的应用**

[链接](https://tech.meituan.com/2016/07/29/distributed-queue-based-programming.html)

何时选择分布式队列，需要从四个方面去考虑：

- when：消息啥时候收到，同步还是异步，当然这里的同步异步是一个很宽泛的概念，在编码中没有绝对的同步，双方的时钟周期不可能是一致的，同理也没有绝对的异步，当等待时间无限长时，异步就没有了意义。所以可以从发出的消息时候需要确认，如果不需要则更像同步，反之如果需要，则根据需要确认的时间长短来判断，时间长则是异步。同理如果发出去的消息会阻碍下一个消息则更像同步。
- who：是否关系发送方是谁，如果不关心则异步就是一个备选，因为这时就不需要记录一些信息，同时每个消息体都是一视同仁，即统一接口，统一代表高效、运维成本低。
- where：消息是否需要暂存，如果需要则异步就是一个备选。
- how：如何传递，这包含几个方面，可用性、可靠性、持久化以及跨平台兼容性，那么在衡量时间成本后，现成的分布式队列就是最好的选择。

### **如何优化Jenkins**

当任务量到一个数量级时，Jenkins的缺点暴露出来，由于Jenkins本身的问题，那么打造一个新的持续发布和交付的平台显然比在Jenkins上打补丁要好

- 使用和维护成本加大：随着项目越来越多，参与配置的人也越来越多，对于某些参数的解释文档或者解释人员都提出了要求
- 任务（Job）数量激增：Job的数量=项目数量*功能项，因为我们发布流程会提供一些必要的功能，而每个业务方在使用这些功能的时候需要配置一些自己的业务参数，出于 Jenkins 的一些局限性，常规的做法就是复制一份示例 Job 然后改成自己的构建任务。
- 构建的数据难以统计：对于Jenkins本身的数据展现能力偏弱，当Job数量过多，那么统计数据的准确性就存疑了；是否可以用Jenkins的插件呢？可以，但是构建系统的整体性就被破坏了
