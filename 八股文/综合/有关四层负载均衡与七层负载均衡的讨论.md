# **OSI七层网络模型**

首先明确一点七层模型的概念：

1. 物理层（Physical Layer）：负责传输原始的比特流，通过物理介质（如电缆、光纤）进行数据传输。
2. 数据链路层（Data Link Layer）：负责节点间的数据传输，提供错误检测和纠正功能，常见协议有以太网（Ethernet）。
3. 网络层（Network Layer）：负责数据包的路由和转发，确定数据从源到目的地的路径，常见协议有IP（Internet Protocol）。
4. 传输层（Transport Layer）：提供端到端的通信服务，确保数据的完整性和可靠传输，常见协议有TCP（Transmission Control Protocol）和UDP（User Datagram Protocol）。
5. 会话层（Session Layer）：管理会话和连接，负责建立、维护和终止通信会话。
6. 表示层（Presentation Layer）：负责数据的格式化、加密和解密，确保数据的语法和语义正确。
7. 应用层（Application Layer）：直接与用户交互，提供网络服务和应用程序接口，常见协议有HTTP、FTP、SMTP等

## **什么是四层负载，什么是七层负载**

对于前者主要针对于TCP-PORT、TCP-IP来做的负载均衡，即决定转发给谁，由于在四层是数据包的内容还没有那么丰富，能处理的功能比较单一，所以效率对比七层负载会更快一些；而第七层就要解析到应用层（比如 HTTP URL path，HTTP header 等）才能确定转发给谁；

可以据三个例子来区分——**其实可以粗暴的理解为当四层流量的走向如果不是向应用层的业务大可都认为是四层**：

1. redis-cluster-proxy 可以根据请求 Redis 的 key 转发到正确的 Redis 实例上去，那么这是一个几层负载均衡？——七层
2. Nginx stream 模式可以给数据库，比如 Mysql 的 3306 端口做一个反向代理，在这个场景下，所有发给 Nginx 的流量都会**透明地**转发给 Mysql，此场景下，Nginx 是一个几层负载均衡？——四层
3. Coredns 可以按照如下方式工作：如果我知道一个 DNS 的结果，我直接返回，如果不知道，我发给 1.1.1.1 来查询。如果我们将其看作一个代理的话，它是几层？——七层

### **如何选择？**

其实大部分公司使用七层就可以满足了，如果无脑上四层则有些费力不讨好，这是因为大部分需求在七层就能得到实现，因为在七层的数据包信息是最全的，最里层的消息本来就要解析；除非流量的目的地不是业务服务器而是什么mysql或redis等一些的组件，则可以使用第四层负载

### **四层负载的经典体现——ECMP**

ECMP（Equal-cost multipath，等价多路径）是一种网络技术。在网络中，当存在多条到达同一目的地且具有相同代价（如带宽、延迟、费用等相同）的路径时，就可以使用 ECMP 技术。

普遍意义上在网络中路由的选择都遵循”跳数“少的，并且选择了这一条路后都不会在改变了。例如下图有A——》B，则肯定是A——C——B的路径

## **如何长连接保持**

思考一个问题：当服务器扩容时，同一个请求如何做到无影响，即TCP正常工作，假设有有三个节点A、B、C，新增一个D节点，原先打在C的节点重新hash后打在了D节点，这是TCP不认识这个请求会拒绝连接（TCP是有状态的）。解决方案有两种：1、扩容的主机只适用于新请求，原先在C节点的请求，还是会再C节点不受扩容影响；2、让扩容机器也能识别旧请求

### **1、Sticky ECMP**

对于第一种来说可以使用如上的技术，此时可能还会思考使用一致性Hash来解决，但是一致性hash的本质就是来平分所有请求，就包含原先的请求，跟我们的需求是冲突的；标题提到的技术是指在负载均衡前一个节点（网络二层或三层的某个元素）来记录Hash出来的具体值，这个值不会受扩容影响，那么就能保证接收的节点是一个了

- 但是要注意hash算法的参数，如果是源IP地址的话，就会出现无论是新旧请求都会一直在某个节点
- 同时我们几乎无法控制第二层或第三层的某个元素有实现Sticky ECMP功能的硬件或软件基础

### **2、Extra Proxy**

遇事不决，再添加一层代理，自己模拟二层或三层的元素节点，记录两种信息

1. TCP的连接状态
2. 现存连接与服务节点的映射关系

这种解决方案同样存在问题，首先代理也要扩容，那么代理节点之间的信息同步肯定存在延迟，并且信息本身还是重复的

### **3、Github 的 GLB**

这个的理念是当请求计算hash时，映射出两个节点的关系，一个叫做 Primary，一个叫做 Secondary，当发现请求不属于第一个节点，则去第二个节点，这么做的好处不需要节点之间同步数据，也就没有延迟了。缺点显而易见，需要多转发一次，同时也存在第二次也是错的，并且不能将重试节点数量加大，就会陷入无限加大的死循环，所以试错一次即可。

### **4、总结**

上面三种方案都只能处理节点添加时的容错，但是无法处理节点下线或节点宕机即节点数量减少的情况，那么归根到底其实是需要LB节点之间同步请求信息的

## **如何保证LB的数据同步呢**

引入一个存放第三方存放连接状态的地方，类似于分布式session的解决方案，这个存放连接状态的地方负责将连接状态定时的同步到所有节点上，当然不是所有请求都需要同步，可以设置一定的阈值例如3s以上的

### **转发架构**

1. LB 的一个重要作用就是保护 Real Server，客户端始终只能看到 LB 的 VIP 地址，不能看到 Real Server 的地址；
2. 一个设备发送给另一个设备 TCP 数据的时候，实际发送的是 IP 包，因为 TCP 是基于 IP 的。IP 包又是基于二层以太网的。所以，可以理解为，每次发送数据都是发送的二层以太网包。
3. 发送二层包的过程可以简化如下：
    - 查看目的 IP 和我是否是在同一个子网，如果是，那么将目的 MAC 地址直接设置为目的 IP 所在的 MAC 地址（如果不知道，就发送 ARP 询问）；
    - 如果不在同一个子网，那么将目的 MAC 地址设置为网关 IP 的 MAC 地址；
4. 可以看到，网络数据发送的过程，其实就是网络设备两两之间发送的过程，交互的是以太网二层的包，每次都需要解开再重新封装。
5. 一个设备在收到数据进行回应的时候，回复给谁呢？它会将 IP 的来源作为回应的目的 IP，将 IP 包的目的 IP（就是自己）作为来源 IP，即发给我的 IP 包，我把它的来源 IP 和目的 IP 调换，然后填充响应发送回去。
6. 一个设备收到一个包的时候，它看这个包的 IP 自己有没有（是不是发给我的），如果没有（只谈 Unicast，不谈 Multicast 等），就丢弃，如果我有这个 IP，我才去处理这个包。

## **Full NET、S-NET和D-NET三种转发模式**

以往在家庭中WIFI会使用S-NET（Source Network Address Translation）的转发模式，即内网分配给你一个IP，而真正负责信息发送和接收的则会使用ISP分配的公网IP，即源IP转换，而目标IP没有变的模式称为SNET

而D-NET 顾名思义，就是 Destination 地址转换。DNAT 完美地解决了原则 1：隐藏 Real Server 的地址。但是有没有隐藏客户端的地址，很巧妙。

相反Full NET则是源IP和目标IP全部发生转化，就可以套用在上面咱们说的LB的案例上面了，作为LB接收目标地址是需要转化成内网地址，而作为服务端发送的目标地址也需要LB做转换；

### **1、Full NET**

那么源IP和目标IP都是中间态，如果有需要真实源IP做一些业务怎么办？——大致的方式就是握手的时候将源IP信息放在请求体中的某个位置即 TCP Option Address (TOA)，但是这种对于客户端需要专门解析出来，这种则可以使用D-NET的转发模式

### **2、D-NET**

这个方式显然违反了原则5，服务将自己的IP设置为源IP发送给客户端时，首先服务器的源IP暴露，其次客户端压根就不认识服务器的源IP，这是经过LB，让LB将源IP改为自己的IP即可，虽然不能改目标IP的地址，但是可以从第二层出发将第二层的MAC地址改为LB的MAC地址，交换机一看是处于同一个LAN下面的，这样也就能经过LB，LB会把源IP设置为自己的

局限：就需要依赖于框架的设置了，即LB与服务器必须要在一个子网下面，不能走三层路由，因为三层路由时目标IP还是客户端的，所以请求会直接给客户端，因为这个局限实际上在应用中很少用D-NET

### **3、D-NET和S-NET混用**

类似于Full-NET，但是在请求和回应做了区分，即回包的时候走 SNAT，就像我们在家里用路由器上网一样，RS 回包不经过 LB，但是经过一个 SNAT（类似家里的路由器），SNAT 会把来源的地址 RS IP 改成 VIP，然后再发给客户端。来回都进行地址转换了

## **DSR模式**

可以发现我们都没有讨论LB本身，在实际应用中用户所作的操作都是下行多上行少，即单个请求可能需要服务回复大量的数据（下载、直播等），但是LB本身的功能又是针对于入流量而言的，负载均衡、流量转发、安全、防止DDOS，但实际上都是出流量很多，甚至于把LB打挂；

那么其实可以思考，因为出流量不需要进行包装可以直接给到客户端而不经过LB吗？但是需要满足两点，一是源IP要隐藏，还得让客户端正确的处理请求

根据原创和需求我们需要保证三点：

1. Client 要能正确处理连接，那么它收到的包必定是：SIP: LB VIP, DIP: Client IP
2. 那代表 Server 发出来的 IP 包必定是：SIP: LB VIP, DIP: Client IP
3. 根据原则 5，那么 Server 收到的包必定是：SIP: Client IP, DIP: LB VIP

![image.png](%E6%9C%89%E5%85%B3%E5%9B%9B%E5%B1%82%E8%B4%9F%E8%BD%BD%E5%9D%87%E8%A1%A1%E4%B8%8E%E4%B8%83%E5%B1%82%E8%B4%9F%E8%BD%BD%E5%9D%87%E8%A1%A1%E7%9A%84%E8%AE%A8%E8%AE%BA/image%205.png)

要满足上面三点首要需要server得到LB同样的VIP，同时避免server回复的请求，要精准打到对应的LB而不是别的（二层MAC地址转发），同时要保证客户端的请求不能跨过LB直接到Server（因为两者的VIP是一样的）；这套最大的局限还是二层的MAC转发，因为要保证LB和server在一个子网内才能”骗过“交换机

### **1、支持跨二层的DSR模式**

为了解决二层MAC转发，可以有一种大致的方案，就是将二层的信息模拟成三层的信息冗余，要使用三层则必须知道server的真实IP，将客户端IP+VIP封装在一个UDP包（外层信息就变为LB的真实地址+server的真实地址）中，server收到后就会当作一个正常的IP包处理，但这样做数据包的体积会增大，会涉及到 MTU 超过 1500 bytes 的问题；这样就可以在三层工作了，因为IP层面都是对的，路由器也不会乱路由，同样也不需要server和LB在同一个子网；

局限：由于回流不经过LB，如果回流的是RST，那么LB完全是无感知的，还会保持连接
