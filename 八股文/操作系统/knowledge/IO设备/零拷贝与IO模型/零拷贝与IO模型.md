# 零拷贝与IO模型

## IO模型卡
Q: 阻塞 IO、非阻塞 IO、IO 多路复用、异步 IO 如何区分？
A:
- 阻塞 IO 调用后线程等待数据准备和拷贝完成
- 非阻塞 IO 立即返回，需要应用轮询或重试
- IO 多路复用用 select/poll/epoll 等等待多个 fd 就绪
- 异步 IO 提交请求后由内核完成并通知应用
- 面试表达：同步/异步看谁完成 IO，阻塞/非阻塞看调用线程是否等待

## epoll卡
Q: epoll 相比 select/poll 的核心优势是什么？
A:
- select 有 fd 数量和每次拷贝/扫描成本问题
- poll 解决部分数量限制，但仍要线性扫描
- epoll 用内核事件表管理关注 fd，并返回就绪事件
- 大量连接少量活跃时，epoll 更适合
- epoll 也不是万能，业务处理慢和大包拷贝仍会成为瓶颈

## 零拷贝卡
Q: 零拷贝解决什么问题？常见方式有哪些？
A:
- 传统 IO 可能在内核态和用户态之间多次拷贝
- 零拷贝减少数据在内核和用户空间之间的复制
- mmap、sendfile、splice、DMA 都体现零拷贝或少拷贝思想
- 网络文件发送、消息队列、静态文件服务常受益
- 零拷贝减少 CPU 拷贝成本，但不消除所有 IO 成本

## 正确性审查卡
Q: IO 模型和零拷贝有哪些常见误区？
A:
- “epoll 就是异步 IO”：错误。epoll 是 IO 多路复用，通常仍是同步读写
- “非阻塞 IO 一定更快”：不一定。编程复杂，仍要处理就绪和重试
- “零拷贝等于没有任何拷贝”：不准确。通常是减少用户态/内核态拷贝
- “select 已经完全不能用”：小规模 fd 场景仍可用
- “网络慢只靠 epoll 解决”：不够。协议、业务处理、拷贝、锁和 GC 都可能影响
