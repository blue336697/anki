## 一句话总结

这份 PDF 讲的是如何把 Agent 从“人在循环里手动喂提示”的保姆模式，升级为“人在循环外写控制程序”的 Loop 模式。Loop 的核心不是更会 prompt，而是写一个带停止条件、验证裁判、错误回灌、熔断机制和外部状态记忆的传统控制流程序。

## 核心命题

作者用一句话概括 Loop Engineering 的认知转变：

```text
我已经不直接 prompt Claude 了，我写 loop 让它去 prompt Claude。
```

这句话背后的重点是：AI Agent 的自主运行不靠一次提示词写得多漂亮，而靠外部系统把“何时继续、何时停止、何时回退、何时叫人、何时别再重复试错”这些工程判断控制住。

课程认为，AI 可以帮你写 loop 的骨架，但以下三件事替不了你做：

1. 什么算“完成”的停止条件。
2. 什么情况必须紧急刹车的熔断条件。
3. 如何记录历史尝试、避免每轮失忆的外部状态。

## Prompt 模式 vs Loop 模式

### Prompt / Context Engineering：人在循环内

这种方式像“保姆模式”：

- 人手动喂提示。
- 人看生成结果。
- 报错后人复制错误再喂给 Agent。
- Agent 的每一步都需要人陪着。

它的问题是：Agent 没有真正自主执行，人是流程控制器。

### Loop Engineering：人在循环外

Loop 模式则是：

- 人写一个自动循环系统。
- 系统调用 Agent。
- 系统运行验证。
- 验证失败时，把错误作为下一轮上下文回灌。
- 成功或卡住时才找人。

在这个模式里，人不再是每一步提示的操作者，而是控制程序、验证体系和安全边界的设计者。

## Loop 的真实结构

PDF 给出的 loop 本质是一个普通 `while` / `for` 控制流：

```python
context = 初始任务

for i in range(max_iterations):
    patch = call_agent(context)
    apply(patch)
    result = run_verification()

    if result.success:
        create_pr()
        return SUCCESS

    context = result.error_log

    if cost > budget:
        return ABORT

return FAILED_CALL_HUMAN
```

这个结构里有几个关键角色：

| 角色 | 作用 |
|---|---|
| `call_agent(context)` | 让 Agent 基于当前任务和历史失败生成修改 |
| `run_verification()` | 外部裁判，判断修改是否正确 |
| `result.error_log` | 失败信息，成为下一轮 prompt |
| `max_iterations` / `budget` | 熔断条件，防止无限循环和成本失控 |
| `FAILED_CALL_HUMAN` | 兜底升级，让人介入 |

真正重要的不是 loop 代码本身，而是：验证是否可靠、错误信息是否精炼、熔断是否及时、状态是否能避免重复试错。

## Loop 的三件灵魂工程判断

### 1. 停止条件

停止条件回答的是：

```text
什么是决定性的完成？
```

好的停止条件必须外部可验证，例如：

- 测试全部通过。
- 契约断言全部通过。
- 关键漏洞数为 0。
- 所有验收标准 pass。
- CI / eval 达到阈值。

坏的停止条件是：

- Agent 说“差不多了”。
- 看起来应该可以。
- 代码生成完了。

如果停止条件不可达，loop 会永远跑下去；如果停止条件太弱，loop 会自信地产出错误结果。

### 2. 熔断机制

熔断回答的是：

```text
什么情况必须强制刹车？
```

常见熔断条件包括：

- 最大轮数。
- 最大运行时间。
- token / API 成本预算。
- 连续多轮同类失败。
- 外部服务连续异常。
- 出现破坏性操作风险。

PDF 用“11 天烧几万美金”的事故说明：一个 loop 如果停止条件写错，又没有 token 熔断和人类监控，就会把预算烧穿，而且产出可能只是“语法完美、逻辑自洽、但偏离目标”的废话。

### 3. 外部记忆

外部记忆回答的是：

```text
loop 每轮失忆，如何避免重复犯同一个错？
```

课程建议用 `STATE.md` 记录每轮：

- 本轮尝试了什么。
- 为什么失败。
- 下轮不要重复哪些方向。
- 是否已经连续多次同类失败。

`STATE.md` 的价值不是为了好看，而是让下一轮 prompt 能带上历史经验，避免 Agent 反复换个说法做同样失败的尝试。

## 真实事故：状态机 3 连挂

PDF 用守护进程自升级举例：

任务看似简单：

```text
停进程 -> 换二进制 -> 重启
```

但 `launchd` 状态机有许多有意义的状态。Agent 连续 3 轮增量修症状都失败：

| 轮次 | 修法 | 失败原因 |
|---|---|---|
| 第 1 轮 | SIGTERM 优雅停止 | SSE 长连接拖住进程，无法退出 |
| 第 2 轮 | SIGKILL 强杀 | launchd KeepAlive 立刻重启旧二进制，与 rsync 抢文件 |
| 第 3 轮 | bootout 注销服务 | bootout 内部又发 SIGTERM，回到第一轮问题 |
| 第 4 轮 | 先画完整状态机再写代码 | 按状态依赖顺序执行，一次成功 |

根因不是代码能力不足，而是心智模型错误：Agent 每轮只修表层症状，没有理解完整系统状态。

这里引出一个很重要的规则：

```text
2-STRIKE 规则：同一类修复连续失败 2 次，说明心智模型错了。停止继续加代码，先理解系统或画状态机。
```

这个规则应该直接进入 loop 设计：连续同类失败不是继续重试的理由，而是熔断或回退到理解阶段的信号。

## 没有验证的 Loop 是垃圾生产机

手动模式下，即使验证不完美，人还可以靠肉眼兜底：

- 看代码不对劲。
- 手动检查边界。
- 手动决定是否合并。

Loop 模式下，人不在循环里，验证体系就成了唯一裁判：

- 验证说通过，loop 就可能提 PR。
- 验证漏掉问题，loop 会批量生产错误。
- 测试被同义反复糊弄，错误会被自动放大。

所以，上 loop 前必须问：

```text
我的验证体系敢不敢当无人值守的唯一判官？
```

如果不敢，应该先回去补验证体系，而不是先做自动 loop。

## Loop 的三级成熟度

PDF 把 Loop 成熟度分为三层：

| 级别 | 形态 | 基建要求 | 适合场景 |
|---|---|---|---|
| L1 本地 loop | 笔记本上跑，契约断言红了就让 Agent 修到绿 | 几乎无额外基建 | 培养 TDD + loop 习惯 |
| L2 CI loop | 草稿 PR 触发，CI 中 Agent 自动修复 | GitHub Actions / CI 等 | 把琐碎 bug 修复外包给系统 |
| L3 生产自愈 loop | 线上错误自动定位、修复、提 PR | 监控、沙箱、可观测、webhook | 系统级自动响应 |

课程建议从 L1 开始，不要一上来就做生产自愈。

对大多数团队来说，最合理的第一步是：

```text
本地 bugfix loop：一个明确 bug + 一个确定性验证脚本 + 有熔断的自动修复循环。
```

## Loop 的成本经济学

Loop 的成本不只来自调用 Agent：

1. Agent 改代码会消耗模型 token。
2. 验证如果调用真实外部服务，也会继续消耗 API 成本。

错题本示例中，验证如果每轮都真调 Bedrock，就会“两头烧钱”。

PDF 提出的省钱杠杆：

| 杠杆 | 做法 | 价值 |
---|---|---|
| 验证金字塔 | 每轮只跑确定性结构检查和 mock 契约断言 | 秒级、便宜、稳定 |
| 精炼失败信息 | 错误信息富而不冗 | 减少收敛轮数 |
| 外部记忆 | 记录试过什么失败 | 避免重复烧钱 |
| 熔断三件套 | 轮数、token、时间上限 | 防止失控 |
| 模型路由 | 小问题用小模型，难问题用大模型 | 控制成本 |

生产级 loop 不只是“能自动跑”，还要“跑得值”。

## Lab：本地 Worker Loop

PDF 的实验目标是跑通第一个 L1 Worker Loop：

```text
让 loop 自动修复错题本识别功能的一个 bug。
```

### 前置条件

- 已有 `ci/verify.sh`。
- 识别功能已有实现。
- Claude Code 可被脚本调用。
- 有一条故意打破的识别契约断言。

### Step 1：准备停止条件和 bug

先确认验证脚本是确定性的：

```bash
./ci/verify.sh
echo "exit=$?"
```

然后故意打破一条契约，例如删除：

```text
confidence < 0.7 时标记待确认
```

预期：`verify.sh` 应该失败。

### Step 2：写最小 loop 控制脚本

核心逻辑：

```bash
TASK="修复 src/ 识别 bug，使 verify 契约全过；不要改测试、不要改断言。"
CONTEXT="$TASK"

for i in $(seq 1 5); do
  claude -p "$CONTEXT" --dangerously-skip-permissions 2>/dev/null

  if OUT=$(./ci/verify.sh 2>&1); then
    echo "第 $i 轮收敛"
    exit 0
  else
    CONTEXT="$TASK\n上轮失败:\n$OUT"
  fi
done
```

这里的关键不是 Claude 命令，而是：

- 任务固定。
- 测试失败信息回灌。
- 明确不允许改测试和断言。
- 有最大轮数。

### Step 3：先装熔断

课程强调：先装刹车，再放手长跑。

建议最小熔断：

```bash
MAX_ITER=5
MAX_SECONDS=300
```

退出码区分停止原因：

| 退出码 | 含义 |
|---|---|
| 0 | 成功收敛 |
| 1 | 轮数熔断 |
| 2 | 时间熔断 |

修不好时主动停，不要无限跑。

### Step 4：加外部记忆 `STATE.md`

每轮失败后追加：

```md
## 第 i 轮

尝试：
- ...

结果：
- 失败原因摘要
```

下一轮 prompt 带上：

```text
历史尝试（不要重复这些已失败方向）：
<STATE.md 内容>

最近错误：
<verify 输出>
```

Done 标准：

- 每轮尝试与失败写入 `STATE.md`。
- 下一轮 prompt 包含历史。
- Agent 不重复已失败方向。
- `STATE.md` 可读、可复盘。

## 这份 PDF 对 AgentOS 的启发

如果把这份内容落实到 AgentOS，至少应形成以下机制：

### 1. `loop-config.md`

必须包含：

```md
## Stop Conditions
- 所有 AC pass
- G4/G5 验证通过
- eval score 达标

## Circuit Breakers
- max_iterations
- max_seconds
- max_tokens / max_cost
- same_failure_pattern >= 2
- destructive_action_detected

## Escalation
- 连续同类失败 2 次：停止写代码，回到 EVALUATE/PLAN
- 连续 gate 失败 3 次：叫人介入
```

### 2. `STATE.md`

Loop 必须记录：

- 当前任务。
- 当前阶段。
- 已尝试方案。
- 失败摘要。
- 不要重复的方向。
- 熔断原因。

### 3. `verify.sh` / Test Contract

Loop 只能基于可靠验证运行。每个可 loop 的任务必须有：

- 明确的 Test Contract。
- 可自动运行的验证入口。
- mock 或低成本验证优先。
- 未覆盖真实质量时禁止自动合并。

### 4. Loop 任务白名单

第一阶段适合：

- 小 bugfix。
- lint / type / test 修复。
- 契约断言修复。
- 文档格式修复。

不适合：

- 架构选型。
- 数据迁移。
- 配置转正。
- 生产自愈。
- 需要业务判断的需求。

### 5. 成本报告

每次 loop 结束要输出：

- 运行轮数。
- 总耗时。
- 触发了哪个停止条件。
- 是否触发熔断。
- 验证命令。
- 人是否需要介入。

## 可直接复用的检查清单

### 上 Loop 前

- [ ] 停止条件外部可验证。
- [ ] 验证脚本确定性强。
- [ ] 每轮验证成本可接受。
- [ ] 有最大轮数。
- [ ] 有时间上限。
- [ ] 有 token / API 成本预算。
- [ ] 有 `STATE.md` 记录历史。
- [ ] 连续同类失败会熔断。
- [ ] 成功后不会直接合并高风险代码。

### Loop 运行中

- [ ] 每轮只做一个明确方向的修复。
- [ ] 不允许改测试逃避验证。
- [ ] 失败信息精炼回灌。
- [ ] 历史失败方向进入上下文。
- [ ] 重复失败时停止继续试错。

### Loop 结束后

- [ ] 成功原因清楚。
- [ ] 失败原因清楚。
- [ ] 成本和轮数可接受。
- [ ] `STATE.md` 可复盘。
- [ ] 未验证的真实质量风险已记录。
- [ ] 是否适合升级到 CI loop 已评估。

## 我的理解

这份 PDF 的关键价值是把“Agent 自动化”从神秘感里拉回工程常识：Loop 不是魔法，而是一段控制程序。它的质量取决于停止条件、验证裁判、错误回灌、熔断和状态记忆。

真正危险的不是 Agent 不够聪明，而是我们给了它一个没有可靠裁判、没有刹车、没有记忆的自动循环。这样它会把小错误放大成自动化灾难。

所以，Loop Engineering 的成熟标志不是“能无人值守跑多久”，而是“知道什么时候停、为什么停、停在哪里、下一步该叫谁”。
