## 一句话总结

这份 PDF 讲的是如何把昨天“人看着 Engine 跑”的 L3 模式，升级为“Agent 自主跑、人偶尔检查”的 L4 模式。Loop Engineering 的核心不是放飞 Agent，而是给 Engine 加上停止条件、熔断机制、成本治理和升级策略。

## 从 L3 到 L4：给 Engine 装自动驾驶

Day 2 的模式是 L3：

- 你下发任务。
- Agent 按阶段走。
- 你看着过程。
- 你纠正偏差。
- 任务最终跑完。

问题是：你成了瓶颈。你不在，系统就跑不了。

Day 3 的目标是 L4：

- 你设定意图。
- Agent 自主跑。
- 你偶尔检查。
- 遇到关键问题时找你。

这要求 Engine 不仅有阶段和 Gate，还要知道：

- 什么时候停。
- 什么时候求助。
- 什么时候放弃。
- 什么时候熔断。
- 什么时候继续。

课程定义：

```text
Loop = 停止条件 + 熔断机制 + 成本治理 + 升级策略
```

## 停止条件：完成不是 Agent 说了算

如果让 Agent 自己判断“完成了吗”，它很容易说“差不多了”。

因此停止条件必须外部化、可验证。

| 类型 | 示例 | 可判定 |
|---|---|---|
| 目标达成 | 所有 AC pass，G4 通过 | 是 |
| 时间限制 | 运行超过 60 分钟 | 是 |
| 成本限制 | token 消耗超过 $5 | 是 |
| 循环限制 | 同一 Gate 失败超过 5 次 | 是 |
| 质量阈值 | eval score >= 80% | 是 |
| 主观感觉 | Agent 觉得差不多了 | 否 |

示例 `engine/loop-config.md`：

```markdown
## 停止条件（满足任一即停）
- goal: 所有 AC pass（G4）
- timeout: 60 min
- cost: $5 / 50K tokens
- max_retries: gate 失败 5 次
- eval_threshold: score >= 80%
```

哪个条件先触发，就停在哪。剩下的由人判断下一步怎么办。

## 熔断机制：异常时立即停下

课程用了一个很清楚的区分：

```text
停止条件 = 正常着陆
熔断机制 = 弹射座椅
```

需要熔断的情况包括：

| 情况 | 示例 |
|---|---|
| 无限循环 | 连续 3 次走同一路径无进展 |
| 成本爆炸 | token 速率 >10K tokens/min 持续 3 min |
| 破坏行为 | 试图删除大量文件、修改安全配置、危险命令 |
| 外部异常 | API 连续失败、网络断开、连续 5 次异常 |

熔断后的处理：

- 立即停止所有活动。
- 保存当前状态到 `STATE.md`。
- 输出诊断信息。
- 说明停在哪、为什么停。
- 等待人介入。
- 不自动恢复。

区别是：

| 类型 | 含义 | 后续 |
|---|---|---|
| 正常停止 | 目标达成或预算/时间上限触发 | 可以自动开始下一任务 |
| 熔断 | 异常中断 | 必须人来看 |

## 成本治理：自动跑也要跑得值

Loop 的隐性成本很高。

课件给出大致量级：

- 一个 feature 跑完约 50-200K tokens。
- 有重试可能 300K+。
- 10 个任务 batch 可能 500K-2M tokens。
- 一晚上无约束 loop 可能花 $100-300。

因此 L4 的关键不是“能不能自动跑”，还包括：

> 跑得值不值？

课程提出一个效率指标：

```text
tokens / AC
```

| 状态 | 指标 |
|---|---|
| 好效率 | 5-10K tokens 完成一个 AC |
| 差效率 | 30K+ tokens 还在循环 |

成本治理策略：

| 策略 | 做法 | 效果 |
|---|---|---|
| 预算帽 | 单任务 $5，批量 $20 | 硬限制 |
| 渐进放权 | 小任务先跑，成功后放大 | 降低风险 |
| 效率监控 | tokens / AC | 发现浪费 |
| 停损点 | 同一任务重试 3 次仍 fail 就停 | 避免沉没成本 |

成本意识是 Loop Engineering 的核心组成部分。

## loop-config.md 的四个区块

课程建议把所有 Loop 约束写在：

```text
engine/loop-config.md
```

它包含四个区块。

### 1. 停止条件

正常退出条件，例如：

- G4 通过。
- 单任务 60 分钟。
- 单任务 $5。
- Gate 最多失败 5 次。
- Eval score >= 80%。

### 2. 熔断条件

异常退出条件，例如：

- 连续 3 次相同 Gate 失败 pattern。
- token 速率异常。
- 危险删除或权限修改。
- API 连续 5 次异常。

### 3. 成本治理

预算和效率，例如：

- `budget_per_task: $5`
- `budget_per_session: $20`
- `efficiency_alert: >15K tokens/AC`
- 每个任务完成后输出成本报告。

### 4. 升级策略

什么时候找人，例如：

- 同一 Gate 连续 3 次失败。
- corrections 出现从未见过的新类别。
- PLAN 阶段产生 ADR。
- 涉及架构决策。

这说明 Loop 不是“什么都自己决定”。不可逆决策仍然要找人。

## 渐进放权：信任是赢得的

课程强调：

> 不要一步到 L4。

推荐路线：

| 时间 | 模式 | 做法 |
|---|---|---|
| Week 1 | 你看着跑，L3 | 观察 corrections 类型和频率 |
| Week 2 | G1/G3 -> L1，G2 保留 L2 | 部分无人值守，只在方案审查找你 |
| Week 3 | G2 降 L1，ADR 保留 L3 | 大部分无人值守，只在不可逆决策找你 |
| Week 4+ | 全 L1 + 异常升级 | 真正 loop，只在熔断或新错误类型找你 |

信任不是配置出来的，而是赢得的。

判断依据：

- corrections 频率下降 -> 信任上升 -> Gate 可降级。
- corrections 突然上升 -> 信任下降 -> Gate 要升级回来。

这个过程可能 1 个月，也可能 3 个月，取决于项目复杂度和 Agent 学习速度。

## 对 AgentOS 机制设计的启发

### 1. Loop 是 Engine 的增强层，不是替代层

Loop 不应该绕过 Engine。

正确关系是：

```text
Engine 定义阶段和 Gate
Loop 控制自动运行、停止、熔断、成本和升级
```

没有 Engine 的 Loop 只是无限 prompt。

### 2. 自动化必须先有停止条件

任何 `run unattended` 之前都应该先定义：

- 成功条件。
- 时间上限。
- 成本上限。
- 重试上限。
- 质量阈值。

否则 Agent 会把“继续尝试”当成默认动作。

### 3. 熔断是安全感来源

用户愿意让 Agent 自动跑，不是因为完全信任 Agent，而是因为知道它：

- 危险时会停。
- 卡住时会停。
- 太贵时会停。
- 不确定时会找人。

熔断机制是 L4 的前提。

### 4. 成本应该进入产物

每个任务完成后，AgentOS 应输出成本报告：

- tokens 总数。
- 估算成本。
- 每个 AC 的 token 消耗。
- Gate 重试次数。
- 哪个阶段最耗。

这能帮助团队判断哪些任务适合 loop，哪些不适合。

## 对 payment-agent 的落地建议

支付项目不应该一开始就 L4。

建议第一个 loop 任务选择：

- 单元测试补充。
- 小 bugfix。
- 文档同步。
- 非资金链路的代码清理。
- 可回滚、可验证的小修复。

不要放进 loop 的任务：

- 资金状态机改动。
- 数据迁移。
- 清结算逻辑。
- 幂等策略重构。
- 渠道协议重大变更。
- 权限、安全配置变更。

支付项目的熔断条件应更严格：

- 检测到批量删除立即停。
- 检测到 migration 修改立即升级人审。
- 检测到金额计算逻辑修改立即 L3。
- 检测到测试绕过或断言变弱立即停。
- 外部 API mock 不稳定时停止，而不是继续猜。

## 和前面内容的关系

前面模块提供：

- Knowledge：知道什么。
- Governance：约束什么。
- Engine：按什么流程做。
- Eval：行为是否符合标准。

Loop 在这些基础上增加：

- 自动运行。
- 正常停止。
- 异常熔断。
- 成本预算。
- 人类升级点。

它是从 L3 到 L4 的关键一步。

## 最终结论

这份 PDF 的核心结论是：

> Loop 不是放飞 Agent，而是有约束的自主。

一个成熟 Loop 至少需要：

```text
停止条件：什么时候正常停
熔断机制：什么时候紧急停
成本治理：跑得是否值得
升级策略：什么时候找人
渐进放权：信任用数据赢得
```

有停止条件才能开始，有熔断才能放心，有成本治理才能可持续。
