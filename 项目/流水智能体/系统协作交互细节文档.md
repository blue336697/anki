# 流水解析多系统协作交互细节文档

**版本**: v2.0
**日期**: 2026-05-09

---

## 一、概述

本文档详细描述银行流水解析与风控决策链路中五个核心系统的协作关系。

| 系统 | 语言 | 框架 | 职责 |
|------|------|------|------|
| **intelligent-flow-h5** | JavaScript | Vue 3 + Vite | H5前端：用户认证、账单提交、密码输入、交易指引 |
| **parrot** | Java 17 | Spring Boot 3.3.4 | 邮件网关：H5鉴权、邮箱分配、邮件接收、文件解密 |
| **magpie** | Java 17 | Spring Boot 3.3.4 | 调度引擎：解析编排、AI兜底、配置管理、报告生成 |
| **flowpdf-parse** | Python | FastAPI | 解析服务：PDF解析、OCR、模板匹配、字段提取 |
| **raptor** | Java 17 | Spring Boot 3.3.4 | 规则引擎：策略管理、规则执行、决策树、评分卡、决策输出 |

业务场景：客户在H5页面填写信息 → parrot H5鉴权 → parrot分配邮箱 → 客户银行APP导出流水发送到该邮箱 → parrot收取邮件并破解文件密码 → parrot调用magpie → magpie调用flowpdf-parse解析 → 解析失败时magpie调用百炼AI生成配置或兜底解析 → magpie生成风控报告(含指标计算) → raptor执行风控策略决策。

## 二、系统架构总览

```
贷款平台
    │ 内嵌H5 (iframe/webview)
    ▼
intelligent-flow-h5 (Vue 3 H5前端)
    │ Axios /api/parrot/* (Cookie会话)
    ▼
parrot (邮件网关)
    │ Feign / IrSecureClient (RSA签名+加密)
    ▼
magpie (流水分析引擎)
    │ OpenFeign multipart/form-data             │ Feign
    ▼                                           ▼
flowpdf-parse (PDF解析服务)              raptor (规则引擎)
    │ HTTP                                    │ Feign
    ▼                                         ▼
OCR引擎 (cybertron-parser-api)       peregrine (API网关)
    │
百炼AI (阿里云DashScope)
```

**交互关系**:
- **intelligent-flow-h5** → **parrot**: 所有API请求经 `/api/parrot/*`，Axios + Cookie会话
- **parrot** → **magpie**: RSA签名+加密的 Feign 调用
- **magpie** → **flowpdf-parse**: OpenFeign multipart/form-data 文件上传
- **magpie** → **百炼AI**: HTTPS直接调用阿里云 DashScope
- **magpie** → **raptor**: 报告生成后调用 raptor 执行风控策略决策
- **raptor** → **nest-app**: 文件/用户服务
- **raptor** → **peregrine-app**: API网关/策略打包
- **raptor 内部**: raptor-webapi(管理后台) → raptor-core(引擎执行) → raptor-openapi(对外暴露策略执行)

## 四、parrot — 邮件网关

### 4.1 H5认证流程

```
POST /api/parrot/public/h5-auth
  参数: tenant, authData(AES加密的name/mobile/idCard/callbackUrl/orderNo),
        sign(SHA256), clientType

1. 通过NestFeign解析tenant短码 → 获取租户AES密钥/IV/签名密钥
2. SHA256(authData_raw + clientType + signSecret) 验证签名
3. AES-128-CBC解密authData → 用户信息
4. 创建/查找用户, 标记为已实名认证
5. 生成JWT令牌(RSA签名), 设置accessToken Cookie
6. 保存H5认证订单(t_parrot_h5_auth_order)
7. 异步回调贷款平台callbackUrl
```

加密参数: AES-128-CBC, PKCS5Padding; 密钥/IV每租户可配置; 签名SHA256六角小写。

### 4.2 邮箱分配与邮件收取

**邮箱分配**: 从 `t_parrot_mail_pool` 池中CAS原子更新分配(bind_status=0 → bind_status=1)。邮箱通过MailCow API创建(`@wuyou-cha.com`, 6位随机本地部分, 15位随机密码, 1000MiB配额)。

**邮件收取**: 连接IMAPS(`ls.wuyou-cha.com:993`, 信任所有SSL证书) → 获取最近10封未读邮件 → 提取发件人域名匹配银行白名单(或mailPass绕过) → 提取附件(智能检测Content-Disposition/Content-Type, 过滤text/html等) → 上传原始文件到Nest → 尝试无密码解压 → 创建ParrotMailFile记录 → 标记邮件为SEEN。

微信特殊处理: 从HTML正文提取下载链接 → HTTP下载文件。

### 4.3 文件解密

```
POST /api/parrot/operator/submit-extract-code
  参数: extractCodeList=["密码1","密码2"], pdfDataType="BANK"

FileDecompressUtil.processFile(file, outputDir, password):
  ├─ .zip → zip4j (AES加密支持)
  ├─ .pdf → PDFBox (密码验证)
  ├─ .xlsx/.xls → Apache POI (密码验证)
  └─ .docx/.doc → Apache POI (密码验证)
```

### 4.4 调用magpie

```
POST /api/parrot/operator/generate-record
  → 下载所有已解密文件
  → MagpieService.generateFlowReport():
      ├─ 获取租户RSA密钥对(Redis缓存7天)
      ├─ DefaultIrSecureClientV2 (RSA签名+加密)
      ├─ BankStatementBatchAsyncRequest { files, name, idCard, mobile, sourceType:"H5", mailInfoList, nestLoginName }
      └─ irSecureClient.certificateExecute() → transSerialCode
  → 创建ParrotFlowRecord, 更新ParrotMailFile, H5自动绑定
```

## 五、magpie — 流水分析引擎

### 5.1 解析编排流程

```
BankFlowParseService.parseFile()
  ├─ 文件哈希去重: 相同文件已成功解析 → 直接复用
  ├─ processFilesModeV2() → POST /api/pdf/smart-parse-pdf (file + fileCode)
  │
  ├─ code==0 → 解析成功
  │   ├─ 提取metadata (documentType, account_info, time_range等)
  │   ├─ 提取data (columns + rows 或 detailVOList)
  │   ├─ mergeDuplicateRowsV2() 合并重复行
  │   └─ 构建ParseResult
  │
  └─ code!=0 && message包含"版式暂不支持" → 进入百炼兜底
      │
      ├─ 策略A: "边学边试" (FILE.PARSE.THEN.STUDY.ASYNC.ENABLED=true)
      │   ├─ PDF前2页 → OCR提取 → 百炼生成4层配置 → 持久化到DB
      │   ├─ Redis通知 sys:parser-config:changed
      │   ├─ Sleep 60秒 (等待flowpdf-parse加载新配置)
      │   └─ 重新调用 processFilesModeV2()
      │
      └─ 策略B: "全AI兜底" (FILE_PARSE_BAILIAN_FALLBACK_ENABLE=true)
          ├─ PDF前N页 → 上传OSS → 百炼全量解析
          ├─ parseModel=3 (AI_PARSE)
          └─ 返回BankFlowParseResponse
```

## 六、flowpdf-parse — PDF解析服务

### 6.1 核心端点

| 端点 | 用途 | 调用方 |
|------|------|--------|
| `/api/pdf/smart-parse-pdf` | **主解析端点**(智能检测+银行识别+解析) | magpie |
| `/api/pdf/parse-with-header` | 代码解析(已知parser_type) | 内部 |
| `/api/pdf/ocr-parse-pdf` | OCR解析(已知parser_type) | 内部 |
| `/api/pdf/ocr-raw` | 原始OCR结果 | magpie(百炼学习) |
| `/api/pdf/ocr-page-parse-json` | 逐页OCR结构JSON | magpie |
| `/api/pdf/check-native` | 检测PDF是否原生文本 | magpie |

### 6.2 智能解析主流程

```
POST /api/pdf/smart-parse-pdf (file + fileCode)
  ├─ 1. 检测PDF类型 (check_native_pdf2)
  │     ├─ 原生PDF: 有可提取文本字符 → pdfplumber处理
  │     └─ 扫描PDF: 图片为主 → OCR引擎处理
  ├─ 2. 银行识别 (identify_bank2)
  │     ├─ 加载bankIdentify配置(按priority排序)
  │     ├─ 逐条评估matchText表达式: ${keyword} → ('keyword' in text), eval()执行
  │     └─ 匹配成功→(parser_type, version), 失败→DefaultParser
  ├─ 3. 按页拆分PDF (Redis pageSize配置)
  ├─ 4. 并发调用解析端点(ThreadPoolExecutor)
  ├─ 5. 合并所有分片结果
  └─ 6. 推送进度到magpie
```

### 6.3 解析器体系

**BaseParser** (抽象基类):
- 抽象方法: `parser_type`, `extract_metadata`, `normalize_metadata`
- 模板方法: `parse_with_header` → extract_metadata + _extract_tables + _clean_table_data

**解析器类型**:
- 个人银行解析器 (parsers/, 40+银行): ICBCParser(1309行,最复杂的水印去除), CMBParserV2(单词坐标列分配), 等
- 对公银行解析器 (publicparses/, 6银行): PublicCEBParser(边界绘制+表格提取), PublicBOCParserV2(管道分隔,无OCR), 等
- Smart解析器: CCBSmartParser(V2优先→V1回退), BOCOMSmartParser(表格检测→版本选择→全试回退), 等
- DefaultParser: 查找"交易时间"/"交易日期"关键词

**ParserRegistry** (单例): `_parsers: {parser_type: parser_instance}`, `_parsers_by_base_type: {base_type: {version: parser}}`, 版本回退(v2不存在→v1), 别名映射。

### 6.4 响应格式

成功: `{ data: { columns: [...], rows: [[...]], parseModel: 1/2/3, metadata: {...} }, code: 0 }`
失败: `{ data: null, code: 10001, message: "抱歉，版式暂不支持", traceId: "..." }`

parseModel: 1=代码解析, 2=OCR解析, 3=AI解析(百炼兜底)。

### 6.5 并发模型与资源控制

#### 6.5.1 部署架构

生产/预发布环境部署在 **K8s 集群** 中，每个 Pod 内使用 **uvicorn** 多 worker 模式。

```python
# app.py
uvicorn.run("app:app", host=host, port=port, workers=8, ...)
```

| 环境 | workers | 含义 |
|------|---------|------|
| dev | 1 | 单进程开发 |
| pre/prod/op | 8 | 每个 Pod 内 8 个独立 OS 进程 |

所有 Pod 注册在同一个 **K8s Service** 名下（如 `flowpdf-parse`），Service 提供 TCP 层负载均衡（默认 iptables 随机模式）。

**跨节点分发机制**: 一个请求到达某 Pod 的某个 worker 后，该 worker 将 PDF 切分为子文件，然后通过 K8s Service 名发起 HTTP 调用。K8s 的 kube-proxy 将这些 HTTP 请求**随机负载均衡到集群中任意 Pod**，从而实现跨节点的任务分发。分发粒度是子文件级，非请求级。

#### 6.5.2 单 Worker 内三级线程池

每个 uvicorn worker 进程内部有 **3 个 ThreadPoolExecutor**：

```python
# app.py:169-177
METADATA_WORKERS = max(4, MAX_WORKERS // 4)   # 32//4 = 8
metadata_thread_pool = ThreadPoolManager(max_workers=8)   # 轻量: 银行识别/元数据/native检测
parse_thread_pool    = ThreadPoolManager(max_workers=32)  # 重量: CPU密集解析
```

第三个池在 `SmartPDFParseService` 内部：

```python
# smart_pdf_parse_service.py:75-77
self.request_executor = ThreadPoolExecutor(
    max_workers=flowpdf_max_workers  # prod=30, dev/pre=10
)
```

| 线程池 | 大小(prod) | 用途 |
|--------|-----------|------|
| `metadata_thread_pool` | 8 | 银行识别、元数据提取、native PDF 检测 |
| `parse_thread_pool` | 32 | 直接解析端点 (`/api/pdf/parse-with-header`, `/api/pdf/ocr-parse-pdf`) |
| `request_executor` | 30 | smart-parse 内部自调 HTTP 的阻塞请求池 |

**理论最大并发**: 8 workers × (32 + 8 + 30) = **560 个线程同时运行**。

#### 6.5.3 任务分发机制（自调用模式）

**没有任务队列、没有消息队列、没有背压**。请求即响应模型：

```
HTTP 请求到达
  → FastAPI async handler (asyncio event loop)
    → loop.run_in_executor(thread_pool) 把阻塞工作丢给线程池
    → 请求结束，线程释放
```

但真正的"分发"在 `smart_parse_pdf()` 中通过 **K8s Service 负载均衡** 实现：

```
smart_pdf_parse_service.py:458-500

1. 拿到 PDF
   → _split_pdf_by_pages() 用 PyMuPDF(fitz) 按 pagesPerFile 切成 N 个子 PDF

2. 对每个子文件构造 HTTP POST:
   → 扫描件: POST http://flowpdf-parse/api/pdf/ocr-parse-pdf
   → 原生PDF: POST http://flowpdf-parse/api/pdf/parse-with-header

3. 通过 asyncio.as_completed() + loop.run_in_executor(request_executor)
   并发发出所有 HTTP 调用（同步 requests.post, timeout=300s, 最多3次重试）

4. K8s kube-proxy 将每个 HTTP 请求随机路由到集群中某个 Pod 的某个 worker
   → 各 Pod 各自在线程池中处理子文件
   → 原本到达 Pod A 的请求，子任务可能被 Pod B/C/D 共同处理

5. 发起方等所有子文件返回 → 合并 rows → 返回给 magpie
```

**关键**: `flowpdf_base_url` 指向 K8s Service 名而非 localhost。K8s 的 iptables/IPVS 规则将每个 TCP 连接随机映射到后端 Pod IP，天然实现了跨节点负载均衡。一个 400 页 PDF 的 50 个子文件请求会被打散到集群中所有可用 Pod 上并行处理。

#### 6.5.4 PDF 切分规则

```python
# smart_pdf_parse_service.py:271-311
def _split_pdf_by_pages(self, file_id, source_path, pages_per_file=8):
    total_pages = source_document.page_count
    split_count = (total_pages + pages_per_file - 1) // pages_per_file

    for index, start_page in enumerate(range(0, total_pages, pages_per_file)):
        split_doc.insert_pdf(source_document, from_page=start_page,
                             to_page=min(start_page + pages_per_file - 1, total_pages - 1))
        # 标记: 1片="head", 2片="head"/"tail", 3+片="head"/"body..."/"tail"
        filename = f"{file_id}_{tag}_{index}.pdf"
```

`pages_per_file` 来自 Redis 动态配置:
- 原生 PDF: `parsePageSize`
- 扫描件 PDF: `ocrPageSize`

**无硬编码上限**，只取决于 Redis 中的配置值。

#### 6.5.5 资源防护现状

| 防护手段 | 状态 | 说明 |
|----------|------|------|
| 文件大小上限 | **有** | `max_file_size = 200MB`，在流式读取时校验 |
| 页数上限 | **无** | 完全依赖 Redis 动态配置，无硬限制 |
| 并发子文件 HTTP 调用上限 | **无** | 400页/8=50 个并发请求直接发出，经 K8s Service 分发到各 Pod |
| Semaphore / 令牌桶 | **无** | 代码库中无任何限流机制 |
| 请求队列 | **无** | `ThreadPoolExecutor` 使用**无界队列**，任务无限堆积 |
| 超时控制 | **部分有** | self-call: 300s; OCR引擎: connect_timeout=30s, read_timeout=240s |

#### 6.5.6 风险场景

假设集群有 3 个 Pod，`ocrPageSize=8`，进来一个 400 页扫描件 PDF：

```
发起 Pod (Pod A):
  切分为 50 个子 PDF
    → 50 个 HTTP 请求发往 K8s Service flowpdf-parse
    → kube-proxy 随机分发: Pod A ≈16个, Pod B ≈17个, Pod C ≈17个
    → 每个 Pod 各自在线程池中处理
    → 每个子请求内部再调 OCR 引擎 (外部 HTTP, 最长 240s)

发起方 Pod A:
  → 50 个 request_executor 线程全部阻塞等待 HTTP 响应 (最长 300s)
  → 这些线程不能处理其他请求
  → 如果同时有多个大 PDF 到达 Pod A，request_executor 耗尽 → 后续请求排队
```

**风险点**：

| 风险 | 说明 |
|------|------|
| 发起方 request_executor 耗尽 | 一个 400 页请求占用 50 个线程等待响应，池大小仅 30(prod)，超出部分进入无界队列排队 |
| 集群级资源竞争 | 如果多个大 PDF 同时到达，子请求可能路由到同一个 Pod → 某 Pod 的 parse_thread_pool(32) 被打满 |
| 无界队列堆积 | `ThreadPoolExecutor` 默认无界工作队列，任务只进不出 → 内存持续增长 → OOM |
| 无背压机制 | 没有 Semaphore 限制同时处理的子文件数，上游 magpie 也无流控 |

**当前仅有的隐性保护**: uvicorn 自身请求超时 + OS TCP backlog + K8s Service 分发稀释 + `max_file_size=200MB`。没有显式的并发控制或降级策略。

## 七、raptor — 规则引擎

### 7.1 概述

raptor 是风控决策规则引擎，负责策略管理、规则执行和决策输出。采用多模块 Maven 工程，部署为三个独立的 Spring Boot 微服务。

| 模块 | 端口 | 职责 |
|------|------|------|
| **raptor-webapi** (raptor-app) | 8088 | 管理后台API：策略/规则/变量/决策树/评分卡/决策流的CRUD、发布管理、PMML模型管理 |
| **raptor-core** (core-app) | 9034 | 引擎核心：知识库构建、LiteFlow规则链执行、缓存管理、测试运行 |
| **raptor-openapi** (raptor-interface) | 9035 | 对外API：暴露策略执行端点供外部系统调用 |

**技术栈**: Java 17, Spring Boot 3.3.4, Spring Cloud 2023.0.3 (OpenFeign), MyBatis-Plus 3.5.7, LiteFlow 2.12.4 (规则链执行), RocketMQ 2.3.1 (缓存失效广播), Caffeine + Redis (多级缓存), PMML Evaluator 1.6.7 (机器学习模型评分), Jython 2.7.4 + GraalVM.js (脚本节点), Redisson 3.22.0 (分布式锁)。

### 7.2 核心概念

| 概念 | 说明 |
|------|------|
| **策略 (Strategy)** | 顶层业务单元, 包含输入/输出变量、关联的规则/决策流、版本发布 |
| **规则 (Rule)** | 决策的基本单元, 有多种类型: 规则集(set)、决策表(table)、交叉表(crosstab)、决策树(tree)、评分卡(scorecard)、复杂评分卡(complexscorecard)、HTTP调用(http)、函数规则(funRule)、代码块(code) |

### 7.5 多级缓存架构

## 八、四层配置系统 — 参数详解与代码验证

> 本章基于 `README_OCR_CONFIG解析规则配置必读.md` 与 `parser_refactoring_plan.md` 两份文档，反向对照实际代码（`ocr_config.py`、`ocr_config_registry.py`、`bank_identification_service.py`、`ocr_result_parser.py`）逐一验证每个配置参数的实际行为。

### 8.1 配置架构

```
Layer 1: 环境配置 (config/{dev,prod,pre}.json) — host, port, redis, mysql, ocr_service
    ↓
```

**配置来源优先级**（`ocr_config_registry.py:146-155`）：已通过 `register()` 在代码中注册的 parser_type，不会被数据库中同名配置覆盖。未在代码中注册的 parser_type 才走数据库加载。

### 8.2 配置类型一：bankIdentify — 银行识别

#### 8.2.1 参数定义

| 参数 | 类型 | 说明 |
|------|------|------|
| `parserType` | string | 解析器类型标识, 如 "icbc", "ccb" |
| `priority` | number | 优先级(数值越小越优先匹配), 默认9999 |
| `version` | string | 配置版本, 如 "v1" |
| `matchText` | string | 匹配表达式, `${keyword}` 语法 |
| `matchModel` | string | 匹配模式: "parse"(代码解析) / "ocr"(OCR解析) |
| `codeAnalyse` | string | 代码分析辅助, 如 "hasTable"(检测PDF是否含表格) |

#### 8.2.2 代码验证

**matchText 求值核心** (`bank_identification_service.py:461-470`):

```python
def matchBank(self, text: str, match_text: str) -> bool:
    expr = match_text
    keywords = re.findall(r'\${(.*?)}', match_text)
    for kw in keywords:
        expr = expr.replace(f'${{{kw}}}', f"('{kw}' in text)")
    try:
        return bool(eval(expr))
    except Exception as exc:
        logger.warning(f"matchBank表达式解析失败: {exc}")
        return False
```

关键行为：
- `${keyword}` → `('keyword' in text)` 字面替换，即对 PDF 全文做 `in` 检查
- `&&` / `||` 作为 Python 布尔操作符正常工作
- 最终 `eval()` 执行，matchText 来自数据库，需确保配置的完整性

**匹配流程** (`identify_bank2`, 行247-321):
1. 从 `LocalConfigCacheService` 获取所有缓存配置（key 格式: `{parserType}_bankIdentify_config_{version}`）
2. 按 `priority` 升序排序（priority 越小越先匹配）
3. 逐条执行 `matchBank()`，第一个匹配成功即返回 `{parser_type, version, matchModel}`
4. 如果配置项包含 `codeAnalyse` 字段（如 `"hasTable"`），还需额外通过 `codeAnalyseMatch()` 检测（用 pdfplumber 检查 PDF 是否包含表格），不通过则跳过

**配置 key 解析** (`_parse_bank_version`, 行254-256):
- 从缓存 key `"{bank}_bankIdentify_config_{version}"` 中分割出 bank 和 version

**实际 DB 配置示例**（icbc）:
```json
{"parserType": "icbc", "priority": 9, "version": "v1",
 "matchText": "${中国工商银行} && (${借记账户历史明细} || ${银行流水}) && ${交易日期}",
 "matchModel": "parse"}
```

### 8.3 配置类型二：clean — 字段清洗

#### 8.3.1 header_rules — 表头映射规则

**参数定义**（`HeaderRule` 类, `ocr_config.py:84-140`）：

| 参数 | 类型 | 说明 |
|------|------|------|
| `source_field` | string | 源字段名(OCR识别出的原始列名) |
| `target_field` | string | 目标字段名(标准列名) |
| `extract_method` | `"direct"` / `"keyword"` / `"regex"` | 匹配方式 |
| `extract_rule` | string | 匹配规则: direct 用于 contains 匹配; keyword 用于 in 检查; regex 用于正则 |

**extract_method 匹配逻辑**（`HeaderRule.match()`, 行142-164）:
- `DIRECT`: `cell_text == self.source_field or self.source_field in cell_text` — 精确匹配或包含匹配
- `KEYWORD`: `self.extract_rule in cell_text` — 查找 extract_rule 是否在单元格文本中

**代码验证细节**: DIRECT 模式既支持精确匹配也支持包含匹配。例如当 OCR 识别出 "账户余额(元)" 时，`source_field="账户余额"` 仍能匹配。这是文档未明确说明的实现细节。

**combine_fields 使用示例**（ABC 农业银行）:
```json
{"field_name": "交易时间", "clean_type": "combine_fields_normalize_date",
 "combine_with": "交易日期", "separator": " "}
```
将 OCR 分开识别的"交易日期"和"交易时间"合并后统一格式化。

#### 8.3.3 page_rule — 页面规则

**参数定义**（`PageRule` 类, `ocr_config.py:832-919`）：

| 参数 | 类型 | 说明 |
|------|------|------|
| `header_row_type` | `"first_row"` / `"first_row_by_col_count"` / `"by_keyword"` / `"first_row_second_table"` | 表头行识别方式 |
| `multi_page_header` | `"no"` / `"yes"` | 多页是否复用第一页表头 |
| `keyword` | string | 单个关键字（by_keyword 模式） |
| `keywords` | string[] | 关键字列表（by_keyword 模式，需全部匹配） |

**4种 header_row_type 代码验证** (`find_header_row()`, 行868-919):

| 类型 | 代码行为 |
|------|----------|
| `first_row` | `return 0` — 直接返回第0行作为表头 |
| `first_row_by_col_count` | 遍历所有行，返回列数最多的那一行索引 |
| `by_keyword` | `keywords` 不为空时需全部匹配；否则用单个 `keyword`。每行文本 = `" ".join(row)`, `all(kw in row_text for kw in keywords)` |
| `first_row_second_table` | 不在 PageRule 层处理，而是在 `ocr_result_parser.py:_extract_table_data()` 中特殊处理：每2个 table 为1页，table_index%2==0 为元数据表格，table_index%2==1 为数据表格（首行=表头） |

**first_row_second_table 模式详解**（`ocr_result_parser.py:445-495`）:
- 该模式专为邮储银行等"第一个表格是元数据、第二个表格才是数据"的版式设计
- 使用全局计数器 `global_table_counter`，不对页面分组
- 第0个表格 → 元数据表格（`is_metadata_table=True`），其内容作为文本拼入元数据提取范围
- 第1个表格 → 数据表格（`is_data_table=True`），第一行直接作为表头（`header_row_idx=0`）

**multi_page_header 行为**:
- `"yes"`: 第一页表头缓存到 Redis (`cache_header_row()`)，后续页从 Redis 读取 (`fetch_header_row()`)
- `"no"`: 每页独立识别表头
- 多文件场景：`is_first_file=False` 时从 Redis 读取第一文件缓存的表头，读不到则使用 header_rules 的 target_field 顺序作为列顺序

#### 8.3.4 amount_fields — 金额字段过滤

**代码验证** (`ocr_result_parser.py:852-865`):
```python
if self.ocr_config.amount_fields:
    all_amount_fields_empty = True
    for amount_field in self.ocr_config.amount_fields:
        amount_value = row_data.get(amount_field, "")
        if amount_value and str(amount_value).strip():
            all_amount_fields_empty = False
            break
    if all_amount_fields_empty:
        continue  # 跳过该行
```
如果配置了 `amount_fields` 列表，当一行中所有金额字段均为空时，该行被过滤。这是用于过滤汇总行/小计行的机制。

### 8.4 配置类型三：metadata — 元数据提取

#### 8.4.1 extract_rules — 提取规则列表

**参数定义**（`MetadataRule` 类, `ocr_config.py:377-493`）：

| 参数 | 类型 | 说明 |
|------|------|------|
| `target_field` | string | 提取后的目标字段名, 如 "标题", "卡号", "户名" |
| `extract_method` | `"regex"` / `"keyword"` / `"direct"` | 提取方式 |
| `extract_rule` | string | 提取规则 (regex pattern / keyword / fixed value) |
| `format_method` | `"none"` / `"date_format"` / `"date_time_format"` / `"remove_prefix"` / `"remove_suffix"` | 格式化方式 |
| `format_param` | string | 格式化参数（如 remove_prefix 的前缀字符串） |
| `default_value` | string | 提取失败时的默认值 |

**extract_method 代码验证** (`extract()`, 行412-458):

| extract_method | 代码行为 |
|----------------|----------|
| `REGEX` | `re.search(extract_rule, text)` → 多捕获组: `f"{group(1)} 至 {group(2)}"`；单捕获组: `group(1)`；无捕获组: `group(0)` |
| `KEYWORD` | `extract_rule in text` → 存在则返回 `default_value` 或 `extract_rule` 本身 |
| `DIRECT` | 直接返回 `extract_rule` 或 `default_value`，不检查文本内容 |

**format_method 代码验证** (`_format_value()`, 行460-493):

| format_method | 代码行为 |
|---------------|----------|
| `date_format` | 仅处理8位数字: `f"{value[:4]}-{value[4:6]}-{value[6:8]}"`，非8位数字原样返回 |
| `date_time_format` | 当前直接 `return value`（未实现额外格式化） |
| `remove_prefix` | `value.startswith(format_param)` 则移除前缀 |
| `remove_suffix` | `value.endswith(format_param)` 则移除后缀 |
| `none` | `value.strip()` |

**can_identify 轻量识别** (`OCRConfig.can_identify()`, 行1053-1087): 只检查"标题"字段的 metadata_rule，不执行完整提取。这是 OCR 配置注册表中快速匹配配置的方法。REGEX 方法检查 `re.search()`, KEYWORD/DIRECT 方法检查 `extract_rule in text`。

#### 8.4.2 normalize_rule — 标准化规则

**参数定义**（`MetadataNormalizeRule` 类, `ocr_config.py:656-809`）：

| 参数 | 类型 | 说明 |
|------|------|------|
| `field_mappings` | `{原始字段: 标准路径}` | 如 `{"卡号": "account_info.account_id"}`，路径用 `.` 分隔 |
| `fixed_values` | `{标准路径: 固定值}` | 如 `{"currency.currency_code": "CNY"}` |
| `time_range_config` | object | 时间范围配置 |
| `extra_fields` | string[] | 额外信息字段列表，放入 `extra` 对象 |

**time_range_config 子参数**:

| 子参数 | 说明 |
|--------|------|
| `start_date_field` | 原始起始日期字段名 |
| `end_date_field` | 原始结束日期字段名 |
| `date_format` | 输入日期格式（为空则走自动检测：YYYYMMDD→加连字符, YYYY/MM/DD→替换斜杠） |
| `start_time_suffix` | 开始时间后缀，默认 `" 00:00:00"` |
| `end_time_suffix` | 结束时间后缀，默认 `" 23:59:59"` |

**代码验证**: `_set_nested_value()` (行755-770) 将点号路径 `"account_info.account_id"` 转换为嵌套字典 `{"account_info": {"account_id": value}}`。

#### 8.4.3 post_process_rule — 后处理规则

**参数定义**（`MetadataPostProcessRule` 类, `ocr_config.py:496-653`）：

**(a) field_combinations — 字段组合**:
```json
{
  "target_field": "交易时间段",
  "source_fields": ["开始时间", "结束时间"],
  "format": "{start_time} 至 {end_time}",
  "condition": "if_missing"
}
```
当 `target_field` 缺失时才用 `source_fields` 拼出 `format` 字符串。`format` 使用 Python `str.format()`。

**(b) field_conversions — 字段转换**:
```json
{
  "target_field": "起始日期",
  "source_field": "原始文本字段",
  "regex": "起止日期[：:\\s]+(\\d{4})年(\\d{1,2})月(\\d{1,2})日",
  "format": "{year}-{month}-{day}",
  "condition": "if_missing"
}
```
用 `regex` 从 `source_field`（或原始全文）中提取，然后 `format` 格式化。特殊处理: `{year}`, `{month}`, `{day}` 占位符自动从正则捕获组映射（3组=一组日期，6组=起始+结束各一组，分别取对应捕获组）。

### 8.5 配置类型四：merge — 数据合并/列映射

merge 配置用于将 OCR 解析后的数据 columns 映射为最终返回的标准列名，支持：
- `column_mapping`: 字段名映射表
- `amount_split`: 金额正负拆分规则
- `date_format`: 日期格式化

> merge 配置在 `parser_refactoring_plan.md` 中有设计但当前实际代码中主要通过 `ocr_result_parser.py` 中的 `header_rules` 的 target_field 映射实现类似功能，独立的 merge 配置消费逻辑在 `services/` 中未找到独立实现文件。

### 8.6 配置同步机制

```
magpie BailianParserConfigPersistService
  → 遍历4种 configType (bankIdentify/clean/metadata/merge)
  → INSERT INTO t_parser_config (isActive=1)
  → HSET sys:parser-config:changed "{parserType}#{version}" "enable#{timestamp}"

flowpdf-parse OCRConfigRegistry (每60秒 daemon 线程)
  → _refresh_cache()
  → load_from_database()
    ├─ 清空缓存中的 DB 配置（保留代码注册的配置）
    ├─ 查询 t_parser_config WHERE is_active=1
    ├─ 按 parser_type 分组 (只处理 clean + metadata)
    └─ _build_ocr_config_from_db() 构建 OCRConfig 对象 → 放入缓存
```

**版本管理** (`BailianParserConfigPersistService.resolveNextVersion()`):
- 无历史版本 → `"v1"`
- 最新 active 版本 → `"v{N+1}"`
- 最新 disabled 版本 → `null` (跳过,不创建新版本)

### 9.1 集成点

百炼集成在 **magpie** 侧, flowpdf-parse 不直接调用AI。

**两个百炼应用**:
| AppId | 用途 |
|-------|------|
| `227ed050b52b4b9faa734af8eada7853` | OCR配置生成Agent (从OCR JSON生成4层配置) |

### 9.2 配置生成流程 (核心链路)

```
版式不支持触发
  → PDF前2页 → OCR (flowpdf-parse /api/pdf/ocr-raw)
  → OCR JSON → 百炼 callBaiLianAI (timeout=300s)
  → 百炼返回 output.text (JSON, 含markdown代码块)
  → BailianParserConfigPersistService.persistFromBailianOutput():
      1. parseRootJson(): 去除 ```json...``` 标记
      2. 提取 data.bankIdentify → parserType, configName
      3. resolveNextVersion(): 无历史→"v1", 最新active→"v{N+1}", 最新disabled→null(跳过)
      4. 遍历4种configType, 各INSERT一条 t_parser_config (isActive=1)
      5. bankIdentify行额外写入templateFileId
      6. setRedisChangeKey(): HSET sys:parser-config:changed "{parserType}#{version}" "enable#{timestamp}"
  → 等待60秒
  → 重试 smart-parse-pdf
```

### 9.3 百炼输出JSON结构

百炼被要求输出含data节点的JSON, 包含4个section: bankIdentify, clean, metadata, merge。每个section对应一个configType。

### 9.4 成功率分析

当前百炼生成4层配置成功率约**60%**。

| 失败原因 | 估计占比 |
|----------|---------|
| 百炼输出格式不符合预期(JSON结构错误、缺字段) | 25% |
| OCR质量差(扫描件模糊→识别错误→百炼基于错误文本) | 20% |
| 复杂表格结构(多行表头、合并单元格、不规则列) | 15% |
| 元数据提取失败(账号等不在前2页) | 15% |
| 配置版本冲突(同银行已停用→resolveNextVersion返回null) | 10% |
| 其他(超时、网络异常等) | 15% |

## 十、错误处理与降级链

```
flowpdf-parse解析失败
  → 银行识别失败 → DefaultParser → ParserError
  → HTTP 200, code=10001, message="抱歉，版式暂不支持"

magpie接收到失败响应
  → code==0: 成功
  → code!=0 && "版式暂不支持":
      → ThenStudy开关开 → 百炼学习 → 等60秒 → 重试
      → Fallback开关开 → 百炼全PDF兜底(parseModel=3)
      → 均关闭 → ServiceException
  → 其他错误 → ServiceException(CHECK_FILE_OR_UPLOAD_AGAIN)
```

**关键Feature Flags**:
- `FILE.PARSE.THEN.STUDY.ASYNC.ENABLED` — 百炼学习模式开关
- `FILE_PARSE_BAILIAN_FALLBACK_ENABLE` — 全AI兜底开关
- `FILE_PARSE_BAILIAN_FALLBACK_PAGE_STEP` — 百炼兜底最大页数(默认2)

## 十五、核心疑问解答

### 15.1 四层配置为什么能让 PDF 解析出明细？

**关键前提**：OCR 引擎已经把 PDF 变成了结构化 JSON（`page_parse_json`）。四层配置不"理解"PDF 内容，而是告诉代码如何对这个 JSON 做规则驱动的映射和清洗。

整个链路分为五步：

**Step 0 — OCR 产出**：PDF → OCR → `page_parse_json`（交替包含 `{"type": "text", ...}` 文本块和 `{"type": "table", "table_body": "<table>...</table>"}` 表格块）。

**Step 1 — 定位表头行**（`page_rule.header_row_type`）：

| 模式 | 代码行为 | 适用场景 |
|------|----------|----------|
| `first_row` | `return 0`，表格第0行即表头 | 工行等表头固定在第一行的版式 |
| `first_row_by_col_count` | 遍历所有行，返回列数最多的行 | 表格上方有摘要行的情况 |
| `by_keyword` | `all(kw in " ".join(row) for kw in keywords)`，全部关键字匹配才认定 | 建行（需同时含"序号""摘要""交易日期"） |
| `first_row_second_table` | 每2个table为一页，第0个=元数据表格，第1个=数据表格(首行即表头) | 邮储银行等元数据+数据双表格版式 |

**Step 2 — 表头映射**（`header_rules`）：OCR 识别的原始列名五花八门（"交易日期"/"Date"/"起息日"/"债入/支出金额"），通过 `direct`/`keyword`/`regex` 匹配规则统一映射为标准列名。同一个标准列名可以有多个原始列名（如 ICBC 的"收入/支出金额"和"债入/支出金额"都映射到同一个 target_field）。

```python
# ocr_config.py:981-1013
for cell in header_row:           # 遍历表头行每个单元格
    for rule in self.header_rules:
        if rule.match(cell_text):  # direct/keyword/regex 匹配
            mapped_header.append(rule.target_field)  # 标准名
```

**Step 3 — 逐行取值+清洗**：这是纯位置对应的，不需要任何"理解"。

```python
# ocr_result_parser.py:820-845
for row in data_rows:                           # 遍历数据行
    row_context = {}
    for col_idx in range(len(mapped_header)):   # 第i列
        field_name = mapped_header[col_idx]     # 标准字段名
        cell_value = row[col_idx]              # 该行第i列的原始值
        row_context[field_name] = cell_value

    for field_name, cell_value in row_context.items():
        cleaned = self.ocr_config.clean_field_value(
            cell_value, field_name, row_context  # 按字段名查FieldRule → 执行清洗
        )
```

所以核心逻辑就是：**拿到标准列名数组 → 数据行的第 i 个单元格就是第 i 个列的值 → 按该列的清洗规则处理**。

**Step 4 — 元数据提取**（`metadata_rules`）：所有非表格文本块拼接成一段全文 → 逐条正则/关键字/直接提取 → 标准化（`normalize_rule` 的点号路径映射 + `post_process_rule` 的字段组合/转换）。

**Step 5 — 合并结果**：所有分片的 metadata（只取第一片）+ data（拼接所有分片）→ 返回给 magpie。

### 15.2 OCR 结果的用途

OCR 结果在系统中只有三种用途：

| 用途 | 触发场景 | 涉及数据量 |
|------|----------|-----------|
| 银行识别（`bankIdentify`） | 扫描件 PDF 需要确定 parser_type | **仅首页** OCR，然后 eval matchText |
| 解析明细（`clean`/`metadata`） | 扫描件 PDF 的实际解析 | 全部页面，按 ocrPageSize 分批 |
| AI 生成配置的入参 | 版式不支持时触发百炼学习 | **仅前2页** OCR，作为 prompt 传给百炼 |

除此之外，OCR 结果不会被用于其他任何用途。原生 PDF（文字类）完全不经过 OCR。

### 15.3 原生 PDF vs 扫描件 PDF

系统在入口处通过 `check_native_pdf2()` 做分叉判断：

```
check_native_pdf2()
  ├─ 原生PDF（有可提取文本字符）
  │   → pdfplumber 直接提取文本/表格
  │   → 传统 Parser（ICBCParser、CMBParserV2 等）硬编码解析
  │   → 0 次 OCR 调用
  │
  └─ 扫描PDF（图片为主）
      → OCR 引擎
      → OCRConfig 四层配置解析
      → 1（银行识别首页）+ ceil(总页数/ocrPageSize) 次 OCR 调用
```

两条路径互斥，不会混用。四层配置只在扫描件路径上生效。

### 15.4 400 页 PDF 的 OCR 开销

假设 `ocrPageSize=8`（Redis 配置 `Nest:RdConfig:magpie:file.ocr.modelName` 中读取）：

| 步骤 | OCR 调用次数 | 说明 |
|------|-------------|------|
| 银行识别 | 1 次 | 仅首页 → 创建临时单页 PDF → OCR → matchBank |
| 分片解析 | ceil(400/8) = 50 次 | PDF 按 8 页/片拆分 → 50 个分片并发调 OCR |
| **合计** | **51 次** | 并发执行（ThreadPoolExecutor），非串行 |

`_split_pdf_by_pages` 用 PyMuPDF 按页切分为独立物理文件，命名规则：`head_1.pdf` / `body_2.pdf` ... `body_{n-1}.pdf` / `tail_n.pdf`。每个分片调用 `/api/pdf/ocr-parse-pdf`，返回各自的结构化 JSON，最后合并（metadata 取第一片，data 拼接所有片）。

**为什么每页都要 OCR**：扫描件 PDF 本质是图片集合，pdfplumber 无法从图片中提取文字。OCR 成本由扫描件本身决定，四层配置只是替代了原来每个银行写一个 Parser 类的硬编码方式，不改变 OCR 调用量。

### 15.5 代码解析报错是否触发 AI 回退？

**结论**：会。不只是"解析器未注册"会触发，代码解析器存在但执行过程中抛异常同样触发。

关键在两层异常处理：

**第一层** — `pdf_parse_service.py:355-362`：
```python
except ParserError:
    # 清理临时文件后重新抛出
    raise  # ← 往上抛到 FastAPI
```

**第二层** — `app.py:277-288`（全局异常处理器）：
```python
@app.exception_handler(ParserError)
async def parser_error_handler(request, exc: ParserError):
    return JSONResponse(content={
        "code": 10001,
        "message": "抱歉，版式暂不支持",  # 所有 ParserError 子类统一返回
    })
```

异常继承链（`parsers/exceptions.py`）：
```
ParserError (基类)
  ├─ ParserNotFoundError      → 解析器未注册
  ├─ ParseFailedError         → 解析执行失败
  ├─ MetadataExtractionError  → 元数据提取失败
  └─ InvalidPDFFormatError    → PDF格式无效
```

四种异常**全部**被全局处理器捕获，全部返回 `code=10001, "抱歉，版式暂不支持"`。magpie 只检查 `code!=0 && message包含"版式暂不支持"`（`BankFlowParseService.java:900-909`），不区分具体原因。

| 异常类型 | 返回 | magpie行为 |
|---------|------|-----------|
| `ParserNotFoundError` / `ParseFailedError` / `ParserError` | code=10001 | → AI fallback |
| 非 `ParserError`（如网络超时、OOM） | code=500 | → 直接返回错误 |

> **注意**：`parse_with_header` 端点中第319-330行直接返回 code=10001 的情况（parser 不在 registry）是不抛异常的，而是直接构造响应返回。这会跳过全局异常处理器，但 magpie 看到相同的 code/message，行为一致。

### 15.6 AI 生成 OCR 配置后可能与代码解析形成循环

**背景**：银行识别缓存（`local_config_cache`）只从 DB 加载（`t_parser_config` WHERE `config_type='bankIdentify'`），与 `ParserRegistry`（代码注册的解析器）是两套独立体系。

```
local_config_cache（仅DB来源）
  ├─ icbc_bankIdentify_config_v1 → {matchText: "...", matchModel: "parse", priority: 9}
  └─ icbc_bankIdentify_config_v2 → {matchText: "...", matchModel: "ocr", priority: 5}  ← AI生成
```

**路由决策**在 `bank_identification_service.py:274-320`：
- 所有缓存项按 `priority` 升序排列（数值越小优先级越高）
- 遍历匹配 `matchText`，第一个匹配成功的返回
- `matchModel`（默认 `"parse"`）决定走代码解析还是 OCR（`smart_pdf_parse_service.py:432`）

**循环场景**：

```
第1次请求:
  identify_bank2() → 遍历缓存
    → icbc_v1 (priority=9, matchModel="parse") 先匹配 → 代码解析
    → 代码解析失败 → ParserError → code=10001
    → magpie AI回退 → 生成配置 → 落库 icbc_v2 (matchModel="ocr", priority=?)

60s后重试（local_config_cache已增量刷新）:
  identify_bank2() → 遍历缓存:
    ├─ icbc_v1 (priority=9, matchModel="parse")
    └─ icbc_v2 (priority=?, matchModel=?）

  情况A ✓: AI设 priority=5, matchModel="ocr"
    → v2先匹配 → OCR路径 → 成功

  情况B ✗: AI设 priority=10, matchModel 缺失或为"parse"
    → v1先匹配 → 代码解析 → 再次失败
    → 再次触发AI生成 v3 → priority 不变 → 无限循环
```

**为什么可能死循环**：

1. AI 生成的 priority 和 matchModel **完全取决于百炼 prompt 输出**，代码没有强制覆盖（`BailianParserConfigPersistService.java:103-132` 直接将 AI 输出的 JSON 写入 `config_content`）
2. `resolveNextVersion()` 只检查最新版本是否 `is_active=0`（断路器），不检查 priority 是否合理
3. 代码注册配置优先级固定（`bank_identification_service.py:54-71`，如 icbc=9），AI 生成的 priority 如果数值更大就会被排在后面

**当前防护措施**：

| 措施 | 位置 | 局限性 |
|------|------|--------|
| `resolveNextVersion` 断路器 | `BailianParserConfigPersistService.java:234` | 仅在最新版 is_active=0 时触发，首次不生效 |
| 百炼 prompt 工程 | 百炼智能体配置（非代码） | 无法保证 AI 一定输出正确的 matchModel 和 priority |
| 人工监控 | 运维 | 需手动禁用 is_active=0 来打断循环 |

**本质原因**：代码解析和 OCR 解析共用同一套银行识别缓存体系，但 priority 和 matchModel 的来源不同（代码硬编码 vs AI 生成），缺乏统一的优先级协调机制。
