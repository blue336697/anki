### 1.3 流水标注（cate4 / cate5 / cate6）

后端先把每条流水打上 3 个标签（特征标注引擎），下游所有指标都依赖这些标签：

## 二、各章节指标计算说明

### 2.1 核心速览（`core_overview`，M001-M020 + M091）

| 指标 | 名称 | 类型 | 大白话计算逻辑 |
|---|---|---|---|
| M091 | 流水文件概览 | JSON 结构 | 把所有上传的流水文件按起始时间排好，每个文件记下"平台 / 银行 / 文件名 / 起止日 / 月数"，再算出整体最早开始日、最晚结束日和最大月数，全部打包成 JSON |
| M001 | 分析主体数 | 数值 | 数一下流水里出现了多少个不同的"自己人"账户主体名称（最少返回 1） |
| M002 | 分析账户数 | 数值 | 按"主体+账号"去重计数（一个流水文件对应一个银行账户） |
| M003 | 数据时长（月） | 数值 | 把所有流水的"年-月"提出来去重，看一共覆盖了多少个不同的自然月 |
| M004 | 日均余额（项目级） | 数值 | 每个账户内对所有"余额>0"的记录求平均，再把所有账户的均值再平均一次 |
| M005 | 借贷流入合计 | 数值 | 把 `cate4`='贷款流入' 或 '借款流入' 的所有收入金额绝对值加起来 |
| M006 | 偿还借贷合计 | 数值 | 把 `cate4`='偿还贷款' 或 '偿还借款' 的所有支出金额绝对值加起来 |
| M007 | 有效流入 | 数值 | 全部收入相加，但要排除掉"内部转账 / 贷款流入 / 借款流入 / 活期利息"这 4 类（这些不算真正的经营性入账） |
| M008 | 有效流出 | 数值 | 全部支出相加（取绝对值），但要排除掉"内部转账 / 偿还贷款 / 偿还借款"这 3 类 |
| M009 | 核心有效流入方 TOP5 | JSON 结构 | 在"有效流入"口径下按对手方名字汇总金额，从大到小排序取前 5 名 |
| M010 | 核心有效流出方 TOP5 | JSON 结构 | 在"有效流出"口径下按对手方名字汇总金额，从大到小排序取前 5 名 |
| M011 | 决策建议结论 | 文本【AI】 | Coze `decision_summary` 综合全报告产出 `{rating, comprehensiveScore, ratingReason}`，rating ∈ 🔴拒绝 / 🟡关注 / 🟢准入 |
| M012 | 风险信号结论 | 文本【AI】 | Coze `decision_summary` 输出 4 类风险信号 `{redLines（高风险）, yellowLines（中风险）, lowRiskHints（低风险）, normalItems（正常项）}`，每条带 `title + source` 章节代码 |
| M013 | 建议核实清单 | 文本【AI】 | Coze `decision_summary` 输出 8-12 条核实事项 `[{seq, item, suggestedMaterials}]`，按风险优先级排序 |
| M014 | 综合数据质量评级 | 文本 | 每条记录看是否同时具备"余额>0、对手方非空、交易时间非空"三要素，命中几项给几分（满分 3）；每个账户取其内部最高分，再对所有账户求平均：≥2.5 良好、≥1.5 一般、否则较低 |
| M015 | 余额不连续/缺失账户数 | 数值 | 按账户分组，账户内有余额的记录按时间排序，只要发现相邻两条之间的天数差 > 7 天，就把这个账户计 1 次 |
| M016 | 命中数据质量风险账户数 | 数值 | 按账户分组，账户内"质量评分 ≤ 2"（一般或较低）的记录数超过该账户记录总数一半时，算 1 个风险账户 |
| M017 | 关联方数 | 数值 | 在 `cate6` 里命中"法人关联 / 投资关联 / 共同股东关联"任意一种的对手方，去重计数 |
| M018 | 需关注对手方数 | 数值 | 在 `cate6` 里命中"业务重叠 / 大额利息 / 个人大额 / 新公司 / 高风险 / 异常 / 涉诉"任意一种的对手方，去重计数 |
| M019 | 疑似关联方数 | 数值 | 在 `cate6` 里命中"疑似关联方"标签的对手方，去重计数（专业版规则） |
| M020 | 个人敏感支出笔数 | 数值 | 所有支出记录里，命中"敏感场所关键词"（KTV/会所/娱乐/彩票等），或者交易时间在 22:00-06:00 且金额 ≥ 5 万的笔数 |

### 2.2 数据验证（`data_validation`，M021-M030）

| 指标 | 名称 | 类型 | 大白话计算逻辑 |
|---|---|---|---|
| M021 | 余额不连续处数（账户级） | 数值 | 按账户分组并按时间排序，相邻两条算"前一条余额 ± 当前金额"（收入加、支出减）= 理论余额，与实际余额差超过 0.01 元就计 1 处，所有账户累加 |
| M022 | 数据时间范围 | 文本 | 取整段流水的最早交易日和最晚交易日，拼成 "yyyy-MM-dd ~ yyyy-MM-dd" |
| M023 | 数据时长（账户级） | 数值 | 用最早日到最晚日的总天数 ÷ 30 再四舍五入，最少 1 个月 |
| M024 | 数据来源 | 文本 | 从每个文件的 `pdfDataType` 取对应来源描述，去重后用"、"拼起来；没有文件就返回"本地上传" |
| M025 | 活期结息校验 - 缺失次数 | 数值+文本 | 按总天数折算应有几个完整年（四舍五入），每年应有 4 次季度结息；实际命中"活期利息"标签的记录数即"实际次数"；缺失=应有-实际，文本输出"实际/应有" |
| M026 | 活期结息校验 - 差异较大 | 文本 | 用账户简单均余额 × 0.35%（活期年利率）÷ 365 × 90 = 理论单季利息；每条实际结息与理论值偏差超过 50% 计入"差异笔数"，输出"差异笔数/总结息笔数" |
| M027 | 文件属性校验 | 数值+JSON | 遍历每个文件，发现"勾稽校验未通过"或"解析报错"就记一条异常（"文件名：原因"），最终给出异常项数 + 异常清单 JSON |
| M028 | 数据质量评级 | 文本 | 看余额不连续处数(M021)/活期结息校验-缺失次数(M025)/活期结息校验-差异较大(M026)/文件属性校验(M027)这 4 类各自是否命中（命中=该类计数>0），累计命中项数：≥3 较低、1-2 一般、0 良好 |
| M029 | 数据质量详情 | 文本 | 把余额不连续处数(M021)/活期结息校验-缺失次数(M025)/活期结息校验-差异较大(M026)/文件属性校验(M027)中命中的异常用一段话拼出来（如"余额不连续 X 处；活期结息缺失 Y 次；文件属性异常 Z 项：…"），全无命中输出"无异常" |
| M030 | 未提交账户识别 | 明细列表 | 当前规则下无法可靠检测，固定返回空数组 `[]` |

### 2.3 余额分析（`balance_analysis`，M031-M038）

> **基础概念**：先按账户构造"每日 EOD（End-of-Day）余额表"——当日有交易就取该日最后一笔的 `balance` 作为 EOD，无交易日沿用前一日的 EOD。下面所有指标都基于这个表。

| 指标 | 名称 | 类型 | 大白话计算逻辑 |
|---|---|---|---|
| M031 | 账户日均余额 | 数值+JSON | 每个账户：分析期内每日 EOD 求和 ÷ 天数 = 该账户日均；项目级 = 把所有账户日均再求平均；同时输出"账户→日均余额"的明细 JSON |
| M032 | 账户月日均余额 | JSON 结构 | 把每个账户的每日 EOD 按"年-月"分桶，每月内所有日 EOD 求平均，输出"账户×月份"矩阵 JSON |
| M033 | 月日均余额均值（账户级） | 数值 | 把账户月日均余额(M032)输出里所有"账户-月份"格子的月日均收集起来求一次算术平均 |
| M034 | 账户期末余额 | 数值+JSON | 每个账户取最后一条有交易时间的记录的 `balance` 作为期末余额；项目级 = 各账户期末余额的算术平均；同时输出明细 JSON |
| M035 | 账户月末余额 | JSON 结构 | 每个账户每个月内取最后一条交易记录的 `balance` 作为该月月末余额，输出"账户×月份"矩阵 JSON |
| M036 | 账户月末余额均值 | 数值 | 把账户月末余额(M035)里所有"账户-月份"格子的月末余额收集起来求一次算术平均 |
| M037 | 项目期末余额 | 数值 | 把所有账户的账户期末余额(M034)直接相加 |
| M038 | 项目月末余额均值 | 数值 | 先对每个月份把"各账户当月月末余额"相加得到该月项目级合计；再对所有月份的合计求算术平均 |

### 2.4 借贷分析（`lending_analysis`，M039-M048）

| 指标 | 名称 | 类型 | 大白话计算逻辑 |
|---|---|---|---|
| M039 | 借贷流入月度 | JSON 结构 | 筛 `cate4`='贷款流入' 或 '借款流入' 的收入流水，按交易月份累加金额，逐月输出 `{month, value}` 序列 |
| M040 | 偿还贷款月度 | JSON 结构 | 筛 `cate4`='偿还贷款' 的支出流水，按月把金额绝对值累加，逐月输出 |
| M041 | 借贷净额月度 | JSON 结构 | 每个月：当月借贷流入合计 − 当月偿还贷款合计，得到逐月净增序列 |
| M042 | 借贷规模净增 | 数值 | 整个分析期 Σ借贷流入（贷款+借款） − Σ偿还借贷（贷款+借款） |
| M043 | 月均偿贷占经营性流入比 | 数值 | 偿还借贷合计 ÷ 经营收入合计 × 100，月数会被约掉，得到百分比 |
| M044 | 借贷方家数（按类型） | JSON 结构 | 把所有借贷类流水按对手方类型 `cate5`（本方/银行/非银/民间等）分组，每组内统计去重对手方数量 |
| M045 | 借贷方明细 | 明细列表 | 按对手方名称聚合：累加它的借贷流入、偿还借贷金额，算净额（流入−偿还），打上 `cate5` 类型标签，按总金额降序排列 |
| M046 | 偿还贷款类流水聚合明细 | 文本【AI】 | 把每个偿债对手方的特征（名称、类型、首末扣款日、固定扣款日 `regularDay`、扣款月数、月均、累计、变异系数 `cv`）丢给 Coze `debt_analysis`；大模型据 `regularDay` 有规律 + `cv<0.3` 判"中长期刚性月供(高)"，否则判"不规律偿债(低)"，并给出置信度，输出 `debtAnalysis` 列表 |
| M047 | 借贷流入端明细 | 文本【AI】 | 把每个借贷流入对手方（名称、初始类型、笔数、累计金额、首末日期）丢给 Coze `debt_analysis`；大模型据规则给定性判断——自然人大额→疑似体外融资/实控人输血；含"小贷"或非银→高息融资渠道；银行授信→需核实合同，输出 `lendingAnalysis` 列表 |
| M048 | 借贷结论 | 文本【AI】 | Coze `debt_analysis` 综合两端结果生成多行文本结论（✓正面发现 + ⚠风险信号，如总体偿债压力、是否存在同业融资租赁在租等） |

### 2.5 收支分析（`income_expense`，M049-M054）

| 指标 | 名称 | 类型 | 大白话计算逻辑 |
|---|---|---|---|
| M049 | 账户月度流入 | JSON 结构 | 把每条流水按"账户 × 交易月份"分组，每个账户每个月的全部流入金额累加，逐月输出 |
| M050 | 账户流入合计与均值 | JSON 结构 | 每个账户：把各月流入相加得 `sum`；统计 `sum>0` 的月份数得 `activeMonths`；`avg = sum / activeMonths`（只按"活跃月"取均值，不被零月稀释） |
| M051 | 账户月度流出 | JSON 结构 | 同账户月度流入(M049)思路，每个账户每个月支出金额绝对值合计 |
| M052 | 账户流出合计与均值 | JSON 结构 | 每个账户的流出 `sum`、活跃月数、`avg = sum / activeMonths` |
| M053 | 项目月度流入流出净额 | JSON 结构 | 跨所有账户按月汇总：每月 `inflow` = 各账户当月流入之和，`outflow` 同理，`net = inflow − outflow` |
| M054 | 项目月均流入流出净额 | JSON 结构 | 全部账户总流入 ÷ 分析期总月份数 = `avgMonthlyInflow`，流出同理；`avgMonthlyNet = avgMonthlyInflow − avgMonthlyOutflow`（除数用总月数，不是活跃月数） |

### 2.7 指标性收支（`indicator_income_expense`，M064-M069）

> **现金流还原公式链（月度现金流还原明细(M068) 核心）**：
>
> A 月均经营收入 → B 月均经营支出 → C = A − B 月均经营净流入 → D 月均偿债 → **E = C − D 月均可支配自由现金流** → F 月租金（外部输入） → **G = E / F 租金保障倍数**

| 指标 | 名称 | 类型 | 大白话计算逻辑 |
|---|---|---|---|
| M064 | 水电能源支出 | JSON 结构 | 筛 `cate4`='水电能源' 的支出，按月累加；输出 `total`（累计）、`monthlyAvg`（按活跃月取均值）、逐月明细 |
| M065 | 租金支出 | JSON 结构 | 筛 `cate4`='租金支出' 的支出，按月累加；输出 `total / monthlyAvg / 逐月` |
| M066 | 人力成本 | JSON 结构 | 筛 `cate4`='人力成本' 的支出，按月累加；输出 `total / monthlyAvg / 逐月` |
| M067 | 纳税支出 | JSON 结构 | 筛 `cate4`='纳税支出' 的支出，按月累加；输出 `total / monthlyAvg / 逐月` |
| M068 | 月度现金流还原明细 | JSON 结构 | 按"账户 × 月份"逐月还原：①经营收入 = 当月所有经营性流入；②经营支出 = 当月"经营支出+纳税+人力+水电+租金"五类合计；③经营净流入 = ①−②；④偿债 = 当月"偿还贷款+偿还借款"合计；**⑤可支配自由现金流 = ③−④**。同时输出 `tax/labor/utilities/rent` 四个单项金额。F（月租金）和 G（保障倍数）在下游 Coze 处计算，本指标只产出 A→E 的逐月还原矩阵 |
| M069 | 现金流还原结论 | 文本【AI】 | 把水电能源支出(M064) ~ 月度现金流还原明细(M068)的数据（月度经营收入/支出/净流入三条序列、年化净流入、月均可支配自由现金流、变异系数 `cv`、收入趋势、月度偿债序列）打包送 Coze `cash_flow_conclusion`；大模型据规则评出 `cashFlowRating`（优秀/良好/一般/关注/高风险）、`cashFlowTrend`、3-5 条 `keyFindings`、2-4 条 `riskFactors`、逐月 `monthlyAnalysis`（正常/偏弱/亏损/大额流入/大额流出）、`overallAssessment` 综合文本和 `confidence` 置信度 |

### 2.8 对手方分析（`counterparty_analysis`，M070-M075）

> **共用前置**：先按对手方名称聚合两套字典——
> - `inflowMap`：剔除"内部转账/贷款流入/借款流入/活期利息"4 类后的所有收入聚合
> - `outflowMap`：剔除"内部转账/偿还贷款/偿还借款"3 类后的所有支出聚合
>
> 各自取金额前 10 名作为 TOP10 流入/流出对手方。

| 指标 | 名称 | 类型 | 大白话计算逻辑 |
|---|---|---|---|
| M070 | 前 10 大流入方（含月度） | JSON 结构 | 在 `inflowMap` 取金额前 10 名，每名输出 `{rank, name, totalIncome, ratio（占合计比）, count（笔数）, monthly[{month, amount}]}` |
| M071 | 对方流入构成 | JSON 结构 | 对 TOP10 流入方各自再按 `cate4` 拆解，输出 `{对手方: {cate4: 占比, ...}}`，看每个大客户的钱是哪种性质（经营 vs 投资 vs 内部 等） |
| M072 | 对方类型标注 | JSON 结构 | 对 TOP10 流入方各自统计 `cate5`（取出现次数最多的作为该对手方主类型）+ 收集全部 `cate6` 标签去重，输出 `{rank, name, cate5, cate6[]}` |
| M073 | 前 10 大流出方（含月度） | JSON 结构 | 在 `outflowMap` 取金额前 10 名，每名输出 `{rank, name, totalExpense, ratio, count, monthly[{month, amount}]}` |
| M074 | 对方流出构成 | JSON 结构 | 对 TOP10 流出方各自再按 `cate4` 拆解，输出 `{对手方: {cate4: 占比, ...}}` |
| M075 | 前 10 大流入流出重合方 | JSON 结构 | 找同时出现在流入和流出的对手方，每个算出 `overlapAmount = min(inflow, outflow)`、`overlapRatio = overlap / max(inflow, outflow)`；按 `overlapAmount` 降序取前 10——值越高说明该对手方"既给你打钱也收你钱"，可能是循环交易/票据 |

### 2.9 关联方交易（`related_party_transaction`，M076-M085）

> **关联方识别口径**：流水的 `cate6` 含 "法人关联 / 投资关联 / 共同股东关联 / 疑似关联方" 中任一标签即视为关联方。
>
> **三类细分**：
> - 类别 1（类别1关联方明细(M082)）法人/股东/主要人员/总公司
> - 类别 2（类别2关联方明细(M083)）对外投资/分支机构
> - 类别 3（类别3关联方明细(M084)）相同法人/股东企业

| 指标 | 名称 | 类型 | 大白话计算逻辑 |
|---|---|---|---|
| M076 | 关联方家数 | 数值 | 按对手方名称去重计数所有命中关联方标签的对手方 |
| M077 | 关联方合计流入 | 数值 | 关联方对手方的所有收入金额绝对值合计 |
| M078 | 关联方合计流出 | 数值 | 关联方对手方的所有支出金额绝对值合计 |
| M079 | 关联方流入占总流入比（%） | 数值 | 关联方合计流入(M077) ÷ 全部收入合计 × 100 |
| M080 | 关联方流出占总流出比（%） | 数值 | 关联方合计流出(M078) ÷ 全部支出合计 × 100 |
| M081 | 关联方进入 TOP10 流入方数 | 数值 | 内部按前10大流入方(M070)同口径再算一遍 TOP10 流入方，统计这 10 名里有多少是关联方 |
| M082 | 类别 1 关联方明细 | 文本【AI】 | 筛 `cate6`='法人关联' 的对手方聚合 `{name, inflow, outflow, diff, net, count}`，外加两个占位字段 `qualitative` 和 `riskLevel`——前两个由后端算，后两个由 Coze `related_party_analysis` 模式回填（red/yellow/green 风险等级 + 一句话定性判断） |
| M083 | 类别 2 关联方明细 | 文本【AI】 | 同类别1关联方明细(M082)，但筛 `cate6`='投资关联'；`qualitative/riskLevel` 同样由 Coze 填 |
| M084 | 类别 3 关联方明细 | 文本【AI】 | 同类别1关联方明细(M082)，但筛 `cate6`='共同股东关联'；`qualitative/riskLevel` 同样由 Coze 填 |
| M085 | 整体结论 | 文本【AI】 | 完全由 Coze `related_party_analysis` 生成的 `overallConclusion`：综合所有关联方的双向流水，给出企业是否依赖关联方资金输血、撤出风险等多行文本判断 |

## 三、标签打标规则（cate4 / cate5 / cate6）

> **打标顺序**：每条流水先打 `cate4`（按 18 条优先级规则），再打 `cate5`（对手方类型），最后打 `cate6`（关联方关系 + 需关注族）。这三层标签是后续 90 个指标计算的基础。
>
> **代码位置**：`tech.magpie.app.service.bankflowv2.corp.label.CorpFlowLabelRules`
>
> **关键词字典**：`tech.magpie.app.constants.CorpMetricKeywordRegistry`

### 3.1 四级标签 cate4 — 18 条优先级规则（按 1→18 顺序"首次命中即停止"）

执行模型：每条流水从规则 1 开始往下试，**只要命中一条就立刻定型**，后续规则不再判断。这意味着 18 条规则之间存在隐含的语义优先级——专项类（利息/税/人力/水电/租金）优先于筹资类（贷款/借款），筹资类优先于经营类（兜底），最末是"其他"兜底。

| 优先级 | cate4 标签值 | 方向 | 对手方约束 | 摘要/交易类型关键词（命中任一即可） | 金额约束 | 备注 |
|---|---|---|---|---|---|---|
| 1 | 活期利息 | 流入 | 空 或 本方 | `结息 / 利息 / 利息结算 / 活期结息 / 收息` | 一般 < 10 万 | 数据校验类 |
| 2 | 投资收益 | 流入 | 含 `证券 / 基金 / 理财 / 信托 / 资管` | `理财收益 / 分红 / 赎回` | — | 投资性 |
| 3 | 纳税支出 | 流出 | 含 `国家金库 / 税务局 / 税务` | `扣税 / 税款 / 缴税` | — | 经营-专项 |
| 4 | 人力成本 | 流出 | 空 / 本方 / 对方含 `社保` | `工资 / 代发工资 / 薪资 / 社保 / 公积金` | — | 经营-专项 |
| 5 | 水电能源 | 流出 | 含 `电力 / 燃气 / 自来水 / 供水 / 能源` | `电费 / 水费 / 燃气费` | — | 经营-专项 |
| 6 | 租金支出 | 流出 | 含 `物业 / 地产` | `租金 / 房租 / 场地费` | — | 经营-专项 |
| 7 | 贷款流入 | 流入 | 银行 或 持牌非银 | `放款 / 贷款发放` | 通常整百万/千万 | 筹资性 |
| 8 | 偿还贷款 | 流出 | 银行 或 持牌非银 | `还本 / 还息 / 支付贷款` | — | 筹资性 |
| 9 | 借款流入 | 流入 | 非本方 + 非银行/非银 | `借款 / 往来 / 往来款 / 资金往来` | **≥ 50 万** | 筹资性 |
| 10 | 偿还借款 | 流出 | 非银行/非银 | `还款 / 归还借款` | — | 筹资性 |
| 11 | 内部转账 | 双向 | 本方主体清单 **或** 命中关键词 | `同名账户 / 内部转账 / 同名划转 / 本行转账` | — | 跨账户互转 |
| 12 | 经营收入 | 流入 | 企业 + 非银行/非银 + 非本方 + 非需关注 | — | — | **对公转入兜底** |
| 13 | 经营支出 | 流出 | 企业 + 非银行/非银 + 非本方 + 非需关注 | — | — | **对公转出兜底** |
| 14 | 需关注流入 | 流入 | 命中需关注对手方清单 | — | — | 依赖 L4 风险层回写 |
| 15 | 需关注流出 | 流出 | 命中需关注对手方清单 | — | — | 依赖 L4 风险层回写 |
| 16 | 退款流出 | 流出 | （理论上是历史本方流入方） | `退款 / 退回 / 返还 / 退费 / 退汇` | — | 当前仅按关键词匹配 |
| 17 | 个人流入 | 流入 | 非企业（自然人） | `报销 / 个人转账 / 退款` 且**不**含 `借款/往来/往来款/资金往来` | **< 50 万** | 其他 |
| 18 | 其他流入/流出 | 双向 | — | — | — | **最终兜底**：未命中以上任一规则 |

**核心判定方法（4 个共用助手）：**

| 方法 | 判定逻辑 |
|---|---|
| **企业对手方** `isEnterpriseCounterparty` | 对手方名称包含 `公司 / 有限 / 股份 / 集团` 任一字 |
| **银行对手方** `isBankByName` | 对手方名称包含 `银行 / 支行 / 营业部 / 信用社` 任一字 |
| **持牌非银** `isNBFIByName` | 对手方名称包含 `小额贷款 / 融资租赁 / 消费金融 / 信托 / 保理 / 汽车金融 / 财务公司` 任一字 |
| **本方对手方** `isSelf` | 对手方名称包含本项目主体清单中任一主体名（用于"内部转账 / 人力成本 / 活期利息"判定） |

**执行顺序产生的关键效应：**
- 金额 ≥ 50 万的"借款流入"在规则 9 命中后，就**不会**再走到规则 17 的"个人流入"——即使对方是自然人；
- 对公企业之间的转账如果未命中前面 11 条专项规则，会在规则 12（经营收入）/ 13（经营支出）兜底，**实际打到"其他流入/流出"的只剩奇葩对手方组合**；
- "需关注流入/流出"（14、15）位于"经营收入/支出"（12、13）之后，意味着**普通企业对手方 → 经营，被打了风险标的对手方 → 需关注**——优先级翻转的关键设计；
- 规则 18 永远返回 `true`，是兜底规则。

### 3.2 五级标签 cate5 — 对手方类型（6 种，识别顺序"首次命中即停止"）

| 顺序 | cate5 标签值 | 判定条件 |
|---|---|---|
| 1 | **本方** | 对手方名称命中本项目主体清单（同一企业的不同账户互转） |
| 2 | **无对方名称** | 对手方字段为空（手续费、利息、部分税费等场景） |
| 3 | **银行** | 对手方名称包含 `银行 / 支行 / 营业部 / 信用社` 任一字 |
| 4 | **非银（持牌）** | 对手方名称包含 `小额贷款 / 融资租赁 / 消费金融 / 信托 / 保理 / 汽车金融 / 财务公司` 任一字 |
| 5 | **民间** | 对手方为自然人（不含"公司/有限/股份/集团"）<br>**或** 名称非金融机构但摘要含借贷类关键词：<br>`借款 / 还款 / 贷款发放 / 拆借 / 民间借贷 / 付息 / 融资 / 票据贴现 / 信贷 / 授信 / 还贷 / 偿还 / 按揭 / 结清 / 垫付 / 归还 / 放款 / 还本 / 还息` |
| 6 | **其他** | 兜底（一般是企业类对手方，但无明显借贷特征） |

**注意点**：cate5 与 cate4 是相互独立的两个维度——同一笔流水会同时拿到一个 cate4 和一个 cate5。例如"对方=工商银行某支行 + 摘要=放款 100 万"→ `cate4=贷款流入`、`cate5=银行`。

### 3.3 六级标签 cate6 — 关联方关系 + 需关注对手方（11 种，多标签可叠加）

cate6 是**集合型标签**——一个对手方可同时持有多个 cate6 标签，存储时用 `,` 分隔（如 `个人大额往来,涉诉/失信`）。

| 类别 | cate6 标签值 | 数据来源 | 判定逻辑 |
|---|---|---|---|
| **关联族（4 个）** | 被尽调方法人/股东/主要人员/总公司 | 🌐 外部数据 | 法人/股东名单 + 母公司清单匹配 |
|  | 被尽调方对外投资/分支机构 | 🌐 外部数据 | 对外投资 + 分支机构清单匹配 |
|  | 与被尽调方具有相同法人/股东的企业 | 🌐 外部数据 | 共用法人/大股东企业清单匹配 |
|  | 疑似关联方 | 🌐 外部数据 | 股权穿透 + 行为模式分析综合判定（L4 风险层产出） |
| **需关注族（7 个）** | 新成立企业 | 🌐 外部数据 | 工商成立日距交易日 ≤ 阈值（一般 1 年） |
|  | **流入流出重合** | ✅ 流水内部可算 | 同一对手方既有流入又有流出，且 `min(流入,流出) / max(流入,流出) ≥ 50%` |
|  | **大额整数交易** | ✅ 流水内部可算 | 单笔金额 ≥ 100 万 **且**整数部分尾数 ≥ 5 个 0（如 1,000,000 / 5,000,000） |
|  | **个人大额往来** | ✅ 流水内部可算 | 对方为自然人 + 与本方累计往来 ≥ 50 万 + 不在已识别关联方清单 |
|  | 高风险行业 | 🌐 外部数据 | 工商行业分类（类金融 / 虚拟货币 / 传销 / 博彩 等高风险类目） |
|  | 经营异常 | 🌐 外部数据 | 工商状态（吊销 / 注销 / 经营异常名录 / 限制高消费） |
|  | 涉诉/失信 | 🌐 外部数据 | 司法数据（涉诉 / 失信被执行人） |

**重要说明：**
- ✅ 标记的 3 个标签**仅依赖流水本身**就能打出，是当前后端可独立完成的；
- 🌐 标记的 8 个标签**依赖 L4 风险层 / 三方外部数据接入**——若外部数据未接入或字段缺失，对应规则会自动跳过（不会误打），相关下游指标会显示为 0；
- cate6 的"关联族 4 个"对应类别1关联方明细(M082)/类别2关联方明细(M083)/类别3关联方明细(M084)的三种关联方分类（疑似关联方数(M019)单算）；
- cate6 的"需关注族 7 个"是需关注对手方数(M018)/需关注对手方明细(M086)/需关注方进入TOP10数(M087)的口径基础。

## 五、Coze 工作流入参详细计算逻辑

> 本节详细说明 4 个 Coze 工作流的入参**具体是怎么从流水计算来的**，以及出参回填到哪些指标。重点关注大模型在判定时依赖的关键数值（如 CV、regularDay）的精确计算方式。

### 5.1 `debt_analysis` 模式（偿还贷款类流水聚合明细(M046) / 借贷流入端明细(M047) / 借贷结论(M048)）

#### 入参 1：`debtParties[]`（偿债对手方列表）

**数据来源**：取所有支出流水中 `featureCate4 = '偿还贷款'` 或 `'偿还借款'` 的记录，按对手方名称分组聚合。

每个对手方产出以下字段：

| 字段 | 含义 | 计算方式 |
|------|------|----------|
| `name` | 对手方名称 | 直接取流水的 counterparty 字段（trim + 空白过滤） |
| `type` | 对手方类型 | 该对手方的所有偿债流水的 `featureCate5` 做频次统计，取出现最多的值（如"银行""非银""民间"） |
| `totalAmount` | 累计偿债金额 | Σ\|amount\|（所有该对手方偿债流水金额取绝对值累加） |
| `monthlyAvg` | 月均偿债金额 | totalAmount ÷ months |
| `months` | 分析期月数 | 整段流水总天数 ÷ 30，最小 1 |
| `firstDeduction` | 首次扣款日 | 该对手方偿债流水按时间排序后第一条的日期 |
| `lastDeduction` | 末次扣款日 | 该对手方偿债流水按时间排序后最后一条的日期 |
| `regularDay` | 固定扣款日 | 统计该对手方所有偿债记录的"日"（dayOfMonth），取出现次数最多的那一天；如某银行扣款日分别为 20、20、21、20 → regularDay=20 |
| **`cv`** | **变异系数** | **见下方详解** |

#### CV（变异系数）的精确计算公式

> 代码位置：`CorpMetricProcessServiceImpl.computeCv()`

```
输入：某对手方的所有偿债记录（每笔的 |amount|）
步骤：
  1. amounts = [|a₁|, |a₂|, ..., |aₙ|]          // 所有金额取绝对值
  2. mean = (a₁ + a₂ + ... + aₙ) / n             // 算术平均
  3. variance = Σ(aᵢ - mean)² / n                 // 总体方差（除以 n，非 n-1）
  4. stdDev = √variance                           // 标准差
  5. cv = stdDev / mean                           // 变异系数
  
精度：中间计算保留 4 位小数，最终输出保留 2 位小数
特殊情况：笔数 < 2 → cv = 0；均值 = 0 → cv = 0
```

**大模型如何使用 CV 做判定**：
- `regularDay` 存在（有规律扣款日）**且** `cv < 0.3` → 判定为 **"中长期刚性月供(高)"**（高置信度）
- 否则 → 判定为 **"不规律偿债(低)"**（低置信度）
- 直观含义：CV 越小说明每月还款金额越稳定（等额本息特征），配合固定扣款日可确认为正规贷款月供

**举例**：
- 某银行每月 20 日扣款 5000 元，连续 12 个月 → regularDay=20, cv≈0 → 判定"中长期刚性月供"
- 某对手方还款 10 万、3 万、50 万，日期不规律 → regularDay=null 或频次很散, cv>0.3 → 判定"不规律偿债"

#### 入参 2：`lendingParties[]`（借贷流入方列表）

**数据来源**：取所有收入流水中 `featureCate4 = '贷款流入'` 或 `'借款流入'` 的记录，按对手方分组。

| 字段 | 含义 | 计算方式 |
|------|------|----------|
| `name` | 对手方名称 | 直接取 counterparty |
| `type` | 对手方类型 | 同上，取 featureCate5 频次最高值 |
| `count` | 放款笔数 | 该对手方的借贷流入记录条数 |
| `totalAmount` | 累计放款金额 | Σ\|amount\| |
| `firstDate` | 首次放款日 | 按时间排序第一条 |
| `lastDate` | 末次放款日 | 按时间排序最后一条 |

**大模型对 lendingParties 的判定规则**：
- 自然人 + 大额 → "疑似体外融资/实控人输血"
- 对手方名称含"小贷"或 type=非银 → "高息融资渠道"
- type=银行 → "银行授信（需核实合同）"

#### 出参

| 出参字段 | 回填指标 | 说明 |
|----------|----------|------|
| `debtAnalysis[]` | **偿还贷款类流水聚合明细(M046)** | 每个偿债方的 `{inferredNature, confidence}`，与 Rule 侧聚合数据合并输出 |
| `lendingAnalysis[]` | **借贷流入端明细(M047)** | 每个借贷流入方的 `{qualitativeNote}` |
| `conclusion` | **借贷结论(M048)** | 多行文本结论（✓正面发现 + ⚠风险信号） |

### 5.2 `cash_flow_conclusion` 模式（现金流还原结论(M069)）

#### 入参

**当前实现**：将 `analysisPeriod`（分析期间字符串）和 `indicator_income_expense` 章节的全部指标详情（水电能源支出(M064) ~ 月度现金流还原明细(M068) 的 metricText JSON）直接打包传给 Coze，由大模型从 JSON 中自行提取所需数值。

**DTO 定义的完整入参结构**（部分字段预留，后续填充）：

| 字段 | 含义 | 计算方式 |
|------|------|----------|
| `monthlyOperatingIncome[]` | 月度经营收入序列 | 来自月度现金流还原明细(M068)的逐月经营收入字段 |
| `monthlyOperatingExpense[]` | 月度经营支出序列 | 来自月度现金流还原明细(M068)的逐月经营支出字段 |
| `monthlyOperatingNetFlow[]` | 月度经营净流入序列 | 每月 = 经营收入 − 经营支出 |
| `annualizedNetFlow` | 年化经营净流入 | 月均经营净流入 × 12 |
| `disposableFreeCashFlow` | 月均可支配自由现金流 | 月均经营净流入 − 月均偿债 |
| `negativeFlowMonths` | 净流出月份数 | 经营净流入 < 0 的月份数 |
| `totalMonths` | 总月份数 | 分析期覆盖的自然月数 |

| `monthlyDebtRepayment[]` | 月度偿债序列 | 每月"偿还贷款+偿还借款"金额合计 |

**cashFlowStabilityCv 的含义**：
- CV < 0.3 → 现金流非常稳定（评级：优秀/良好）
- CV 0.3~0.6 → 现金流一般（评级：一般）
- CV > 0.6 → 现金流波动大（评级：关注/高风险）
